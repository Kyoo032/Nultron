# Knowledge

Knowledge is an Account-rail page (like Usage), not a `PRODUCT_MODES` id. Soul, pinned Memory, and Sources persist in workspace SQLite. The owner picks Embedding / Brain / Verifier models. Chat injects soul + pinned memories + RAG-retrieved chunks (vectors with FTS fallback). Map reviews the desk; stub map is valid. Sources also fill themselves: every finished Chat turn or job writes a text work card (see [knowledge-ingest.md](./knowledge-ingest.md)); the Sources tab shows that cycle as `knowledge-loop`. See [`docs/internal/maps/knowledge-base-page.md`](../../../../docs/internal/maps/knowledge-base-page.md) for how the page itself works (routes, the one `reload()`, the loop maths, the graph fetch, and what Chat does with Soul / Memory / Sources), and [`docs/internal/maps/knowledge-ingest-loop.md`](../../../../docs/internal/maps/knowledge-ingest-loop.md) for the ingest pipeline behind it.

Product: both · Instance: main :3000

The `· hybrid`, `· rag` and `· fts` suffixes come only from a `?query=` call, which retrieves and so embeds. Driven 2026-10-05 after a live send on the operator's key: the breakdown read `Sources 2 chunks 414` (count, then tokens) with no engine word. The Sources count stays `0 chunks` and the miss line is counted in the Sources tokens only on a `?query=` call, because the Chat chip is rebuilt from the run's record and has no miss to count. Removing a source also strips that id from the saved map: a topic that only cited it is dropped, and `ready` follows what remains. A scan is still refused (`pdf_no_text_layer` / `document_needs_ocr`).

## Gotchas

- Knowledge is not a workspace mode checkbox. Hiding Finance/Data must not hide Knowledge.
- Extract handles text-like files (.txt/.md/.csv/.json), HTML (.html/.htm, read as prose), text-layer PDFs, .docx, and — through the local converter, no network — .pptx .ppt .xlsx .xls .ods .odt .odp .doc .rtf .epub (`packages/host/src/knowledge-extract.ts:57-68`). A PDF with a text layer and a Word file both reach `Indexed` with `chunks > 0`; PDF text keeps `<!-- page N -->` markers, so a chunk may start with one.
- A scanned (image-only) PDF is the failure case: it comes back 400 `pdf_no_text_layer` — "This PDF has no text layer (scanned image). OCR is not supported yet." No OCR in this build, and the harness does not add one.
- PDF caps: 25 MB (`pdf_too_large`), 20 s (`pdf_timeout`), 500 pages (extra pages are dropped, not an error). Damaged files give `pdf_invalid`; damaged Word files give `docx_invalid`. A converter format that fails gives `document_<reason>` (`document_needs_ocr` for a scan, `document_format_mismatch` when the name and the bytes disagree, `document_too_large` as a 413; `packages/host/src/knowledge-extract.ts:139-141`). A file that is none of the above (an image such as `.png`, with a MIME that is not `text/*` or JSON) is refused `unsupported_content_type`, 400, "That file type is not indexed. Try .txt .md …" (`packages/host/src/knowledge-extract.ts:269-274`).
- URL fetch is HTTPS only, existing TLS rules, size-capped. GET settings still never returns the gateway key.
- **Hosted, a colleague's Chat card is hidden from you, and so is its id.** A `DELETE /api/v1/knowledge/sources/:id` or `POST /api/v1/knowledge/sources/:id/reindex` with a colleague's card id answers like an id that is not there (DELETE skips the delete and returns `{ ok: true }` with status 200, `handlers/knowledge.ts:431-434`; the 404 `not_found` belongs to reindex only, `:195-197`), the card stays, and `POST /api/v1/knowledge/reindex` never lists it. A count that looks short by "one card per colleague thread" on a team desk is this rule, not a bug. The Soul, the pinned memories and the `retrievals` count are still the company's (`knowledge-flows.md` § 7). Off server mode (webdev, any non-hosted build) none of it applies: every card on the desk is listed, retrieved and mapped as before.
- Do not POST `/api/v1/knowledge/*` as a substitute for the page on a live proof.
- Only Map triggers a generate; picking models only PUTs the saved ids.
- Pasted / uploaded / URL text goes through the injection guard like auto cards: "Ignore all previous instructions…" pasted into `knowledge-paste` gives a `Failed` row (`injection_blocked (rule: ...)`, the reason on the status tag's title, `knowledge.ts:490`), not `Indexed`; a pasted URL does the same, while an uploaded file is a 400 `injection_blocked` with **no** row (`knowledge.ts:589-593`). That is correct; the owner bypass in Settings lifts it.
- Offline with a saved key: the first KB write after the gateway goes dark takes ~4 s, then everything is instant for 5 min (local vectors + FTS). Chat fails within ~10 s with "Gateway unreachable"; Settings save within ~8 s. Nothing here needs the internet.
- Work cards never copy files into `tenantDataDir(tenantId)/knowledge/<organizationId>/`; only `knowledge-file` uploads write there (`packages/host/src/knowledge.ts:510-512`). `addFileSource` stores the original bytes and indexes the extracted text.
- Chat's context popover `Sources` count excludes the current thread's own card (anti-loop). A thread that only has its own card shows `0 chunks` — that is why the planted-fact recipe uses a fresh thread.
- **A Chat work card can say its embeddings timed out (driven 2026-10-05).** The row for the thread written by a live send read `Chat`, `1 chunk` and "Saved. Live embeddings timed out, so this source is on a local index until the gateway answers." (`knowledge.sources.embedLocal`, `apps/web/locales/en/knowledge.json:40`), while an older Chat card on the same desk read `Indexed` with no note. The note is `knowledge-embed-local`, drawn only when the row is `Indexed` and its error is `embed_local` (`apps/web/components/knowledge-page.tsx:615-618`). The host writes that code when a live embed fell back to local vectors (`error: indexed.degraded ? EMBED_LOCAL_ERROR : null`, `packages/host/src/knowledge.ts:430`): a 4 s timeout or another retryable error (`EMBED_TIMEOUT_MS`, `isRetryableEmbedError`), after which every write goes straight to local vectors for 5 minutes (`EMBED_DOWN_MS`; `packages/host/src/knowledge-embed.ts:30-37`). The row is still searchable by keyword. It is the fallback working, not a failed ingest, so do not assert the bare `Indexed` text alone on a card made right after a live send.
- `retrievals` only counts **completed** runs. A run that failed, was aborted, or retrieved nothing adds no rows, so a flat counter after a failed Chat send is correct.
