# Code

`run_code` is the sandbox tool: the model can run a short Python or JavaScript program, read what it printed, and save text results to the desk. It is not a product mode, has no rail entry and no page of its own. The owner reaches it by asking Chat to compute or analyse something, and the only on-screen evidence is its tool row inside the Thinking disclosure and the files it saved. This recipe has two halves: the real engines driven from the repo (no key and no browser), and the Chat scenarios (a live key, a browser, and a host started after 2026-10-03). Map: [`docs/internal/maps/agent-tools-and-files.md`](../../../../docs/internal/maps/agent-tools-and-files.md) § 12. The Chat side of the tool rows is also in [chat.md](./chat.md), and the files it writes are in [files.md](./files.md).

Product: both · Instance: main :3000

## Sub-features

- `code-tool` is what the model can call: `run_code` with `language` (`python` or `javascript`), `code` and optional `files` (at most 20 desk paths). It answers `{ ok, stdout, stderr, filesWritten, reason? }`. Chat binds it (6 calls a turn) and Data binds it for exploration (4 calls a job, never evidence). Finance and Market never get it. A binding the owner switched off stays off.
- `code-paths` is one rule for both languages: a desk path is the path under `/workspace`. The desk file `data/sales.csv` is `/workspace/data/sales.csv` in Python (the working directory is `/workspace`, so `pd.read_csv("data/sales.csv")` works) and `files["data/sales.csv"]` in JavaScript. A result worth keeping goes under `/workspace/out/` in Python or into `outFiles["<name>"]` in JavaScript, and lands on the desk as `out/<name>`. Only new or changed UTF-8 text files are saved, at most 20 of at most 2 MB each, and nothing is saved when the run fails.
- `code-row` is the Chat tool row, inside `message-thinking` → `message-tools` → `message-tool` (`data-tool="run_code"`). It holds `tool-row-code` with `data-state` (`running` while the call is open with no output blocks; `done`; `failed` for any `ok: false` result, so a timeout, `busy` and an unavailable sandbox read `failed` too and not only a program error; `refused`; `budget`), `tool-row-code-language` (a `Python` or `JavaScript` badge), `tool-row-code-source` (a closed `<details>`, "Show code") with `tool-row-code-text` inside, `tool-row-code-stdout` ("Output"), `tool-row-code-stderr` ("Errors", muted), `tool-row-code-reason` (a sentence when it did not finish) and `tool-row-code-files` ("Files saved") with one `tool-row-file-chip` per saved file. The label reads `Ran Python` or `Ran JavaScript` (`Menjalankan Python` on `id`) and `Python run failed` after a failure. A program that printed nothing shows "It ran and printed nothing."
- `code-reasons` is the failure class and its sentence on `tool-row-code-reason`: `timeout` "It ran too long and was stopped.", `memory` "It needed more memory than it is allowed and was stopped.", `syntax` "The code has a syntax error, so it did not run.", `runtime` "The code stopped with an error while running.", `too_large` "The code or its output was too large.", `busy` "Another run is in progress. Try again in a moment.", `unavailable` "Running code is not available right now.", and anything else "The run did not finish." Each has an `id` twin. The model gets the same classes with fixed sentences of its own.
- `code-limits` are the numbers: code up to 100 KB; up to 20 input files and 20 MB together; a run stops after 30 s wall clock; Python memory 512 MB, JavaScript 256 MB (heap 128 MB); stdout and stderr cut at 64 KB each; a `/workspace` over 500 files or 64 MB is `too_large`; one run at a time on a non-hosted build, two in all and one per tenant when hosted; a run that cannot get a slot within 5 s answers `busy` instead of queueing behind a 30 s job (`QUEUE_WAIT_MS`, `packages/host/src/code-runner/limits.ts:46`); a warm child is dropped after 5 idle minutes. The first Python run after a pause starts Pyodide and takes about 20 s.
- `code-ship` is the runtime folder the child reads: `vendor/sandbox-runtime/` (gitignored), built by `npx pnpm@9.15.9 sandbox:build` and checked by `npx pnpm@9.15.9 sandbox:verify`. The host finds it through `AGENTFORGE_SANDBOX_DIR` (dev, test and hosted), `<resources>/sandbox` in the packed app, or `vendor/sandbox-runtime` in a checkout. A missing or mismatched folder makes every call answer `unavailable`.
- `code-switch` is the kill switch, `AGENTFORGE_CODE_RUNS` (`packages/host/src/code-runner/limits.ts:60-61`). Unset, `run_code` is on for webdev and every other non-hosted build and **off on the hosted server**, until the sandbox has been driven inside the image (the security register, `docs/internal/security-register.md` around `:2819-2823`, records one Python (pandas) run and one JavaScript run through `createSandboxRunner()` inside the hardened production image on 2026-10-05: read-only root, `noexec` /tmp, `cap_drop ALL`, uid 1000, Node 22.23.3, `AGENTFORGE_CODE_RUNS=on`; a hosted Chat run, the compose and k8s stacks and an OS egress deny are still owed, and the default stays off) (`codeRunsEnabled`, `packages/host/src/code-runner/enabled.ts:5-9`, `:24-30`). `on`, `1` and `true` turn it on; every other value, a typo included, turns it off. Off means the model is never offered the tool (`withCodeRunPolicy` adds `run_code` to the disabled-tools list, `enabled.ts:38`), and a call that still arrives is refused without running anything: the runtime keeps the tool in its map, hidden from the model's list, and answers `{ success: false, error: "Tool run_code is disabled on this machine." }` (`buildAiTools`, `packages/core/src/runtime/ai-tools.ts:47`, 2026-10-06; before that the SDK found no such tool and the whole run failed). Chat's prompt no longer names `run_code` while it is off (`withoutDisabledToolSentences`); the Data job's instruction still does, so a Data run may call it and get the same refusal. The tool's own `unavailable` refusal (`run-code-tool.ts:225-228`) is the second line for any caller outside that path. So a hosted drive without the variable shows no `tool-row-code` at all, which is correct and not a failure.
- `code-engines` are Pyodide (Python 3.14 with numpy and pandas, no other package) and QuickJS (plain ECMAScript: no `require`, no `import`, no Node or browser APIs). Neither has a network. The child process has no write, no child-process and no worker permission, and an empty environment.

## How to get to it (user POV)

- The owner does not open it. In Chat they ask for a calculation or an analysis that needs several steps, name a file on the desk, or ask to check some code ("Use code to add up the squares of 1 to 20", "Read verify/data.csv with pandas and save a summary"). Chat decides whether to call it.
- The result is a row in the Thinking disclosure ("Ran Python"), and a chip for each saved file that opens the Files section of the Knowledge Base at `/knowledge?file=out%2F<name>`.
- A Data analysis may call it for exploration. Nothing shows in the Data studio when it does.
- With no sandbox folder, the row says "Running code is not available right now." and Chat tells the owner it cannot run code.

## Driving it with the Nultron harness

Preconditions:

- Doctor exits 0 against `http://127.0.0.1:3000` for the Chat half. The engine half needs no instance at all.
- The engine half needs `vendor/sandbox-runtime/` (run `npx pnpm@9.15.9 sandbox:build` first if it is missing; the five Python wheels are the only download, and `--offline` works with a warm `vendor/.sandbox-cache`).
- The Chat half needs `runtime: "ai"` in doctor's output, the owner's go-ahead for a few billed exchanges, `GET /api/v1/files` answering 200 (if it answers 404, the host process predates the route: report "not driven, `:3000` needs a restart" and stop), `run_code` switched on (it is on for webdev and every non-hosted build; see `code-switch`), and a throwaway desk as [files.md](./files.md) describes. A stub Chat never calls the tool.
- Prompts start with `VERIFY code <run-id>:`.

**The real engines (no key, no browser).** Run these from a terminal and keep the output under `evidence/code/<run-id>/`.

1. From the repo root, `npx pnpm@9.15.9 sandbox:verify`. Expect a line like `sandbox-runtime: 37 files, 27.58 MiB, manifest verified (...\vendor\sandbox-runtime)` and exit 0 (the numbers move when the lock is bumped). `stale: py-child.mjs` means a child script was edited after the build: run `npx pnpm@9.15.9 sandbox:build --offline`. `missing: MANIFEST.json` means the folder was never built. Since the third-party notices landed the folder also holds `THIRD_PARTY_NOTICES.txt` (94,392 bytes, the first manifest entry), and `--verify` now fails a folder built before it existed with `THIRD_PARTY_NOTICES.txt is not listed in MANIFEST.json`; the fix is `npx pnpm@9.15.9 sandbox:build --offline` (`scripts/build-sandbox-runtime.mjs:584-597`). Driven 2026-10-05 (maintain3): `sandbox-runtime: 37 files, 27.58 MiB, manifest verified`, exit 0; the integration file `27 passed (27)` in 220 s (`AGENTFORGE_SANDBOX_DIR=<repo>/vendor/sandbox-runtime`, throwaway `AGENTFORGE_DATA_DIR`). `pnpm ci:local --only sandbox:integration` runs the same file and fails on an all-skipped result (`scripts/ci-local.mjs:340-358`). Driven 2026-10-16 in the main checkout: `sandbox:verify` passed (37 files, manifest verified).
2. From `packages/host`, in PowerShell, `$env:AGENTFORGE_SANDBOX_DIR = "<repo>\vendor\sandbox-runtime"` then `npx vitest run src/code-runner/sandbox.integration.test.ts`. In Git Bash, `AGENTFORGE_SANDBOX_DIR=<repo>\vendor\sandbox-runtime npx vitest run src/code-runner/sandbox.integration.test.ts`. Expect `Tests 27 passed (27)` after about 3 minutes (176 s on 2026-10-03; the first Python test alone took 18.7 s). Without the variable the file is reported as skipped, and 27 skipped is not a pass. The suite covers a cold Python start with a pandas round trip, a fresh namespace in a warm child, `sys.exit`, the 30 s wall-clock kill, the 512 MB memory cap, JavaScript limits, an `os.system` crash that gets a fixed sentence, and 31 escape ids that must stay blocked with a loopback listener that must see zero connections.
3. From `packages/host`, `npx vitest run src/code-runner`. Every unit suite passes against a fake child; the integration file shows as skipped here, which is expected.

**Through Chat (live key).** After each send wait for `composer-send` to read `Send` again (up to 90 s, because a cold Python start is about 20 s), then open `message-thinking`.

- **Compute and save.** Send "Use code to add up the squares of 1 to 20 and find the mean of 3, 5, 8 and 13, then save both results to out/stats.txt." A `message-tool` with `data-tool="run_code"` holds a `tool-row-code` with `data-state="done"`, a `tool-row-code-language` badge, `tool-row-code-stdout` containing `2870` and `7.25`, and `tool-row-code-files` with a `tool-row-file-chip` named `out/stats.txt`. Open `tool-row-code-source`: `tool-row-code-text` is the program. Click the chip: URL `/knowledge?file=out%2Fstats.txt`, `file-viewer` opens and its text holds both results. `GET /api/v1/files/versions?path=out/stats.txt` shows `authorKind: "agent"`, `mode: "chat"` and an `authorId` that is a run id, not the thread's id. If the model used `calculator` and no code, say so and send a prompt that names code.
- **Read a desk file.** In the Files section create `verify/data.csv` with the lines `a,b`, `1,2`, `3,4`, `5,9` (`files-new`, `files-new-path`, `files-new-content`, `files-new-save`). Send "Use pandas to read verify/data.csv, print the mean of column b, and save describe() to out/summary.csv." Expect `tool-row-code-stdout` containing `5.0` (the mean of 2, 4 and 9 is 5) and a chip `out/summary.csv`. The model had to name the file in `files`; if the row's stderr says the file was not found, the model forgot that argument, which is its mistake and not the sandbox's.
- **A program that fails.** Send "Run this Python and tell me what happens: print(1/0)". The row's `data-state` is `failed`, `tool-row-code-reason` reads "The code stopped with an error while running.", `tool-row-code-stderr` contains `ZeroDivisionError`, and nothing is saved. A second send ("Now run print(2+2)") shows `4`, and the host's log line `code_run` says `cold: false`: the child survived an ordinary exception. If the model wraps the line in `try` first, the run is `done`; send the prompt again.
- **The wall clock (optional, about a minute).** Send "Run `while True: pass` in Python and report what happens." After about 30 s the row is `failed` with "It ran too long and was stopped." The next run starts a new child, so it pays the cold start again.
- **No network (optional).** Send "In Python, fetch https://example.com with urllib and print the first 100 characters." The row is `failed` (a `runtime` error: Pyodide has no sockets) and the reply contains no text from that site. This proves the program could not reach it, not that the model could not: the model's own `web_fetch` is a separate tool.
- **Limits you cannot drive cheaply.** The 100 KB code limit, 20-file input limit, the 64 MB workspace limit, `busy` and `unavailable` are covered by the unit suites; do not try to hit them through Chat.
- **Locale (id).** With the desk on `id` (see [locale.md](./locale.md)) the same rows read `Menjalankan Python`, `Tampilkan kode`, `Keluaran`, `Kesalahan` and `Berkas tersimpan`, and the reasons read in Indonesian (`Kode berhenti dengan kesalahan saat berjalan.`). Testids do not move. The model's own error text inside `tool-row-code-stderr` stays English.
- **Data.** A Data analysis can call `run_code`, but the studio shows nothing for it; see [data.md](./data.md). Do not try to prove it from the page.

Capture each Chat scenario as a screenshot with the opened Thinking disclosure and the Files section visible, and record the doctor JSON and the two `GET /api/v1/files/versions` answers beside it. ## Gotchas

- **Two hosts, two answers.** The engine half proves the sandbox on this checkout. The Chat half proves the wiring (prompt, binding, budget, rows, authorship) and needs a host started after the code. A passing engine half says nothing about Chat, and a missing row in Chat says nothing about the engines until `sandbox:verify` has been run.
- **Hosted is off by default.** With `AGENTFORGE_CODE_RUNS` unset the hosted server never offers `run_code` (see `code-switch`), so the Chat scenarios below cannot pass there: set the variable to `on` first, and only after the sandbox has been driven inside the image. On webdev and every other non-hosted build nothing needs setting.
- **`busy` is a 5 s wait, not a failure.** A second run that arrives while another holds the slot waits up to 5 s, then answers `busy` ("Another run is in progress. Try again in a moment."). The unit suites cover it (`code-limiter`); do not try to provoke it through Chat.
- **27 skipped is not 27 passed.** Without `AGENTFORGE_SANDBOX_DIR` the integration file is skipped and the suite exits 0. Read the line `Tests`.
- **The first Python run is slow.** About 20 s for Pyodide with numpy and pandas, and again after 5 idle minutes, after a desk switch on a non-hosted build (one warm child per language), and after any failure that kills the child (timeout, memory, crash). The tool description tells the model; the row shows "Running Python…" the whole time. JavaScript starts in under a second.
- **The warm child keeps its imported modules.** Variables and files are reset on every run, but a Python program that patches a module changes later runs on the same desk until the child is killed.
- **Edit a child script, rebuild the folder.** The sandbox runs the copy in `vendor/sandbox-runtime/`, not `packages/host/src/code-runner/child/`. `sandbox:verify` fails with `stale: ...` when they differ.
- **Text only, and only on success.** A binary file, a file over 2 MB, the twenty-first file, and every file of a failed run are not saved. A program that writes outside `/workspace/out/` loses it when the call ends. An input the program did not change is not saved again.
- **Python paths are absolute under `/workspace`, JavaScript uses objects.** `open("data.csv")` works because the working directory is `/workspace`. In JavaScript there is no file system: `files["data.csv"]` is the text and `outFiles["summary.txt"] = text` saves one.
- **The row is inside a closed `<details>`.** `message-tool` rows stay in the DOM, so a count passes and a visibility check fails until `message-thinking` is opened. `tool-row-code-source` is a second closed `<details>` whose "Show code" summary has no testid (click the summary inside it). The Thinking disclosure is open while the turn is live and collapses when the reply lands.
- **`web_fetch` after a code run is limited.** A `run_code` answer taints the turn (SR-112): a later `web_fetch` opens only a host the owner named or a search returned. A prompt that runs code and then fetches an unnamed site will see the fetch refused.
- **Not proven everywhere.** The sandbox has not run from a packed installer (where the child is the app's own executable with `ELECTRON_RUN_AS_NODE=1`), on a Mac, in the hosted image from a Chat run (one direct engine run is recorded, see above), or with an OS-level egress deny on the hosted server (the plan's Appendix A2 and SR-97). The engine half runs on this Windows checkout only.
- **Memory.** A Python child with pandas holds hundreds of megabytes. Run one engine suite at a time, and do not run the integration file while another Pyodide child is warm on the same machine.
- A code row can also hold `tool-row-refusal` (`data-state="refused"`) or `tool-row-budget` (`data-state="budget"`, for example a seventh call in one turn). `tool-row-code-stderr` also carries the host's own `[run_code] ...` notes (`outcome.ts`), so an unavailable-sandbox row shows the reason sentence and a stderr block together. Code text is cut at 20,000 characters with "Shortened here." (`code-row.tsx:9`, `:45`), at most 20 file chips show, a saved turn rebuilds its row after a reload (`toolsFromContent`, `chat-turn.tsx:216-230`), and the chip's `aria-label` is "Open <path> in the Knowledge Base".
