# Folder

**Personal lane (desktop only).** The folder lets the owner open one real folder on their own computer so Chat can read its files and propose changes to them. Nothing is written until the owner presses Approve. The control and the "Changes to approve" panel sit above the Chat composer, and they exist only in the packaged desktop app: the hosted app and webdev render nothing here. The agent reaches the folder with the same six file tools as the desk's own files ([files.md](./files.md)), with `root: "folder"`. How it works: [`docs/internal/maps/agent-tools-and-files.md`](../../../../docs/internal/maps/agent-tools-and-files.md), § 9 and § 11.

## Sub-features

- `folder-surface` wraps the whole thing above the composer (`apps/web/components/folder/folder-surface.tsx:42`). It is mounted on the empty Chat as well as in a thread (`FolderSurface` at `apps/web/components/chat-session.tsx:489` has no `empty` guard), so on the packed app `folder-open` is there before the first message. It renders nothing at all (count 0) when the host reports `available: false`, and also when the shell has no folder picker and no open folder has changes to show.
- `folder-control` is the group; `folder-open` ("Open folder", "Opening…" while the dialog or the mount is busy) opens the shell's native folder dialog. After a folder is open the control is `folder-chip`, the folder's **last segment only** (the path is never shown), with `folder-close` ("Close folder {name}"; its tooltip warns that waiting changes will be dropped only while `pendingCount > 0`, otherwise it is the plain "Close folder", `folder-control.tsx:61`).
- `folder-error` is a one-line host or client refusal in words, chosen by error code from the catalog (`folderErrorText`, `apps/web/lib/folder-copy.ts:19`; strings in `apps/web/locales/en/folder.json:50-56`): `folder_mount_refused` ("That folder cannot be opened. A whole drive, your whole home folder, system folders, and folders that hold keys or this app's own data are not allowed. Pick a different folder.", `:52`), `folder_mount_ipc_only` ("Pick the folder from the desktop app's window. It cannot be opened from here.", `:51`), `folder_unavailable`, `folder_not_mounted`, no picker, a network failure, or a generic line. `folder_mount_ipc_only` has a second sentence on the wire: the HTTP error body of `POST /api/v1/folder/mount` says "A folder can only be picked from the desktop app." (`packages/host/src/folder-root/api-errors.ts:21`). The page shows the catalog string in `folder-error`; an HTTP client reads the wire string.
- `folder-proposals` is the panel ("Changes to approve") with a `folder-proposals-count` badge while any change is pending. Each change is a `folder-proposal` row with `data-proposal-id`, `data-kind` (`write` or `delete`) and `data-state` (`pending` or `decided`). A pending row has `folder-proposal-toggle` ("Show changes" and "Hide changes", `aria-expanded`), `folder-proposal-reject` and `folder-proposal-approve`.
- `folder-proposal-diff` is the region the toggle opens. `folder-proposal-lines` holds the lines, each with `data-kind` `add`, `remove`, `same` or `gap` (long unchanged runs fold into one `gap` line). `folder-proposal-stale` says the file changed since the change was proposed and Approve will not write anything. `folder-proposal-truncated` says only the first lines are shown while Approve still applies the whole change.
- `folder-proposal-outcome` is the sentence after a decision, with `data-outcome` of `applied`, `stale`, `failed`, `rejected` or `gone` (the host says it was already decided). `folder-proposal-dismiss` removes a decided row. `folder-proposal-error` shows when the decision call itself failed.
- `folder-chat-rows` (a feature id, not a testid; likewise `folder-api` and `folder-denied`) are the Chat tool rows for a folder change. A `write_file`, `edit_file` or `delete_file` with `root: "folder"` shows `tool-row-pending-approval` ("Waiting for your approval") with `tool-row-pending-path` and `tool-row-pending-review` ("Review"). Review scrolls to and focuses `folder-proposals`; when the panel is not on the page it shows `tool-row-pending-missing` instead.
- `folder-api` is `GET /api/v1/folder` (`{mounted, name, available}`), `POST /api/v1/folder/mount` (IPC only), `DELETE /api/v1/folder/mount`, `GET /api/v1/folder/proposals?status=`, `GET /api/v1/folder/proposals/:id` (the diff: `before`, `after`, `stale`), and `POST /api/v1/folder/proposals/:id/approve` and `/reject` (`packages/host/src/folder-root/routes.ts:99-105`).
- `folder-denied` is what the agent may not touch: `.env`, `.envrc`, `.env.*`, `.npmrc`, `.netrc`, `.git-credentials`, `id_rsa` and its siblings (`id_ed25519`, `id_ecdsa`, `id_dsa`, and anything beginning with those, so `id_rsa.pub` too; the match is by name prefix, case-insensitive, on any path segment, `folder-root/denied-names.ts:8-23`), `*.pem`, `*.key`, `*.p12`, `*.pfx`, and anything under `.git`, `.ssh`, `.aws` or `.gnupg`. A refused read or write shows `tool-row-refusal` with "That file is not available to the agent.".

## How to get to it (user POV)

- Install or unpack the packaged Nultron for this platform and open Chat. On Chat, empty or in a thread, the composer's ledge shows an **Open folder** button. Press it, choose a folder in the system dialog, and the button becomes a chip with the folder's name.
- Ask Chat to look at or change a file in that folder. A change shows up under "Changes to approve" when the reply finishes.
- There is no route for this on webdev or the hosted app.

## Driving it with the Nultron harness

Preconditions:

- **A packed app is required.** `pnpm desktop:dev` is `electron .` with no preload (`webPreferences.preload` is set only when `app.isPackaged`, `apps/desktop/main.cjs:410`), so there is no `window.agentforge`, no folder picker and no IPC transport in it ([desktop.md](./desktop.md), `desktop-dev`). Pack with the pack skill (`.cursor/skills/pack-nultron`) and launch `win-unpacked\Nultron.exe`, then `node .cursor/skills/verify-agentforge/scripts/doctor.mjs --desktop` exits 0. **As of 2026-10-03 no packed app has run this code, so part B below is owed.**
- A live key and the owner's go-ahead for a few billed exchanges (doctor reports `runtime: "ai"`). The agent has to call the tools; stub Chat never does.
- A **throwaway folder** that is not the home directory, not inside or above the app's data dir (`%APPDATA%\Nultron`) and not a system folder. A new folder under `%TEMP%` works (for example `%TEMP%\verify-folder-<run-id>`). Create inside it `notes.md` containing `Teh plan is ready.`, `.env` containing `SECRET=1`, and `sub\readme.md`.
- The pick is a native dialog, which the page cannot press. A person presses `folder-open` and chooses the folder. A driver that launches Electron itself could replace `dialog.showOpenDialog` in the main process first; that has not been tried.
- Stop and report when `folder-open` has count 0 on a packed app: the preload line (`apps/desktop/preload.cjs:59`) or the capability flag is missing.

### A. Webdev: the refusals and the hidden control

Run these first; they need only `:3000`. `GET /api/v1/folder` answered 200 `{"mounted":false,"name":null,"available":true}` there on 2026-10-05, so the route is live. A 404 means the process predates the route: say "restart :3000" and do not drive.

- **Nothing on the page.** Open `/chat`. `folder-surface`, `folder-control` and `folder-open` all have count 0, and `tool-row-pending-approval` does not exist. (The renderer needs both a real shell bridge and `nativeFilePicker`, `apps/web/components/folder/folder-surface.tsx:36`.)
- **The status read answers, with the folder allowed.** `GET /api/v1/folder` answers 200 with `{"mounted":false,"name":null,"available":true}`. Webdev reports `localPaths: true`, so the folder is *available* in the host's eyes even though no page can press it. On the hosted server the same read answers `available: false`.
- **A mount over HTTP is refused.** `POST /api/v1/folder/mount` with `{"path":"C:\\Windows"}` answers 403 with code `folder_mount_ipc_only` and the wire message "A folder can only be picked from the desktop app." (`api-errors.ts:21`; the page's own copy for the same code is in `folder-error`). The check is on the transport, before the path is looked at, and the HTTP adapter stamps every request `http` whatever header a caller sends (`packages/host/src/http-adapter.ts:689`).
- **The proposal routes are empty and strict.** `GET /api/v1/folder/proposals` answers `{"items":[]}`; `?status=nonsense` answers 400; `GET /api/v1/folder/proposals/nope`, and `POST .../nope/approve` and `.../nope/reject`, answer 404 `not_found`.
- **The hosted refusal is a unit test, not a live drive.** With `AGENTFORGE_SERVER=1` the status read answers `{"mounted":false,"name":null,"available":false}` and every other folder route answers 403 `folder_unavailable`, including a mount over IPC (`packages/host/src/folder-root/routes.test.ts:198-214`). A live check needs the review instance ([login.md](./login.md)).

### B. Packed app: open, propose, approve, reject, stale

- **Open.** In the packed app, open Chat (the empty Chat or a thread). `folder-open` is visible. Press it and choose the throwaway folder. Proof: `folder-chip` shows the folder's name (not its path), `folder-close` is present, `folder-open` is gone, and `folder-error` has count 0.
- **A folder the host refuses.** Press `folder-close`, press `folder-open`, and choose the home directory or `%APPDATA%\Nultron`. `folder-error` reads the `folder_mount_refused` sentence and no chip appears. (Real folder rules: `checkMountPath`, `packages/host/src/folder-root/mount-validate.ts:141`.)
- **A read.** Open the throwaway folder again. Send "Read notes.md in my folder and tell me what it says." `message-thinking` holds a `message-tool` with `data-tool="read_file"` and a `tool-row-file` with `data-state="done"`; the reply quotes `Teh plan is ready.`. No `folder-proposal` exists.
- **A proposal, nothing written.** Send "Fix the typo in notes.md in my folder (Teh to The)." When the reply ends: a `tool-row-file` with `data-state="pending"` and `tool-row-pending-approval` appears; `folder-proposals` appears with `folder-proposals-count` reading 1 and one `folder-proposal` (`data-kind="write"`, `data-state="pending"`). **The file on disk still reads `Teh plan is ready.`** (read it with the file system, not the app). The reply tells you the change is waiting; a reply that says the file was changed is a bug.
- **The diff.** Press `folder-proposal-toggle`. `folder-proposal-diff` opens with `folder-proposal-lines`; one `[data-kind="remove"]` line contains `Teh` and one `[data-kind="add"]` line contains `The`. `folder-proposal-stale` has count 0.
- **Review.** Open `message-thinking` first (click its summary): it is `open` only while the turn is live (`chat-turn.tsx:109`) and collapses once the reply lands (`chat-session.tsx:550-572` clears the live tools and reloads the messages), so the row is in the DOM but hidden. The same applies to asserting `tool-row-pending-approval` and `tool-row-refusal` visibility. Then press `tool-row-pending-review` on the Chat row. `folder-proposals` scrolls into view and takes focus.
- **Approve.** Press `folder-proposal-approve`. `folder-proposal-outcome` has `data-outcome="applied"` ("Applied. Your folder now has this change."). The file on disk reads `The plan is ready.`, no `.tmp` file is left beside it, and the row is `data-state="decided"` with `folder-proposal-dismiss`. Press dismiss; the row goes and `folder-proposals` goes with it when it was the last one.
- **Reject.** Ask for another change ("Add a line saying Second line to notes.md"). Press `folder-proposal-reject`. `data-outcome="rejected"`; the file on disk has no `Second line`.
- **Stale.** Ask for another change and, before pressing anything, append a line to `notes.md` with a text editor. Press `folder-proposal-toggle`: `folder-proposal-stale` is visible. Press `folder-proposal-approve`. `data-outcome="stale"` ("Not applied. The file changed after this was proposed, so nothing was written. Ask Chat for a fresh change."), and the file keeps your edit.
- **A delete.** Ask Chat to delete `sub/readme.md`. The row has `data-kind="delete"`. Approve; the file is gone from disk (`data-outcome="applied"`, "Applied. The file was deleted.").
- **Protected names.** Ask Chat to read `.env`. The `tool-row-file` has `data-state="refused"` and `tool-row-refusal` reads "That file is not available to the agent."; the reply does not contain `SECRET=1`. Ask it to create `.env.local`: refused the same way, and no proposal appears.
- **Close drops waiting changes.** Ask for a change, then press `folder-close` before deciding. `folder-chip` and `folder-proposals` go away; reopening the same folder shows no pending change (they were rejected).
- **Cleanup.** Press `folder-close`, delete the throwaway folder, and leave the desk as you found it. The mount record (`folder-mounts.json` in the data dir) is cleared by the close.
- **Evidence.** Screenshots of `folder-chip`, the open diff and each outcome, with the file contents read from disk before and after, under `evidence/folder/<run-id>/`, plus doctor `--desktop` JSON.

## Gotchas

- `pnpm desktop:dev` cannot run any of part B. Do not report a folder drive from it.
- The panel refreshes when a run ends and after each decision, never while the reply streams. A proposal made mid-run shows up when the reply finishes (`apps/web/components/folder/use-folder.ts:16`). Do not wait for it earlier.
- Approve answers 200 `{status: "stale"}` for a changed file; that is a normal answer, not an error. A second decision on the same proposal is 409 `proposal_not_pending`, which the page shows as `data-outcome="gone"`.
- A second change to the same path replaces the first pending one: the first is rejected, not stacked, and the Chat reply for it said it was waiting. Count `folder-proposal` rows after two edits to one file: one pending row.
- Picking a different folder, or closing the folder, rejects every pending change for the desk. The mount is per desk and per machine (`folder-mounts.json`), so a folder opened on one desk is not open on another, and a leftover mount survives a restart until `folder-close`.
- The agent reads UTF-8 text up to 2 MB. A binary file, a Latin-1 file or a larger file comes back refused (`denied` or `too_large`), and so cannot be edited. A byte-order mark and CRLF endings are kept when a change is approved.
- At most 50 changes can wait at once; the 51st is refused (`too_many_files`) unless it replaces a pending change for the same path. This is unit-tested, not worth driving by hand.
- Deleting a desk now also drops its folder mount and its stored changes: `handleDeleteWorkspace` calls `forgetFolderMount` and `purgeFolderProposals` (`packages/host/src/handlers/workspaces.ts:217`, `:219`; `folder-root/purge.ts:11`, `proposal-store.ts:215` `purgeDesk`, pinned by `purge.test.ts`). This line used to say the opposite; the code is the authority.
- Two parallel `edit_file` calls on one path in one Chat step can lose an edit: the second proposal rejects the first (read from the code, not driven).
- Locale: on an `id` desk the button reads `Buka folder`, the panel `Perubahan menunggu persetujuan`, and the buttons `Setujui` and `Tolak`. Testids are unchanged; parity is held by `apps/web/lib/folder-locale.test.ts`.
- Not in the recipe above: a mount the host refuses answers HTTP 400 `folder_mount_refused` (`mount-service.ts:41`) and an approve with no usable mount answers 409 `folder_not_mounted`; cancelling the native dialog shows no error and no chip (`folder-actions.ts:88`); re-picking the same folder does **not** reject pending changes (`mount-service.ts:44`) while picking a different one does. After a decision the Chat row still reads "Waiting for your approval" (it is derived from the saved tool output) and Review then shows `tool-row-pending-missing` once the panel is gone; pending rows read "Proposed writing / editing / deleting a file" (`chat.json:222`, `:233-235`) and a refused read "Could not read {path}". A decided row's `folder-proposal-toggle` exists only if its diff was loaded before the decision; a line-ending-only change reads "The text is the same..." with no `folder-proposal-lines` (`folder-diff-view.tsx:74-77`), and the diff is capped at 2000 lines a side with 3 lines of context. `data-outcome="failed"` (the `failedDenied` and `failedIo` texts) is never exercised by the recipe. `node_modules`, `dist`, `build`, `.next` and `.turbo` are skipped by list and search but readable by path; model paths are also limited by `parseDeskPath` (240 characters, 8 parts, no drive letters, no trailing dot or space); the injection guard can refuse a write whose text trips a rule. `SKILL.md`'s folder row lacked `folder-proposal-diff`, `-lines`, `-stale`, `-truncated` and `-error`; they exist.
- **Driven 2026-10-05 on `:3000`, part A only (webdev refusals).** `GET /api/v1/folder` -> 200 `{"mounted":false,"name":null,"available":true}`; `POST /api/v1/folder/mount` over HTTP -> 403 with `folder_mount_ipc_only`; `GET /api/v1/folder/proposals` -> 200 `{"items":[]}`; a bad status filter -> 400; on `/chat` `folder-surface`, `folder-control`, `folder-open`, `folder-chip` and `folder-proposals` all count 0. Part B (the native dialog, a packed app, a paid agent turn) is unreachable here and was not driven.
- **Part A driven 2026-10-09 on a throwaway stub instance.** `folder-surface`, `folder-control`, `folder-open`, `folder-chip` and `folder-proposals` were count 0 on `/chat`; `GET /api/v1/folder` 200 `{"mounted":false,"name":null,"available":true}`; `POST /api/v1/folder/mount` 403 `folder_mount_ipc_only`; `GET /api/v1/folder/proposals?status=nonsense` 400; `.../proposals/nope` 404. Part B (packed app, live key) is **verified-unreachable** here: it needs the installed 0.16.0 `Nultron.exe`, a live key and the owner's go-ahead. Evidence: `drive5.json` (`folder_partA`).
