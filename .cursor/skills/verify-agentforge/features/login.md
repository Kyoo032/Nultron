# Login (hosted sign-in)

The **only** door into a hosted deployment, and it exists nowhere else: webdev and every other non-hosted build have no portal, so on those builds every testid below has count 0 and that is the pass. The app itself has no password field and takes no code: one button hands the browser to the portal, which by default emails a six-digit code (or, on a deployment run with `PORTAL_SIGNIN_MODE=password`, asks for a username and a password: **login-password-mode** below), and the browser comes back to `/auth/callback` with an authorization code the **host** exchanges server-side. Full mechanism: [`maps/portal-session-auth.md`](../../../../docs/internal/maps/portal-session-auth.md) for the host's half, [`maps/portal-service.md`](../../../../docs/internal/maps/portal-service.md) for the portal's. Plan of record: [`web-phase9-portal-login.md`](../../../../docs/internal/web-phase9-portal-login.md).

Product: both · Instance: hosted review :3443 (not :3000)

## Sub-features

- **login-screen** — `/sign-in` renders `auth-signin` (`apps/web/components/sign-in-screen.tsx:112`): the brand mark, the title "Sign in to {productName}", the intro "Use the work email your company invited.", the one button `auth-signin-start` ("Continue with email", and "Opening the sign-in page…" while busy, when it is disabled) and "No password. First time here? Have the invite code we emailed you ready. After that, we email you a sign-in code each time." (`apps/web/locales/en/auth.json`, `signIn`; reworded 2026-10-01 for invite-code sign-up; Indonesian in `locales/id/auth.json`). A hosted visitor with no session sees this **in place** of whatever they asked for, without the address bar changing, so `/meeting` and `/settings` render it too. Three paths are public and render before the gate: `/pricing`, `/sign-in` and `/auth/callback` (`PUBLIC_PATHS`, `App.tsx:154`), so a signed-out `/pricing` shows `PricingPage`.
- **login-reason** — `auth-reason` appears when the URL carries `?reason=<code>`, **or** when pressing `auth-signin-start` fails (`login_not_configured`, `portal_unavailable`, or whatever code the host's answer carried). A failed press overrides the URL's reason (`failure ?? arrivedWith`, `apps/web/components/sign-in-screen.tsx:95`). The code selects a key from a fixed list in `apps/web/lib/auth-reason.ts`: the 13 host reasons plus `login_not_configured` have their own copy, and anything else gets "Sign-in could not be completed. Please try again." A visitor's own string is **never** rendered.
- **login-start** — pressing `auth-signin-start` calls `GET /api/v1/auth/start`, which mints the login `state`, sets the login-state cookie (`__Host-agentforge_login_state` in secure/server mode, `agentforge_login_state` otherwise; HttpOnly, SameSite=Lax, 10 min; `packages/host/src/auth/login-state.ts:30-31`) and returns `{ authorizeUrl }`. The renderer refuses to navigate to anything that is not an absolute `http(s)` URL, so a `javascript:` body cannot reach `location.assign`.
- **login-portal** — the portal's own pages, reached by top-level navigation and not by `fetch`. There are five (`apps/portal/src/views/pages.ts`): the e-mail form (`signInPage`, `:86`, field `#email`, button "Continue"), the six-digit code form (`enterCodePage`, `:244`, field `#code`), the invite-code page (`inviteCodePage`, `:292`, field `#invite_code`), a state page for dead ends (`statePage`, `:334`), and the error page (`errorPage`, `:442`). The browser posts are `POST /authorize/email`, `/authorize/invite`, `/authorize/invite/resend` and `/authorize/verify` (`apps/portal/src/routes/authorize.ts:5-8`, the paths at `:63-69`, the route table at `:156-169`), handled by `handleEmailStep`, `handleInviteStep` and `handleInviteResend` (`apps/portal/src/routes/sign-in-flow.ts:318`, `:347`, `:384`).
- **login-portal-states** — the e-mail step is state-aware: which page follows depends on who the address is (owner decision 2026-10-01, no sign-up; the decision list is the header of `apps/portal/src/flows/sign-in.ts`, the page and status per state is `respondTo`, `apps/portal/src/routes/sign-in-flow.ts:201`):
  - `code_sent` (200): an active member gets the code form, and a code is mailed. A valid invite leads here too.
  - `code_wait` (429 with `Retry-After`): the code form with a wait notice, because the resend cooldown or the send limit applies.
  - `code_mail_failed` (503): the code form with a mail-failed notice. Nothing was delivered.
  - `invite_required` (200): an invited address that has not signed in yet gets the invite-code page and no code is mailed. A resend notice on that page can make the status 429 or 503.
  - `invite_wrong` (400): the invite-code page, with the attempts left.
  - `invite_unusable` and `no_access` (200): a state page. The invite expired, was used or is gone, or the address was never invited, is disabled or was removed.
  - `invite_locked` (429): a state page after the fifth wrong invite code. The fifth wrong code is itself the lock, so there is no "0 attempts left" form.
  - `otp_locked` (429): a state page after 20 wrong sign-in codes in a day.
  - `seat_cap_reached` (403): a state page ("no seats left"), shown before an invite is redeemed or a code is sent.
  The limits are in code: an invite can be re-mailed after 60 s and at most 4 times an hour per address (`INVITE_RESEND_COOLDOWN_MS`, `INVITE_RESEND_MAX_PER_WINDOW`, `INVITE_RESEND_WINDOW_MS`, `apps/portal/src/flows/sign-in.ts:42-45`), 5 wrong invite codes lock the address (`MAX_FAILED_INVITE_ATTEMPTS`, `apps/portal/src/store/postgres/invites.ts:27`), and 20 wrong sign-in codes a day lock it (`MAX_GUESSES_PER_DAY`, `apps/portal/src/store/postgres/otps.ts:27`). Redeeming an invite opens only the first door: the six-digit code is mailed next, so the invite alone is never a session. Because the pages differ per address, the e-mail step tells a caller whether an address is a member, an invitee or neither; that is deliberate and is why the step is rate limited per IP and per address.
- **login-invite-cli** — an operator issues an invite with `pnpm --filter @agentforge/portal invite -- --email <address> [--role owner|admin|member] [--print]` (`apps/portal/scripts/invite.ts`; the root shortcut is `pnpm portal:invite`, root `package.json:20`). The first invite in a tenant must be `--role owner`, because every tenant needs an owner (`owner_required`, exit code 5). `--print` also prints the code; without it the code goes only to the address, and exit code 7 means the mail transport refused it. For an address that is already an active member, `--role` changes the role instead of inviting.
- **login-callback** — `/auth/callback` renders `auth-callback` ("Finishing sign-in…") while it posts `{ code, state }` to `POST /api/v1/auth/login`. The code is stripped from the address bar **before** the exchange, the exchange runs exactly once per page load, and success is a **full page load** to `/chat`.
- **login-account** — `auth-account` on Settings (`apps/web/components/account-session-row.tsx:96`): the user id, the organisation id and the session expiry, with `auth-signout` (`:118`). The row draws nothing unless the session is signed in. The `auth.account` block (`apps/web/locales/en/auth.json:33-39`) holds `title`, `user`, `org`, `expires`, `signOut` and `signingOut`; there is no `auth.account.tenant` key.
- **login-erase** — the red **Erase company account** button is the owner's door out of a hosted company: `settings-reset-tenant` opens `settings-reset-tenant-confirm`, the phrase box is `settings-reset-tenant-confirm-name`, and `settings-reset-tenant-submit` stays disabled until the typed word is `DELETE` (`ERASE_ACCOUNT_CONFIRM_WORD`, `apps/web/lib/reset-app.ts:42`). It renders only for a session whose `role` is `owner` **and** where `capabilities.tenantReset` is true (`showErase = tenantReset && isOwner`, `settings-reset-card.tsx:186`). Everything about it, including the safe probe and the destructive warning, is in [settings.md](./settings.md); here it is the one visible thing the role changes.
- **login-signout** — `auth-signout` calls `POST /api/v1/auth/logout`, which revokes the refresh chain and the `sessions` row, clears the cookie and answers with a `portalLogoutUrl` when portal sign-in is configured (`handleLogout`, `packages/host/src/auth/routes.ts:591`; the URL is built by `portalLogoutUrl`, `:563-575`). The browser is then sent through the portal's `/logout` and back to `/sign-in`, or straight to `/sign-in` when there is no portal URL (`signOutAndLeave`, `apps/web/components/account-session-row.tsx:69-80`). The Chat header has a second door to the same call: the chip `chat-account`, rendered only when signed in, opens `chat-account-signout` (`apps/web/components/chat-account-chip.tsx:32,65`).
- **login-seat-cap** — a `seat_cap_reached` refusal lands back on the sign-in screen with that reason, because the person is signed out by definition. There is **no link**: `auth-reason` is a bare `<p>` (`sign-in-screen.tsx:123-130`) and nothing in `apps/portal` mentions pricing; `/pricing` is separately reachable signed out ([plans.md](./plans.md)).

- **login-password-mode** — the portal run with `PORTAL_SIGNIN_MODE=password` (owner decisions 2026-10-07, and 2026-10-09 for the Nultron Enterprise release bundle's default: its `portal.env.example` and k8s base set the mode; the portal's own default when the variable is absent is still the e-mailed code, and the Mailpit rehearsal overlay pins `code`). The app side: the host asks the portal `GET /auth/signin-mode` (registered only in that mode; a 404 is the default mode) and `GET /api/v1/auth/session` then carries `signInMode: "password"`, only then; the sign-in screen (still `auth-signin`, still one `auth-signin-start`) reads "Use the username and password your company gave you." and the button "Continue to sign in", and shows neither "work email", "invite code" nor "sign-in code" (Indonesian: "Gunakan nama pengguna dan kata sandi yang diberikan perusahaan Anda.", "Lanjut ke halaman masuk"). The portal side: `GET /authorize` renders `#identifier` (a username, or the address on record) and `#password` and posts to `/authorize/password`; a person with an operator-issued password gets the change page (fields `#current_password`, `#new_password`, `#confirm_password`, `/authorize/password/change`) and no session until they have chosen their own; every refusal (unknown username, wrong password, a lock, a disabled person) gets one message, "That username or password is not right. If you keep seeing this, ask your admin." (`apps/portal/locales/en/portal.json:17`); five counted failures lock the account for 15 minutes; the e-mail, invite and verify routes answer 404. Accounts are made by the operator command `portal.sh account create|reset-password|disable|enable|set-role|list` (no self-sign-up, no self-service reset). Map: [portal-service.md](../../../../docs/internal/maps/portal-service.md) section 8; spec: [device-code-login.md](../../../../docs/internal/portal/device-code-login.md), "Password sign-in".

## How to get to it (user POV)

- On a hosted deployment, everywhere. A signed-out visitor who opens any route gets the sign-in screen; there is nothing else to press.
- `/sign-in` directly. On a **non**-hosted build that route redirects to `/chat`, and so does `/auth/callback` — both are mounted only where a sign-in can be completed.
- After signing in: Rail → Settings, after the whole settings form and before the plan panel, is `auth-account` (`apps/web/components/settings-page.tsx:598-600`: `AccountSessionRow` at `:598`, then `AccountPlanPanel` at `:600`). The Chat header's `chat-account` chip is the other way in to sign-out.

## Driving it with the Nultron harness

**Preconditions, and none of them is optional.**

- This needs the **review instance**, not `:3000`. Webdev is not in server mode and has no portal. Start it from the repo root: `powershell -NoProfile -File scripts\review-instance.ps1 -Start -Production`. Default (no `-Start`) prints what it would launch and exits 0 — read that first.
- Doctor cannot doctor this instance: `https://localhost:3443` is self-signed TLS, and a signed-out hosted `GET /api/v1/settings` answers 401 (SKILL.md **Doctor**). Instead run `scripts\review-instance.ps1` without `-Start` and confirm it prints the origins you expect (app `127.0.0.1:3100`, portal `127.0.0.1:4000`, proxy `127.0.0.1:3443`), and record in the evidence that doctor was skipped and why. Never drive an instance this run did not start.
- The portal needs a seeded tenant and an OAuth client. `pnpm --filter @agentforge/portal migrate`, then `pnpm --filter @agentforge/portal seed -- --email <you> --tenant nultron --org Kyo --seat-cap 2 --redirect https://localhost:3443/auth/callback`. **The client secret prints once.** Paste it into `$HOME\.nultron-review\review.env` as `AGENTFORGE_PORTAL_CLIENT_SECRET`.
- **A second hosted target: the Phase 0 pilot stack (compose).** `node webapp-deploy/pilot-local.mjs up` builds and starts the production-shaped stack on this machine (app, Caddy, portal, Postgres, a Mailpit that speaks implicit TLS like SES) at `https://nultron.localhost` and `https://portal.nultron.localhost`, on 127.0.0.1 ports 80 and 443 (`webapp-deploy/README.md`, "Phase 0 pilot (compose)" and "Rehearsal on a developer machine"). Its Mailpit UI and REST API are on `http://127.0.0.1:18025` (`webapp-deploy/compose.local.yml:79-81`), not on the dev stack's 8025, so a code mailed by the pilot never shows in the 8025 inbox. The pilot seeds the seed script's defaults (tenant `nultron`, org `Kyo`, seat cap 20; `apps/portal/src/seed/args.ts:31-33`) and one owner, `tester@nultron.test` unless `up --email` said otherwise; do not run `seed` again. `pilot-local.mjs drive` runs its own sign-in and then restarts the app and the proxy and stops the portal (`webapp-deploy/pilot-local.mjs` header), so never run it against a stack you did not start. The pilot's portal is a production build, so the `otp` mint fallback in step 5 is refused there; issue an invite instead (`login-invite-cli`). The repo's route is `webapp-deploy/scripts/portal.sh invite ...` with `DC_ARGS="-p nultron-pilot-local -f compose.local.yml --env-file .pilot-local/.env"` set; `portal.sh` refuses `otp` by design (`webapp-deploy/scripts/portal.sh:13-14`, `:30-33`). The same thing by hand: `MSYS_NO_PATHCONV=1 docker exec nultron-pilot-local-portal-1 sh /app/webapp-deploy/portal-entry.sh ./node_modules/.bin/tsx scripts/invite.ts --email <address> --role member --print` (`--role admin` for an admin). `--print` shows the code when mail is down, and exit code 7 means the mail was not sent. The container name is the compose project `nultron-pilot-local` plus `portal-1`. Check the inbox first with `curl http://127.0.0.1:18025/api/v1/messages`: the pilot's `mailpit` service has `restart: "no"` (`webapp-deploy/compose.local.yml:82`), so after a Docker engine restart it stays `Exited` and every send fails with `ENOTFOUND mailpit`. Starting that container is the operator's call.
- Use a **real browser**, not `fetch` and not curl. See the first gotcha; this is the whole point of the recipe.
- Never point any of this at `:3000`, and never at `.webdev-data`. The script refuses a data dir inside the checkout, but the rule is yours to keep too.

**The walk.**

1. `goto https://localhost:3443/chat`, accept the self-signed warning once. Settle. `auth-signin` is visible and `auth-signin-start` has count 1. Neither `composer` (the Chat composer's testid, `apps/web/components/chat-composer.tsx:663`) nor `onboarding-form` is on screen — if `onboarding-form` is, that is [SR-06](../../../../docs/internal/security-register.md#sr-06) and a fail.
2. **Open the browser console and leave it open.** On the happy path (member, code form, signed in) zero messages on either origin is part of the pass. A page with a non-2xx status (the 400, 403, 429 and 503 states in `login-portal-states`) logs one "Failed to load resource" line for its own status. That line is expected; the check there is no CSP violation and no page error.
3. Click `auth-signin-start`. The address bar leaves your origin for the portal's. The e-mail form renders.
4. Type the seeded address, submit. An active member's address renders the six-digit code form. An address that was invited but has not signed in yet renders the invite-code page (`#invite_code`) instead and no code is mailed until the invite code is accepted; an address the portal does not know renders a state page. Walk those branches from `login-portal-states` with their own addresses, one at a time. **Submitting this form is the step that catches CSP** — if the button does nothing and the console says `form-action`, read [SR-20](../../../../docs/internal/security-register.md#sr-20).
5. Read the code from **Mailpit** at `http://127.0.0.1:8025`. Or mint one: `PORTAL_ALLOW_MANUAL_OTP=1 pnpm --filter @agentforge/portal otp -- <email>` — that **issues** a fresh code (only the sha256 is stored, so nothing can read one back), prints it once, and writes `otp.issued_manually` to the audit log.
6. Enter the code, submit. The browser goes `302` → `https://localhost:3443/auth/callback?code=…&state=…` → `auth-callback` flashes → `/chat`, signed in. **Check the address bar: no `code`, no `state`.** Check the console: still empty.
7. Rail → Settings. `auth-account` is visible and carries the user id, the organisation id and the expiry. No token appears anywhere in the payload or the DOM — `GET /api/v1/auth/session` returns `signedIn`, `userId`, `orgId`, `tenantId`, `expiresAt` and the person's `role` (no labels, `session.ts:185-193`) (`owner` | `admin` | `member`, the membership row's, which is the portal's word; `roleForAnswer` at `packages/host/src/auth/routes.ts:609` answers it at `:637-643`) only. The role decides one visible thing: the red **Erase company account** button on Settings (`settings-reset-tenant`, `login-erase`) appears for an `owner` and for nobody else (SR-65; [`settings.md`](./settings.md) has the safe probe). Drive it with two invited people — `invite.ts --role member` and `--role admin` — and the seeded owner. Do not press `settings-reset-tenant-submit`.
8. **Mutation after sign-in.** Save anything on Settings, or create a workspace. A 403 here means the session-bound CSRF token was not re-minted, which is [SR-07](../../../../docs/internal/security-register.md#sr-07) and means the full page reload was skipped.
9. Click `auth-signout` (or `chat-account`, then `chat-account-signout`, on Chat). The browser goes through the portal's `/logout` and lands on `/sign-in` showing `auth-signin`. `GET /api/v1/auth/session` answers `{"signedIn":false}` and `/chat` renders `auth-signin` again.
10. **The negatives**, each on its own: `goto /auth/callback?error=seat_cap_reached&state=x` lands on `/sign-in?reason=seat_cap_reached` with `auth-reason` reading "No seats left in your organisation."; `goto /sign-in?reason=<a string of your own>` renders the **generic** sentence, never your string; `POST /api/v1/auth/login` with a `state` that does not match the cookie answers `invalid_request` from the handler (`readState`, `packages/host/src/auth/routes.ts:364-371`), but only if the request carries the CSRF cookie and `x-agentforge-csrf` header and a trusted origin. A bare POST from a signed-out hosted browser is stopped first with `403 csrf_missing` (`mutatingRejection`, `packages/host/src/http-adapter.ts:772-801` (the origin and CSRF branch is `:784-795`, answered at `:632-636`; with no or an untrusted `Origin` the first answer is `origin_forbidden`, and `csrf_missing` needs a trusted `Origin` and no cookie or header, `csrf.ts:151-153`); driven 2026-10-05 on the pilot), so assert the code you actually reached and say which layer answered.
11. Evidence under `evidence/login/<run-id>/`: screenshots of the sign-in screen, the portal's forms and any state page you reached, the signed-in `/chat`, and `auth-account`; the `review-instance.ps1` printout and a note that doctor was skipped and why; and a note that the console was empty on both origins.

## Gotchas

- **The preview form is a different door from this page.** The live preview is not server mode and does not use the portal. Its external `preview-server.ts` must mount `PreviewGate.requireProduction(process.env)`; stock-server or webdev tests do not prove that mount. Before touching Caddy Basic Auth, follow the [preview cutover checks](../../../../webapp-deploy/README.md#preview-desks-mount-the-form-before-changing-caddy): check anonymous requests at each upstream, then drive sign-in and sign-out in a fresh browser on the approved TLS canary and verify desk isolation. A native Basic Auth dialog on a route still using it does not exercise the form. The portal recipe on this page is unchanged.

- **Preview with an IPv6-literal URL.** On an approved TLS canary with a certificate for that address, sign in and out by the bracketed IPv6 URL. A same-origin form POST should redirect (303), not return 403. Connecting to a DNS name over IPv6 does not exercise the literal-host comparison. The local preview gate suite covers both default and non-default ports without changing Caddy.

- **CSP is only enforced by a real browser, so a curl drive proves nothing about it.** This is not a style preference. `form-action 'self'` blocked the OAuth redirect for every human while `routes/browser.test.ts` walked the same three hops green, because a non-browser client does not implement CSP at all. `__Host-` cookie acceptance, `SameSite` and mixed-content blocking are in the same class. If you did not press the button in Chromium, you did not test the login.
- **The portal's browser session is 30 days, and only the sign-out hop ends it.** After one successful sign-in, pressing **Sign in** again goes straight through — no address, no code, no mail — because `getAuthorize` completes the sign-in when the cookie carries a live session for that tenant. In-app sign-out sends the browser through the portal's `/logout` and back to `/sign-in`, which clears that cookie. So **the second run of this recipe on the same browser profile skips the OTP step only if the portal hop failed or portal logout is not configured** (no `portalLogoutUrl` in the sign-out answer, or a failed sign-out POST, lands on `/sign-in` with the portal still signed in). Check the address bar went through the portal on sign-out; if it did not, use a fresh profile, a private window, or a second origin with its own cookie jar. That is [SR-21](../../../../docs/internal/security-register.md#sr-21), whose status is "Fixed-unverified, fix pass X": the browser drive of sign-in → sign-out → sign-in-again is still owed.
- **A hosted desk still needs a gateway key.** Signing in gets you past the door; it does not give the tenant a working gateway. After sign-in, a tenant with no key sees the welcome and, behind it, the paste-your-key step — and *that* is correct, because the person is now signed in. Since 2026-10-01 that step also offers **Add it later** (`onboarding-later`), which opens Chat with no key and is remembered per person; every pane then says a key is missing instead of failing, and Settings shows the key form. Do not record either as a login failure. See [onboarding.md](./onboarding.md) and [gateway-gate.md](./gateway-gate.md).
- **A deep link does not survive sign-in.** The `redirect_uri` is fixed at `/auth/callback` and carries no return path, so the round trip always lands on `/chat` however you arrived. Known, recorded as an owner decision in [`worklog-2026-09-21.md`](../../../../docs/internal/worklog-2026-09-21.md) §6 — not a harness miss.
- **`/auth/callback` runs its exchange once per page load, guarded at module scope** rather than in a ref, because StrictMode remounts a component and a module is not re-created. A reload of that URL after a successful sign-in is therefore a *failed* exchange (the code is spent), which lands on `/sign-in?reason=invalid_grant`. Expected.
- **Everything here is 404 or a redirect off server mode.** `GET /api/v1/auth/start` answers 404 on webdev, and `/sign-in` and `/auth/callback` redirect to `/chat`. `GET /api/v1/auth/session` is the one exception — it answers `200 {"signedIn":false}` on every build, deliberately ([SR-37](../../../../docs/internal/security-register.md#sr-37)). But the renderer only asks it where `GET /api/v1/ping` reports `capabilities.sessions` (`apps/web/lib/session.tsx:16-17`; the `readSessionOnce` guard is `if (!capabilities.sessions)` at `:155`), so webdev and every other non-hosted build make no such request, and no `/api/v1/auth/session` entry in their network tab is the pass.
- **Known portal bug, not fixed: a failed send blocks its own retry for 60 s.** After `code_mail_failed`, "Send a new code" within a minute answers 429 "We already sent a sign-in code…" although nothing was delivered, because the cooldown measures from the newest code row's send time (`status.newestSentAt`, `apps/portal/src/otp/send.ts:119-122`, limit `OTP_RESEND_COOLDOWN_MS`, `:39`) and a refused send's row is retired, not removed (`:186`). Driven 2026-10-05 on the pilot. Record it as this finding, not as a mail failure on the second try.
- **The tunnels are ephemeral.** If you are driving through a `trycloudflare.com` hostname, it dies with `cloudflared` and the next one is a different name — which has to be re-seeded as a `--redirect` and re-passed as `-AppPublicUrl` / `-PortalPublicUrl`. Close them when the review is done ([SR-28](../../../../docs/internal/security-register.md#sr-28)).
- **Password mode: the screen follows the host, and the host follows the portal.** The sign-in screen says "username and password" only when `GET /api/v1/auth/session` carries `signInMode: "password"`, which the host sends only when the portal answered `GET /auth/signin-mode` with exactly `{"mode":"password"}`. A portal that is down, slow or older answers nothing the host believes, and the screen then says what it has always said (the e-mailed code); the host re-asks after 15 s and caches an answer for 5 minutes. So a screen that still promises a code in front of a password portal means the host has not heard from the portal yet, not that the renderer is wrong. A desk never asks, so on webdev and every other non-hosted build none of this exists.
- **Password mode: a person made by `seed` cannot sign in until they have a password.** The owner that `seed` creates is active with no credential. `account create --email <that address>` attaches one and keeps their role.
- **G1 applies twice over.** The portal's two forms are real `<form>` submits and so is the sign-in button's navigation. Settle after every `goto` before pressing, or the browser does a native submit and you lose the state cookie.
