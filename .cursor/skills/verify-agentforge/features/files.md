# Files

Desk files are the versioned text files an agent and its owner share on one desk. They live in a Files section at the bottom of the Knowledge Base's Sources tab (`mode-knowledge`, `knowledge-tab-sources`). There is no rail entry and it is not a product mode. Chat writes them through six tools (`list_files`, `read_file`, `write_file`, `edit_file`, `search_files`, `delete_file`), the owner writes them from the page or the API, and every change is kept as a version that can be restored. Both products have them. How it works: [`docs/internal/maps/agent-tools-and-files.md`](../../../../docs/internal/maps/agent-tools-and-files.md), § 6 to § 8 and § 11. The Personal-only folder is [folder.md](./folder.md).

Product: both · Instance: main :3000

## Sub-features

- `files-section` is the whole section. It sits under the source rows in `knowledge-sources` (`apps/web/components/knowledge-page.tsx:638`). Its header carries `files-count` (absent at zero files; "1 file" or "N files"), `files-new` and `files-upload` (a label wrapping the hidden `files-upload-input`).
- `files-list` holds the files grouped by folder: one `files-folder` header per folder (`data-folder` is the path, empty for the top level, which reads "Top level") and one `files-item` button per file (`data-path`, `data-on`). `files-loading`, `files-empty` and `files-load-error` with `files-retry` are the other states. The list is `max-h-72` and scrolls inside itself.
- `files-new` opens `files-new-form` with `files-new-path`, `files-new-content`, `files-new-save`, `files-new-cancel` and, on a refusal, `files-new-error`. A path the form can tell is wrong is refused before any request (`checkNewPath`, `apps/web/lib/files-model.ts:100`); the host refuses the rest.
- `files-upload-input` takes one text file (UTF-8, no NUL, at most 2 MB) and saves it at the top level under its own name. A file that is too large, not text or unreadable shows `files-upload-error`.
- `files-notice` says what just happened: "Saved notes/plan.md as version 2.", "Restored version 1 as version 3." or "Deleted notes/plan.md.".
- `file-viewer` opens when a `files-item` is pressed, after a save, or from a link. It carries `data-path` and `data-phase` (`loading`, `failed` or `ready`). Inside it: `file-viewer-path`, `file-viewer-close`, `file-viewer-which` ("Viewing version N of M"), the text as `file-viewer-text` with `file-viewer-numbers` and `file-viewer-lines` (or `file-viewer-empty`, and `file-viewer-truncated` past 5000 lines), and `file-versions`. `file-viewer-loading`, `file-viewer-error` ("That file is not on this desk, or it was deleted." for `not_found` only; any other host code shows its own text under the same testid, for example `?file=con.md` gives "That file path is not allowed.", `file-viewer.tsx:279-281`), `file-viewer-version-loading` and `file-viewer-text-error` are the other states. The text is plain text only, never parsed as HTML or Markdown.
- `file-version` is one version button, newest first, with `data-version` and `data-on`. Each shows who saved it: "You", "A teammate" (hosted only) or "Agent in {mode}", then the time and size.
- `file-download` (added 2026-10-06) is the viewer's Download button, shown only while the newest version is in view (it is absent when `file-restore` is present). It saves that file to the computer under its own name; its `aria-label` is "Download {path} to your computer" and it reads "Downloading…" and is disabled while the request runs. A refusal shows `file-viewer-action-error`; in the packaged app a save the shell could not write shows "The file could not be saved to your computer. Check the location and try again." there (`files.errors.saveFailed`, code `save_failed`, 2026-10-07), not the network sentence, and a closed save dialog shows nothing.
- `file-restore` shows only while an older version is in view and asks first: `file-restore-confirm` is an alert dialog with `file-restore-confirm-yes` and `file-restore-confirm-cancel`. Restore saves the old text as a new latest version. `file-delete` asks the same way (`file-delete-confirm`, `-yes`, `-cancel`). `file-viewer-action-error` shows a refusal.
- `files-deep-link` is `/knowledge?file=<url-encoded path>`. It opens that file's viewer on arrival and again on a repeat visit to the same link; the address is only read and is not rewritten when the viewer closes (`apps/web/components/files/desk-files.tsx:36` and `:88`).
- `files-api` is eight routes, all on the selected desk: `GET /api/v1/files` (query `dir`, `glob`), `GET /api/v1/files/content?path=`, `GET /api/v1/files/download?path=` (the newest version as an attachment, 2026-10-06), `GET /api/v1/files/versions?path=`, `GET /api/v1/files/version?path=&version=`, `POST /api/v1/files` with `{path, content}`, `POST /api/v1/files/revert` with `{path, version}` and `DELETE /api/v1/files?path=` (`DESK_FILE_ROUTES`, `packages/host/src/desk-files/routes.ts:199`). Paths ride in the query string. They are not gated by the gateway gate.
- `files-chat-tools` is what Chat shows when a file tool runs, inside the Thinking disclosure (`message-thinking` → `message-tools` → `message-tool` with `data-tool`): a `tool-row-file` (`data-tool`, `data-state` of `running`, `done`, `refused`, `budget` or `pending`) with a sentence such as "Read notes/plan.md", a small fact, and for a saved `write_file` or `edit_file` (status `saved`, root not `folder`; never for read, list, search or delete, `results.ts:170-184`; a `pending` row comes only from folder-root writes) a `tool-row-file-chip` that links to the deep link above and a `tool-row-file-download` button beside it (a `run_code` row has one beside each saved file, 2026-10-06). A refusal adds `tool-row-refusal`; a spent budget adds `tool-row-budget`. `knowledge_search` gets `tool-row-knowledge` and `tool-row-knowledge-sources`.

## How to get to it (user POV)

- Choose Knowledge Base on the Account rail (`mode-knowledge`). The Sources tab is the default (`knowledge-tab-sources`). Scroll past the source rows to the Files section.
- Or follow a chip in a Chat reply: "Open" on a saved file goes to `/knowledge?file=…`.
- Or open `http://127.0.0.1:3000/knowledge?file=notes%2Fplan.md`.

- Work under a `verify/` path on the current desk and delete the files at the end: the chat-first UI has no way to create a throwaway desk (`create-new-workspace` and `workspaces-switcher` are count 0), so a desk made through `POST /api/v1/workspaces` is for a throwaway data dir only (it becomes the process-global current desk). Files on Default are only soft-deleted and stay in the data dir; a deleted non-Default desk purges its files, versions and sealed objects (`purgeDeskFiles`). The API acts on the selected desk (the workspace cookie, else the host's remembered selection).
- Use paths under `verify/` so nothing collides with a real file.
- A stub desk is enough for everything below except the Chat scenario at the end, which needs `runtime: "ai"` and a key (doctor's `runtime`). **Stub Chat never calls a file tool** (`StubRuntime` runs `calculator`, `datetime` and `past_sessions` only).

- **Empty section.** Click `mode-knowledge`. `knowledge-sources` is visible; scroll to `files-section`. On a new desk `files-empty` shows and `files-count` has count 0.
- **New file, version 1.** Click `files-new`; `files-new-form` opens. Fill `files-new-path` with `verify/plan.md` and `files-new-content` with three lines (`Step one`, `Step two`, `Step three`). Click `files-new-save`. Proof: `files-notice` reads "Saved verify/plan.md as version 1."; `file-viewer` is visible with `data-path="verify/plan.md"` and `data-phase="ready"`; `files-count` reads "1 file"; one `files-item` has `data-path="verify/plan.md"`, under a `files-folder` with `data-folder="verify"`; `file-viewer-which` reads "Viewing version 1 of 1"; `file-viewer-lines` holds the three lines.
- **Second version.** Click `files-new` again, fill the same path with `Step one`, `Step two changed`, `Step three`, save. `files-notice` reads "...as version 2."; `file-version` has two rows (`data-version` 2 first, `data-on="true"`); `file-viewer-which` reads "Viewing version 2 of 2". Saving the same text again changes nothing: the notice still says version 2 and the row count stays 2.
- **Look back.** Click the `file-version` with `data-version="1"`. `file-viewer-which` reads "Viewing version 1 of 2", `file-viewer-lines` reads exactly "Step two" and does not contain "changed" (version 2 is "Step two changed", which also contains "Step two", so assert the exact line or the absence of "changed"), and `file-restore` appears (it is absent on the latest version).
- **Restore.** Click `file-restore`; `file-restore-confirm` opens with focus on `file-restore-confirm-cancel`. Press Escape: the dialog closes and nothing is saved. Open it again and click `file-restore-confirm-yes`. `files-notice` reads "Restored version 1 as version 3."; three `file-version` rows; version 3 is `data-on` and its text equals version 1's. - **Delete.** Click `file-delete`, then `file-delete-confirm-yes`. `files-notice` reads "Deleted verify/plan.md."; `file-viewer` is gone; the `files-item` is gone. A reload still shows no `files-item` for it, and `GET /api/v1/files/content?path=verify/plan.md` answers 404.
- **Download (added 2026-10-06; driven in a browser on 2026-10-16: the saved `plan.md` bytes equal version 2, and the response headers are `attachment`, `no-store`, `nosniff` and `sandbox`).** With `verify/plan.md` at version 2 open and the newest version in view, `file-download` is visible and `file-restore` is absent. A deleted or never-written path answers 404 `not_found` and `file-download` shows `file-viewer-action-error` if the file was deleted under an open viewer. ## Gotchas

- A host process that started before the files code has no `/api/v1/files` route. Check `GET /api/v1/files` first (200, not 404); on a 404, say "restart :3000" and do not drive.
- Stub Chat never writes a file (`StubRuntime` answers only `calculator`, `datetime` and `past_sessions`). Do not read a green stub Chat send as proof of the file tools; only the live scenario above, or the unit suites, prove them.
- Files are sealed text. A file's plain text is never in SQLite or the object store; the API is the only way to read it. Do not look for it on disk.
- Delete is soft and ends the file's history for every route: after a delete, `versions` and `version` answer 404, and writing the same path again starts a new file at version 1. Deleting a file does not free storage; deleting the desk does.
- The quota only exists on the hosted server. On webdev and any non-hosted build a write is never refused for space. A quota refusal (`storage_quota_exceeded`, 403) is reachable only on the review instance.
- The 2000-file cap and the 2 MB cap are real: file 2001 answers 409 `too_many_files` and 2 MB plus one byte answers 413. Driving the 2000-file cap by hand is slow; the unit suite (`packages/host/src/desk-files/file-store.test.ts`) holds it.
- Regex search (`search_files` with `regex: true`) is refused on the hosted server and works on webdev. Nothing in the Files section searches; search is a Chat tool.
- The injection scan reads file content. A Chat `write_file` whose text trips a rule is refused and shows `tool-row-refusal` or a blocked message; saving the same text from the page or the API is not scanned.
- Two `edit_file` calls on one file in one Chat step no longer lose an edit silently. `edit_file` sends the sha256 of the text it read as `expectedSha256` (`editFileTool`, `packages/core/src/tools/files/tools.ts:163`), and the desk store compares it with the head under the desk lock (`saveLocked`, `packages/host/src/desk-files/file-store.ts:213`, the compare at `:227-229`). The call that loses is refused with code `conflict` ("The file changed after it was read (or was deleted), so this edit was not saved. Read the file again and redo the edit.", `CONFLICT_MESSAGE`, `:38`), which shows as a `tool-row-refusal` on that `tool-row-file`, and the tool text tells the model to read again and redo it. So a Chat drive that asks for two edits can show one refusal and one extra `file-version` before both edits are in the file; fewer edits than asked with no `conflict` row is a bug. `write_file` sends no expected hash and still replaces the head. The desk store's `compare and set` suite in `packages/host/src/desk-files/file-store.test.ts` holds it; the live Chat race is not driven.
- Download always sends the newest version. The viewer hides it while an older version is open for that reason; do not expect it to save the version on screen. The route is served with `Cache-Control: no-store` on purpose: the adapter's default for bytes (an hour, private) would hand back an old version after an edit.
- A visited Knowledge page is not kept mounted the way job studios are, so `files-section` is count 0 on every other route. Assert visibility on `/knowledge` only.
- Locale: on an `id` desk the section reads `Berkas`, the buttons `Berkas baru`, `Unggah berkas teks` and `Pulihkan versi ini`. Testids are unchanged; parity is held by `apps/web/lib/files-locale.test.ts`.
- Also on this page: the form closes on Escape (`files-new-form.tsx:50`) and pressing `files-new` while it is open **closes** it (`aria-expanded`), so a script that clicks `files-new` before every save toggles it shut on the second pass: click it only when `files-new-path` is not visible. A text over 2 MB gives `files-new-error` on the client (the too-large copy); an upload also runs the path check on the file name (`files-upload-error` with a path message, `desk-files.tsx:181`), and the input has no `accept` (a different input on the same tab, `knowledge-file`, is source ingest). The list is top-level files first, then folders A to Z, each A to Z by base name (not by recency, `files-model.ts:75`); a row shows base name, size, "v{n}" and "Updated {when}". After a save, restore or open the viewer goes loading then ready (`file-viewer-loading`, `data-phase`): wait for `data-phase="ready"` before counting `file-version` rows. A desk switch closes the viewer and the form and clears the notices (`desk-files.tsx:65-78`). The API answers `DELETE` with `{status: "saved", path, version: head}`, a missing path or a non-whole `version` with 400 `invalid_request`, a bad glob with 400 `bad_pattern`, a revert to a nonexistent version with 404 `not_found`; `conflict` 409 is unreachable by routes (none passes `expectedSha256`).
- **"Add from desk files" in Documents and Presentations** is the shared `DeskSourcePicker` (`desk-source-picker.tsx:135`): testids `desk-sources`, `-toggle`, `-hint` ("Up to 5 files", `MAX_DESK_SOURCE_FILES`), `-chips`, `-chip`, `-remove`, `-list`, `-option` (`data-path`, a checkbox) and `-over`; hidden while the desk has no files, refreshed at most every 4 s (`REFRESH_MIN_MS`). Scope it to the studio's root (G3).
- **Driven 2026-10-05 on `:3000` (keyed; maintain3), no model call.** A clean desk showed `files-empty`; `verify/plan.md` saved as version 1, then 2 (two `file-version` rows), identical text added nothing; look back at version 1 (`file-restore` visible, no "changed" in the text); Restore opened `file-restore-confirm`, Escape cancelled it (still 2 versions), the second Restore gave "Restored version 1 as version 3." and 3 rows; `/knowledge?file=verify%2Fplan.md` opened the viewer, `?file=verify%2Fnope.md` read "That file is not on this desk, or it was deleted." and `?file=con.md` read "That file path is not allowed."; five bad paths (`/abs.md`, `../x.md`, `a\b.md`, `con.md`, `a:b.md`) each gave `files-new-error` ("Start the path at the top, with no leading /.", "Parts named . or .. are not allowed.", "Use / between folders, not a backslash.", "That file path is not allowed." twice); `verify-upload.txt` uploaded; `verify/plan.md` deleted through `file-delete-confirm-yes` ("Deleted verify/plan.md."). Every file was removed afterwards (`GET /api/v1/files` -> `[]`). The paid Chat scenario (a model writing and editing a file) was **not driven**.
