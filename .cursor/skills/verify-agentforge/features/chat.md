# Chat

Chat is the default assistant: model picker, composer, thinking toggle, usage chip, and its own sessions at `/chat`. Since 2026-09-17 the sessions live **in the left rail** under `mode-chat` (`rail-thread-list`: `new-chat-link`, 4 rows, and a `threads-see-all` toggle that expands the list in place). There is no session column any more — `/chat` is just the chat pane. Stub replies without a gateway key; a saved key uses the live Toko Token gateway. A turn is three layers: **Thinking** (collapsible), **tools** (one row per call; Chat binds 16, see `chat-tools`), **output** (the answer only — never a copy of the prompt, never a `Stub reply` prefix). Maps: [`chat-send.md`](../../../../docs/internal/maps/chat-send.md) and [`chat-sessions-and-rail.md`](../../../../docs/internal/maps/chat-sessions-and-rail.md).

## Sub-features

- `chat-open` shows the empty Chat home with composer, model picker, and the composer toolbar (`composer-toolbar`: `composer-attach` as a 32px icon, `model-picker`, `reasoning-effort`, `composer-enhance`, `composer-send`). The toolbar is one row only when the composer is wide (about 626px and up); narrower it is two rows and then compact chips — see `chat-composer-layout`. Header chips sit in `chat-header`, one row at every width, and fold into one menu when they do not fit (`chat-header-menu`). `chat-home` is the pane's `<main>`; `assistant-live` wraps the in-flight assistant turn inside `message-list` (present while running, thinking, streaming or after a failed send); `composer-attachments` is the list of unsent attachments below the drop zone (present only while a file is attached) and each file is one `composer-attachment` chip.
- `chat-composer-layout` (2026-09-29) — the composer and the empty-state intent cards size to the room they have (CSS container queries on `composer`), not to the viewport. Four layouts by the composer's content width (its box minus 26px): **wide** ≥ 600 one row, vertically centred; **medium** 470–599 controls on the top row, attach left and `composer-send` right beneath; **narrow** 220–469 compact chips (no visible `Model:` prefix, Thinking as icon plus value, icon-only Enhance, 40px tap targets, model chip on the top row with Thinking, attach and Enhance beside `composer-send` beneath); **tiny** under 220 a wrapping flex. `composer-needs-key` spans the full width in all four. The prompt box is two lines tall below 600, and still grows to 160px. `chat-suggestions` is 1 column when narrow and 2 when its grid is 524px or wider. - `chat-header-menu` (2026-09-29) — `chat-header` is one row, 56px tall, at every width. Title left; `chat-context` and `chat-usage` (and `chat-account` when signed in) right **while they fit** beside the title (`data-mode="inline"`). Each chip is mounted once and never remounted by a fold, so the usage chip's fetch is not repeated. The default agent runs under Chat's budget: 12 model steps, 40 tool calls, and per-tool caps (`write_file` and `edit_file` 20, `delete_file` 10, `web_fetch` 8, `run_code` 6, `self_check` 4; `packages/core/src/harness/modes/chat.ts:33-37`, spec at `:29`, `perTool` at `:36`). The file tools, `knowledge_search` and `run_code` draw rich rows, `tool-row-file`, `tool-row-knowledge` and `tool-row-code`, each with `data-tool` and `data-state` (`running`, `done`, `refused`, `budget`, `pending`; a code row that ran and failed is `failed`). Personal and webdev are unaffected. See [code.md](./code.md), `code-switch`. Recipes: "Tool rows" below, [files.md](./files.md), [folder.md](./folder.md), [code.md](./code.md). - `chat-tool-recovery` (2026-10-06) — a tool that throws no longer ends the run. `buildAiTools` (`packages/core/src/runtime/ai-tools.ts:31`) catches the error and hands the model `{ ok: false, reason: "tool_error", message }`: `The <key> tool failed with: "<detail>". Fix the arguments or try another way; …`. The detail is quoted, has keys and bearer tokens masked, host paths replaced by `[host path]` (only paths under a root a host has, such as `/home` or `/tmp`; `/workspace/out/x.csv` and a desk path like `/notes/plan.md` stay), is cut at 220 characters, and is followed by one line of advice (`toolErrorResult`, `packages/core/src/runtime/tool-error.ts:67`). For every tool, an error text that reads like instructions is withheld (the media tools throw a gateway's error body under `internal` trust). A call to a tool that is off spends the run's budget like any other call, so a flood of them ends in the budget refusal. The row shows the refusal state with that message (`data-state="refused"`, `tool-row-refusal` on the rich tools). A cancel is never turned into a result: while the client has left or the stall guard fired, the error is rethrown and the run ends as a cancelled run (`isRunAbort`, `tool-error.ts:98`). Still ending the run: a call whose arguments fail the SDK's own schema check, and a call to a tool name that does not exist at all (`InvalidToolArgumentsError`, `NoSuchToolError`); see Gotchas.
- `chat-step-limit` (2026-10-06) — a run that uses all 12 model steps and whose last step still asked for tools used to finish with tool rows and no words. The runtime now says so (`run.step_limit`, `packages/core/src/runtime/ai-sdk-runtime.ts:605`; the SDK does not report it, `createStepTracker` reads it from the stream), and Chat adds one closing sentence (`chatTurnCopy(locale).stepLimit`, en `I ran out of steps before I could finish this. Ask me to continue and I will pick up from where I stopped.`, id `Langkah kerja saya habis sebelum ini selesai. …`) after a blank line, streamed as an `assistant.delta` and saved with the turn (`settleChatTurn`, `stepLimit`). The `run.step_limit` event itself is not sent to the screen. Jobs get the event and ignore it. The SDK in use (ai 4.3.19) cannot force a tool-free final step in `streamText`, so the sentence is written by the host, not by the model.
- `chat-tool-turn-interrupted` (2026-10-07; found by a live drive, fixed in the tree, not re-driven) — a turn whose tool completed and whose follow-up model call then failed used to end with the tool rows and no words and no error: `shouldKeepToolTurn` (`packages/core/src/runtime/retry.ts:173`) keeps the turn so a completed tool is neither lost nor run twice, and the runtime answered it with a bare `run.completed`. The runtime now sends `run.interrupted` with the failure's message just before `run.completed` (`ai-sdk-runtime.ts`, the `shouldKeepToolTurn` branch; the type is in `runtime/types.ts`). Chat does not send it to the screen: it records the reason, masked and cut at 400 characters (`interruptedReason`, `packages/host/src/runs.ts`), and `persistAssistant` passes it to `settleChatTurn`, which appends `chatTurnCopy(locale).interrupted` after a blank line, once. En: `The tool steps above ran, but I could not finish the answer.` + `Reason: <the failure>` + `Send "continue" and I will try again.` Id: `Langkah alat di atas sudah berjalan, tetapi saya tidak dapat menyelesaikan jawabannya.` + `Alasan: …` + `Kirim "lanjutkan" dan saya akan mencoba lagi.` It streams as an `assistant.delta` (so `assistant-live` shows it with no reload) and is saved as the turn's `text` part (so it is there after a reload). The tool rows stay. The reason is the failure's own words, so on an Indonesian desk it is Indonesian for a gateway 5xx and for either watchdog, and English for a raw network error (`fetch failed`). Mirrored in `chat.harness.interrupted` in both catalogs. Edit and the job modes get the event and ignore it (see the map's Gotchas). **`continue` does not replay the tool results:** only `text`, `image_url` and `video_url` parts go back to the model (`modelHistoryParts`, `packages/core/src/content/transcript.ts:39`), so the next turn starts from the person's words and the sentence, and a read is read again.
- `chat-header-wait` (2026-10-07; found by the same drive) — a model request has `HEADERS_TIMEOUT_MS` (45 s, `packages/core/src/runtime/stream-watchdog.ts`) to send its response headers, once per request and not per run, so each call of a tool loop gets its own. It was 10 s, and `gpt-6-luna` took 15.1 s to answer HTTP 200 on two calls of a Word-file turn with Thinking Off (15 146 ms and 15 135 ms, measured on a diagnostic server), so the run was cut three times and ended `Could not reach gpt-6-luna after 3 tries. The model is given the real result; media is collected from the real output. ## Gotchas

- **Two tool mistakes still end a Chat run (2026-10-06).** The recovery in `chat-tool-recovery` covers a tool that throws while it runs and a call to a tool that is bound but not offered. It does not cover a call whose JSON fails the tool's schema, or a call to a name that is not bound at all: the AI SDK rejects those before `execute` runs (`parseToolCall`, `packages/core/node_modules/ai/dist/index.js:4079`, which throws `InvalidToolArgumentsError` and `NoSuchToolError`) and the run fails with the SDK's message. Not fixed here: it needs a loose schema for validation or `experimental_repairToolCall`, and either changes what the screen is told about every tool call.
- **A closing sentence is not a model answer.** The step-limit sentence is written by the host in the person's language. Do not read it as the model's own summary, and do not look for it in the model's reasoning text.
- A document is read when it is attached but saved when the message is sent, so an attached-then-removed document leaves no desk file. The copy lives under `uploads/~<user>/` and, on a hosted team desk, is visible to that person only. Sending the same file again is a no-op (same bytes, same version). The extracted text is masked before it is stored or sent, so a figure that looks like an identifier (a 16-digit value, a card-like number) can come back as `[nik]` or `[card]`. A plain text file attached as `.txt` or `.csv` is read in the browser, not by the host, and is not masked in the thread (the outbound copy still is); it is held to the same 60,000 characters as a document and is not saved on the desk.

- **A deck card is not in `message-thinking`.** Every other tool row is, so a script that looks for the deck there finds only the one-line `tool-row-deck`. Find `chat-deck-card` directly under the reply. A stub Chat never calls `build_deck`; the card needs a live model.
- **A deck refused for a limit is not a failed turn, and the hosted storage ceiling counts saved decks.** The tool's schema sets no length or count ceiling (an argument the SDK refuses ends the whole turn), so an overrun comes back as `{ ok: false, reason: "limits", message }` and the model can fix it. On a hosted desk at its storage ceiling the refusal is `reason: "quota"` ("The owner's storage is full ..."), because a saved deck now counts in the tenant's use; on Personal there is no ceiling and no such refusal.
- The composer toolbar is a container-query grid (`.composer-toolbar`, `apps/web/app/globals.css`), and its controls group (`.composer-controls`) **wraps** (`flex-wrap: wrap`); that group must never go back to `overflow-hidden`. It used to clip, which hid the model palette (a thin sliver in the 32px toolbar row, clicks falling through to `message-list`) and squeezed the trigger to 18px on narrow panes. Any popover anchored in that group (model picker, and anything added next to it) **must** be portalled to the body and positioned with `placePickerPanel` (`apps/web/lib/picker-panel.ts`). Playwright still calls a clipped option "visible", so assert the click actually changes the trigger label — a visibility check alone will not catch it.
- **The whole desk pauses its loops when the window is not focused, and the Browser pane is not focused between calls.** `<html data-ambient="paused" data-ambient-reason="blurred">` and 0 running loops on a fresh read is the switch working, the same way `data-paused` below is. `left_click` the page before counting running animations; a click is input, so an idle desk wakes too. Do not remove the attribute in code to "fix" a count you will rely on later. Entrances are never paused by it.
- **The hero pauses its loops in a hidden tab, and the Browser pane is hidden between calls.** A read of `chat-hero` `data-paused` after a tool call says `"true"`, its transitions are frozen mid-flight and `getAnimations()` shows 0 running: that is the pause working, not a stuck hero. Do not "fix" it by unpausing in code. Force `document.hidden` false (see "Hero") or read in the same batch as a screenshot. A screenshot right after a DOM change can also show the previous frame; take it again. A viewport under 768px emulates touch, so drive the pointer effects at the pane's own size or 1280px; and a screenshot of an emulated viewport larger than the pane is scaled down, so measure and use the picture only to look.
- **Composer widths are content widths, and thresholds can be off by a pixel.** The queries read the composer's content box (border box minus 26px), so a 626px composer is the first wide one, not a 600px one. In a scaled or zoomed browser pane the 1px border floors to a device pixel, which moves a boundary by under a pixel; drive a width one or two px either side of a threshold, not on it. The `mobile` viewport preset also swaps the user agent and turns on touch; reset it with `preset desktop` as soon as the check is done, the pane may keep it otherwise.
- In the medium and narrow layouts `composer-attach` is first in the DOM and second on screen, so Tab goes attach → model → Thinking → Enhance → Send while the eye goes model → Thinking → attach → Enhance → Send. That is a known focus-order mismatch of the two-row layouts (wide matches). Do not "fix" it by reordering the DOM without checking wide.
