# Onboarding

The first-run screen, in three steps. A fresh desk says hello, then asks for a key, then offers four examples (Chat, Research, Images, Presentation) and a line that a quick tour comes next. On the Personal app the first desk's rail has five modes, Chat, Research, Images, Videos and Presentation (`FIRST_RUN_MODES`, `packages/core/src/agents/product-modes.ts:55-61`); the examples leave Videos out. The hosted app's first desk has every work mode (`HOSTED_FIRST_DESK_MODES`, `:69`, chosen by `firstDeskModes`, `:76-78`), and the four examples are the same there. The examples render only after the host reports `allowed`. The renderer displays that decision and does not decide it. The in-app name is `{productName}` (Nultron). There is no password and no sign-in form, and the gateway address is not on the screen. **On the hosted app only** (Nultron Enterprise, owner decision 2026-10-01) a signed-in person also gets "Add it later" next to Check this key, which opens Chat with no key and is remembered by the host; the Personal app never shows it. How the gate is derived is [gateway-gate.md](./gateway-gate.md); the document-reader panel is [components.md](./components.md). The gate map is [`docs/internal/maps/settings-and-gateway-gate.md`](../../../../docs/internal/maps/settings-and-gateway-gate.md).

## Sub-features

- `onboarding-steps` is the three-item step list (`welcome`, `key`, `try`) above every step: each item is `onboarding-step-<id>`, and the current one carries `aria-current="step"` (`apps/web/components/onboarding-screen.tsx:243-250`). The `try` item is there before the examples exist; the list is the way to read which step is showing.
- `onboarding-hello` is a fresh desk: `onboarding-welcome` (gradient hello in the in-app name, one short sentence) and `onboarding-next`. `onboarding-form` has count 0 on this step.
- `onboarding-key` is the paste: `onboarding-form`, `onboarding-key` (an `<input type="password">`, `apps/web/components/onboarding-screen.tsx:326-334`), `onboarding-continue` ("Check this key"), and `onboarding-back`. On the hosted app a person who may not change the company key (a member) gets `onboarding-key-restricted` (`:337`) in place of `onboarding-key` and `onboarding-continue`. A desk the host already closed (`invalid_key`, `unreachable`, `error`) skips the hello and opens here, with `onboarding-gate-reason` and `onboarding-recheck`. A fresh `needs_key` desk has neither.
- `onboarding-later` / `onboarding-later-hint` are **hosted only**: on the key step, a secondary "Add it later" button next to `onboarding-continue` and a line saying models stay off until a key is added in Settings. They exist only when the app hands the screen an `onLater`, which it does only for a signed-in person on the hosted build (`canOfferKeyLater`, `apps/web/src/App.tsx`). **On webdev and the packaged app both have count 0, and that is the pass.**
- `onboarding-examples` is `onboarding-try`: `onboarding-key-success`, four `onboarding-example` cards (`data-example` `chat` / `research` / `images` / `presentation`), `onboarding-tour-hint` (absent once the host says the guide was seen), and `onboarding-start`, which opens Chat (`chat-empty`) with the quick tour on top of it ([guide.md](./guide.md)). This step exists only after `resolveGate` says `"app"`.
- `onboarding-setup` is `component-setup` inside `onboarding-setup-check`, on the key step, above the key form. It does not block the form. When the reader shipped inside the app and ffmpeg is found the section is absent; a missing ffmpeg renders `onboarding-setup-check` on its own, with the ffmpeg notice (`needsFfmpeg`, `apps/web/components/onboarding-screen.tsx:120`, `:293`). On the **hosted** build `needsFfmpeg` is always false (`!isHostedBuild()`): a tenant cannot install anything on the server, so the key step never shows the ffmpeg guide or the "install ffmpeg later" line there. Drive the install itself in [components.md](./components.md).

## How to get to it (user POV)

- Open the app on a machine with no saved key. The hello is the whole window: no rail, no Settings, no Chat.
- Continue, paste a Toko Token key, and press Check this key. A key the gateway accepts moves to the examples. A key it rejects stays on the form and says so in plain words.
- Pick an example, or Start in Chat. Chat opens.

## Driving it with the Nultron harness

Preconditions:

- Doctor the instance you started. Use a throwaway `AGENTFORGE_DATA_DIR`.
- `AGENTFORGE_RUNTIME=stub` reports `allowed: true` before it looks at the key, so this screen never appears. Start with the runtime unset, or `AGENTFORGE_RUNTIME=ai` and no key saved. `GET /api/v1/settings` must report `gateway.status: "needs_key"` and `allowed: false` before the first screenshot.
- Never paste a real key, and never drive this on a desk you do not own.

- **Cheapest route to the screen on webdev.** The screen also opens, on the hello step, when the settings read itself fails: the catch in `apps/web/src/App.tsx:288-295` sets `gateway` to null and the gate to onboarding. In the browser, abort `GET /api/v1/settings` and reload `/chat`. `onboarding-welcome` shows; `onboarding-next` opens `onboarding-form`, `onboarding-key` and a disabled `onboarding-continue`, with `onboarding-step-key` at `aria-current="step"`. Nothing reaches the desk, so it needs no throwaway data dir and no runtime change. It proves the steps, not the host's verdict: with no `gateway` there is no `onboarding-gate-reason`, and the settings-payload precondition above does not apply.
- **Hello.** Open `/chat`. `onboarding-welcome` is visible and reads "Welcome to Nultron". `onboarding-next` is visible. `onboarding-form`, `onboarding-try`, `onboarding-gateway-host` and `onboarding-endpoint` have count 0. No text on the screen contains `tokotokenai` or `DPSBuddy`.
- **Key.** Click `onboarding-next`. `onboarding-form` and `onboarding-key` are visible. `onboarding-continue` is disabled until the field has text. The step list marks `onboarding-step-key` with `aria-current="step"`.
- **Rejected key.** On your own desk, paste a bogus string and click `onboarding-continue`. `onboarding-gate-reason` reads "That key didn't work. Check it at Toko Token and paste it again." `onboarding-recheck` is visible. `onboarding-try` still has count 0. The host's technical `message` (HTTP status, URL) is not on the screen.
- **Examples only after `allowed`.** When the host next reports `allowed: true` (a key it accepts, or opening another desk whose verdict is allowed), `onboarding-try` appears and the four `onboarding-example` values are `chat`, `research`, `images`, `presentation`, and none names a tool the first desk lacks. Do not record this step against a payload that still says `allowed: false`.
- **Start.** Click `onboarding-start` (or any `onboarding-example`). The desk is Chat: `chat-empty` is visible and `chat-hero-bubble` reads "Hi, I’m Nultron." and "What are we working on today?" (the headline has no testid of its own; assert inside `chat-hero-bubble`).
- **Setup panel.** On the key step, `component-setup` is inside `onboarding-setup-check` and above `onboarding-form`. ## Gotchas

- **Stub hides the screen.** A green doctor on `:3000` with `runtime: "stub"` is not a drive of this recipe. The gate is open and Chat renders.
- **`needs_key` has no reason and no re-check.** Their absence on a fresh desk is the pass. They appear after a rejected, unreachable, or error verdict. The one exception is a hosted person who may not change the company key (a member): that key step shows `onboarding-key-restricted` in place of `onboarding-key` and `onboarding-continue`, and `onboarding-recheck` is drawn with no reason at all (`apps/web/components/onboarding-screen.tsx:323-340`, `:345-365`). `onboarding-later` stays and `onboarding-later-hint` goes (`:378`).
- **The examples are not a second hello.** Reloading after the host has already allowed the desk skips onboarding and opens the app. The examples step is the in-screen step that runs when `allowed` flips while the screen is still mounted.
- **One input.** The only field is `onboarding-key`. An endpoint field, a host line, or a password field is a regression.
- **"Add it later" is not a bypass.** It changes what the screen shows and nothing the host allows: the gate still reads closed and every model call still answers `403 gateway_blocked`. A recipe that treats the open desk as proof the key works is testing the wrong thing; a successful send is.
- **Other desks.** `onboarding-desks` / `onboarding-open-desk` render only when the install has another desk. Opening one asks the host for that desk's gate and applies it. A one-desk install correctly shows nothing there.
