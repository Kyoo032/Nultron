# Gateway gate

The host decides whether this desk may talk to the gateway and the renderer only displays that decision. `GET /api/v1/settings` carries `gateway: { status, allowed, grace, endpoint, endpointLocked, checkedAt, lastOkAt, message? }` with `status` in `stub | needs_key | ok | invalid_key | unreachable | error`; `allowed` is the only field the renderer branches on, and when it is false the desk drops to onboarding and every gateway-calling route answers a flat `403 gateway_blocked`. The gate is advisory and, on a desk, fails **open** — a missing or unreadable `gateway-gate.json` opens the desk on trust, so this is a UX signal, never an entitlement check. In server mode (hosted) silence closes it instead: a stub runtime is `needs_key`, and a saved key with no verdict is `error` with `allowed: false` (`packages/host/src/gateway-gate.ts:292-312`). Map: [`docs/internal/maps/settings-and-gateway-gate.md`](../../../../docs/internal/maps/settings-and-gateway-gate.md).

## Sub-features

- `gate-onboarding` is the first-run / blocked screen, in three steps. A fresh desk opens on `onboarding-welcome` (gradient hello in the in-app name, one short sentence, `onboarding-next`). The key step is `onboarding-form`, `onboarding-key`, `onboarding-continue`, and — when there is a reason — `onboarding-gate-reason` plus `onboarding-recheck`. A desk the host already closed (`invalid_key`, `unreachable`, `error`) skips the hello and opens on that form. `component-setup` sits inside `onboarding-setup-check` on the key step, above the key form, when ffmpeg is missing or the document reader is installing; it does not block the form. The step walk is [onboarding.md](./onboarding.md). Since 2026-09-26 there is **no** `onboarding-gateway-host` and **no** `onboarding-endpoint`: the address is not shown. The screen has exactly one input, the key. After the host reports `allowed`, `onboarding-try` shows four examples (`onboarding-example`, `data-example` `chat` / `research` / `images` / `presentation`) and `onboarding-start` opens Chat.
- `gate-status-row` is `settings-gateway-status` on Settings: the status word, the last-checked timestamp, and `settings-gateway-recheck`.
- `gate-grace` is `settings-gateway-grace`, shown only while `grace` is true: "Working offline with a key verified on {date}."
- `gate-reason` is `settings-gateway-reason`, shown only for `invalid_key`, `unreachable` and `error` — the same three copy keys onboarding uses.
- `gate-recheck` is the button's effect: `POST /api/v1/settings/gateway/check` re-runs one 3s `GET <endpoint>/models` and returns a fresh `{ gateway }`. `stub` and `needs_key` short-circuit with no network call. The `<endpoint>` is `resolvedGatewayBaseUrl()` (`packages/host/src/gateway-gate.ts:340-341`): a packaged Kemenkeu AI / AIHub Metranet build probes its brand gateway (`AGENTFORGE_BRAND_GATEWAY_URL`), every other build the pinned one (`packages/core/src/gateway/pinned.ts:72-81`).
- `gate-blocked-route` is the enforcement: `requireGatewayAllowed()` in every gateway-calling handler (runs, jobs, finance, market, legal, knowledge, enhance, edit) answers `403 { error, status, message }` — flat, not the usual nested error envelope.
- `gate-open-routes` are the ones deliberately left open so a closed gate is recoverable: settings, workspaces, threads, artifacts, media, usage and the model refresh.
- `gate-deferral` is **hosted only** (Nultron Enterprise, 2026-10-01): a signed-in person who chose "Add it later" (`onboarding-later`, [onboarding.md](./onboarding.md)) opens the desk on a gate the host still reports closed. The host records the choice (`POST /api/v1/settings/key-later`, `keyLater` on the settings answer, server mode only) and never reads it as permission. Every pane then shows its calm needs-key note (`composer-needs-key`, `research-needs-key`, `data-needs-key`, `finance-needs-key`, `market-needs-key`, `legal-needs-key`, `meeting-needs-key`, `presentations-needs-key`, `knowledge-needs-key`, plus the older `documents-needs-key`, `images-studio-needs-key`, `videos-studio-needs-key`, `music-studio-needs-key`, `edit-needs-key`; each link is `<testid>-settings`) instead of a generic error. Education makes no gateway call and has none.
- `gate-reset` is the Start over card, `settings-reset` — see [settings.md](./settings.md). **Do not drive it on a shared desk.**

## How to get to it (user POV)

- **Hosted, signed in, "Add it later" chosen:** the desk opens on the closed gate and Settings is reachable (see `gate-deferral`). Everything below is the Personal app, and the hosted app for a person who has not chosen yet.
- A desk with no key, or a key the gateway rejected, opens straight on the onboarding screen instead of Chat — on **every** route, `/settings` included (`App.tsx` swaps the whole router, so `settings-form` has count 0 while the gate is closed). There is no rail, no Settings and no reset card; the only ways past are a key that validates, a re-check that succeeds, or deleting `gateway-gate.json` on disk.
- A working desk reaches the gate through Rail → Settings (`settings-link`), where the status row sits under the gateway key block.
- "Re-check" is the only user control that forces a fresh verdict.

## Driving it with the Nultron harness

Preconditions:

- Doctor exits 0.
- Use your own isolated desk (`AGENTFORGE_DATA_DIR` pointed at a throwaway dir). A re-check can turn a stale `ok` into `invalid_key`, which **closes the desk** — never do that to the operator's instance.
- Never type into `onboarding-key` or `openai-key` on a desk you do not own, and never press anything in `settings-reset`.
- Order matters: drive every other feature first. A re-check that fails leaves the desk on onboarding and blocks the rest of the run.
- To see a **closed** gate at all, start your isolated instance with an explicit `AGENTFORGE_RUNTIME=ai` and no key saved. From `apps/web`, with a free port and a fresh data dir: `PORT=3201 AGENTFORGE_RUNTIME=ai AGENTFORGE_DATA_DIR=<fresh dir> node_modules/.bin/tsx server.ts`. `server.ts` reads `PORT` (`apps/web/server.ts:145`) and binds loopback (`:146-147`). Do not set `AGENTFORGE_SERVER`: that turns on hosted mode, which is a different gate (`deriveGatewayGate`, `packages/host/src/gateway-gate.ts:289-296`). Doctor it with `node .cursor/skills/verify-agentforge/scripts/doctor.mjs --base http://127.0.0.1:3201`. A dotenv file can pin the runtime: `@agentforge/db` loads the root `.env`, the root `.env.local`, `apps/web/.env` and `apps/web/.env.local` in that order (`packages/db/src/client.ts:11-14`), and dotenv never overwrites a variable that is already set, so the first file to name `AGENTFORGE_RUNTIME` wins over the later ones and the command line wins over all of them. A `stub` pin opens the gate unconditionally, which is why `AGENTFORGE_RUNTIME=ai` is on the command line. Read `GET /api/v1/settings` → `gateway.status` before you trust the screen. `needs_key` is then reachable with no key at all; `invalid_key` needs a key the gateway rejects — a deliberately bogus string on **your own** desk is enough, never the operator's key and never a real one.

- **Status row.** Open Settings. `settings-gateway-status` paints immediately, and that first paint is only Re-check — wait until the status word is in the row (the settings fetch has not landed yet). It then reads one of "Key verified" / "No key saved" / "Key rejected by gateway" / "Gateway unreachable" / "Gateway error", followed by "Last checked <date>" (only when `checkedAt` is set) and the Re-check button. The row is three sibling nodes with no `·` in its `textContent`, so assert the parts ([settings.md](./settings.md), `settings-gateway-status`). `stub` and `needs_key` both read "No key saved" in English since 0.15.0 (`apps/web/locales/en/settings.json:33-34`); "Offline demo" is gone and must not appear. On a webdev process that has `AGENTFORGE_RUNTIME=stub` in effect (`apps/web/.env.local` pins it) the row reads "No key saved" plus Re-check even with a key saved, and a Re-check answers `200` with the same `stub` payload and no network call — driven 2026-09-23 on `:3000` before its 16:28 restart; after the restart the same desk reported `status: "ok"` with a fresh `checkedAt`. Read `GET /api/v1/settings` → `gateway.status` before interpreting the row.
- **Grace and reason.** `settings-gateway-grace` is present only when the payload says `grace: true`; `settings-gateway-reason` only for the three failure statuses. Absent is the correct state on a healthy desk — do not record it as a miss.
- **Re-check.** Click `settings-gateway-recheck`, wait ~5s, and read the row again. The timestamp must move. On a desk whose key has since been revoked the row flips from "Key verified" to "Key rejected by gateway" and `settings-gateway-reason` appears.
- **Read the gate from the settings answer.** Doctor's JSON names the gateway (`gatewayName`, `gatewayBaseUrl`) but carries no `gateway.status` or `allowed`, so read `GET /api/v1/settings` yourself and record `gateway.status` before the first screenshot of any step below. If a later doctor prints the gate, use that; the recipe works either way.
- **Gate closes.** With `allowed: false`, reload `/chat`: the page renders the onboarding screen instead of the desk. A fresh `needs_key` desk shows `onboarding-welcome` first (`onboarding-next` moves to the key). A rejected key shows `onboarding-form`, `onboarding-gate-reason`, `onboarding-key`, `onboarding-continue`, `onboarding-recheck`. `onboarding-gateway-host` and `onboarding-endpoint` have count 0, and no text on the screen contains `tokotokenai`. The reason reads "That key didn't work. Check it at Toko Token and paste it again." with no status code and no URL on screen. A bogus key on your own desk gives `gateway.status: "invalid_key"` with `message: "HTTP 401"` in the payload. A reload of a desk the host has closed skips the hello and opens on the form (`onboarding-form`), and Re-check moves `checkedAt`. When the host then reports `allowed`, `onboarding-try` appears and `onboarding-start` opens Chat (`chat-empty`).
- **Deferral (hosted only).** After `onboarding-later`: `GET /api/v1/settings` carries `keyLater.chosen: true` **and** `gateway.allowed: false`; a gateway-calling route still answers the flat 403; every pane shows its note and no `*-error` banner. Save a key in Settings and the panes you already visited lose their note without a reload (the shared gate store hears the save, `lib/gate-state.ts`); a re-check does the same. Drive the save only with a throwaway tenant and a deliberately bogus key if you want the `invalid_key` path: the desk stays open, the note stays, and `settings-gateway-reason` explains.
- **Blocked route.** `POST /api/v1/finance/parse` or `POST /api/v1/threads/<threadId>/runs/text` answers `403` with a flat body. The run routes are `threads/:threadId/runs/text|image|video` (`packages/host/src/router.ts:333-335`); there is no `/api/v1/runs/text` and that path answers 404. `handleRun` checks the gate before it looks up the thread (`packages/host/src/handlers/runs.ts:26-30`), so any thread id reaches the 403. Driven 2026-10-05 on a closed gate: `finance/parse`, `research/stream`, `knowledge/context`, `prompts/enhance` and `threads/<id>/runs/text|image` all answered the flat 403, and `prompts/enhance` with `{"prompt":""}` still answered `400 empty_input` (see the next bullet). Driven 2026-09-17 on an isolated desk: no key → `{"error":"gateway_blocked","status":"needs_key","message":"No gateway key is saved on this machine."}`; after a rejected key → `{"error":"gateway_blocked","status":"invalid_key","message":"The gateway rejected the saved key. HTTP 401"}`. `error` is a flat string, not `{ code, message }`, and `status` follows the verdict.
- **Not every route gates on entry.** `POST /api/v1/prompts/enhance` validates the body first (`empty_input` throws at `packages/host/src/handlers/enhance-prompt.ts:24` and `:28`, while `requireGatewayAllowed` only runs at `:53`), so a probe with an empty prompt answers `400 empty_input` even on a fully closed desk. Use a route that gates first when you want to prove the 403.
- **Open routes.** With the gate closed, all of these still answer `200`: `GET /api/v1/settings`, `/api/v1/threads`, `/api/v1/workspaces`, `/api/v1/usage`, `/api/v1/models`. If any of them starts answering 403 the gate has stopped being recoverable, and that is a product bug, not a recipe miss.
- **Stub.** With `AGENTFORGE_RUNTIME=stub`, off server mode, the payload is `status: "stub", allowed: true`. Chat Send and Documents / Images Generate stay enabled; `composer-needs-key` and `documents-needs-key` have count 0; `chat-empty-settings` is a plain button, not `btn-primary`. Videos and Music still follow their route `ready` flag, so a keyless stub desk shows `videos-studio-needs-key` / `music-studio-needs-key` and a quiet Generate. Images follows the same host gate as Chat and Documents: on stub, `images-studio-needs-key` has count 0 and Generate stays enabled. This is why Cloud and Playwright can send Chat.
- **Evidence.** Screenshots of the status row before and after the re-check, the closed-gate onboarding screen, and the 403 body, under `evidence/gateway-gate/<run-id>/`.

## Gotchas

- **"Key verified" can be a lie.** The row shows the last stored verdict, and an `ok` verdict stands for 24h before it falls back to the 7-day grace. Driven on 2026-09-15: the row read "Key verified" with "Last checked 12:16 PM" while every live call returned 401, and only `settings-gateway-recheck` turned it into "Key rejected by gateway". A green status row is never proof that the key still works — a successful send is.
- **Re-check is destructive on a bad key.** It replaces a comfortable cached verdict with the truth, and `invalid_key` gets no grace, so the desk closes immediately. Drive it last.
- **The gate fails open on a desk, by design.** Delete or corrupt `gateway-gate.json` on a desk with a key saved and `deriveGatewayGate` returns `ok / allowed: true / grace: true` with "Not checked yet." (`packages/host/src/gateway-gate.ts:304`, returned at `:310-312`). In server mode the same silence returns `error / allowed: false` with "This gateway key has not been verified with the gateway yet." (`:303`). A desk that opens is not evidence the key is good.
- **The deferral is hosted-only and three-part.** `resolveGate` opens a closed gate only for the hosted build **and** a live session **and** the host's `keyLater.chosen` (`apps/web/lib/gateway-gate.ts`, `KeyDeferral`). Webdev and the packaged app pass none of the three, so a faked closed gate on webdev still shows `onboarding-welcome` and no `onboarding-later`.
- **Webdev and packaged disagree on a broken payload.** When the settings answer parses but its `gateway` field is missing or malformed, `resolveGate` returns onboarding for the packaged app and for a hosted build and lets plain webdev through (`hosted || isElectron ? "onboarding" : "app"`, `apps/web/lib/gateway-gate.ts:108-110`). A gate the host does report is obeyed as-is on every build, webdev included: `allowed: true` gives the app (`:111-113`) and `allowed: false` gives onboarding (`:114`, unless the hosted deferral applies), called as `setGate(resolveGate(…))` from the `.then` in `apps/web/src/App.tsx:269-287` (`:286`). That is why a faked `needs_key` / `allowed: false` answer shows `onboarding-welcome` on webdev. A settings read that fails outright (no JSON object, a network error) also gives onboarding on every build, through the catch at `App.tsx:288-295`. To exercise a closed gate on webdev the host, or a faked settings answer, must report one.
- **`AGENTFORGE_RUNTIME=stub` opens the gate (off server mode) but does not force stub runtime.** On a desk with a key already saved, the payload reads `gateway.status: "stub", allowed: true` while `runtime` stays `"ai"` and sends still hit the live gateway. Observed on 2026-09-15. For a real stub drive use a data dir with no key saved.
- **Sign-out does NOT return you to onboarding while the runtime is stub.** `deriveGatewayGate` short-circuits `envRuntime === "stub"` to `payload(endpoint, "stub", true, …)` *before* it looks at whether a key exists, but only when the host is not in server mode (`packages/host/src/gateway-gate.ts:292-294`; in server mode a stub runtime is `needs_key`, `:295-296`). So `settings-reset-key-submit` does run and the key really is forgotten on every desk, but the gate it announces is still `allowed: true` and the desk stays open — which reads as "nothing happened" (owner report 2026-09-23). This is a **webdev-only artifact**: a dev machine's dotenv files can pin `stub` (`apps/web/.env.local` does here; they are gitignored), and the host reads them (`packages/db/src/client.ts:11-14`). `apps/desktop/main.cjs` never sets `AGENTFORGE_RUNTIME` — it only reads it, at `:717` — so the packaged personal app runs unset, derives `needs_key`, and sign-out does drop to `onboarding`. To drive the real behaviour on webdev, start an instance with `AGENTFORGE_RUNTIME=ai` and no key saved (the command is under Preconditions).
- **The English `message` never reaches the screen.** The renderer picks localized copy from `status` alone; `gateway.message` ("HTTP 401", "The gateway rejected the saved key.") exists only in the payload and the log. Assert the localized sentence, not the host's technical string.
- **A 401 during a send is not the gate.** The gate is a cached verdict; a live 401 surfaces as ordinary gateway-failure copy in `composer-error` only (`packages/core/src/gateway-http-copy.ts`), in the desk language, with the status code in the headline. `chat-error` stays clear for that send, and the live mascot goes to `error`.
- **`needs_key` shows no reason and no re-check.** `onboarding-gate-reason` and `onboarding-recheck` render only once there is a failure to explain. On a fresh keyless desk the hello has no reason, and the key step is the help sentence, the key field, Back, and Check this key. Their absence there is the pass, not a miss. There is no gateway host line to look for.
- **`allowed` is advisory and must stay that way.** It decides what the desk shows and which local handlers refuse. Seats, plan limits and spend are enforced server-side against the bearer. Anyone can delete one JSON file to get past this gate; a recipe that treats it as an entitlement proof is testing the wrong thing.
