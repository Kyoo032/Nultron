# Gateway gate

The host decides whether this desk may talk to the gateway and the renderer only displays that decision. `GET /api/v1/settings` carries `gateway: { status, allowed, grace, endpoint, endpointLocked, checkedAt, lastOkAt, message? }` with `status` in `stub | needs_key | ok | invalid_key | unreachable | error`; `allowed` is the only field the renderer branches on, and when it is false the desk drops to onboarding and every gateway-calling route answers a flat `403 gateway_blocked`. The gate is advisory and, on a desk, fails **open** — a missing or unreadable `gateway-gate.json` opens the desk on trust, so this is a UX signal, never an entitlement check. In server mode (hosted) silence closes it instead: a stub runtime is `needs_key`, and a saved key with no verdict is `error` with `allowed: false` (`packages/host/src/gateway-gate.ts:357-379`). On the hosted server the verdict is one per **company** (an organisation inside the white-label partner), not one per partner, so a second company saving a different key never closes the first (SR-163, see the hosted bullet below). Map: [`docs/internal/maps/settings-and-gateway-gate.md`](../../../../docs/internal/maps/settings-and-gateway-gate.md).

## Sub-features

- `gate-onboarding` is the first-run / blocked screen, in three steps. A fresh desk opens on `onboarding-welcome` (gradient hello in the in-app name, one short sentence, `onboarding-next`). The key step is `onboarding-form`, `onboarding-key`, `onboarding-continue`, and — when there is a reason — `onboarding-gate-reason` plus `onboarding-recheck`. A desk the host already closed (`invalid_key`, `unreachable`, `error`) skips the hello and opens on that form. `component-setup` sits inside `onboarding-setup-check` on the key step, above the key form, when ffmpeg is missing or the document reader is installing; it does not block the form. The step walk is [onboarding.md](./onboarding.md). Since 2026-09-26 there is **no** `onboarding-gateway-host` and **no** `onboarding-endpoint`: the address is not shown. The screen has exactly one input, the key. After the host reports `allowed`, `onboarding-try` shows four examples (`onboarding-example`, `data-example` `chat` / `research` / `images` / `presentation`) and `onboarding-start` opens Chat.
- `gate-status-row` is `settings-gateway-status` on Settings: the status word, the last-checked timestamp, and `settings-gateway-recheck`.
- `gate-grace` is `settings-gateway-grace`, shown only while `grace` is true **and** `lastOkAt` is non-null (`gateway?.grace && gatewayLastOkAt`, `settings-page.tsx:506`; the fail-open desk payload, `ok` with `grace: true` and `lastOkAt: null`, reads "Key verified" with no grace line): "Working offline with a key verified on {date}."
- `gate-reason` is `settings-gateway-reason`, shown only for `invalid_key`, `unreachable` and `error` — the same three copy keys onboarding uses.
- `gate-recheck` is the button's effect: `POST /api/v1/settings/gateway/check` re-runs one 3s `GET <endpoint>/models` and returns a fresh `{ gateway }`. `stub` and `needs_key` short-circuit with no network call. The `<endpoint>` is `resolvedGatewayBaseUrl()` (`packages/host/src/gateway-gate.ts:408-410`): a packaged Kemenkeu AI / AIHub Metranet build probes its brand gateway (`AGENTFORGE_BRAND_GATEWAY_URL`), every other build the pinned one (`packages/core/src/gateway/pinned.ts:72-81`).
- `gate-blocked-route` is the enforcement: `requireGatewayAllowed()` in every gateway-calling handler (runs, jobs, finance, market, legal, knowledge, enhance, edit, meetings `:140`, `:155`, `:175`, the Presentations stream routes `open-slide.ts:27`, `:38`, `knowledge-search-tool.ts:58`, `edit/jobs.ts:226`; Finance import and export, components, health and billing are deliberately ungated) answers `403 { error, status, message }` — flat, not the usual nested error envelope.
- `gate-open-routes` are the ones deliberately left open so a closed gate is recoverable: settings, workspaces, threads, artifacts, media, usage and the model refresh.
- `gate-deferral` is **hosted only** (Nultron Enterprise, 2026-10-01): a signed-in person who chose "Add it later" (`onboarding-later`, [onboarding.md](./onboarding.md)) opens the desk on a gate the host still reports closed. The host records the choice (`POST /api/v1/settings/key-later`, `keyLater` on the settings answer, server mode only) and never reads it as permission. Every pane then shows its calm needs-key note (`composer-needs-key`, `research-needs-key`, `data-needs-key`, `finance-needs-key`, `market-needs-key`, `legal-needs-key`, `meeting-needs-key`, `presentations-needs-key`, `knowledge-needs-key`, plus the older `documents-needs-key`, `images-studio-needs-key`, `videos-studio-needs-key`, `music-studio-needs-key`, `edit-needs-key`; each link is `<testid>-settings` for the `NeedsKeyNote` panes; `images-studio-needs-key`, `videos-studio-needs-key`, `music-studio-needs-key` and `edit-needs-key` use a `SettingsLinkHint` with no testid, and `composer-needs-key-settings` and `documents-needs-key-settings` exist only on the hosted build; also `edit-agent-needs-key`) instead of a generic error. Education makes no gateway call and has none.
- `gate-reset` is the Start over card, `settings-reset` — see [settings.md](./settings.md). **Do not drive it on a shared desk.**

## How to get to it (user POV)

- **Hosted, signed in, "Add it later" chosen:** the desk opens on the closed gate and Settings is reachable (see `gate-deferral`). Everything below is the Personal app, and the hosted app for a person who has not chosen yet.
- A desk with no key, or a key the gateway rejected, opens straight on the onboarding screen instead of Chat — on **every** route, `/settings` included (`App.tsx` swaps the whole router, so `settings-form` has count 0 while the gate is closed). There is no rail, no Settings and no reset card; the only ways past are a key that validates, a re-check that succeeds, deleting `gateway-gate.json` on disk, or opening another desk the host allows (`onboarding-desks` then `onboarding-open-desk`, absent on a one-desk install).
- A working desk reaches the gate through Rail → Settings (`settings-link`), where the status row sits under the gateway key block.
- "Re-check" is the only user control that forces a fresh verdict.

## Driving it with the Nultron harness

Preconditions:

- Doctor exits 0.
- Use your own isolated desk (`AGENTFORGE_DATA_DIR` pointed at a throwaway dir). A re-check can turn a stale `ok` into `invalid_key`, which **closes the desk** — never do that to the operator's instance.
- Never type into `onboarding-key` or `openai-key` on a desk you do not own, and never press anything in `settings-reset`.
- Order matters: drive every other feature first. A re-check that fails closes the host gate at once and blocks every gateway route, but the Settings Re-check only calls `setGateway(next)` (`settings-page.tsx:358-360`): it never announces the gate, so the renderer stays on Settings with the flipped row and reason until the next shell settings read (a reload, or the locale-restart event). Only the onboarding Re-check and Sign out update the shell.
- To see a **closed** gate at all, start your isolated instance with an explicit `AGENTFORGE_RUNTIME=ai` and no key saved. From `apps/web`, with a free port and a fresh data dir: `PORT=3201 AGENTFORGE_RUNTIME=ai AGENTFORGE_DATA_DIR=<fresh dir> node_modules/.bin/tsx server.ts`. `server.ts` reads `PORT` (`apps/web/server.ts:145`) and binds loopback (`:146-147`). Do not set `AGENTFORGE_SERVER`: that turns on hosted mode, which is a different gate (`deriveGatewayGate`, `packages/host/src/gateway-gate.ts:352-365`). Doctor it with `node .cursor/skills/verify-agentforge/scripts/doctor.mjs --base http://127.0.0.1:3201`. A dotenv file can pin the runtime: `@agentforge/db` loads the root `.env`, the root `.env.local`, `apps/web/.env` and `apps/web/.env.local` in that order (`packages/db/src/client.ts:11-14`), and dotenv never overwrites a variable that is already set, so the first file to name `AGENTFORGE_RUNTIME` wins over the later ones and the command line wins over all of them. A `stub` pin opens the gate unconditionally, which is why `AGENTFORGE_RUNTIME=ai` is on the command line. Read `GET /api/v1/settings` → `gateway.status` before you trust the screen. `needs_key` is then reachable with no key at all; `invalid_key` needs a key the gateway rejects — a deliberately bogus string on **your own** desk is enough, never the operator's key and never a real one.

- **Status row.** Open Settings. `settings-gateway-status` paints immediately, and that first paint is only Re-check — wait until the status word is in the row (the settings fetch has not landed yet). It then reads one of "Key verified" / "No key saved" / "Key rejected by gateway" / "Gateway unreachable" / "Gateway error", followed by "Last checked <date>" (only when `checkedAt` is set) and the Re-check button. The row is three sibling nodes with no `·` in its `textContent`, so assert the parts ([settings.md](./settings.md), `settings-gateway-status`). `stub` and `needs_key` both read "No key saved" in English since 0.15.0 (`apps/web/locales/en/settings.json:33-34`); "Offline demo" is gone and must not appear. On a webdev process that has `AGENTFORGE_RUNTIME=stub` in effect (`apps/web/.env.local` names `stub`, but the repo-root `.env` names `ai` and is read first, so a bare `tsx server.ts` on this checkout is `ai` unless the command line says otherwise (checked 2026-10-06, values by length only); it pinned stub when this was written) the row reads "No key saved" plus Re-check even with a key saved, and a Re-check answers `200` with the same `stub` payload and no network call — driven 2026-09-23 on `:3000` before its 16:28 restart; after the restart the same desk reported `status: "ok"` with a fresh `checkedAt`. Read `GET /api/v1/settings` → `gateway.status` before interpreting the row.
- **Grace and reason.** `settings-gateway-grace` is present only when the payload says `grace: true`; `settings-gateway-reason` only for the three failure statuses. Absent is the correct state on a healthy desk — do not record it as a miss.
- **Re-check.** Click `settings-gateway-recheck`, wait ~5s, and read the row again. The timestamp must move. On a desk whose key has since been revoked the row flips from "Key verified" to "Key rejected by gateway" and `settings-gateway-reason` appears.
- **Read the gate from the settings answer.** Doctor's webdev JSON carries `gateway: { status, allowed, grace }` (`scripts/doctor.mjs:359-376`; `gatewayBaseUrl` is desktop-only, `:165`), so record it from the doctor JSON before the first screenshot of any step below; reading `GET /api/v1/settings` yourself gives the same fields plus `checkedAt` and `lastOkAt`.
- **Gate closes.** With `allowed: false`, reload `/chat`: the page renders the onboarding screen instead of the desk. A fresh `needs_key` desk shows `onboarding-welcome` first (`onboarding-next` moves to the key). A rejected key shows `onboarding-form`, `onboarding-gate-reason`, `onboarding-key`, `onboarding-continue`, `onboarding-recheck`. `onboarding-gateway-host` and `onboarding-endpoint` have count 0, and no text on the screen contains `tokotokenai`. The reason reads "That key didn't work. Check it at Toko Token and paste it again." with no status code and no URL on screen. A bogus key on your own desk gives `gateway.status: "invalid_key"` with `message: "HTTP 401"` in the payload. A reload of a desk the host has closed skips the hello and opens on the form (`onboarding-form`), and Re-check moves `checkedAt`. When the host then reports `allowed`, `onboarding-try` appears and `onboarding-start` opens Chat (`chat-empty`).
- **Deferral (hosted only).** After `onboarding-later`: `GET /api/v1/settings` carries `keyLater.chosen: true` **and** `gateway.allowed: false`; a gateway-calling route still answers the flat 403; every pane shows its note and no `*-error` banner. Save a key in Settings and the panes you already visited lose their note without a reload (the shared gate store hears the save, `lib/gate-state.ts`); a re-check does the same. Drive the save only with a throwaway tenant and a deliberately bogus key if you want the `invalid_key` path: the desk stays open, the note stays, and `settings-gateway-reason` explains.
- **Hosted, two companies (SR-163; not drivable on webdev).** Needs a hosted build with a portal and **two organisations under one portal tenant**, each with an owner, and a gateway key you may use for each (two real keys, or one good and one deliberately bogus string on a throwaway tenant; never an operator key). Sign in as owner of company A, save key A in Settings (`openai-key`), read `GET /api/v1/settings` → `gateway.status: "ok"`. Sign in as owner of company B in another browser profile, save a different key B. Back in A: `gateway` must still be `ok` / `allowed: true` and a Chat send must reach the model, not answer `403 gateway_blocked`. Then make B's key the bad one: A is still open, B reads `invalid_key` / `allowed: false`. In the database, `tenant_state` holds one `gateway_gate:<organisation id>` row per company under the partner's `tenant_id`. Press `settings-reset-key-submit` as B only on a throwaway pair: A's key must still be saved. **Review round (2026-10-07).** (a) Two desks: in company A create a second desk (`/workspaces`), then rotate A's key on the first desk; on the second desk `GET /api/v1/settings` must show the same new key's verdict (`ok`) and a Chat send must reach the model, and B's desks must still hold B's key. (b) Settings `probe` and the model list: A's `probe.openaiError` must not carry B's failed probe, and `GET /api/v1/models` must list A's own models. (c) Usage: `GET /api/v1/usage` and the `usage` field of settings list A's models and token counts only. (d) Erase: as the owner of company B press `settings-reset-tenant-submit` only on a throwaway pair; it must answer `409 tenant_erase_shared_partner`, show `settings.reset.eraseAccountShared` ("This server holds several companies under one account..."), and leave both companies' rows, files and keys, and the caller's session, exactly as they were. The same checks run without a server in `packages/host/src/gateway-gate-companies.test.ts`, `usage-companies.test.ts`, `model-cache-companies.test.ts` and `tenant-reset-companies.test.ts` (real router, stand-in gateway), which is the proof so far. **Not driven on a hosted server.**
- **Blocked route.** `POST /api/v1/finance/parse` or `POST /api/v1/threads/<threadId>/runs/text` answers `403` with a flat body. The run routes are `threads/:threadId/runs/text|image|video` (`packages/host/src/router.ts:335-337`); there is no `/api/v1/runs/text` and that path answers 404. `handleRun` checks the gate before it looks up the thread (`packages/host/src/handlers/runs.ts:26-30`), so any thread id reaches the 403. Driven 2026-10-05 on a closed gate: `finance/parse`, `research/stream`, `knowledge/context`, `prompts/enhance` and `threads/<id>/runs/text|image` all answered the flat 403, and `prompts/enhance` with an empty body still answered `400 empty_input` (the field is `text`, with optional `surface` and `model`, `enhance-prompt.ts:22-31`; to prove the 403 send a non-empty `text`, and it only gates when the runtime mode is `ai`, `:49-53`) (see the next bullet). Driven 2026-09-17 on an isolated desk: no key → `{"error":"gateway_blocked","status":"needs_key","message":"No gateway key is saved on this machine."}`; after a rejected key → `{"error":"gateway_blocked","status":"invalid_key","message":"The gateway rejected the saved key. HTTP 401"}`. `error` is a flat string, not `{ code, message }`, and `status` follows the verdict.
- **Not every route gates on entry.** `POST /api/v1/prompts/enhance` validates the body first (`empty_input` throws at `packages/host/src/handlers/enhance-prompt.ts:24` and `:28`, while `requireGatewayAllowed` only runs at `:53`), so a probe with an empty prompt answers `400 empty_input` even on a fully closed desk. Use a route that gates first when you want to prove the 403.
- **Open routes.** With the gate closed, all of these still answer `200`: `GET /api/v1/settings`, `/api/v1/threads`, `/api/v1/workspaces`, `/api/v1/usage`, `/api/v1/models`. If any of them starts answering 403 the gate has stopped being recoverable, and that is a product bug, not a recipe miss.
- **Stub.** With `AGENTFORGE_RUNTIME=stub`, off server mode, the payload is `status: "stub", allowed: true`. Chat Send and Documents / Images Generate stay enabled; `composer-needs-key` and `documents-needs-key` have count 0; `chat-empty-settings` is a plain button, not `btn-primary`. Videos and Music still follow their route `ready` flag, so a keyless stub desk shows `videos-studio-needs-key` / `music-studio-needs-key` and a quiet Generate. Images follows the same host gate as Chat and Documents: on stub, `images-studio-needs-key` has count 0 and Generate stays enabled. This is why Cloud and Playwright can send Chat.

## Gotchas

- **"Key verified" can be a lie.** The row shows the last stored verdict, and an `ok` verdict stands for 24h before it falls back to the 7-day grace. Driven on 2026-09-15: the row read "Key verified" with "Last checked 12:16 PM" while every live call returned 401, and only `settings-gateway-recheck` turned it into "Key rejected by gateway". A green status row is never proof that the key still works — a successful send is.
- **Re-check is destructive on a bad key.** It replaces a comfortable cached verdict with the truth, and `invalid_key` gets no grace, so the host closes the desk immediately (the renderer follows on the next shell read, see above). Drive it last.
- **A failed check heals itself; a rejected key does not (since 2026-10-06).** `GET /api/v1/settings` starts a background check, at most once per tenant and key per 10 minutes, for no verdict, a stale `ok`, **and** an `unreachable` or `error` verdict (`needsGatewayRefresh`, `packages/host/src/gateway-gate.ts:641-649`). `invalid_key` is never re-checked on its own. The response that starts the check still carries the old verdict, so read `GET /api/v1/settings` a second time (a few seconds later) to see it change; an already-closed onboarding screen does not refresh by itself. To drive it without touching a real desk: on a throwaway `AGENTFORGE_DATA_DIR` with a key saved, edit `gateway-gate.json` to `status: "unreachable"` with `lastOkAt` 8 days old (the gate reads `allowed: false`; the host reads that file on every request), then read settings twice. With the gateway reachable the second read says `ok` / `allowed: true`; with `invalid_key` in the file it stays closed. The 10-minute throttle lives in host memory, so a restarted host may check at once.
- **The gate fails open on a desk, by design.** Delete or corrupt `gateway-gate.json` on a desk with a key saved and `deriveGatewayGate` returns `ok / allowed: true / grace: true` with "Not checked yet." (`deriveGatewayGate`, `packages/host/src/gateway-gate.ts:352-380`; the desk payload is built at `:372`). In server mode the same silence returns `error / allowed: false` with "This gateway key has not been verified with the gateway yet." (`:371`). A desk that opens is not evidence the key is good.
- **On the hosted server the tenant is the partner, not the company (SR-163).** `TenantContext.tenantId` is the white-label partner (HYP AI, Nultron Enterprise); the company is `organizationId`. Before 2026-10-07 the verdict was one row per partner, so two companies that saved different keys overwrote each other's verdict and the first company's next Chat turn answered `403 gateway_blocked`. A test or a drive that uses **two tenant ids** (the shape most older tests use) cannot show that bug; it needs two organisations under one tenant id. After the fix, a hosted company with no verdict row of its own reads `error` / "has not been verified" until its first Settings read starts a check, so one send before that read can be refused once, **unless its key is the one the old partner-level verdict judged**, which it adopts (`lastOkAt` included). The model list, the `probe` summary and the usage view are the company's too (review round, same day); a key saved on one desk is written to every desk of the company; and the hosted erase is refused on a partner with more than one company (scoping it to one company is still owed, SR-163).
- **The deferral is hosted-only and three-part.** `resolveGate` opens a closed gate only for the hosted build **and** a live session **and** the host's `keyLater.chosen` (`apps/web/lib/gateway-gate.ts`, `KeyDeferral`). Webdev and the packaged app pass none of the three, so a faked closed gate on webdev still shows `onboarding-welcome` and no `onboarding-later`.
- **Webdev and packaged disagree on a broken payload.** When the settings answer parses but its `gateway` field is missing or malformed, `resolveGate` returns onboarding for the packaged app and for a hosted build and lets plain webdev through (`hosted || isElectron ? "onboarding" : "app"`, `apps/web/lib/gateway-gate.ts:108-110`). A gate the host does report is obeyed as-is on every build, webdev included: `allowed: true` gives the app (`:111-113`) and `allowed: false` gives onboarding (`:114`, unless the hosted deferral applies), called as `setGate(resolveGate(…))` from the `.then` in `apps/web/src/App.tsx:269-287` (`:286`). That is why a faked `needs_key` / `allowed: false` answer shows `onboarding-welcome` on webdev. A settings read that fails outright (no JSON object, a network error) also gives onboarding on every build, through the catch at `App.tsx:288-295`. To exercise a closed gate on webdev the host, or a faked settings answer, must report one.
- **`AGENTFORGE_RUNTIME=stub` opens the gate (off server mode) but does not force stub runtime.** On a desk with a key already saved, the payload reads `gateway.status: "stub", allowed: true` while `runtime` stays `"ai"` and sends still hit the live gateway. Observed on 2026-09-15. For a real stub drive use a data dir with no key saved.
- **Sign-out does NOT return you to onboarding while the runtime is stub.** `deriveGatewayGate` short-circuits `envRuntime === "stub"` to `payload(endpoint, "stub", true, …)` *before* it looks at whether a key exists, but only when the host is not in server mode (`packages/host/src/gateway-gate.ts:360-362`; in server mode a stub runtime is `needs_key`, `:363-365`). So `settings-reset-key-submit` does run and the key really is forgotten on every desk, but the gate it announces is still `allowed: true` and the desk stays open — which reads as "nothing happened" (owner report 2026-09-23). This is a **webdev-only artifact**: a dev machine's dotenv files can pin `stub` (`apps/web/.env.local` names `stub` here, but the repo-root `.env` names `ai` and wins as the first file read, so on this checkout a bare start is `ai`; both are gitignored), and the host reads them (`packages/db/src/client.ts:11-14`). `apps/desktop/main.cjs` never sets `AGENTFORGE_RUNTIME` — it only reads it, at `:717` — so the packaged personal app runs unset, derives `needs_key`, and sign-out does drop to `onboarding`. To drive the real behaviour on webdev, start an instance with `AGENTFORGE_RUNTIME=ai` and no key saved (the command is under Preconditions).
- **The English `message` never reaches the screen.** The renderer picks localized copy from `status` alone; `gateway.message` ("HTTP 401", "The gateway rejected the saved key.") exists only in the payload and the log. Assert the localized sentence, not the host's technical string.
- **A 401 during a send is not the gate.** The gate is a cached verdict; a live 401 surfaces as ordinary gateway-failure copy in `composer-error` only (`packages/core/src/gateway-http-copy.ts`), in the desk language, with the status code in the headline. `chat-error` stays clear for that send, and the live mascot goes to `error`.
- **`needs_key` shows no reason and no re-check.** `onboarding-gate-reason` and `onboarding-recheck` render only once there is a failure to explain. On a fresh keyless desk the hello has no reason, and the key step is the help sentence, the key field, Back, and Check this key. Their absence there is the pass, not a miss. There is no gateway host line to look for.
- **`allowed` is advisory and must stay that way.** It decides what the desk shows and which local handlers refuse. Seats, plan limits and spend are enforced server-side against the bearer. Anyone can delete one JSON file to get past this gate; a recipe that treats it as an entitlement proof is testing the wrong thing.
- More handles and copy: `onboarding-later` / `onboarding-later-hint` (hosted and signed in only), `onboarding-key-restricted` (a hosted member sees it in place of `onboarding-key` and `onboarding-continue`; Re-check can then show with no reason, `onboarding-screen.tsx:323-340`, `:355`), `onboarding-step-welcome|key|try`, `onboarding-steps`, `onboarding-back`, `onboarding-key-success` ("That key works."), `onboarding-tour-hint`, `edit-agent-needs-key` (hosted); `settings-error` shows `settings.gateway.checkFailed` ("Could not re-check the gateway right now. Try again in a moment.") when Re-check returns nothing usable. An `unreachable` or `error` verdict with `lastOkAt: null` closes the desk at once (no grace); and, as SKILL.md **Keys** says, only an `ok` verdict is ever re-checked in the background (`needsGatewayRefresh`, `gateway-gate.ts:641-649`), so one past the 7-day grace keeps the desk closed with the gateway up until someone presses Re-check.
- **Driven 2026-10-05 on `:3000` (keyed, gate `ok`; maintain3), read-only plus a browser-side fake.** `GET /api/v1/settings` carried `gateway: { status: "ok", allowed: true, grace: false }`; the Settings row read "Key verified | Last checked Oct 5, 2026, 10:07 AM | Re-check" with `settings-gateway-grace` and `-reason` count 0 and `settings-endpoint`, `settings-endpoint-reset`, `openai-base-url` count 0; `GET` on `/api/v1/settings`, `/threads`, `/workspaces`, `/usage` and `/models` all 200. With `GET /api/v1/settings` faked to `invalid_key` (`allowed: false`) in the page only, reloading `/chat` opened `onboarding-form` directly (the hello skipped) with `onboarding-gate-reason` "That key didn't work. Check it at Toko Token and paste it again." (no host, no status code) and `onboarding-recheck`, and `settings-form` and `settings-link` were count 0. `settings-gateway-recheck` and `onboarding-recheck` were **not pressed**, and the flat 403 bodies and `settings-gateway-grace` need a real closed gate (an isolated `AGENTFORGE_RUNTIME=ai` instance with no key), which was not available this pass because `:3000` answered.
