# Knowledge ingest loop

Every finished piece of work becomes a **text work card** in the Knowledge Base without the user doing anything: Chat turns, Images / Videos / Edit generates, Research dossiers, Data analyses, Finance briefs, Documents drafts, Presentation outlines. Bytes stay where they already live (`media` rows, `artifacts` rows); the card carries title, mode, prompt excerpt, a pointer (`media:<id>` / `artifact:<id>` / `thread:<id>`), and a capped body (≤ 8k chars). Chat retrieves cards, never mp4s. The Sources tab shows the cycle as `knowledge-loop`. Stub runtime indexes too, so a webdev stub proof is valid. Per-surface detail — what triggers each mode's card, what text lands in it, what is left out, who can retrieve it and what a delete removes — is [`docs/internal/maps/knowledge-flows.md`](../../../../docs/internal/maps/knowledge-flows.md); the pipeline underneath it is [`docs/internal/maps/knowledge-ingest-loop.md`](../../../../docs/internal/maps/knowledge-ingest-loop.md).

Product: both · Instance: main :3000

## Sub-features

- `knowledge-loop` on the Sources tab is the **Knowledge health** strip as of 2026-09-17. The six-box cycle diagram is gone: **`knowledge-loop-cycle` no longer exists, and neither does `knowledge-loop-stage-Graph`** — do not assert either, and do not file their absence. What is there: the Verified pill `knowledge-loop-verified`, carrying `data-state` and a new `data-tone` of `pass` / `stale` / `fail` / `never` (a pass older than 24 h reads `stale` — not a failure and not proof); the self-check button `knowledge-loop-verify`; and `knowledge-loop-summary`, now the wrapper around four stat tiles whose headline numbers are `knowledge-loop-work`, `-manual`, `-indexed` and `-retrieved`, each with `data-value`; `knowledge-loop-chunks` is the Indexed tile's sub-line (`apps/web/components/knowledge-loop.tsx:247`), not a fifth tile. `knowledge-loop-failed` renders **only when something failed**. The stage testids `knowledge-loop-stage-<Work|Saved|Indexed|Retrieved|Verified>` ride on the tiles they became (`knowledge-loop-stage-Verified` sits on the Verified pill instead, `apps/web/components/knowledge-loop.tsx:136`), so an older recipe still finds its numbers — but on the `Saved` tile the stage's `data-value` is the total while the tile's own number is the manual count. `knowledge-loop-count-<Type>` with `data-count` now sits in the one-line breakdown `knowledge-loop-counts`, which renders **only when more than one type has sources** — a desk holding only Chat cards shows no by-type line at all, and the per-bar `auto` tag went with the bars. `knowledge-loop-empty` still paints when there are none.
- `knowledge-file` reaches the converter formats through one local reader. The picker `accept` is `KNOWLEDGE_UPLOAD_ACCEPT` (`apps/web/lib/knowledge-upload.ts:51`), which includes `.html`, `.pptx`, `.xlsx`, `.doc`, `.rtf`, `.epub` and the rest of `KNOWLEDGE_UPLOAD_EXTENSIONS`. A scanned PDF never reaches the converter (`.pdf` is handled earlier, `packages/host/src/knowledge-extract.ts:89-90`): it is a 400 `pdf_no_text_layer`, "This PDF has no text layer (scanned image). OCR is not supported yet." (`:116`); `document_needs_ocr` is unreachable from the upload picker. An upload that cannot be read is a 4xx with no row.
- `knowledge-source-type` tag on every `knowledge-source-row`. The host auto-writes thirteen types, including `Music` and `Meeting` (`packages/host/src/knowledge.ts:630-644`). `WORK_SOURCE_ORDER` (`apps/web/lib/knowledge-loop.ts:22-34`) still lists eleven and omits those two, so a Music or Meeting card lands in `knowledge-loop-manual`. Manual types stay `File`, `URL`, `Paste`; pasted text may also carry `Dossier`, `Analysis`, `Brief`, `Memo` or `Playbook` (`PASTED_SOURCE_TYPES`, `packages/host/src/knowledge.ts:627`).
- Chat writes **one card per thread**, rewritten after each completed assistant turn (latest user + assistant only). Retrieval for that thread skips its own card (`startModalityRun` passes `excludeThreadId`, `runs.ts:189`; the `?query=` call skips it too, `handlers/knowledge.ts:327`; `GET /api/v1/knowledge/context?threadId=` alone does not retrieve, it reads the last completed run's record, `handlers/knowledge.ts:328`), so Chat never reads its last reply back.
- Idempotent origin: `(workspace, origin_kind, origin_id)` is unique. Re-generating the same media / artifact / thread updates the row; it does not add a duplicate.
- `*-send-kb` (Research, Data, Finance, and `market-send-kb` and `legal-send-kb`; the Legal one is disabled unless a memo or red-flags artifact exists) is idempotent: when the job already indexed that artifact the note reads `Already in the Knowledge Base.`; otherwise it indexes once as the work type and later clicks say already.
- Index failure never fails the work: the generate still succeeds and the row shows `Failed` with the reason on hover.
- Cards are PII-masked (`[email]` / `[phone]` / card tokens, same as the outbound prompt) because chunks are plaintext FTS while messages are sealed. A card whose text trips the injection guard is recorded `Failed` with `injection_blocked (rule: …)` and zero chunks; it is never retrieved. The owner bypass (`injectionGuardBypass` in Settings) applies here too.
- Deleting a thread (`thread-delete`: hover-revealed, a sibling of `thread-item`, behind a native `window.confirm`; accept the dialog) or a saved artifact removes its card. A source that lists a deleted thread's `thread:<id>` pointer is a bug.
- Example clips on Videos (`videos-example-use-*`) load a prompt only. They never `POST /api/v1/videos`, so they never add a source.

## How to get to it (user POV)

- Send anything in Chat, or finish any job mode, then open Knowledge Base on the Account rail (`mode-knowledge`) → Sources.
- Open `http://127.0.0.1:3000/knowledge` after a send.

## Driving it with the Nultron harness

Preconditions:

- Doctor exits 0 and reports `knowledge: true`.
- Stub or live both count. On `runtime: "ai"` a Chat send spends the operator's gateway; say so.
- Live Images / Videos generate only when the operator asked.

- **Baseline.** Open `/knowledge`. `knowledge-loop` is visible on the Sources tab. Note `knowledge-loop-work` `data-value` (call it W) and whether a `knowledge-loop-count-Chat` row exists. **That testid is inside `knowledge-loop-counts`, which renders only when two or more source types exist** (`knowledge-health.ts:132`, `knowledge-loop.tsx:194`), so on a desk with only Chat cards it is count 0 and the baseline, "Chat card" and "one row per thread" assertions fail for the wrong reason: seed a second type first (a free stub Images card, or a pasted note).
- **Chat card.** Open `/chat`, click `new-chat-link` (a rail Link to `/chat`, not a button; there is no `new-chat` testid), send a unique prompt (`VERIFY ingest <run-id>: What is 2 + 3?`), wait for `composer-send` to read `Send`. Back on `/knowledge`: a `knowledge-source-row` with `knowledge-source-type` = `Chat` and the thread title as name is present and reads `Indexed` (on a live key it can instead read `Saved. Live embeddings timed out…`, the `knowledge-embed-local` note: still a pass, see [knowledge.md](./knowledge.md) Gotchas). `knowledge-loop-work` is W + 1 (or W if that thread already had a card) and `knowledge-loop-count-Chat` exists with `data-count` ≥ 1.
- **Retrieved after a live send.** `knowledge-loop-retrieved` equals `retrievals` from `GET /api/v1/knowledge` (doctor's `knowledgeRetrievals`). It counts the chunks a completed run was handed, one row per chunk. On `:3000` 2026-10-05 the tile read 0 on a desk with one Chat card, then 2 after one live Chat send that was handed two chunks (`Sources 2 chunks` in `chat-context-breakdown`; the Work and Indexed tiles went 1 to 2). A run that was handed nothing leaves it flat. That live send also wrote its own Chat card as `1 chunk` with the embed-local note, see [knowledge.md](./knowledge.md) Gotchas, and deleting the thread removed that card again.
- **One row per thread.** Send a second prompt in the same thread. The Chat row count for that thread stays 1; its name / chunks may change. `knowledge-loop-count-Chat` `data-count` is unchanged. Re-driven 2026-10-16: the work tile read 6 before the second send and 6 after it. Evidence: `evidence/knowledge-ingest/2026-10-16-maint/`.
- **Skip-self.** In that thread, click `chat-context` → `chat-context-breakdown`. `Sources` may read `0 chunks` even though the thread's own card is indexed; that is the anti-loop, not a retrieval bug. A different new thread asking the same question may show `1 chunks`. The Chat chip is rebuilt from the run's record and carries no engine suffix (`lastTurnRetrieval`, `packages/host/src/knowledge-last-turn.ts`; see [knowledge.md](./knowledge.md), Sub-features); only a `?query=` context call shows `· rag`, `· fts` or `· hybrid`.
- **Videos does not ingest on example use.** Open `/videos`, click a `videos-example-use-*`. Reload `/knowledge`: no new `Videos` row, `knowledge-loop-work` unchanged.
- **Live generate (operator asked only).** Generate on Videos or Images. `/knowledge` shows an `Images` row named after the prompt (a `Videos` row is named for the first line of the harness shot, `Subject: <prompt>`, and its recorded Duration is the snapped `harness.seconds`, `studio-generate.ts:467`, `:471`, `composeVideoShot` in `packages/core/src/videos/harness.ts:84-95`), `Indexed`, chunks ≥ 1; the gallery keeps the clip; nothing appears under `tenantDataDir(tenantId)/knowledge/<organizationId>/`.
- **Send to KB idempotent (live Research only).** After a dossier, click `research-send-kb`. `research-actions-note` reads `Already in the Knowledge Base.`; `/knowledge` shows one `Research` row for it, not a `Dossier` copy.
- **Unit.** `packages/host/src/knowledge-ingest.test.ts` (upsert twice → one source; retrieve excludes own thread; empty card skipped), `work-cards.test.ts`, `packages/db/src/ensure-schema.test.ts` (origin columns + unique index + heal), `apps/web/lib/knowledge-loop.test.ts`.

## Gotchas

- A stub Chat reply is still indexed (stub embeddings + FTS). That is the product's own test mode, not a mock.
- The Chat card is the *latest exchange only*. Do not expect earlier turns of a long thread to be retrievable from that thread's card.
- Chat cards are fire-and-forget after the stream ends; reload `/knowledge` once if the row is not there within a second.
- Do not read `tenantDataDir(tenantId)/knowledge/<organizationId>/` as proof of Images / Videos ingest. Nothing is written there for work cards; the pointer is `media:<id>`.
- Failed rows are correct output when the embed or write fails; the generate must still have returned its result.
- Documents / Presentation generate now also saves a `draft` artifact (mode `documents` / `presentations`). The saved-artifact picker on those studios lists them.
- Type `test@example.com` in Chat and the Chat row name / chunk reads `[email]`, not the address. Raw PII in `knowledge_chunks` is a fail.
- "Ignore all previous instructions…" in a turn gives a `Failed` Chat row (`injection_blocked`), not `Indexed`. That is the guard working; the next clean turn flips it back to `Indexed`.
- Older sources (before origin columns) have no origin; `Send to Knowledge Base` on an artifact from before this change indexes it once as the work type, then reports already.
- **The graph sweep landed on 2026-09-17.** A deleted source or thread used to leave its node and its `cites` / `retrieved` edges behind, so the graph could show more than the Sources list did. `packages/host/src/knowledge-graph-prune.ts` now cascades inside the delete transaction and `sweepOrphanGraph` repairs older residue on every `GET /api/v1/knowledge`. A node for a row that is no longer in Sources is now worth filing — but reload the page once first, since the sweep runs on that read.
- `knowledgeRetrievals` (doctor, and the `knowledge-loop-retrieved` tile) is one row per injected chunk. Retrieval rows are dropped with their source now, so the number is no longer strictly monotonic — but it still only ever counts *completed* runs, so use it to prove a retrieval happened, not to size the knowledge base.
- **Market auto-ingest landed on 2026-09-17.** A completed `POST /api/v1/market` now writes its own card through `upsertWorkSource`, `Market` is a real work type, and a briefing sent with `market-send-kb` is filed from the artifact's own mode rather than the client's label — so a Market briefing no longer files itself as `Finance`. Both the auto card and the button write the same origin row, so one delete covers both.
- A media card holds the **prompt and the settings only** — `Prompt:` / `Aspect:` / `Duration:` / `File: /api/v1/media/<id>/file`. There is no caption, no alt-text and no vision read anywhere on that path, so an Images / Videos / Edit row can never answer a question about what the picture shows, only about what was asked for.
- The host writes thirteen kinds of card, not the nine the intro lists: also Market, Legal, Music (one per take, `studio-generate.ts:585`), Meeting (the minutes artifact only, `meeting/minutes-artifact.ts:47`, written from `meeting/run.ts:414` and `:493`) and a Presentation open-slide path (`open-slide-generate.ts:189`). The word "chart" in this file, `README.md` and `SKILL.md` is stale: the Sources tab has a health strip of tiles, not a chart. A stub Images generate is free and indexes a real `Images` card (the 1x1 stand-in, `studio-generate.ts:308-318`), so the first four steps run on a stub desk; stub Research, Documents and Presentation return 503 `runtime_stub` and Videos needs a ready route. A free proof of Retrieved: a fresh second thread whose first message carries the first thread's unique token should be handed that card, so `knowledge-loop-retrieved` rises and `chat-context-breakdown` shows `N chunks` (not driven). The source row's Remove button has no testid (text "Remove", no confirm); a failed upload (4xx) shows plain red text with no testid; `knowledge-loop-verify` is gated and throttled to 10 s (free on stub, embeds on a keyed desk); on a closed gate `composer-send` is disabled, so no Chat card can be written.
- **Driven 2026-10-05 (maintain3), isolated stub instance.** A stub Images generate indexed an `Images` row ("VERIFY ingest maintain3 poster", Indexed); two Chat sends made two `Chat` rows (one per thread, "What is the internal code name?" and "what does the desk say about zorblatt7731"); with 2+ types `knowledge-loop-counts` rendered with `knowledge-loop-count-Chat` 1, `-Images` 1 and `-Paste` 1; deleting the two threads through the hover `×` and the native confirm removed both `Chat` rows on the next load. Webdev and non-hosted builds are unchanged. **Driven 2026-10-09 on a throwaway stub webdev desk:** a pasted note became a `Paste` row (Indexed, 1 chunk); two stub Chat turns gave `Chat` rows and, after a "what does the desk say" turn, the graph held `cites · weight 1` and two `retrieved · weight 1` edges (`knowledge-graph-counts` `data-edges` 3) with `knowledge-loop-counts` present once two types existed; the stub answered "From the desk [1]."
