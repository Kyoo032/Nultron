## Hosted: the gateway check is per company, not per partner, 2026-10-07 (Enterprise; fixed in the tree on `feat/hosted-run-limits`, not committed, not driven on a hosted server)

- **What a company saw.** On a hosted server, after company B saved a gateway key that differed from company A's, A's next Chat turn answered `403 gateway_blocked`. Reproduced on `main` as `gateway-gate-companies.test.ts` ("lets both companies chat after each has saved a different key the gateway accepts"): A's turn answered 403 with B's key accepted by the gateway. A variant with B's key rejected closed A as well.
- **Cause.** `TenantContext.tenantId` is the white-label partner (HYP AI, Nultron Enterprise) and a company is an `organizationId` inside it. Keys were already per desk and a desk belongs to one organisation, so two companies never shared a key. The verdict was not: one `tenant_state(tenant_id, 'gateway_gate')` row per partner (`loadGateState`, `saveGateState`, `clearGateState` took only the tenant id). B's check replaced A's verdict, A's key no longer matched the fingerprint on file, and the hosted gate closes on "no verdict for this key". The same row also held one `lastOkAt` for both, and the background re-check's throttle slot was the partner plus key.
- **Fix, server mode only.** The verdict is stored per company: the `gateway_gate` key narrowed to `gateway_gate:<organisation id>`, a row under the partner's own `tenant_id` in the same table (`companyStateKey`, `packages/host/src/tenant-state-store.ts:86`; `ownerOf`, `packages/host/src/gateway-gate.ts:169`). No table, no column, no migration. A hosted gate call with no organisation is refused (`company_required`, 500), never answered from the partner's row. The throttle slot carries the company. The verdict an older build wrote for the whole partner is read in one case only, added by the review round below: a company whose slot is empty adopts it when its fingerprint is exactly the fingerprint of the key the company holds. "Forget my key" on the server clears the caller's company's desks only (`ClearKeyWithin`, `packages/host/src/settings-store.ts:536`; it used to clear every desk of the partner, which signed the other companies out of the gateway) and that company's verdict.
- **Personal is unchanged.** A desk's verdict is still `<dataDir>/gateway-gate.json` (`tenants/<id>/` for a non-local tenant), with the same payload and no company in it; the file backend refuses a company slot, and nothing on a desk builds one. Pinned by bytes and path in `gateway-gate-companies.test.ts` ("Personal: server mode off"), including the missing-file upgrade case, and by every existing desk suite (`gateway-gate.test.ts`, `tenant-state.test.ts`). A mutation check that let a desk scope itself by company turned the desk suites red.
- **Cost on deploy.** Every hosted company starts with no verdict of its own. A company whose key is the one the old partner row judged adopts that verdict on its first read (review round, item 5), so it is not closed and keeps its grace if the gateway is unreachable at that moment. Any other company reads "has not been verified" until its first Settings read starts a check (the shell makes one on load); one Chat turn sent before that read can answer `403 gateway_blocked` once, and the renderer asks the host for its gate again after a refusal.
- **Tests.** `packages/host/src/gateway-gate-companies.test.ts` (30: two organisations under one partner through the real router with a stand-in gateway, the two-partner topology, two desks in one company, the probe per company, the deploy window, the id used as it is, the Personal cases), `tenant-secrets.test.ts` (the rows, the refusal, the partner row adopted only for its own key, `within`), whose fixtures gained an `organizationId`. ## Password sign-in for the hosted portal, 2026-10-07: a second way in, chosen by configuration (uncommitted, branch `feat/portal-password-signin`)

**Product: Enterprise (the hosted app and its portal), for the HYP AI white-label. Not Personal, and not in any installer.** Owner decision, 2026-10-07 (Rizky): *"the login portal doesnt need email code, we will use username and [password] protection for now, with 2FA method being designed."* The rule "no password" is lifted for this mode only; the e-mailed one-time code stays the default and is what the other hosted product runs. Three people are waiting to be onboarded on a fresh server.

- **The switch.** `PORTAL_SIGNIN_MODE=code|password`, read once at boot (`apps/portal/src/config.ts`), default `code`, anything else refuses to start. In `password` mode SMTP is not required to boot in production and the mailer refuses to send (`apps/portal/src/mail/disabled.ts`); every other production guard stays.
- **The portal.** `GET /authorize` renders a username (or the address on record) and a password; `POST /authorize/password` and `POST /authorize/password/change` replace the e-mail, invite and verify posts, which are not registered and so answer the server's own 404; the device-code page has the same two posts under `/activate`. A person with an operator-issued password must choose their own before a session is issued. Every failure (unknown username, wrong password, a lock, a disabled person) is one sentence, one page and one scrypt derivation. Five counted failures lock an account for 15 minutes, counted before the comparison and in the database; under the lock a source address with no earlier failure against that person may still take three more attempts (see "Review fixes" below). A person who is in goes down the same `completeSignIn` the code flow ends in, so the app needs no new trust decision. New: migration `0012_password_signin.sql` (`user_credentials`, `resolve_tenant_for_username`; no second-factor column) and `0013_password_grace.sql` (the three slots), `src/password/`, `src/flows/password-sign-in.ts`, `src/routes/{password-flow,signin-mode}.ts`, `src/store/postgres/credentials.ts`, `src/accounts/`, `scripts/account.ts`.
- **The operator.** `pnpm portal:account` or `sh webapp-deploy/scripts/portal.sh account <create|reset-password|disable|enable|set-role|list>`: no self-sign-up, no self-service reset; `create` prints a generated initial password once and enforces the seat cap; `disable`, `reset-password` and a `create` that attaches a password to somebody who already exists end every session the person holds. `list` also shows the locks of the last 24 hours. `invite` and `otp` refuse to run in this mode.
- **The app side.** The host asks the portal `GET /auth/signin-mode` (registered only in password mode; `packages/host/src/auth/portal-mode.ts`) and `GET /api/v1/auth/session` carries `signInMode: "password"` only then; `SignInScreen` says "username and password" and "Continue to sign in" instead of "work email", "invite code" and "Continue with email", in `en` and `id`. The desktop app is not affected: the reader is wired only when `isServerMode()`.
- **Proven, by test, through the real server and a real Postgres:** the whole walk (forced change, the redirect, the code the host redeems, the role in the token); one refusal with equal derivations and comparable time; the lockout, a restart, 12 parallel guesses getting exactly 5 comparisons, and its expiry on a moved clock; the forced change's refusals; a disabled person and the browser they had open; CSRF; the code routes absent; the device-code approval; the seat gate; re-hashing at a changed cost; the two budgets; and no password in any page, redirect, audit row or log line. **The default is proven unchanged** by an exact list of its 21 routes, 18 of its screens pinned by sha256 against hashes made from `main`'s own view code, and the 404s of every password route. The operator command is also run as a real process against a real Postgres (`src/accounts/cli.test.ts`: usage, the refusal on a portal that is not in password mode, create and its one-time password, the refusals and their exit codes, reset, disable, enable, and `invite` and `otp` turned away). Portal 43 files, 662 tests; host `src/auth` and the tenancy suites 30 files, 826 tests; the web session, sign-in, onboarding and every locale parity suite (24 files, 100 tests).
- **Not driven.** Nothing here was driven in a browser against a running portal and app, and nothing ran on a server. The host half is unit-tested against a stub portal, and the screen against rendered markup. Owed: the walk in `features/login.md` ("The password-mode walk") on the review instance or the pilot stack, and a real-browser check that the new portal pages are not blocked by the CSP (the pages carry the client's origin in `form-action` exactly as the code pages do, SR-20, but only a browser enforces it).
- **The deploy bundle.** `PORTAL_SIGNIN_MODE` is in `webapp-deploy/portal.env.example` and the README, and now also in the portal template that `scripts/release-web.mjs` generates (`PORTAL_SIGNIN_MODE=code`, with a comment saying `code` is the default and `password` the other value; an optional name, listed as `OPTIONAL_PORTAL_ENV`). It reaches the container through `portal.env`, which the `portal` and `portal-prepare` services load in both compose files, and neither pins it, because a value under `environment:` would win over the file. ## Chat: a turn that ended after a tool with no words, and a 10 s header limit that cut a slow gateway, 2026-10-07 (both products; in the tree on `feat/chat-resilience`, not committed, not driven on a live model since the fix)

## Chat: an attached image never reached the model, 2026-10-06 (both products; fixed in the tree, not driven live)

- **Bug (owner report, live preview).** A PNG sent in Chat on "GLM 5.3" came back as "the image isn't reaching me. The attachment came through only as a note that a screenshot was added in the app." Cause, in three links. (1) The thread stores the picture as `/api/v1/media/<id>/file`, and the host handed that reference on: `inlineLocalMediaParts` ran only for a loopback provider (`shouldInlineLocalMediaForProvider`, `packages/host/src/inline-local-media.ts:10-17` before this change, called at `packages/host/src/runs.ts:302-321`), on the guess that a remote gateway "may reject data URLs". (2) The runtime then turned any image that was not a data URL or an https URL into the sentence "[Image attached in the local app. It is already shown to the user.]" (`imagePartForProvider`, `packages/core/src/content/provider-media.ts:38-43`, called at `packages/core/src/runtime/ai-sdk-runtime.ts:108-109`), so the model was told a picture existed and was given none; a second net, `rewriteUnreachableMediaInJson`, did the same on the wire body. (3) Nothing told the person. **It hit every model, not only GLM**: nothing in the path looked at the model, and the red run's recorded bodies carried the sentence and no image part. Video had the same shape: "[Video attached in the local app...]" for every model.
- **Second bug, why GLM 5.3 was offered at all.** "Which models read images" was the prefix list in `packages/core/src/models/capabilities.ts` (`glm`, `deepseek` and `kimi` yes; no `gpt-6`). `docs/internal/gateway-model-selection.md` § 1.8 lists `glm-5.3` and `deepseek-v4-pro` as text-only, and GPT 6 reads images. So the composer let a text-only model take an image, and refused (`chat.error.noImageInput`, only after Send) the Chat default, GPT 6 Luna. The model picker tagged the same wrong answers "image".
- **Fix.**
  - One rule, `modelImageInput(id)` → `yes | no | unknown` (`packages/core/src/models/image-input.ts`, evidence: the doc's "Modality" column), read by the host and the renderer. `getModelModalities().image` follows it for Chat models.
  - The host sends every image as bytes: `prepareChatImageHistory` (`packages/host/src/chat-image-history.ts`) turns each stored reference into a data URL, the latest message's images always (or the turn fails in words), earlier ones newest first within 6 MiB (16 MiB in the first version; see the review fixes below), the rest as a note that says the model cannot see them. A model known to be text-only gets no pixels and is refused a new image with `400 model_missing_modality`; a model with no line is tried (`assertChatModelAcceptsModality`).
  - `imagePartForProvider` no longer makes a sentence: a reference that is still local **throws** a sentence for the person. The video stand-in now tells the model it cannot see the video.
  - A gateway 413 or 415, or a 400 or 422 about the image, is shown as "The model could not accept the image you attached (status_code=…)" in both locales, not "send again with a shorter prompt".
  - The composer says, under the chip and before Send (`composer-image-note` `data-state` `no` or `unknown`, `composer-image-switch`, `composer-video-note`), what the model will receive, and `composer-image-switch` moves the picker to the best model that reads images. The picker's "image" tag follows the same rule.
  - **Review fixes, 2026-10-07 (an independent review said "ship after named fixes").**
    - **Request size.** The budget is 6 MiB of image per request, not 16, because the AI SDK sends the whole prompt again on every tool step (Chat allows 12) and each wire wrapper parses, edits and re-writes the body each time. Measured on a 6 MiB picture (an 8 MiB body): parse about 25 ms and stringify about 30 ms per step on every wire, and on the Anthropic and Gemini wires, which carry the picture as raw base64, the rewriter's walk cost 65 to 70 ms more, because `isUnreachableProviderMediaUrl` ran `new URL` over all of the base64, twice. That matcher now answers no for a string with no colon and no `/api/v1/media/` prefix, and the rewriter looks at the key before the string (`packages/core/src/content/provider-media.ts`); the walk is about 0.1 ms. The parse and the write-out stay: the other body edits (reasoning level, zero retention, per-model clean-up) need the parsed body. **A gate that skips the walk for a clean body was built and dropped**: after the matcher fix it was slower than the walk it guarded (2 to 7 ms against 0.1 to 1.7 ms), and before the fix it ran the same matcher on the same string, so it saved nothing. What a person sees: a picture, or pictures together, over 6 MiB is refused at Send with "These images are too large to send together (over 6 MB). Send fewer or smaller images." A single picture between 6 and 10 MiB passes the 10 MB upload cap and is then refused; the composer does not warn first.
    - **Stored files that are not pictures.** A crafted `image_url` part naming a stored video or audio was read whole and sent as an image. Chat now reads a stored row only when its kind is `image`, and compares its stored size to what is left of the budget before any bytes are read (`statMedia`, `chat-image-history.ts`). The real size is checked again after the read.
    - **Job regeneration.** The first version of the image rule answered "no image" for every id it had no line for, so a Documents, Presentation or Finance regeneration with an attachment on a hand-picked `glm-`, `deepseek-`, `doubao-`, `kimi-` or `ep-` model was refused, and the cached picker tags lost "image" for them. `getModelModalities` now keeps the older prefix answer where the rule says unknown (a known no stays no). `job-regen.test.ts` pins it.
    - **Links.** An `https://` image part in a Chat user turn is refused with a sentence (latest turn) or becomes the "cannot see it" note (earlier turn). On the Google wire the AI SDK would have fetched it from this host with no size cap (SR-150).
    - **Smaller items.** `historyHasImage` counts the person's turns only, so a thread with one generated picture no longer makes an unrelated 400 read as "could not accept the image you attached". A picture that cannot be sent is refused before the message is stored, so it leaves no bubble without an answer (`assertChatImagesSendable`, `runs.ts:294`; it reads each row, not the bytes). A data URL is recognised before a media reference is looked for. The composer clears its refusal sentence when the model changes, so the switch button no longer leaves it standing.
  - **Why a visible choice and not a silent per-turn switch.** The only fallback in the tree, `model_fallback` (`packages/core/src/models/job-fallback.ts`), is for jobs, transport failures only, and shows its notice on a job result; it refuses to swap on a 400 so a rejected prompt is not hidden behind a mystery model. ## Edit agent stream, probe logging, Chat card and onboarding setup check, 2026-10-08 (fixed in the tree)

- **Edit agent: an interrupted run said nothing.** The studio dropped `run.interrupted`. It now shows one sentence above the Edit composer (`edit-agent-note`, `edit.agent.interrupted` in en and id), cleared when the next turn starts (`apps/web/lib/edit-agent-note.ts`, `apps/web/components/edit-studio.tsx`).
- **Edit agent: the stream carried tool input and output unredacted.** `screenEvent` in `packages/host/src/edit/agent-run.ts` sends the copy `redactToolEvent` makes, the way Chat does. A failure's own words (`run.failed`, `run.interrupted`) are masked too. The tool frames are read from the same copy.
- **Edit probes failed silently.** `probeSilence` and `probeScenes` (`packages/host/src/edit/harness-run.ts`) logged nothing when a probe threw. They now log `edit_silence_probe_failed` or `edit_scene_probe_failed` with the attempt and the redacted message, and keep the same fallback.
- **Onboarding: an empty box above the key form after an install.** The 4-second collapse lived in the panel, so the Setup check section stayed on screen after the panel had drawn nothing. The collapse moved into `useComponentSetup`, and `visible` is now `component !== null && !collapsed` (`apps/web/lib/use-component-setup.ts`).
- **Chat Knowledge card indexed the host's own sentence.** `packages/host/src/runs.ts` builds the card from `modelAnswer`, the model's words captured before `settleChatTurn` adds the step-limit or interrupted sentence. Decision for Rizky: a turn where the model wrote no words now writes no card. Before, a tool sentence such as "2 + 3 = 5" was indexed.
- **Open:** the harness and stub paths in `harness-run.ts` (`invoke`) and `agent-run.ts` (`runStub`) still push their own tool events raw. The harness passes the owner's text into some tools (for example "words on the picture"), so a pasted key can reach that stream.
