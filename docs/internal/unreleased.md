## Chat resilience: a failed tool, a tool that is off, the step limit, redaction and `self_check`, 2026-10-06 (both products; in the tree, not committed, not driven on a live model)

Branch `feat/chat-resilience` (worktree `agentforge-chatfix`, from `main` at `6105c5c`). Map: [`maps/agent-tools-and-files.md`](maps/agent-tools-and-files.md) § 13. Recipe: `features/chat.md` (`chat-tool-recovery`, `chat-step-limit`, `chat-self-check`, `chat-tool-redaction`). Register: [SR-136](security-register.md#sr-136), [SR-137](security-register.md#sr-137). The first four came from a read-only audit; each was confirmed in the code before it was changed.

- **Every Chat request changes, on both products, and costs tokens.** Each turn now sends two more sentences in the system prompt (one for `self_check`, one on how to read a result with `ok: false`) and one more tool definition (`self_check`, with its description) in the tool list, on every desk, Personal and Enterprise alike. That is a small, fixed extra input cost on every Chat turn, whether or not the model ever calls the tool. On the hosted server, where `run_code` is off, the prompt is a sentence shorter than before and the tool list one tool shorter than Personal's. A Chat desk made earlier gets all of it with no migration (the prompt is read at run time, the missing tool binding is added when Chat opens).
- **A tool that throws no longer ends the run.** The SDK turned a rejected `execute` into an `error` part with no tool result, and the runtime mapped it to `run.failed`. `buildAiTools` now answers the model with `{ ok: false, reason: "tool_error", message }`: the detail is quoted, redacted, stripped of host paths (only roots a host has; `/workspace/...` and desk paths stay), capped, and withheld for every tool when it reads like instructions. A cancel is still rethrown, never turned into a result.
- **A tool the run does not offer.** Chat's prompt named `run_code` on the hosted server where it is off, and a call to it ended the run (the SDK found no such tool). The prompt now drops that sentence while the tool is off, and a call to it gets the existing disabled refusal. That refusal spends the run's budget like any other call, so a flood of calls to a tool that is off ends in the budget refusal. The old note in the map that a model "may try it once and get the refusal" was wrong and is corrected.
- **The step limit (G6).** A Chat run that used all 12 steps on tools finished with no words. It now ends with one sentence, in English or Indonesian, saying the steps ran out and to ask it to continue. `ai` 4.3.19 cannot force a tool-free last step in `streamText`, so the host writes the sentence.
- **Redaction (G7).** What a Chat turn streams to the screen, stores in `tool_invocations` and saves on the assistant message for a tool call is now a redacted copy. The model's result and the media it collects are not changed. The shapes masked now include JWTs, Telegram bot tokens, AWS access key ids, PEM private key blocks, URL user and password, and `Cookie:` headers, plus more secret-named keys; hashes, signed links and figures are left alone on purpose. The Chat card written to the Knowledge Base is masked too; the assistant's own reply is not (a secret the model repeats stays in that thread), and the reasons are in SR-136. Opaque tokens with no known prefix are not caught.
- **`self_check`.** A read-only Chat tool that reports the gate status, whether code runs and the sandbox are in place, whether ffmpeg and ffprobe resolve, server mode, the tools this run does not offer and its step and tool-call limits. Facts only (SR-137). Chat now binds 16 tools, with a cap of 4 calls a turn. With code runs off it does not hash the sandbox's files (`sandbox: "not_checked"`).
- **Found, not fixed.** A call whose arguments fail the tool's schema, or that names a tool that is not bound at all, still ends the run: the SDK rejects it before `execute` runs (`parseToolCall`, `ai/dist/index.js:4079`). The Data job's instruction still names `run_code` where it is off; a call now gets the refusal. The Edit agent streams its tool events unredacted. A job that ends at its step cap still ends silently.
- **Proof.** Unit and runtime tests with the real AI SDK and a replaced `fetch`, host tests through the real router with a scripted runtime. Counts are in the map's Verify section. Not driven: no live model, no browser, no packaged app, no hosted server.

## Hosted: in-flight run limits, 2026-10-06 (Enterprise; in the tree on `feat/hosted-run-limits`, not committed)

- **Gap.** Nothing bounded how many model runs one signed-in account could hold open. The request limiters count requests (300 a minute per session), and the job pools in `packages/host/src/concurrency.ts` are global and guard only ffmpeg and SQL workers. Fifty `POST /api/v1/videos` in a burst were all admitted.
- **Change.** `packages/host/src/run-limits.ts` adds a per-tenant cap (`AGENTFORGE_MAX_RUNS_PER_TENANT`, default 6) and a whole-server cap (`AGENTFORGE_MAX_RUNS_TOTAL`, default off), server mode only. A run over the tenant cap is refused before it starts with 429 `too_many_runs`, over the server cap with 503 `server_busy`. `0` is a cap of zero and refuses every run; `off`, `none` or `unlimited` remove a cap. Every route that calls the gateway gate takes a slot (`withRunSlot`, the stream wrappers, `streamJob`'s `tenant`, and `onSettled` for Edit jobs that outlive their request) except five short, bursty calls written down in `LEFT_OUT`. The slot is given back exactly once, however the work ends. The tenant is the organisation inside its white-label partner. Personal and webdev have no cap and no count. `apiFetch` puts the catalog sentence (`common.runLimit.*`, `en` and `id`) into both refusals on the web and in the packaged app. Both variables are in `webapp-deploy/.env.example`.
- **Also fixed on the way.** A Chat run whose client had already gone before it registered its abort listener never saw the disconnect (`packages/host/src/runs.ts:238`); the Chat stream wrapper now forwards `return()` to the run even before the first frame.
- **Tests.** `run-limits.test.ts` (55), `run-limits-routes.test.ts` (inventory plus every counted route through the real router), `run-limits-router.test.ts` (15), `run-limits-edit-jobs.test.ts` (5), `run-limits-adapter.test.ts` (6, the real HTTP adapter), `job-stream.test.ts` (8 new), `apps/web/lib/run-limit-copy.test.ts`.
- **Owed.** In memory and per process, not a billing control, not driven on a hosted instance. Security register SR-138; map `maps/hosted-security-controls.md` § 5.

## Hosted image carries ffmpeg, 2026-10-06 (Enterprise image and the preview; the desktop bundle, the input limits and the Windows export fix are in the tree, see the bullets from "Update, same day")

- **Bug.** The image had no `ffmpeg` or `ffprobe` (`command -v` printed nothing in an image built from `6105c5c`), so every desk on it showed the "ffmpeg was not found" notice and Edit could not probe, cut or render. Rizky, 2026-10-06: ffmpeg is mandatory and nobody is asked to install anything.
- **Fix.** `webapp-deploy/Dockerfile` gets an `ffmpeg` stage: BtbN's static build `n8.1.3-9-g29e619e767` (month-end release `autobuild-2026-09-30-13-08`, GPL variant because the render recipe uses `libx264`), pinned by URL and sha256 for amd64 and arm64. The runtime stage copies both programs to `/usr/local/bin` with the licence text, and the build fails if either does not run or lacks `libx264` or `libmp3lame`. Debian's own package is 5.1, below the host's minimum of 6.
- **Proof.** The stage built on this PC and both programs ran (`ffmpeg version n8.1.3-9-g29e619e767-20260930`, both encoders listed). `scripts/{deploy-scripts,pilot-deploy,release-web}.test.mjs`: 70 tests green.
- **Not done.** `apps/desktop/resources/ffmpeg/` still holds only its README, so the packaged Personal app ships without ffmpeg and shows the same notice on a machine that has none. Webdev still reads PATH. Licence and source pointer: `docs/internal/ffmpeg-attribution.md`; register SR-135.
- **Update, same day (desktop bundle, in the tree, not packed).** The line above is the state before this change. `apps/desktop/scripts/stage-ffmpeg.mjs` now stages a pinned ffmpeg and ffprobe plus the GPL v3 text into `resources/ffmpeg/` (lock: `apps/desktop/scripts/ffmpeg.lock.json`: Windows x64 from BtbN `n8.1.3-9-g29e619e767`, macOS arm64 and x64 from FFmpeg 9.0.2 on Martin Riedl's build server). `pnpm desktop:build` stages `win32-x64` before electron-builder and fails if the check fails; the Docker mac route stages and verifies per arch. In the packaged app a bundled copy that will not run now says "reinstall" on every surface (Edit banner, onboarding setup check, Meeting studio note and refusal, Edit agent prompt) and never shows `winget` or `brew`; webdev keeps the install guide. **Still not done:** no installer has been packed with it (Windows launch of `Nultron.exe` with the bundled copy, the mac `build-mac.sh` run and a Mac launch are all unproven), the Windows installer grows by an estimated 100 MB or more (the two programs are 314 MiB uncompressed; the zip ratio suggests a third of that; not measured), the 0.16.0 and later release notes must carry the GPL source line (`docs/internal/ffmpeg-attribution.md`), and the macOS source is accepted for the preview installer only (next bullet).
- **macOS source, Rizky's decision (2026-10-06).** The macOS programs come from a one-person build server that ffmpeg.org does not link (FFmpeg 9.0.2, Martin Riedl). Rizky accepted it for now, for the preview Mac installer only, because the Mac app is still labelled preview, and kept both `darwin-*` lock entries. The pin proves the file did not change since it was pinned; it does not prove who built it (the publisher's `.sha256` comes from the same host). The acceptance ends when the Mac app leaves preview or the publisher's build behind a pinned URL changes. Owed before that: a committed script that builds FFmpeg from source on Rizky's Mac, our own hashes in the lock, and one FFmpeg version on Mac and Windows (today 9.0.2 and 8.1.3). Full record: `docs/internal/ffmpeg-attribution.md` and SR-135.
- **Not proven for macOS.** Nothing has been packed or opened on a Mac. macOS may refuse the bundled helper on first launch (a quarantined program inside an un-notarised app); the app would then say "Reinstall", and reinstalling would not fix it.
- **Input limits on every ffmpeg run (review point 3; in the tree, not deployed).** `runFfmpeg` adds `-protocol_whitelist file,crypto,data` before every input, so a file cannot make ffmpeg open an address. An upload whose container is a playlist, a concat script, an SDP or RTSP description, a DASH manifest or a metadata file is refused at the probe with `400 unsupported_media` and its own sentence (`mediaFormatRefused`, both locales), in Edit's import and in Meeting. A declared media length is believed up to six hours, and a hosted run stops at an hour for analysis, two for a render, two for any single run; a desk keeps its old timeouts. Measured: ffmpeg 8.1.3 already refuses an address named inside a local HLS or SDP file on its own, so the flag matters for an input that is itself an address (1 request run directly, 0 through `runFfmpeg`). Code `packages/host/src/edit/ffmpeg/input-safety.ts`; tests `input-safety.test.ts`, `run-input-safety.test.ts` and `ffmpeg-input-safety-real.test.ts` (against the staged 8.1.3 programs); record SR-135. Residual: an `ffconcat` script is read with `safe=1`, so if the format gate were bypassed it could read other files of the same tenant; the gate refuses the format first.
- **Packaged app with its ffmpeg folder missing no longer walks PATH (review point 4; in the tree, not packed).** In the packaged app (`AGENTFORGE_PACKAGED=1`, no `AGENTFORGE_FFMPEG_PATH`) the bundled path is the answer even when the file is absent: the doctor reports it `missing` against that path and the notice says "Reinstall". A copy on PATH never replaces it. Electron without the flag (the `desktop:dev` window) keeps the old fallback. Code `ffmpeg-binary.ts` `packagedBinary`; tests `ffmpeg-binary-bundled.test.ts`.
- **Bug found and fixed outside the review list: every Windows export of a timeline with a video clip failed.** `escapeFilterPath` (`packages/host/src/edit/ffmpeg/paths.ts`) escaped the drive colon one level (`C\:/Users/...`). ffmpeg unescapes a filter-graph string twice (once when it splits the graph, once when it splits a filter's options), so it read `C` as the file name and the rest as another option, and the render failed with "Unable to parse original_size". When a timeline has a video clip, `compileFilterGraph` always attaches the `.ass` file (the filter that draws captions and titles, even with none), so this hit every such export on Windows, and `frameAt` the same. It now escapes two levels. Proven against the real ffmpeg 8.1.3: `ffmpeg-input-safety-real.test.ts` renders a timeline with and without a clip with `libx264` and reads the result back with ffprobe. Paths without a colon (macOS, Linux, the hosted image) were never affected, which is why it went unseen. It was the finding in `docs/internal/maps/edit-timeline.md` ("`escapeFilterPath` under-escapes a Windows drive letter"); the map now says fixed.
