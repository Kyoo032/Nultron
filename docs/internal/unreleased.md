- **Found, not fixed.** (1) `continue` replays no tool result: only `text`, `image_url` and `video_url` parts go back to the model (`modelHistoryParts`, `packages/core/src/content/transcript.ts:39`), so after either closing sentence the model reads the file again; the same limit applies to the step-limit sentence. ## Chat resilience: a failed tool, a tool that is off, the step limit, redaction and `self_check`, 2026-10-06 (both products; in the tree, not committed, not driven on a live model)

- **Every Chat request changes, on both products, and costs tokens.** Each turn now sends two more sentences in the system prompt (one for `self_check`, one on how to read a result with `ok: false`) and one more tool definition (`self_check`, with its description) in the tool list, on every desk, Personal and Enterprise alike. The Chat card written to the Knowledge Base is masked too; the assistant's own reply is not (a secret the model repeats stays in that thread), and the reasons are in SR-136. Opaque tokens with no known prefix are not caught.

Facts only (SR-137). Chat now binds 16 tools, with a cap of 4 calls a turn. With code runs off it does not hash the sandbox's files (`sandbox: "not_checked"`).

## 2026-11-06: backup.sh missed-run alert (BUG-19)

Lanes: enterprise.

- **What.** The hosted box runs `backup.sh` hourly from cron, and nothing said so when a run was missed or failed. The release bundle's `.env.example` is generated by `scripts/release-web.mjs`, which this change leaves alone, so the bundle does not list the variable yet.

## A Chat run claims its end before it saves the answer, 2026-11-06 (branch `fix/chat-run-settle-recheck`, Notion Dev Findings card 49)

Lanes: enterprise, tester.

- **What.** `persistAssistant` sets `finishing` before its first write, and the stall guard (`onStall`) and a closed connection (`onClientAbort`) do nothing once it is set (`packages/host/src/runs.ts:253`, `:272`, `:283`, `:332`). The watchdog and a closed connection can still end a run before it starts saving its answer, and the run's own path ends it after that.
- **Why.** The formal check of how a Chat run ends (`.cursor/skills/chat-run-settle`, PR #205) failed three properties under `--hazard`, a database driver whose writes yield, such as Postgres. The model answered, the host started saving the answer, the watchdog fired during the save and marked the row `failed`, and the save then landed. The person saw the answer and then `run.failed`, the run row said `failed` beside a saved answer, and a billed call could go without a usage row. It is not live today, because `packages/db/src/client.ts` uses `better-sqlite3`, whose writes never yield to a timer or a socket. It would have broken on the move off SQLite (open decision 1, K-D9).
- **Proof.** `node scripts/formal/chat-run-settle.mjs` passes at 44 distinct states, and `--hazard` now passes (74 states generated, 55 distinct). `--hazard --break ClaimOnPersist` and `--hazard --break CancelYieldsToClaim` fail the three properties again. The script reads `ClaimOnPersist` as true only when `finishing = true;` is the first statement of `persistAssistant` and no `await` sits between each `if (settled) {` and its `persistAssistant()` call. On scratch copies of `runs.ts`, moving the claim inside `if (persisted)`, or adding an `await` before any of the three calls, now fails the same three properties under `--hazard`. `packages/host/src/runs-settle-async-db.test.ts` holds the answer's save or the completed `finishRun` on a promise and fires the watchdog or a client abort during it. It failed all three cases before the fix and passes after.
- **Owed.** A driver that yields still needs a timeout on each write. After the claim the watchdog no longer ends the run, so a write that never returns would keep the stream and its run slot open. A write that rejects after the claim sends the run to the catch path, which calls `persistAssistant` again. The retry sends no second closing sentence, because `settleChatTurn` appends a note only when the text lacks it. If that retry also rejects, or the first rejection is the catch path's own save or a `finishRun`, the row stays `streaming` with no terminal frame, as it already did before this change on `better-sqlite3`. The usage writes are synchronous today. On a yielding driver their ordering is argued in the skill, not checked.
