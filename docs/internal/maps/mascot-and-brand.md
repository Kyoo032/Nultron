## Overview

The desk has one character, Nultron, shown wherever the product wants a face: the empty Chat hero, an empty studio, the onboarding hero, and, once there is work to watch, **the desk buddy standing in the rail** (section 7), or on a page stage when the page has one (section 7a), which is the one status character for the chat run, a running job, the first-run installer and updates. Where there is no buddy (no rail, a collapsed rail, another full body already on screen) a chip beside the job or the reply, the installer panel and the updates panel draw it as before. It is **a set of pre-rendered images**: an offline 3D scene (glossy clay, one fixed camera, transparent background) renders one still per state, a short one-shot clip for six states and a four-frame loop for thirteen working states; the app ships only those files (about 2 MB of WebP) and never a 3D engine. The scene's source is `tools/nultron-3d`, outside the pnpm workspace (see "Regenerating"). **What the character does is data** (21 states, one motion each, in `lib/mascot-states.ts`); which picture it shows is a file per state named by a manifest. **What a page loads is decided by its mount points**, not by the mascot: the Chat's first load fetches 3 of the 61 files (66 KB), and a strip is fetched when a pointer, a focus or a started job says it is about to play (section 2, "What loads, and when").

The product **logo** is a different thing and is on this page too (section 6): Rizky's painted Nultron head in a blue rounded-square tile, in the rail, the favicon, the splash, the Windows and macOS icons. The 3D head renders are the in-app mascot and are never the logo.

History that still matters: the character was first drawn by a flat vector rig (an SVG converted to React, poses toggled by data attributes) and a flat brand kit. The owner rejected the flat look on 2026-09-29 ("more 3D and realistic, following the reference image"); the 3D renders were approved the same day, and the SVG rig, its generator and the flat brand kit were deleted from the tree. See `Why`.

## How it works

### 1. One state table

`MASCOT_STATES` (`apps/web/lib/mascot-states.ts:8`) names the 21 states; `STATE_MOTION` (`:66`) says how each moves. The picture for a state is not in this file: it comes from `manifest.json`.

| motion | states | what it means |
|---|---|---|
| `still` | idle, sleep | no animation at all |
| `once` | wave, celebrating, error, surprised, love, lets-go | one finite clip of 600-1200 ms when the state is entered, ending on the still |
| `loop-busy` | thinking, writing, answering, searching, calculating, charting, reviewing, listening, painting, filming, editing, presenting, charging | loops, **only while `data-busy` is set**; without it the state holds its still. A body's four-frame strip steps in every shell; a head's small transform loop (nod, bob, swell) is smooth in a browser and stepped in the packaged app (§ 4, "Two shells") |

`MascotMotion` (`mascot-states.ts:64`) is the performance contract: the packaged Windows app has no GPU, so one running CSS loop costs a full software-composited frame sixty times a second. `isMascotBusy` (`:158`) is any placement but `empty` (a chip `beside` a job, or the `buddy`) and `loop-busy`; the component sets `data-busy` only when the caller also says a job is running (`busy`), because a dropped job stream leaves a working pose behind. `mascotStateFor` (`:174`) picks a job's state from its mode and phase, `MASCOT_MODE_HOME` is the state of an empty desk.

Four states are new on 2026-09-29: `surprised`, `love`, `charging`, `lets-go` (labels `common.mascot.*`, both locales).

### 2. The component

`NultronMascot` (`apps/web/components/nultron/nultron-mascot.tsx:64`) renders one root `<span class="chat-mascot nx-root">` carrying `data-testid="chat-mascot"`, `data-mascot="nultron"`, `data-state`, `data-motion`, `data-variant` (head | full), `data-clip`, `data-loop`, `data-placement`, `data-busy`, `data-mode`, and inside it `NxImageRig`. The root class and `data-busy` are what the desk's ambient pause and reduced-motion rules name (`app/globals.css:2640-2651`), so the root class stays.

- **Sizes.** `size` px below 64 draws the head picture, from 64 the body (`variantForSize`, `:28`; `NX_FULL_MIN`, `:19`). Default: `beside` a job 40 px, `empty` desk 72 px. `variant` picks the picture when the stylesheet sizes the box (the hero). Heads at 24 px cannot tell error from sleep: keep chips at 32 px or more.
- **`decorative`** makes the mascot silent to a screen reader (`aria-hidden`, no role, name or tooltip). Used where text next to it already says the same: the installer status region, the updates panel, job progress, the chat error line, the busy chip beside "Generating…" on Documents, Images, Music, Videos and Presentations (and beside Edit's export line), and the hero (the button carries its own name). The live Chat turn's mascot is not decorative today. Left off where the character stands alone: empty desks, onboarding.
- **Picture.** `NxImageRig` (`nx-image-rig.tsx:56`) draws the still (`full/<state>` or `head/<state>`) and, on the body only, the clip strip for a `once` state (`hasClip`, `nx-picture.ts:20`) or, **only while the mascot is `busy`**, the loop strip for a working state (`hasLoop`, `:25`): an idle body never mounts its loop, so it never fetches it (an empty desk's home pose is a working state that is never busy). Which files draw a state is `pictureUrls` (`nx-picture.ts:34`), shared by the rig and the warm-up. Each state is one keyed `NxArt` (`nx-image-rig.tsx:77`), because a CSS animation restarts only when its name changes or its element is new and two clip states share their animation names.
- **Never an empty box** (2026-09-29). Two rules, driven with every image request delayed 300 ms and with the HTTP cache off through CDP `Network.setCacheDisabled`: (1) a strip animates only under `.nx-art[data-sheet="ready"]`, set once the strip is loaded and decoded (`whenPaintable`, `nx-image-rig.tsx:18`, `img.decode()`) and the art's own still is painted, so until then the still stays and the clip starts late instead of playing over nothing (`nultron.css:135-163`); (2) the art of the state the desk was showing stays mounted as `.nx-held`, under the new art, until the new still can be painted (`NxImageRig`, `:56-75`; `nultron.css:50`). It is the same element and not a copy of its URL: with the cache off Chromium requests a URL again for every new `<img>`, so a second `<img>` of the old still is itself an empty box until it is refetched (17 blank frames, about 266 ms, in the first version's CDP drive; 0 in the final one). The cost of rule (1) is a few frames: with a warm cache a hover reaches the wave clip in about 120 ms and a tap the cheer in about 65 ms on webdev, where the ungated version took about 115 and 35 ms (medians of 6 runs each under other agents' load, so read them to within 20 ms). With the cache off and a 300 ms link the clip starts after the fetch (about 420 ms) and the still holds meanwhile.
- **What loads, and when** (2026-09-29; it replaced `warmStrips`, which fetched all 19 strips, 1.31 MB in 20 requests, on every page load that mounted a mascot, and none of the stills). `nx-warm.ts` fetches what a mount point says it can reach next, through `Image` objects it keeps (so the browser's in-memory copy serves a later `<img>` of the same URL), and never decodes them: a decoded strip is `frames x 320 x 320 x 4` bytes (5 MB for a clip, 1.6 MB for a loop, 48 MB for all 19), and painting decodes it. Two moves: `warmMascotAtIdle` (`requestIdleCallback` with a 2 s timeout, a 250 ms timer where there is none) for stills, and `warmMascot` at once for strips when an event makes them likely. A head has no strip, so `pictureUrls` gives a head its still only. Nothing warms at import or at mount except what a mount point asks for through the mascot's `next` prop (an effect, `nultron-mascot.tsx:87`).

  | mount point | stills, at idle (`next`) | strips, on an event |
  |---|---|---|
  | Chat hero | `wave`, `celebrating`, body (`HERO_NEXT`, `mascot-triggers.ts:96`) | both clips (290 KB) on the first `pointerenter`, `pointerdown` or focus anywhere on the hero section, which comes before the orb is reached (`chat-hero.tsx:57-68`) |
  | `MascotSlot` (`slotNextStates`, `mascot-triggers.ts:112`) | empty desk: home pose and `sleep`; chip beside a job: home pose, every pose a phase calls for, `celebrating`, `error` (heads, about 1 KB each) | none; an empty desk's own `wave` strip is fetched by its mount, and its still shows until the strip is ready |
  | live Chat turn | `lets-go`, `thinking`, `answering`, `error` (`LIVE_TURN_NEXT`, heads) | none: a 40 px chip is a head |
  | installer and updates panels | `celebrating`, `error`; `surprised`, `error` (heads) | none |
  | onboarding hero | `idle`, `love` (`ONBOARDING_NEXT`) | the `love` clip when the key step opens (`onboarding-screen.tsx:104-110`), one step ahead |
  | desk buddy | `celebrating`, `error`, `sleep` (`BUDDY_NEXT`, `desk-buddy-state.ts:60`; body stills, 64 KB) | the `celebrating` and `error` clips (270 KB) only once a run makes the buddy busy (`warmMascotAtIdle` with `sheet: running`); the wave, the tap reactions and a working pose's loop are fetched when they play, the still holding until the strip is ready |

  Measured on webdev, a cold load, `Image` requests for `components/nultron/images`: `/chat` **3 requests, 66,222 bytes** (was 20, 1,338,036), `/market` **4, 207,630** (was 22, 1,367,045; the `wave` clip is the one strip a mount needs). Renderer memory in a software-composited Electron 35 window (7 loads each, median): the old warm added 1.6 to 6.6 MB of private memory (median 2.3) to a renderer that had already settled, which is the 1.3 MB of encoded files and their bookkeeping; it never decoded a strip, so the "tens of MB" of decoded strips (a forced `decode()` of all 19 added 32 MB of working set) was never held by the warm itself, and it is what a strip costs once it is painted. A `warmMascot` after a hover of the hero costs the two clips' 290 KB and, once they play, their decoded frames.

### 3. The manifest and the files

`apps/web/components/nultron/images/manifest.json` (the contract with the 3D pipeline):

```
{ "version": 1,
  "full":  { "size": 512, "states": { "<state>": "full/<state>.webp", ... } },
  "head":  { "size": 256, "states": { ... } },
  "clips": { "<state>": { "src": "clips/<state>.webp", "frames": 10-14, "fps": 12, "size": 320 } },   // six once states
  "loops": { "<state>": { "src": "loops/<state>.webp", "frames": 4, "fps": 3|4|6, "size": 320 } },   // thirteen working states
  "bytes": 1993520 }
```

- The manifest is imported (`nx-image-manifest.ts:32`, typed and bundled), not fetched. `clipMs` / `clipBeats` (`:57`, `:62`) and `loopBeats` (`:67`) turn `frames / fps` into beats of `--motion-4` (`NX_BEAT_MS` 320), so every duration still comes from the desk's motion scale. A loop runs at the fps recorded for **that loop**; it is exactly 4 frames because `--ease-busy` is `steps(4)`.
- Files resolve through `import.meta.glob` (`nx-image-urls.ts:8`), not a `/nultron/...` path: the desktop shell loads the renderer as a `file://` document where an absolute path points at the disk's root, and the bundler puts a content hash in each name so a replaced render is never served stale. A production build turns each one into `new URL("<name>-<hash>.webp", import.meta.url).href`, so it resolves against the script, not the page (read from a `vite build` on 2026-09-29: all 61 files in `assets/`). The files therefore live in `components/nultron/images/`, not `public/`. `images/README.md` is the drop-in guide for the 3D team.
- The strips are static sprite sheets, moved with `transform` and `steps()`; nothing is an animated WebP.
- **Framing.** One fixed camera: the body is about 77% of the frame height in every `full/` image (74% for `listening`, 79% for `lets-go`, 83% for `charging`) and every boot sits on the same line, 86.7% of the frame, except `charging`, which stands on 93% (measured from the alpha channel of each file, 2026-09-29). A state change never makes the character jump, and nothing is re-cropped per state. The hero box therefore gives back 8% of its side at each end (`margin-block`, `app/globals.css:2426`; the rule opens at `:2420`): only transparent pixels sit outside the layout.

### 4. Motion in CSS

`components/nultron/nultron.css` holds the box, the hero drift, the strips and the fallbacks. Keyframes are named `nxm-*` (the desk already has `nx-rise`, `nx-pop`, `nx-wiggle` and `nx-bob`) and animate `transform`, `opacity` and the individual `rotate` / `translate` / `scale` properties. No filters.

- **Clip** (`once`, body with a strip): under `.nx-art[data-sheet]` (the strip is loaded and decoded), `.nx-strip` shows and `.nx-still` hides for `frames / fps`, the strip's image steps with `steps(frames, jump-none)` (`--nx-clip-ease`, `nultron.css:34`; rules at `:140-150`), then the still is back. The last frame equals the still.
- **Loop** (`loop-busy`, body with a loop, only under `[data-busy][data-loop]` and `.nx-art[data-sheet]`): the loop strip replaces the still and steps through its 4 frames, `steps(4)` with `--ease-busy` (`:153-163`).
- **Held art** (`.nx-held`, `:50`): the previous state's art, kept under the new one until its still can be painted. The rules above key on the root's attributes, which are the new state's, so the held still cancels its own animation (`animation-name: none !important`) and shows at opacity 1; it has no strip and no `data-sheet`.
- **Fallback** for a state with no strip, or a head (under 64 px, which has neither): a small percent-based transform on the still (hop, tilt, throb, lean; bob, nod, swell while busy), guarded by `:not([data-clip])` / `:not([data-loop])` (`:250` on). Every fallback clip starts and ends on the identity.
- **Hero drift**: the whole picture moves a few pixels with `--px` / `--py` (written on the hero by `attachHeroMotion`), transform only (`:55-67`). The old eyes-follow-the-pointer is gone with the SVG rig: there are no eyes to move.
- **Two shells, two timings (2026-10-05).** The packaged Personal app has no GPU (`app.disableHardwareAcceleration()`, `apps/desktop/main.cjs:829`), so every running loop costs software-composited frames there; a browser (webdev, the hosted Enterprise app) has one. `main.tsx` calls `applyDeskShell(document.documentElement, isElectron())` (`lib/shell-motion.ts`) before the first render and writes `data-shell="desktop"` in the packaged shell only (`"browser"` everywhere else; only `lib/desktop-bridge.ts` reads `window.agentforge`). The loops are declared once and read tokens: `app/globals.css` `:root` holds the browser's (smooth: `--ease-ambient: ease-in-out` for the shapes' bob, `--ease-ambient-steady: linear` for the shapes' turn and the dot grid's drift, `--ease-busy-move: ease-in-out` for the working dots and the head's nod, bob and swell; the cycles are shorter, a bob 4 s, a turn 8 s, the drift 12 s a tile, amplitudes unchanged) and `html[data-shell="desktop"]` hands back exactly what the stepped desk shipped with (`steps(8)`, `steps(8)`, `steps(4)`; 6.4 s, 12.8 s, 19.2 s on the 400 ms grid). `--ease-busy` is `steps(4)` in both shells and is the **frame strips'** token (`.nx-loop img`, and `--nx-clip-ease` for a clip): a picture moves one frame at a time whatever the shell, and a busy body's loop is still four frames at the manifest's 3 to 6 fps. Every brake is shell-independent: `html[data-ambient="paused"]`, `[data-busy]`-only busy loops, reduced motion. Driven on webdev (headless Chromium, 1280 x 800, `/documents`, every animation frame for 4 s): before, each shape and the grid changed value 2.5 times a second (every 400 ms, 1 px or 1 degree; the turn 11.25 degrees; the grid 1.25 times a second, 1 px); after, about 50 to 57 times a second, a different value every frame (at most 0.34 px, 2.3 degrees and 0.1 px between frames); with `data-shell="desktop"` set in the page the old numbers come back exactly. `lib/motion-shell.test.ts` holds both sets of values and that every loop's token resolves to a step function under the desktop shell. **Cost:** the animations run on the compositor (main thread 0.2 to 0.9% either way), but one running loop makes the page produce 60 frames a second. Headless Chromium on this machine, CPU summed over every process, percent of one core, median of 3 runs of 8 s on `/documents`: smooth 42%, stepped 15%, paused (12 s idle) 1.5% with the real GPU compositing; 93%, 5% and 0.1% with `--disable-gpu` (the software path). Which loops run barely matters (GPU run, 2 runs each: with the grid off 37 to 49%, with the shapes off 37 to 45%, all smooth 45 to 52%, no ambient loop 14 to 17%), so the cost is producing 60 frames a second and not the number of elements. See `Why`.
- **Reduced motion** removes every animation and transition and keeps the picture (`.chat-mascot, .chat-mascot * { animation: none }` in `nultron.css` and in the global block at `app/globals.css:2685-2691`). A busy body would otherwise show frame 0 of its loop strip in place of the still, so the same block puts the still back under `[data-busy][data-loop]` (`nultron.css:311-330`, with `!important` because the swap rules above wait for `.nx-art[data-sheet]` and are more specific); driven on 2026-09-29 with real `reducedMotion` emulation: hero tap, a `once` desk state and a forced-busy `writing` body all showed the still and ran no animation.

Every loop is under `[data-busy]`, so the desk's ambient pause (`app/globals.css:2640`, everything not busy) and its hidden-window pause (`:2648`, busy ones too) reach it through `.chat-mascot`. `lib/nultron-motion.test.ts` holds the contract; `lib/motion-tokens.test.ts` reads `nultron.css` as well for its infinite-loop and stepped-loop checks.

### 7. The desk buddy

Owner, 2026-10-01: "make Nultron the real mascot instead of just an icon on the app". He chose a **desk buddy** (a full-body Nultron always on screen that reacts to the whole app) and the character back on the empty desks (section 5 and `StudioEmptyDesk`).

**Where it stands: the rail.** The first plan was a corner of the desk pane, and it was measured before it was built (an 88 x 96 box 12 px in from the bottom-right, bottom-left and top-right corners of the visible desk pane, at 1440x900, 1366x768, 1280x800, 1100x800 and 1024x768 on 19 routes, 95 route and width pairs, landing states). The bottom-right corner was free of text, controls and cards in 56 of 95; **Chat, Images, Knowledge, Legal, Market and Usage in none of their 5 widths** (Chat's composer and Send fill it at every width); every page is full width, so there is no gutter either: 13 of 95 had 100 px or more of slack to the right of the content. A character floating there would sooner or later lie on a control, and a page that scrolls (every desk page but Chat and Edit) moves its content under whatever is fixed to the pane. The rail is the one place nothing else is: its list ends where its last row ends, and what is left under that is empty by construction.

- `DeskBuddyDock` (`components/desk-buddy.tsx`) is the last child of the rail's list, after the pinned Account group (`app-rail.tsx:445`). It is a flex child that takes only the room the last row leaves over, `flex: 1 1 0` with `min-height: 0` and `overflow: hidden` (`desk-buddy.css`), so it is 0 px tall when the list scrolls and can never push a row. A `ResizeObserver` reports its height and width (`setBuddyRoom`); `buddyView` (`lib/desk-buddy-state.ts:105`) turns that into a body of 56 to 96 px (`BODY_MIN`, `BODY_MAX`, minus `BODY_GAP` 6 px, and never wider than the list less 16 px), standing on the footer's line, or nothing.
- `DeskBuddyChip` (`app-rail.tsx:462`) is the answer when there is no room for a whole body, or the person made it small: a 32 px head in the footer row, between the theme control and the rail's right-hand controls, in flow like them. It never squeezes anything, and 32 px is the size where `error` and `sleep` can still be told apart.
- **Room, measured 2026-10-01** (rail rows are 28 px under 940 px of window height, 32 px above, `app/globals.css`): 1920x1080 a 96 px body, 1440x900 a 61 px body (67 px of room with three recent sessions; four, or an open Finance or Market sub-list, or a window of 800 or less, gives the chip), 1366x768, 1280x800, 1100x800 and 1024x768 the chip. The rail is the same width at every window width, so the answer depends on height only.
- **Hidden, not squeezed:** a collapsed rail (the icon rail, always under 481 px) has no dock, so a phone layout has no rail buddy (a Chat thread still has the composer's stage, section 7a); a page stage on screen takes the character off the rail (7a); and any full-body character on screen stands it down (below). Where nothing holds the status the inline chips come back.
- Placement proof (a Playwright script, kept outside the repo; the method is in `features/mascot.md`): for every route and size the buddy's box is read from the DOM and compared with every visible text node, control, card, image and bordered or shadowed box on the page; it must intersect none, lie inside the rail and the viewport, and be what `elementFromPoint` returns at its own centre.

**One character on screen.** Every `NultronMascot` that draws the body (64 px and up) and is not the buddy announces itself (`useFullBodyPresence`, an `IntersectionObserver`: a pane kept mounted and hidden is `display: none` and does not intersect, a character scrolled out of its pane stops counting, 25% must show). While any is on screen the store is `suppressed` and the dock draws nothing; when the last leaves the buddy steps in after 350 ms (`BUDDY_RETURN_DELAY_MS`), so a hero that remounts (the desk id arrives about 300 ms after load) never shows two for a frame. `takesStatus` is the other flag and ignores that wait: it is true as soon as a dock is mounted or a page stage is on screen (section 7a) and no full body is on screen (`desk-buddy-store.ts:115`), and it is what makes a chip beside a job (`MascotSlot`), the live turn, the chat error line, the installer panel and the updates panel stand down, so the empty desk's character leaving and a job's chip appearing never overlap by a 350 ms flash of a head.

**What it is told** (`lib/desk-buddy-store.ts`, a module store read with `useSyncExternalStore`; `pickClaim` and `runReaction` in `desk-buddy-state.ts` are pure and tested):

| source | speaks | how |
|---|---|---|
| the chat run (`ChatTurn`, `ChatSession`) | `lets-go` (first turn, 900 ms), `thinking`, `answering` busy; a cheer when the reply lands (1.8 s), a flinch on a failure | claim from the live turn; flash from `useChatBuddyReactions` |
| a job (`MascotSlot` beside, `useJobStream`) | the phase's pose busy (`mascotStateFor`: searching, writing, calculating, charting, reviewing, listening, painting, filming, editing, presenting); a cheer or a flinch when it ends, none for a cancel | claim while running; `useBuddyRunEnd` in `useJobStream` |
| the first-run installer, a downloading update | `charging` busy; `celebrating` or `error`, `surprised` once an update is ready | `useBuddyStatus` in `useComponentSetup` and `AppUpdatesButton`, panel open or not |
| the gateway gate (`GATE_EVENT`) | `surprised` once when the host reports model calls blocked | `DeskBuddyReactions` |
| the first-run tour | `presenting` while the guide is open (the card keeps its own head) | claim at the guide's priority |
| arrival | `wave` when the buddy steps into view and on the first visit of each mode, at most one in 20 s | `DeskBuddyReactions` |
| a tap | `love`, `lets-go`, `celebrating`, round again | `tapBuddy` |
| the window idle-paused (`data-ambient-reason="idle"`) | `sleep`, when nothing else is claimed | `useAmbientReason`, read only |

A flash (a finished job, a tap) speaks over every claim for 2.4 s (`FLASH_MS`); among claims the order is installer and updates (70), job and chat run (60), tour (40), and `?buddy=<state>&buddyBusy=1` (100, a drive hook) over all.

**It moves like the other status characters, and costs no more.** `placement="buddy"` is busy-capable (`isMascotBusy`), so for the first time a body-size four-frame loop is visible to a user: the buddy's loop mounts only while a claim says work is running, exactly as an empty desk's does not. Idle it holds the still (`sleep` and `idle` have no animation); an idle-paused window freezes any clip (`html[data-ambient="paused"]`), and busy loops stop only when the window is hidden. The picture leans up to 3 x 2 px toward the pointer (`--px`, `--py` written on the buddy by `useBuddyLean`: fine pointers, not under reduced motion, not while paused; the desk's own `--px` lives on `.desk-canvas`, a sibling of the rail, so it does not reach here). Measured in Chromium with `--disable-gpu`, CDP `SystemInfo.getProcessInfo` summed over the browser, renderer and GPU processes for 10 s (percent of one core): at rest the buddy is not measurable: 4.9% as a sleeping body and 6.0% as a chip, against 5.4% for the Chat hero page with no buddy (window idle-paused, 15 s without input first); awake and still, 14.1% (body) and 18.4% (chip) against 18.7% for the hero page, which is the desk's own pointer light and parallax and not the buddy; with a faked research job running and the window idle-paused (the status character keeps moving) 28.8% as a body and 17.6% as a chip, against **37.2% for the 40 px inline chip it replaces** (the same job with the rail collapsed). A first run on a busy machine read 5.7 / 5.4 / 5.3 (rest) and 28.4 (inline chip), so read the awake and busy figures to within about 5 points. A working loop is the expensive thing in a no-GPU window, 12 to 32 points over rest, which is why it exists only under `data-busy`; the buddy does not add one, it moves the one that was already there (the 2026-09-29 perf entries are in `docs/internal/unreleased.md`).

**Accessibility.** The character is `decorative` (`aria-hidden`); a button around it, `desk-buddy-tap`, carries the name (`common.buddy.tap`) and rotates the reactions; `desk-buddy-minimise` (a quiet corner control, shown on hover and focus) makes it a chip, remembered per viewer in `localStorage` (`nultron.buddy`, wrapped in try and catch); the chip is a button too and, once made small by the person, brings the body back (`common.buddy.restore`). Every word is in both catalogs.

## Regenerating

Both sources are in the repo. Neither needs Python, and neither needs anything installed by hand beyond `pnpm install` (for Electron) and, for the mascot, one `npm ci`. Read `tools/nultron-3d/README.md` before changing the character.

**The mascot images.** From the repo root (Windows; about 30 s for the render):

```
cd tools/nultron-3d
npm ci
node render-all.mjs --out <dir>       # full/, head/, clips/, loops/, brand/, manifest.json
node verify-out.mjs <dir>             # files present, strip sizes and alpha as advertised, bytes add up
node sync-images.mjs <dir> --check    # what would change in components/nultron/images/, and the app's own contract
node sync-images.mjs <dir>            # copy what differs, delete what the manifest no longer names
node --test "poses/test/*.test.mjs" "test/*.test.mjs"
```

A re-render is close to the shipped images, not identical: mean 0.9 of 255 per channel over the character's pixels, at most 0.9% of those pixels off by more than 16, alpha within 1 (`node compare-images.mjs <dirA> <dirB>`). Two renders of the same scene differ by the same amount because the ambient-occlusion pass draws its noise from `Math.random()`; `scene-main.js` seeds it now, which makes about 50 of the 61 files byte-identical between runs. `poses.json` and `dims.json` do regenerate byte-identical (`node poses/build-poses.mjs`, `node gen-dims.mjs`). Sync only when the scene changed on purpose.

**The logo files.**

```
node apps/desktop/scripts/brand-icons.mjs --out <dir> --check    # regenerate into <dir>; exit 1 if a repo file differs
node apps/desktop/scripts/brand-icons.mjs --out <dir> --apply    # the same, then write the differing files over the repo's
node --test apps/desktop/scripts/brand-icons.test.mjs apps/desktop/scripts/brand-logo-cut.test.mjs
```

`--png-src` defaults to `docs/internal/brand/nultron/reference`. With only `app-logo.webp` there, the script decodes it in Electron (byte-identical to a Pillow decode), cuts the tile out of the white corners (`brand-logo-cut.mjs`; written to `<dir>/source/app-logo-cut.png`) and derives everything from that. It then compares the 15 repo paths in `REPLACEMENTS` with the kit's files. On 2026-11-06 `brand-icons.mjs --out <scratch> --check` from the new default folder gave 14 identical, 0 differ (the 15th row is the optional, untracked `apps/desktop/logo.png`, absent in a clean checkout). The 2026-09-29 run from the repo's own master, before the six rows under the deleted desktop kit were dropped, gave 21 of 21 byte-identical: the three 256 px `logo.png` files are `mark/mark-256.png`, the 1024 px `build/icon.png` is `replace/logo-1024.png`, the four `brand-art/mark-*.png` are `mark/mark-{24,32,48,64}.png`, `favicon.ico`, `favicon-32.png`, `favicon-180.png`, the two `icon.ico` and the one `icon.icns` are the kit files of the same name, and the untracked `apps/desktop/logo.png` (160 px) is `replace/logo-160.png`.

## Gotchas

- **`.chat-mascot` and `data-busy` are a contract with `app/globals.css`.** The ambient pause, the hero's off-screen pause and the reduced-motion block name them. A wrapper class in place of the root, or a loop outside `[data-busy]`, silently runs on an idle desk (`lib/motion-tokens.test.ts` and `lib/nultron-motion.test.ts` fail).
- **`:is(a, b)` in a loop rule breaks the loop audits**, which split selectors on commas. Write two selectors.
- **A head chip has no clip and no loop**, only the small transform motion. Working chips nod, bob or swell; the richer strips are on the body (64 px and up).
- **The hero's height budget is real, and its numbers are owed.** At 1280 x 800 the empty Chat has little room. Measure `[data-testid="message-list"]` `scrollHeight - clientHeight`. The figures taken on 2026-09-29 (0 at 800, 860, 900, 940, 960 and from 961 up; 14 px at 780, 34 at 760, 21 at 901) were for the card hero, with the status pill under the headline and a character 60 to 68 px on a side at small heights. The 2026-10-01 scene replaced both (the character is at least 96 px on a side and the status sits in the bubble), so none of them holds; re-measure before quoting one (`features/chat.md`, "Hero"). The height tiers are in [`chat-send.md`](chat-send.md) § 9.
- **Assets are bundled.** `import.meta.glob` includes every file in `images/` in every build (about 2 MB); a file the manifest does not name fails `lib/nultron-images.test.tsx`. Bundled is not loaded: the page requests only what `nx-warm.ts` and the mounted art ask for.
- **A new mount point declares what it can reach.** Pass `next` (a stable array: an effect depends on it) or call `warmMascot` on the event that makes a strip likely; do not add a page-wide warm-up. `lib/nultron-warm.test.tsx` fails a rig that warms everything or a hero that warms on mount.
- **With the cache off, a new `<img>` fetches again.** CDP `Network.setCacheDisabled(true)` (DevTools "Disable cache") makes Chromium request a URL for every new `<img>`, warmed or not. That is why the held art is the same element and why a clip starts after its fetch in that mode. Measure blank frames per animation frame (any visible, loaded image layer), not with screenshots.
- **Busy loops have a live body now: the desk buddy.** Loops are drawn on the body and busy needs a placement that is not `empty`; the buddy (`placement="buddy"`, 56 to 96 px) is the one body a user sees loop, while a chip beside a job is still a head. `/meeting?mascot=<working state>&mascotBusy=1` (`mascot-slot.tsx`) still forces a 72 px body beside a running job, and `?buddy=<state>&buddyBusy=1` holds the buddy in a state. Setting `data-busy` from the console does not work: the loop is mounted by React only while busy.
- **The buddy is in the rail, so it is not under `.desk-canvas`.** The desk's `--px` / `--py` and pointer light are written on the canvas and do not reach it; the buddy writes its own. A page that wants to know whether the buddy is showing reads `data-testid="desk-buddy"` (body) or `desk-buddy-chip`, and `desk-buddy-dock`'s `data-view` (`body`, `chip`, `none`).
- **`takesStatus` is not `view !== "none"`.** The first ignores the 350 ms wait before the buddy steps back in, on purpose (a chip beside a job must not flash up for that long); do not "simplify" the two into one.
- **Hooks cannot be driven in the node tests.** `useSyncExternalStore` renders its server snapshot there, so `renderToStaticMarkup` always draws the chip beside a job: the routing is held by the store tests and by source checks in `lib/desk-buddy-wiring.test.tsx`, and proved live (features/mascot.md).
- **No eyes-follow, no blink.** Both belonged to the SVG rig. If the 3D team ships a blink frame, the idle timer that existed (a 130 ms flicker every 4 to 6 s, skipped while the window is idle-paused) can return as a one-shot class on the still.
- **Hero and `--px`/`--py`**: the hero writes them on `.chat-hero`; touch and reduced motion leave them unset, so 0.

## Why

- **Images, not a live rig.** [Direct] Owner, 2026-09-29: the flat vector look was rejected ("it should be more 3D and realistic, following the reference image"); a three.js scene rendered offline to WebP was approved. The app ships images only. Source: the 3D team's `CONTRACT.md` and the coordinator's hand-off for this change.
- **Timer and loops from files, not CSS filters or a rig.** [Direct] The perf pass of 2026-09-29 measured that on the win32 build (hardware acceleration off) a single running loop costs a software-composited frame per tick; idle-visible `/chat` CPU was 0.10 with every loop paused. Source: `docs/internal/unreleased.md` (2026-09-29 perf entries).
- **Files beside the code, not under `public/`.** [Inferred] The desktop shell loads the renderer with `mainWindow.loadFile` (`apps/desktop/main.cjs`) as `file://`; an absolute `/nultron/...` URL would resolve to the disk's root there, while `import.meta.glob` assets resolve against the bundle. Not proven on a packaged app.
- **The flat brand kit and the SVG rig were built and deleted the same day.** [Direct] Nothing of them is in the tree. The logo that replaced the old chevron is the owner's own painted tile.
- **`logo.png` is 256 px, not the 1024 px the kit's map names.** [Inferred] The brand kit's `replacements.json` points the display logo at a 1024 px, 1 MB file. Its consumers draw it at 24 to 88 CSS px (the portal at 24, the splash at 88): the packaged preload reads it and inlines it as base64 on every launch (`apps/desktop/brand-read.cjs`; 1 ms measured, see section 6), and the portal serves it for a 24 px image. `mark-256.png` is the same art at 256 px and 110 KB, about what the old file weighed. The 1024 px tile is kept where it is the source: `icon.png` and the `.icns`.
- **The rail mark is imported, not served from `public/`.** [Inferred] Same reason as the mascot files: an absolute `/brand/mark-24.png` would resolve to the disk's root in the packaged `file://` renderer. The favicon set is in `public/brand/` because `index.html` links it and the build rewrites those links.
- **What a page loads is what its mount points can reach, not the whole set.** [Direct] The 2026-09-29 verification pass found `warmStrips` fetching 19 strips (1.31 MB) on every load, the hosted app included, while the first change of state could still draw an empty box for a round trip. Measured the same day (webdev, cold load): `/chat` 20 image requests and 1,338,036 bytes before, 3 and 66,222 after. Source: `docs/internal/unreleased.md`, 2026-09-29 mascot entries.
- **The previous art stays mounted; a strip waits for itself.** [Direct] With the cache off through CDP, a second `<img>` of the old still was an empty box for the whole fetch (17 frames at a 300 ms link), and a clip whose strip was still loading hid the still over nothing. The fix keeps the old element and starts a clip only when its strip is decoded. Source: the drive scripts of 2026-09-29 (blank frames counted per animation frame). [Inferred] that this also holds on a packaged `file://` desk, where the fetch is a disk read; not driven there.
- **The chips beside "Generating…" are decorative; a body's loop mounts only while busy.** [Direct] A screen reader announced the character's name beside the status that already said it; an idle body fetched a loop it could never show (an empty desk's home pose is a working state that is never busy).
- **The buddy stands in the rail, not over the desk.** [Direct] Owner, 2026-10-01: a desk buddy that is always on screen, then "please still be careful trying to fit the desk buddy on the app". [Inferred] from the survey in section 7 that a desk corner is free on 56 of 95 landing states and on none of Chat's, and a scrolling page moves content under a fixed character; the rail's spare room is empty by construction, measured, and costs the desk nothing. The price: on a window under about 900 px high it is a 32 px head, not a body.
- **The inline status heads give way to it.** [Inferred] "One character on screen" (coordinator, 2026-10-01): with the buddy as the status character a second Nultron beside the live reply or the job's progress list would be two. The text status stays where it was. Without a buddy they draw as before, which is also what keeps `generate-chip-mascot.test.tsx` and the preview hooks meaningful.
- **Smooth in browsers, stepped in the packaged app.** [Direct] Owner, 2026-10-05: "smooth the Nultron animation", the idle motion looked low-frame-rate and slow when not hovered. [Direct] orchestrator decision the same day: the packaged Personal app disables hardware acceleration, so a smooth loop there is software compositing, and the owner's 2026-10-01 exception was granted on the strength of the stepped cost (about 3.4% CPU on an active Chat); browsers have the GPU. So one stylesheet, two token sets, and `<html data-shell>` picks. [Direct] Measured (above, § 4): the smooth set costs about 27 points of one core more than the stepped one with a real GPU in headless Chromium and about 88 more under software compositing, and almost nothing on the main thread. Experiment, same machine and method, the smooth loops with ad-hoc step counts (GPU compositing, median of 3): 60 fps 41%, 30 fps 31%, 20 fps 24%, 15 fps 23%, no ambient loop 15.5%; so a 20 to 30 fps step count would keep most of the look at 40 to 65% less of the extra cost. Not adopted: the owner asked for smooth and the decision was smooth. [Inferred] that the packaged app's numbers follow the stepped ones measured on 2026-10-01; the packaged app has not been packed or driven with this change, so the desktop half is proved by the declared tokens and a browser with `data-shell="desktop"` set by hand, not by `Nultron.exe`.
