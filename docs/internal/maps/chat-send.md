## Overview

One user turn in Chat: text in the composer, Enter, an assistant answer streaming into the transcript. The path crosses four layers â€” renderer, transport (HTTP or Electron IPC), host run orchestrator, core runtime â€” and everything the user sees between "Send" and the finished message is a server-sent-events stream of `RuntimeEvent`s. On the way the model may call tools. The default Chat agent binds 17 tools and one generalist worker at run time (Â§ 3a); each call is a `tool.started` and a `tool.completed` frame on the same stream, and the transcript shows them as rows inside the Thinking disclosure (Â§ 6).

The thing to hold onto: **the streamed text is not what ends up on screen.** The deltas paint a live bubble; when the run completes the renderer throws that state away and re-fetches the thread, so the persisted database copy is what the user actually keeps.

### 3. Host: gate, then run

`packages/host/src/router.ts:333` maps `POST /api/v1/threads/:threadId/runs/text` to `handleRun` (`packages/host/src/handlers/runs.ts:43`); the image and video routes are the next two lines. **What the outbound guard does not catch (accepted, 2026-10-13 review).** Each is a residual of SR-112 / SR-166, not a bug to fix in passing:

- A model that restates a private fact in other words, or translates it, is not matched.
- A private phrase split across two or more queries, each under five words, is not matched.
- A figure spelled out in words, or a round amount ("two million", "5 juta") is not a figure to the matcher.
- A private name or phrase under five words is not matched; a span needs five words and three that are not stopwords.
- A single figure of three to five digits is allowed; only two such figures together, or one of six digits or more, count.
- Earlier assistant turns are not indexed as private: what the model wrote in an earlier turn is neither the person's words nor registered private text.
- A poisoned page can use up the turn's two counted refusals on purpose, after which search stops for that turn (L2). The person can ask again in a new turn.
- A credential or a blob the person pasted into their own message is exempt from the shape rules (M5), so a key the person typed can reach a search provider if the model searches for it.
- A host named in an attached file may be opened by `web_fetch`; an attachment is not the person's words, so a poisoned file can name a host. The address is still checked for private text.
- A job that passes no `outbound` treats its whole prompt as private and nothing as typed. Market passes its question and nothing private (its packet is public market data). The Edit agent registers its project's text, including earlier clip prompts the person wrote, as private, so a search that repeats an earlier Edit request word for word is refused.
- A media URL from an earlier turn is not remembered (the media store keeps no source URL), so a source image for `image_generate` or `video_generate` must be generated in this run, returned by a search in it, or typed or re-attached by the person.

### 5. The watchdogs â€” there are three

One rule, `streamWatchdogDeadline` (`packages/core/src/runtime/stream-watchdog.ts:88-97`), used by three separate instances:

**A fourth timer, in front of those: the response-header limit.** `fetchWithHeaderTimeout` (`packages/core/src/runtime/ai-sdk-runtime.ts:132`) wraps each of the three wire fetches. A live drive measured `gpt-6-luna` taking 15.1 s to send headers on both calls of a Word-file turn with Thinking Off (HTTP 200 each time), so the old limit cut the run three times and the person got "Could not reach gpt-6-luna after 3 tries" 30 s after Send. `HEADERS_TIMEOUT_MS` (`stream-watchdog.ts:243`) is now 45 s: three times what was measured, and three quarters of `STREAM_IDLE_MS`, because on a follow-up call after a tool the idle watchdog above is already counting and this must fire first. It is not keyed on Thinking, since the measured case had it off. A request that times out is not retried (`isRetryableModelFailure`, Â§ 4): the person waits 45 s once on a dead gateway, where they waited 3 Ã— 10 s, and gets `No response within 45s from <model> (timeout). Try a smaller prompt, another model, or send again.` (`formatHeadersTimeoutError`, `stream-watchdog.ts:251`, in both languages; before any tool it is the `run.failed` message, after a tool it is the reason in the closing sentence of Â§ 3b). A refused or dropped connection fails at once and is still retried three times. Proof: `ai-sdk-runtime-header-timeout.test.ts` (fake clock, real AI SDK, a `fetch` that answers after a chosen time and honours the abort). Not covered: a model that needs more than 45 s to send headers.

**Gotchas.**
- The hero's pause rule, `.chat-hero[data-paused="true"] .chat-hero-panel :is(.chat-mascot, .chat-mascot *)` (`globals.css:2541`), is (0,4,0) and has no `!important`, so a rule with an `animation` shorthand of that weight or more resets `animation-play-state` and restarts what it paused. ## Gotchas

- **A completed run now writes twice.** `runs.usage` still carries the per-run detail on the run
  row; `recordChatRunUsage` (`packages/host/src/runs.ts:698`, and `:751` on the mid-stream error
  path) also writes a `tenant_usage` row, gated on `finishRun`'s return so one run is exactly one
  row. A run the watchdog or a closed connection ended is metered once by `meterSettledRun`
  (`:334`) when the gateway billed it. Anything summing both double-counts chat. See [`tenant-usage-ledger.md`](tenant-usage-ledger.md).

- **The 2026-09-06 changelog block is stale in three places.** It says "Watchdog 60s idle if no events after start" â€” the budgets are now a model-aware TTFB/idle pair and the TTFB half is a hard cap. It names `chat-send` / `chat-probe` / `chat-fail-closed` as if they were testids â€” they are **sub-feature names in the verify skill**; there is no `data-testid="chat-send"` anywhere in `apps/web`. And it names `coerceReasoningEffortForModel` as a live step in the wire path; it is not one any more.
- **`coerceReasoningEffortForModel` is dead on this path.** It is implemented, exported from `packages/core/src/index.ts:374` and unit-tested (`packages/core/src/models/reasoning-effort.test.ts:101-109`, `packages/core/src/models/model-policy.test.ts`), but a grep at this sha finds no call site in product code outside its definition and the re-export. The "GPT-6 cannot go Off" behaviour it encodes (for Astra and any GPT-6 id the table does not list; Luna and Sol take Off) is achieved independently by the policy table's allowlist (`packages/core/src/models/model-policy.ts:37`, read through `packages/core/src/runtime/effort-allowlist.ts`); since 2026-09-30 both read the same entry, so the two can no longer disagree.
- **The composer sends a level only once the person has picked one (since 2026-09-30).** It used to post `reasoningEffort` on every send from a state that started at `medium`, so "chosen" was always true from Chat and an id the policy table does not know was always sent the picker's level. Now `ChatSession` starts at Normal with `reasoningChosen` false (`apps/web/components/chat-session.tsx:85`, `:90`) and the composer spreads `thinkingRequestFields(reasoningEffort, reasoningEffortChosen)` into the body (`chat-composer.tsx:421`, `:488`), which is `{}` until a pick. What the picker shows is unchanged. A level picked earlier is restored from `localStorage` as chosen (`readStoredThinkingPref`, `chat-thinking.ts:39`), because only the picker writes it. Consequence to know when driving: a **fresh browser profile** sends no `reasoningEffort` until Thinking is touched, so an unknown model gets no effort parameter; a known model still gets `medium`, unchanged on the wire. See [`model-policy.md`](model-policy.md) Â§ 3.
- **A partial answer is almost never kept, and a saved answer is never failed.** On abort or stall, `settleRun` (`packages/host/src/runs.ts:259-267`) sets `settled` and marks the run failed. Each exit that could save an answer checks `settled` first and, when it is set, meters a billed call and returns without saving: the `run.completed` handler (`:597`), the check after the model call (`:688`) and the `catch` (`:740`). Whatever the model streamed is discarded. When one of those exits does go on to save, `persistAssistant` claims the end of the run first (`finishing = true`, `:342`). From then on `onClientAbort` does nothing (`:295`), and `onStall` never settles the run (`:277-286`). So the watchdog or a closed connection cannot mark a run failed while its answer is being saved, even on a database driver whose writes yield. The watchdog still ends the person's stream while the claim is held, so a save that never returns cannot leave the composer on Running. It closes the queue and leaves the row to the run's own path. Before the answer is saved, it sends `run.failed` with the `saveTimeout` sentence (`chatTurnCopy`, `packages/core/src/agents/chat-locale.ts`), unless the model already sent one, and then `run.completed`. After the answer is saved, it sends nothing. A save that lands later still leaves a `completed` row with its answer and one usage row. A client that left during the claim leaves the watchdog armed, so its stream ends the same way one stall window later. The formal check [`.cursor/skills/chat-run-settle`](../../../.cursor/skills/chat-run-settle/SKILL.md) proves this for both drivers (`--hazard`), and `packages/host/src/runs-settle-async-db.test.ts` holds the save and the completed `finishRun` on a promise while the watchdog or a client abort cuts in. A model that streamed part of an answer and then failed still saves that text and ends `completed`, as before.
- **The renderer's own watchdog never leaves first-token mode.** `readRunStream` is given `onActivity: () => dog.touch()` and nothing else (`apps/web/components/chat-composer.tsx:492`, `:558`); `touchOutput()` is never called on this path. Since `streaming` only flips in `touchOutput`, the client-side deadline stays `startedAt + ttfbMs` for the whole run, and repeated touches re-arm a timer that fires at the same instant. A genuinely long, actively-streaming answer can therefore be aborted client-side. The host-side guards do call `touchOutput` (`packages/host/src/runs.ts` via `isRunOutputEvent`), so this asymmetry is renderer-only. **Treat as a finding, not a design.**
- **`gateway_blocked` is handled in Chat only on the hosted text route.** The host emits it as a flat body with `error` as a *string*, precisely so `parseGatewayBlocked` (`apps/web/lib/gateway-gate.ts:172`) can read it. The text route now reads it through `hostedGatewayBlocked` and shows the catalog sentence (`apps/web/components/chat-composer.tsx:428`; `apps/web/lib/gateway-blocked.ts:19` returns `null` off the hosted build). The image and video route still does `payload?.error?.message ?? t("chat.error.runFailed")` (`:494`), and `.message` on a string is `undefined`, so a blocked gate there, and on the Personal app on either route, shows the generic "run failed" copy. On Personal a closed gate is onboarding, so it shows only if a verdict expires while a desk is open. **A finding, narrower than before.**
- **Probing has no UI.** `ChatComposer` declares an `onProbing` prop with an `attempt` / `attempts` / `message` payload (`apps/web/components/chat-composer.tsx:45`) and never calls it â€” `run.probing` is handled by calling `onStarted()` and dropping the payload (`apps/web/components/chat-composer.tsx:163-165`); `ChatSession` never passes `onProbing` either. The locale string `chat.error.couldNotReach` exists in both catalogs with zero references. This is why `features/chat.md` requires that probe copy must *not* appear on the frontend â€” it cannot.
- **A stub Chat send never shows a file, knowledge or code row.** `StubRuntime` runs `calculator` and `datetime` only, so the rich tool rows (Â§ 6) appear only on a keyed desk with a live model. `features/chat.md` and the Files and Folder recipes say which scenarios need a key.
- **Chat's tool rows are inside a closed `<details>` once the turn lands.** `message-tools` and `message-tool` stay in the DOM, so a count passes and a visibility check fails; open `message-thinking` first. `tool-row-code-source` is a second closed `<details>` inside a code row.
- **`message-output` mounts twice per turn**, once live and once persisted, in different component subtrees. A test that waits on the testid can observe two mount cycles for one message.
- **Three watchdogs, different semantics.** The inner one is retried; the outer one is not. The outer guard is touched by *every* event including `run.probing`, so it mostly protects against total silence rather than against a retry loop.
- **The race between watchdog, abort and completion is decided in the process.** `settled` (`packages/host/src/runs.ts:251`) says the watchdog or a closed connection took the end of the run, and `finishing` (`:253`) says the run's own path took it by starting to save. Only one is ever set. `persisted` and `failedMessage` sit beside them (`:254-255`) so the watchdog can tell whether the answer is saved and whether the person was already told the run failed. `finishRun`'s `WHERE status='streaming'` (`packages/host/src/threads.ts:312-330`, `insertRun` at `:288`) is defense in depth. The formal check finds no property that fails when it is removed, on either driver. `settled` is also what ends a run whose row did not exist yet, because `finishRun` cannot be called before `insertRun` returns a `runId` (`runs.ts:404`). A database write that never returns ends the stream but leaves the row `streaming` for good. No boot sweep closes such a row, so a move off SQLite still owes a timeout on each write, or that sweep.
- **Removing a chip deletes its kept original.** `discardChipOriginal` (`apps/web/lib/composer-documents.ts:272`) deletes the original the host kept at attach (`deleteArtifact`, `:277`). It does nothing while a send is in flight, because the message may already name that original, and a failed delete is logged and never shown. The rules for the original are in [`agent-tools-and-files.md`](agent-tools-and-files.md) Â§ 15.

## Why

**Why the header limit is 45 s, is not keyed on Thinking, and is not retried.** `[Direct]` the coordinator's measurement of 2026-10-07 on a diagnostic server with the old 10 s limit stretched, Thinking Off, `gpt-6-luna`: both calls of a Word-file turn returned HTTP 200 after 15 146 ms and 15 135 ms, where a first call minutes earlier took 3.3 s. Thinking was off, so a longer allowance for Thinking alone would not have helped; `[Inferred]` (the coordinator's guess, not measured) that the near-identical 15 s is a wait on the gateway's side, not model time. `[Direct]` `stream-watchdog.ts:5-9`: after a tool the stream is in its 60 s idle budget (180 s for the always-thinking families), and the limit has to be under it to be the message the person reads. 45 s is three times the measurement and three quarters of the smaller idle budget. It is a judgement from one model on one prompt. It is a stop, not a retry, because the retry loop's three attempts would turn a 45 s wait into 135 s on a dead gateway and re-ask the same silent call, and an aborted paid request may still be billed upstream. **Confidence: high that 10 s was too short for this gateway; medium that 45 s is enough for every model; low on whether a gateway that buffers its first byte can need more on a long Thinking run.**

**Why a failure after a tool is told and not retried.** `[Direct]` `retry.ts:172`: the keep rule exists so a completed tool (an image made, a file written) is not lost when a later fetch fails; `shouldRetryModelContact` stops at `tooled` for the same reason (`:97`), because a retry would run the tool again. Telling the person is therefore the only thing left to do, and it is done the way the step-limit note is (Â§ 3b), so Chat has one road for "the run stopped early". **Confidence: high.**

**Why the first-token budget is a hard cap rather than something a frame can extend.** `[Direct]` `docs/internal/0.14.26-changelog.md:121` records the bug: `AiSdkRuntime.consume` fed the watchdog from every `fullStream` part, and the AI SDK enqueues `step-start` on the provider's first chunk while `@ai-sdk/openai` emits `response-metadata` on the gateway's very first SSE frame â€” "so half a second in, before any token, the 120 s first-token budget was swapped for the 60 s idle one (the reported error is the *idle* wording, which proves a part had already landed)." `[Direct]` `docs/internal/0.14.26-changelog.md:139` records the review fix: "the first-token budget is a hard cap again (a liveness-only frame no longer pushes it out, so a gateway that heartbeats without answering cannot hold a run open â€” one rule now in `streamWatchdogDeadline`, used by both the checker and the armed timer)." The code comment at `packages/core/src/runtime/stream-watchdog.ts:82-86` says the same. **Confidence: high.**

**Why `QUIET_REASONING_FAMILY` exists.** `[Direct]` `docs/internal/0.14.26-changelog.md:123`: the resolved Finance/Documents/Market default is `deepseek-v4-flash`, DeepSeek V4 thinks on by default, "its thinking streams as `delta.reasoning_content`, which AI SDK 4 drops (the same gap `packages/core/src/runtime/minimax-compat.ts` was written for), so nothing at all reached the watchdog for the ~50 s the model spent drafting." The fix was to widen the family, not to change any model default (`:125`). **Confidence: high.**

**Why Chat is excluded from the job thinking knob.** `[Direct]` the type comment at `packages/core/src/runtime/types.ts:62-64` states it, and `packages/core/src/runtime/ai-sdk-runtime.ts:230` carries the matching inline note. `[Supported]` `docs/internal/blockers-2026-09-15.md:226` closes blocker P1 with "Jobs send `{"reasoning_effort":"low"}` and nothing else (`packages/core/src/models/job-thinking.ts`, applied in `ai-sdk-runtime.ts` only when `execute` carries `jobMode`; Chat's body unchanged)." The reason to keep them apart is that Chat's effort is a user choice with a visible picker, and overriding it to `low` would silently disobey the user. **Confidence: high for the mechanism; the "would disobey the user" reading is `[Inferred]` from the picker's existence.**

**Why only the default Chat agent gets Chat's budget.** `[Direct]` the comment at `packages/host/src/runs.ts:318`: "Chat's declared budget is the default agent's; an agent the owner built keeps the runtime's own." `[Direct]` the comment above `chatHarnessSpec` (`packages/core/src/harness/modes/chat.ts:4-21`) gives the reason for the numbers: a file edit is read, edit, re-read and then the answer, and the old default of 6 steps ran out inside one such loop. **Confidence: high for the mechanism; 12, 40 and the per-tool caps are judgements sized by that comment and not measured on a live model.**

**Why the model call has its own abort.** `[Direct]` the comment at `packages/host/src/runs.ts:196-197`: the watchdog and a client that left both tell the person the run failed, and the abort "is what makes the request in flight stop, so a run nobody is waiting for stops billing." **Confidence: high.**

**Why the job knob is `reasoning_effort: "low"` and not thinking-off.** See [`finance-parse-and-generate.md`](finance-parse-and-generate.md#why) â€” the same decision, recorded there because that is where it was driven.
