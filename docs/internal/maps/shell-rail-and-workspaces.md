## Overview

The shell is everything around a mode page: the left rail, the desk switcher, the `/workspaces` page that creates and deletes desks, and the `/usage` page that prices what a desk spent. One fact drives all of it — **the current workspace's `productModes` is the rail**. There is no per-user navigation config, no feature flag, and no entitlement check here; a desk row in SQLite decides which tabs exist, and anything not in that list is redirected away from.

**The first desk is the default agent alone (2026-10-21, replacing 2026-09-29's four tools).** A fresh install writes its Default desk with Chat only (`FIRST_RUN_MODES`, `packages/core/src/agents/product-modes.ts:62`, written by `ensureLocalOwner`, `packages/db/src/ensure-local-owner.ts:66-78`), and so does a hosted tenant's first desk (`HOSTED_FIRST_DESK_MODES`, `:70`). The owner hires the rest from Virtual agents, which edits the desk's `productModes`. A desk row that stores nothing still *reads* as every mode (`resolveWorkspaceModes`), and an existing desk is never rewritten. Details and the tests that hold it: [`first-run-desk-and-guide.md`](first-run-desk-and-guide.md).

It is not a router. React Router owns the URL (`apps/web/src/App.tsx:213-448`); the shell only decides which links to draw and which paths to bounce. It is also not session state: collapse, width and theme are per-browser `localStorage`, never persisted server-side.

## Chat-first shell (2026-10-12)

`SHELL_LAYOUT` (`packages/core/src/agents/product-modes.ts:29`) is `chat-first`. The rail then lists the default agent (the brand's assistant) and one virtual agent per harness on the desk, with the mode screens off the rail. "Workspaces" is shown as "Virtual agents" (`apps/web/components/virtual-agents-page.tsx`), where a person hires and lets go of agents. The page URL stays `/workspaces`, because `/agents/*` is the parked Build redirect. The agent list and run policy are in [`virtual-agents.md`](virtual-agents.md). The rail sections below describe the `modes` layout. They still hold for that value and were not re-read for `chat-first`.

## How it works

### 1. Boot — one GET decides the rail

`AppRoutes` renders a gate (`apps/web/src/App.tsx:317-382`): `loading` while `GET /api/v1/settings` is in flight (since 2026-09-29 through `readSettings({ fresh: true })`, `apps/web/src/App.tsx:263`, whose answer Chat's key pill, usage chip and composer then share instead of each asking again: [`chat-send.md`](chat-send.md) § 2), `onboarding` when the host reports a closed gateway gate, otherwise `<Shell>`. `Shell`'s `reload` (`apps/web/src/App.tsx:105-121`) does the only call the shell needs:

```
GET /api/v1/workspaces
→ { workspaces: [{ id, name, slug, templatePack, productModes, protected }], currentWorkspaceId }
```

It finds the row whose `id === currentWorkspaceId` (falling back to `rows[0]`), and sets the desk (`workspaceId`, `workspaceName`) and its modes, `shellModesFromHost(desk.productModes)` (`apps/web/src/App.tsx:112`; `apps/web/lib/shell-modes.ts:86`: `resolveWorkspaceModes` tagged with the source `host`), then remembers them (`:116`). A rejected fetch is swallowed on purpose — first boot can race SQLite (`:118-120`) — and the state stays where it was. **Where it starts** is the job of `apps/web/lib/shell-modes.ts` (2026-09-29): the desk this browser last drew (`agentforge-shell-modes`, rewritten on every answer, per tenant on the hosted app) or, with nothing remembered, Chat plus a skeleton of four rows, and never every mode; only the host's answer may redirect away from a hidden mode. It used to start from `WORK_PRODUCT_MODES`, so a fresh install drew fourteen tabs and narrowed to five, and a desk that could not be read showed every tab. The source, the frames driven and the tests: [`first-run-desk-and-guide.md`](first-run-desk-and-guide.md) § 6. `Shell` also mounts `<GuideTour visibleModes ready>` after `AppShell` (`apps/web/src/App.tsx:137`), which draws only once the answer has named a desk (`ready`).

`resolveWorkspaceModes` (`packages/core/src/agents/product-modes.ts:164-173`) is the normalizer: `null` / `undefined` / `[]` / all-unknown → **all work modes** (`FALLBACK_PRODUCT_MODES`, `:48`); otherwise the sanitized list, forced to contain `chat`, in catalog order. The host applies the same function on the way out (`packages/host/src/handlers/workspaces.ts:58`), so renderer and API agree by construction.

`reload` re-runs on two triggers (`apps/web/src/App.tsx:123-128`): the `agentforge-shell-refresh` window event, and any change of `location.pathname`. The event is what `useRouter().refresh()` dispatches (`apps/web/lib/nav.tsx:43-45`) — this repo's Next-shaped `refresh()` is a custom event, not a server round trip.

### 2. `AppShell` — the rail and the desk, plus one child that draws nothing

`AppShell` (`apps/web/components/app-shell.tsx:30-51`) is a flex row of `ModeRedirect` (renders `null`), the rail (`AppRail`, or `AgentRail` on the chat-first shell), `DeskBuddyReactions`, and the `app-main-panel` element (`data-testid`, `apps/web/components/app-shell.tsx:42`). The shell and the desk slot are both `h-full` / `min-h-0` and `overflow-hidden`. The slot is **not** keyed on the pathname: keying it remounted `WorkModeKeepAlive` and dropped scroll position.

The document is not a scroller. `html`, `body` and `#root` are `height: 100%`, and `body` is `overflow: hidden` (`apps/web/app/globals.css:516-534`). Each desk page has one scrollport:

- Chat and Edit are fill panes (`FILL_DESK_PATHS`, `apps/web/components/desk-pane.tsx:7`). The pane is `overflow-hidden`; the page scrolls an inner region (the message list, the timeline) so the composer and the stage stay put.
- Every other work mode, and Settings, Knowledge, Workspaces, Usage and Channels, scroll the pane (`overflow-y-auto`). Account routes mount `DeskPane` (`apps/web/src/App.tsx:404-443`). Work modes use the same classes on a node that stays mounted (`apps/web/components/work-mode-keep-alive.tsx:67-84`): an inactive pane is `hidden`, not unmounted, so `scrollTop` survives a rail click. A full page load still starts at the top.
- Entrance motion (`.page-enter`, `apps/web/app/globals.css:1734-1736`) sits on the inner wrapper, not the scrollport, and does not use `animation-fill-mode: both`. A leftover transform would be the containing block for `position: fixed` menus and a second scrollport.

Chat follows the end of its message list while the reader is within 64px of the bottom (`apps/web/lib/stick-to-bottom.ts`, applied in `apps/web/components/chat-session.tsx:157-171` and `:493`). Sending a message re-pins (`:590`). Scrolling up during a stream leaves the list where the reader put it. The rail's own scroller is the `<nav>` (`apps/web/components/app-rail.tsx:282-287`, `overflow-y-auto overscroll-y-contain` at `:284`). The rail still collapses at 480px (`:217`).

Content lanes (`apps/web/app/globals.css:156-160`, steps at `:477-512`): `--content-max` is the reading column (720px, 768px from 2400px) and the composer shares it. `--content-wide` and `--content-stage` centre studios and grow with the viewport (stage 1984px from 3000px) so a side panel uses the extra width and the page stops short of the desk edge. Edit itself stays the full width of the desk; its side panels widen.

`ModeRedirect` (`apps/web/components/mode-redirect.tsx:7-18`) calls the pure `redirectIfHiddenMode(pathname, visibleModes)` (`packages/core/src/agents/product-modes.ts:180-200`) on every render and, in an effect, `router.replace(target)` when it is non-null, but only once `settled`: the modes came from the host's answer, not from the remembered list or from nothing (`components/mode-redirect.tsx:14`; a remembered list narrower than the desk would bounce a deep link). The rule:

1. `/chat*`, `/settings*`, `/workspaces*`, `/usage*`, `/knowledge*` are **always** reachable (`:181-189`) — they are not modes, so no desk can hide them.
2. Parked `/agents*` and `/studio*` go to `firstVisibleHref(visible)` (`:192-194`).
3. Any other path that matches a mode href goes to `firstVisibleHref` **unless** that mode is visible (`:195-199`).
4. A path matching nothing (a 404) is left alone here — `App`'s `<Route path="*">` sends it to `/chat` (`apps/web/src/App.tsx:447`).

`firstVisibleHref` prefers `/chat` and otherwise takes the first catalog id present (`packages/core/src/agents/product-modes.ts:152-158`).

### 5. Switching desks — a file, a cookie, and two refreshes

`WorkspaceSwitcher` (`apps/web/components/workspace-switcher.tsx:22-196`) fetches the same `/api/v1/workspaces` for its own list (`:31-38`) and renders the menu through `createPortal(…, document.body)` (`:104-134`) — the rail is `overflow-hidden` (`apps/web/components/app-rail.tsx:240`), so an in-flow menu would be clipped. Placement is recomputed on open, `resize` and capture-phase `scroll` (`:40-82`), and differs by chrome: expanded drops below the trigger, compact flies out to its right (`:49-54`).

`openWorkspace(id)` (`:84-91`) is four steps in order: `POST /api/v1/workspaces/:id/select`, `notifyThreadsChanged()` (so every session list reloads **before** the route settles — sessions are per desk), `router.push("/chat")`, `router.refresh()`.

Host side, `handleSelectWorkspace` (`packages/host/src/handlers/workspaces.ts:112-128`) verifies the id belongs to the org, then does two things: `writeSelectedWorkspaceId(found.id)` — a plain `data/workspace-id.txt` write (`packages/host/src/workspace.ts:35-41`) — and returns a `workspaceCookie` (`packages/host/src/workspace.ts:54-56`). The file is **process-global**, not per-browser: switching desks in one tab switches them for every client of that host.

### 6. `/workspaces` — create, edit, delete

`WorkspacesPage` (`apps/web/components/workspaces-page.tsx:46-448`) keeps one list plus three mutually exclusive panels (create / edit / delete); opening any one closes the other two (`:88-126`). On the chat-first shell `/workspaces` renders `VirtualAgentsPage` instead (`apps/web/src/App.tsx:424`); this section describes `WorkspacesPage`, which the modes layout still draws.

**Create.** `create-new-workspace` (`:301`) reveals `workspace-create-form` (`:220`). A template chip calls `applyPreset` (`:71-79`), which sets `templatePack` and copies that pack's `productModes` into the checkbox row; `workspace-template-blank` resets to `["chat"]`. Chips come from `WORKSPACE_TEMPLATES` (`packages/core/src/templates/library.ts:676-725`) — `general`, `organisation`, `students`, `office`, `legal`, `sales`, `marketing`, `product`. Chat's checkbox is `disabled` and `toggleMode` refuses it anyway (`apps/web/components/workspaces-page.tsx:81-86`). Submit POSTs `{ name, templatePack?, productModes: withChat(selected) }` (`:128-150`) and, on success, `router.push("/chat")` + `router.refresh()`.

Host `handlePostWorkspaces` (`packages/host/src/handlers/workspaces.ts:76-111`) rejects a blank name (400) and an unknown pack (400 `unknown_template_pack`), then resolves modes: the submitted list through `requireProductModes` (throws 400 on an empty-after-sanitize array, `packages/core/src/agents/product-modes.ts:141-150`), **or**, when the body omits them, `productModesForTemplate(pack)` — which is `["chat"]` for no pack (`packages/core/src/templates/library.ts:737-744`). It inserts the desk and a `workspaceMembers` owner row (`packages/db/src/ensure-local-owner.ts:149-170`, unique-slug retry at `:158-168`), copies the current desk's gateway key into the new desk's settings slice (`inheritGatewayKey`, `packages/host/src/handlers/workspaces.ts:38-44`, called at `:104`), then **selects it** (`:105`) and returns `201` with the cookie. So creating a desk always switches to it, and on an install with a key the switch keeps the gate open: the verdict is the tenant's and keyed by the key's fingerprint, so the copy opens under the verdict the key already has. Only `openaiApiKey` is copied; extras stay empty, the desk can save a different key of its own, and a keyless install creates a keyless desk. Before 2026-09-23 the new desk started empty, the gate derived `needs_key`, and the renderer replaced the whole shell with the key form (finding 1 of the 0.15.0 verify pass).

**Edit.** `edit-workspace-modes` (`:337`) toggles an inline editor; `save-workspace-modes` is disabled until `dirty` (name or mode set changed, `:313`, `:389`) and PATCHes `{ name, productModes }` (`:166-170`). `handlePatchWorkspace` (`packages/host/src/handlers/workspaces.ts:130`) applies only the fields present (`packages/db/src/ensure-local-owner.ts:207-209`). The page then `reload()`s and, when the edited desk is the current one, fires `router.refresh()` so the rail redraws (`apps/web/components/workspaces-page.tsx:175-179`).

**Delete.** `DeskDeleteButton` (`apps/web/components/desk-delete-control.tsx:16`, rendered at `apps/web/components/workspaces-page.tsx:341`) draws `delete-workspace` only for a row that is neither `protected` nor `slug === "home"`. The confirm panel (`:406`) requires the exact name typed into `delete-workspace-confirm-name` (`:415`); `delete-workspace-confirm-submit` is disabled until it matches (`:423`) and the client re-checks before sending (`deleteDesk`, `:188-191`). The DELETE carries `{ confirmName }` in the body.

`handleDeleteWorkspace` (`packages/host/src/handlers/workspaces.ts:183`; every line number in this paragraph was re-read on 2026-10-16) re-checks everything the client checked, and on the hosted server asks who is deleting first. Since 2026-10-07 only an owner or an admin may: a member or a builder gets `403 workspace_delete_forbidden`, checked after the desk is found and before the name is read (`:193-194`), and the page hides the button from a member (`DeskDeleteButton` asks `useMayDeleteDesk`, `apps/web/lib/desk-delete-access.ts:34`). ### 7. `/usage` — one route, one query parameter

`UsagePage` (`apps/web/components/usage-page.tsx:104`) holds `range` in state (default `"day"`, `:106`) and refetches on every change (`:113-126`):

```
GET /api/v1/usage?range=day|week|month
```

`parseUsage` (`:33-48`) is a defensive reader: a payload without a `thisKey.status` is treated as incomplete and surfaces `usage.errors.incomplete` rather than rendering zeros as fact.

Host `handleGetUsage` (`packages/host/src/handlers/usage.ts:8-16`) is three lines: tenant, `parseUsageRange(request.query.range)` (anything not `day`/`week`/`month` → `day`, `packages/core/src/gateway/account.ts:498-503`), `loadRangeUsage`.

`loadRangeUsage` (`packages/host/src/account-usage.ts:333-381`) computes **two unrelated numbers**:

- **this-key wallet** — `thisKeyFor(settings)` asks the gateway what this API key has spent, 2-minute cached (`:94-106`). No key → `{ status: "needs_key" }`.
- **desk estimate** — local run rows (`listRunUsage`) plus in-memory desk usage, filtered to the range's bucket keys (`:293-332`), priced against the gateway pricing catalog (10-minute cache, with a separate 2-minute *failure* cache at `:157-177` so an offline desk pays one timeout, not one per request), then `summarizeUsageDesk` + `buildUsageBuckets`.

A pricing failure is **not** fatal: the message is redacted and attached as `desk.error` while buckets still render unpriced (`:357-379`). With no key and no runs in range the whole thing short-circuits to empty frames (`:342-356`).

Bucket frames are fixed calendar windows, oldest → newest: **14 days, 8 weeks, 6 months** (`packages/core/src/gateway/account.ts:568-596`). Empty buckets are kept at `usd: 0` so the axis does not jump; `trimLeadingEmptyBuckets` then drops leading empties down to a floor of 7 (day) or 4 (week/month) (`apps/web/components/usage-range-chart.tsx:18-34`, floor from `apps/web/components/usage-page.tsx:94-103`).

`UsageRangeChart` (`apps/web/components/usage-range-chart.tsx:50-191`) is hand-rolled SVG — no chart library — with three outcomes: `usage-range-empty` "No … runs in this range." when nothing is in the window (`:54-60`), `usage-range-empty` "Runs in this range are not priced yet." when there are runs but no price (`:61-67`), otherwise `usage-range-chart` with stacked `<rect>`s per bucket × model plus a legend (`:86-189`).

### 8. Ambient motion — one switch for every loop

**Why it exists.** The Windows shell runs Chromium without the GPU (`app.disableHardwareAcceleration()`), so every infinite CSS loop costs a full software-composited frame on a screen nobody may be touching. Measured on the harness below, an idle `/chat` cost 10.5% of the machine (about 1.3 cores, 8.2 of it in the GPU process) and `/edit` 18.6 to 21.7%. Any one loop alone saturated the GPU process, so the loops have to stop together.

**The state.** `useAmbientMotion()` is mounted once, in `App` (`apps/web/src/App.tsx:204`), and binds `attachAmbientMotion` (`apps/web/lib/ambient-motion.ts:91`). It models four states of the person, not of the page: `active`; `idle` (visible and focused, no `pointermove`, `pointerdown`, `keydown`, `wheel` or `touchstart` for `AMBIENT_IDLE_MS`, 12 s, `:36`); `blurred` (`document.hasFocus()` is false); `hidden` (`document.hidden`). The order is hidden, then blurred, then idle (`ambientState`, `:47`). Anything but `active` writes `data-ambient="paused"` and `data-ambient-reason="idle|blurred|hidden"` on `<html>`; `active` removes both. CSS reads only those two attributes. The hero's own `data-paused` (off screen, § 9 of [`chat-send.md`](chat-send.md)) is separate and composes with it: either one pauses a loop.

**What it costs.** Passive, capture-phase window listeners and one outstanding timer. An input event stores a timestamp and nothing else, and not even that within 250 ms of the last one (`onInput`, `:141`); the timer re-arms for the remainder of the quiet period when it comes due (`onDue`, `:117`) instead of being reset per event, so a 1000-event storm creates no timer (`lib/ambient-motion.test.ts`). The focus and visibility handlers re-read `document.hasFocus()` rather than trusting the event, because `blur` also fires when focus moves into an iframe of the same page. Coming back to the tab, or focusing the window, counts as activity, so a returning reader is not paused on arrival.

**What it pauses** (`apps/web/app/globals.css:2706-2760`, "Ambient pause", two rules since the second pass below deleted the decoration loops; the first pass listed four, and the table keeps its history where a row says so; the pauses are `animation-play-state: paused !important` so no specificity tie can restart a loop, and the hero pass found one against the mascot's `animation` shorthands):

**Three things measured that shaped it.** (1) *A custom property written on the canvas restyles the page.* One write per frame cost 8.6 ms a frame on an empty `/chat` (321 elements), 5.3 ms on `/documents` (404) and 128 ms on `/edit` (1907 elements), against 0.13 to 0.17 ms on a leaf; a registered `inherits: false` property written on the canvas still cost 0.86 and 4.2 ms, most likely because the canvas itself is restyled, its 19 `:has(main[data-mode=...])` rules with it. So the backdrop is a real element with a four-element subtree, and the desk's variables (`--pointer-x`, `--pointer-y`, `--grid-x`, `--grid-y`) are written there and `--rx` / `--ry` on the shapes, never on the canvas or `<html>`. There is no desk-wide `--px` / `--py`; the hero's own pair on `.chat-hero` is unchanged, and anything else that wants the pointer needs a listener of its own, or a subscription added to `lib/desk-motion.ts`, because nothing inherits it. (2) *An animation on an `<svg>` root runs on the main thread, and so does any animation on an element that carries a second one, even a finished one.* A style recalculation every frame (481 in 8 s, 163 ms) for as long as the loop runs, although a stepped value changes 2.5 times a second; on a box of its own the same loop costs 12 recalculations, and the renderer's share went from 0.61% to 0.16 to 0.20% of the machine. That is why a shape is two boxes around the `<svg>` (the outer one settles, takes the pointer and pops; the inner one only loops). An `<svg>` also has no `offsetLeft`, which the push needs. (3) *The cost is frames times the pixels each one touches, and stepping is what makes loops affordable.* The same bob smooth (`linear`) held the machine at 7.5% on an empty Chat, GPU process 6.0, against 1.8% stepped, in the same variant run. The first version of the pointer layers wrote a smooth value every frame and let CSS transitions glide it, which kept two desk-sized layers moving at 60 frames a second: 9.7% on `/chat`, 8.6% on `/documents`, 6.8% on `/edit` while the pointer moved. So the light is written to a whole pixel at 30 Hz with no transition, and the grid ticks at about 10 a second.

**Measured.** The scratch harness `cpu.mjs` (Playwright, Chromium with `--disable-gpu --disable-gpu-compositing --disable-software-rasterizer`, which is the packaged Windows app's compositing, 1280 x 800 light; CDP `SystemInfo.getProcessInfo` summed over every process of the browser, 10 s windows, median of 3, % of the 12-thread machine so 8.33 is one core). *idle*: 13 s with no input, so the desk is paused. *pointer*: a synthetic `mouse.move` about every 15 ms along a Lissajous path over the whole desk, the worst case of a person using it. *still*: one move and a key press, then 10 s of nothing, which is inside the 12 s, so the loops run and the pointer does nothing. "Static desk" is the same build with `.desk-backdrop` hidden and `.float-shape-body` stopped, run in the same session as "now", because the machine is shared and its load moved between sessions (the 2026-09-29 numbers above are a different harness). ## Gotchas

- **The Browser pane reads as paused.** It is not focused between tool calls, so `<html>` carries `data-ambient="paused"` with reason `blurred` and `document.getAnimations()` shows 0 running: the switch working, not a stuck desk. A `left_click` on the page focuses it and the loops run (the pane's `hover` sends no `pointermove` at all, but a click's `pointerdown` wakes an idle desk). To count running loops, click first, or remove the attribute from the driver for the read. Entrances still play while paused.
- **A new infinite animation must be listed in the "Ambient pause" block, and in the reduced-motion block.** A status indicator goes in the second rule and steps with `var(--ease-busy)`; decoration is the stepped ambient set (`AMBIENT_LOOP_SELECTORS` in `lib/motion-tokens.test.ts`, `steps` through `--ease-ambient`) and adding to it is a product decision, not a styling one. A loop goes on a box of its own: never on an `<svg>` root and never on an element that already carries another animation (third pass, "Three things measured"). `lib/motion-tokens.test.ts` fails otherwise. Do not list an entrance.
- **`.enter-*` hold no fill.** A rule that needs an entrance's end state to persist (a different resting opacity, a `translate` the animation should keep) must set it on the element, not lean on `forwards`.
- **`product-brand` does not exist on a collapsed rail.** The expanded branch renders it (`apps/web/components/app-rail.tsx:266`); the collapsed branch renders only `product-logo`, inside the compact switcher (`apps/web/components/workspace-switcher.tsx:166-170`). Driven: count 1 expanded, **0** collapsed. A brand assertion must expand the rail first.
- **A rail row's icon is its mode colour on a 14% tint of itself** (`RailItem`, `bg-[color-mix(in_srgb,var(--mode)_14%,transparent)]`), and the current row flips to a solid `--mode` tile with `--on-mode` ink. Both are held by `lib/contrast-tokens.test.ts`: every `--mode-*` clears 3.5:1 on its rail and card tile in the light theme (3:1 on the hovered-row and inset grounds, 3:1 in dark) and 4.5:1 for the ink on the solid tile. On 2026-10-01 nine light values were darkened to get there (documents `#0ea5e9` to `#0b7cb0`, presentations `#ca8a04` to `#9d6b03`, edit `#d97706` to `#b06105`, finance `#16a34a` to `#12873d`, market `#ea580c` to `#ca4c0a`, data `#0891b2` to `#077f9c`, knowledge `#0d9488` to `#0c8378`, usage `#059669` to `#04855d`, workspaces `#6366f1` to `#6063f1`). `:root` holds the light set and `.dark` re-declares every mode, `--mode-documents` and `--mode-presentations` included, because a mode missing from `.dark` inherits the darker light value and falls under 3:1 on the dark rail. A new mode adds its token to both blocks.
- **A row with a chevron is one card, and `data-rail-row` marks the card, not the link.** Finance, Market and Education pass their chevron as `RailItem`'s `trailing` slot, so the row is a wrapper `div` (`data-rail-row`, `h-8`, the active fill and the hover wash) holding the link and the chevron (`apps/web/components/app-rail.tsx:44-142`, the wrapper at `:96-123`); `mode-finance`, `mode-market` and `mode-education` stay on the link inside it, with `aria-current` and `data-mode`. A plain row has `data-rail-row` on the link itself (`:125-141`). Count rows with `[data-rail-row]`, not `a[data-rail-row]`. Driven 2026-10-01 on :3000 (full desk): 19 `[data-rail-row]` (14 modes, 5 account links), and `mode-finance`'s `closest("[data-rail-row]")` is the wrapper and contains `finance-tasks-toggle`.
- **Settings is pinned; the modes are not.** The Account group is `.rail-pinned` (`position: sticky; bottom: 0`, opaque `--rail` background, `apps/web/app/globals.css:672-692`) inside the scrolling `<nav>`, so a short window scrolls the job modes behind it and never pushes the Account links out of reach. `rail-account-group` carries `data-more="true"` while rows are hidden below the nav's visible edge (`apps/web/lib/use-more-below.ts:15-55`) and only then draws a fade and a hairline above it, so `data-more` is also the test for "there are modes you cannot see"; it is `"false"` once the nav is scrolled to its end. Rows are 32px with a 24px tile above a 940px window height and 28px with a 22px tile at 940px or less (`@media (max-height: 940px)`, `:702`). Driven 2026-10-01 on :3000 (full desk, light theme): `settings-link` bottom at 663 of 720 at 1280x720 (`rail-footer` top 671), 743 of 800 at 1280x800, 711 of 768 at 1366x768 and 776 of 900 at 1440x900; `data-more` `"true"` at the first three (the nav's `scrollHeight` 727 against `clientHeight` 614, 694 and 662, fade opacity 1) and `"false"` at 1440x900 and 1440x1000, where every row fits; rows 28px at all four and 32px at 1440x1000; scrolling the nav to its end at the short sizes turned `data-more` `"false"`.
- **A mode header's art is a column in its flow, not a layer over it.** `ModeHeader` renders `FloatingShapes layout="header"` inside `.mode-header-art` (`apps/web/components/mode-header.tsx:19-70`, the column at `:66-70`) whenever `shapes` is true (the default; Settings and Workspaces pass `shapes={false}`, `:26`), and the stylesheet keeps it `display: none` until the header's own width reaches 60rem (`.mode-header` is a size container, `apps/web/app/globals.css:1919-1978`), when it becomes a 12rem column beside the text. Its presence in the DOM says nothing, so read `getComputedStyle(art).display` or its box. Driven 2026-10-01 on `/research`: header 804px wide at a 1100px viewport, art `none`; header 984px at 1280, art `block` and 192px (12rem) wide; 1144px at 1440. Before this change the art was an absolute layer over the header's right 30% from `lg` and lay on the outcome line and the actions; `apps/web/lib/mode-header-art.test.tsx` holds the structure.
- **A hidden mode's studio can still be in the DOM.** `WorkModeKeepAlive` mounts the pane for the entry path (`WorkModePanes`, `apps/web/components/work-mode-keep-alive.tsx:67-75`) before `ModeRedirect`'s effect runs, and keep-alive never unmounts — the pane just goes `hidden` + `class="hidden"` + `aria-hidden` (`:86-92`). Driven on 2026-09-17: on a Legal desk, `/images` redirected to `/chat` yet `images-studio` had count **1**, `isVisible()` false. Assert a hidden mode with the **rail** testid (`mode-images` count 0), never with the studio testid.
- **`rail-collapse` and `rail-expand` are the same button.** One testid, swapped by state (`apps/web/components/app-rail.tsx:469`). Waiting for `rail-expand` is how you know the collapse landed.
- **`rail-resize` and `rail-thread-list` do not exist while collapsed** (`apps/web/components/app-rail.tsx:488`, and `apps/web/components/rail-recent-threads.tsx:49`, where a collapsed rail keeps only a `new-chat-link` icon). Both are expected count 0, not a regression.
- **Collapsed group labels are a divider, not text** (`apps/web/components/app-rail.tsx:144-153`). Never match a rail group by its string on a collapsed rail — and never by string at all on an `id` desk (`Percakapan` / `Mode kerja` / `Akun`).
- **The rail's first frames are never every mode.** A fresh desk with nothing remembered draws Chat and four `rail-modes-skeleton-row` blocks until the workspaces answer lands (one mode link, `mode-chat`, not five, so wait for the fifth before asserting the desk; `mode-knowledge` is an account link and is always there); a returning browser draws the remembered desk. The session rows under Chat have their own placeholders (`rail-recent-skeleton-row`, not sessions) sized from the last load, so on a returning browser `settings-link` holds its place while they arrive; a browser with nothing remembered shifts once. Do not count the skeleton as modes (no `mode-` testid), and do not read a screenshot from the first 100 to 900 ms as the desk. The rows that replace a skeleton do not slide in (`startedPending`); on a rail that mounted with a list they still do. Driven, with the frame counts, in [`first-run-desk-and-guide.md`](first-run-desk-and-guide.md) § 6.
- **First paint always shows an expanded 232px rail.** Collapse and width are read in mount effects (`apps/web/components/app-rail.tsx:216-224`, `apps/web/lib/use-panel-width.ts:9-11`), not in the state initializer, so a screenshot taken before hydration settles shows the default, not the stored preference.
- **The selected desk is a file, not a session.** `data/workspace-id.txt` (`packages/host/src/workspace.ts:19-41`) is process-global. Switching desks in an automated drive switches them for the owner's open window too — switch back before you finish.
- **Creating a desk selects it.** `handlePostWorkspaces` calls `writeSelectedWorkspaceId` before returning 201 (`packages/host/src/handlers/workspaces.ts:105`), which is why the page can go straight to `/chat`. There is no "create without switching". It inherits the creating desk's gateway key first (`:104`), so the switch does not close the gate.
- **A keyless desk still shows the key form, but not as a dead end.** The gate is per selected desk, and `App` swaps the whole shell for `OnboardingScreen` when it is closed (`apps/web/src/App.tsx:338`), so the rail and switcher go with it. A desk made before key inheritance, or one whose own key was cleared, lands there; `OnboardingDesks` (`apps/web/components/onboarding-desks.tsx:11-35`, mounted at `apps/web/components/onboarding-screen.tsx:387`) lists every other desk as `onboarding-open-desk`. Pressing one calls `openDesk` (`apps/web/lib/onboarding-desks.ts:60-68`): the host's `POST /select`, then `GET /api/v1/settings`, and the gate that comes back is applied through the same `resolveGate` as at boot.
- **`productModesForTemplate(null)` is `["chat"]`, not everything** (`packages/core/src/templates/library.ts:737-740`) — but the create form always sends an explicit `productModes`, so that branch only fires for an API caller that omits the field.
- **`resolveWorkspaceModes` treats `[]` as "unset".** An empty stored array yields all work modes (`packages/core/src/agents/product-modes.ts:166-168`), while `requireProductModes` **rejects** an empty submitted array (`:147`). Storing "no modes" is impossible by design.
- **`/usage`, `/knowledge`, `/settings`, `/workspaces` are never redirected** (`:181-189`). A Legal desk still opens `/usage`; do not treat that as a leak.
- **Desk estimate and this-key wallet are different numbers by construction** and the page says so in its footer (`apps/web/components/usage-page.tsx:267`). One is local token math against a price catalog, the other is what the gateway says the key spent across every app using it.
- **Equal totals across Day / Week / Month are normal.** The three frames are 14 days / 8 weeks / 6 months (`packages/core/src/gateway/account.ts:568-596`); a desk whose runs are all recent lands every run in the newest bucket of all three. Only the bucket count and labels change. Observed on 2026-09-17: `$0.0018 · 1 model` in all three.
- **`usage-range-empty` carries two different sentences** (`apps/web/components/usage-range-chart.tsx:56`, `:63`) — "No … runs in this range." and "Runs in this range are not priced yet." Matching the first one only will miss the has-runs-no-prices state.
- **The chart's copy is hardcoded English** while `usage.chart.empty` / `unpriced` / `aria` / `barTitle` exist in both catalogs with zero call sites. Locale bug, recorded in `docs/internal/unreleased.md`, not something to work around in a recipe.
- **`usage-key-meter` renders only when `thisKey.status === "ok"`** (`apps/web/components/usage-panel.tsx:95-103`). On a keyless desk it is count 0, which is the correct state, not a missing element.
- **The switcher menu is portaled to `document.body`** (`apps/web/components/workspace-switcher.tsx:104-134`) because the rail is `overflow-hidden`. Scope a menu query to the document, not to the `<aside>`.
- **Deleting a desk needs the name in two places** — the client's disabled-until-match check (`apps/web/components/workspaces-page.tsx:423`) and the host's `confirmName` body field (`packages/host/src/handlers/workspaces.ts:199-203`). An API-only delete without the body is a 400.
- **Knowledge rows are wiped by hand, threads by cascade.** The six `knowledge_*` tables store `workspace_id` as plain text with no FK, so `wipeKnowledgeForWorkspace` deletes them explicitly (`packages/db/src/ensure-local-owner.ts:219-232`); threads and their children cascade from the workspace FK (`packages/db/src/schema.ts:432`).

## Why

**Why the rail is owned by the workspace and not by agents.** `[Direct]` The dead-code comment on `resolveProductModes` says it outright: "Rail no longer uses this — workspaces own visible modes" (`packages/core/src/agents/product-modes.ts:206`). `[Supported]` `.cursor/skills/verify-agentforge/features/README.md` records the product consequence — "Custom agents do not unlock the rail" and "Default already unlocks all of them" — and `features/workspaces.md` adds "Creating no longer seeds a starter agent". **Confidence: high.**

**Why a missing `productModes` means every tab rather than none.** `[Direct]` `features/workspaces.md` Gotchas: "Default with null `productModes` after migrate is all work modes — not Chat-only." `[Direct]` the doc comment at `packages/core/src/agents/product-modes.ts:160-163` states the same rule, and `packages/core/src/agents/product-modes.test.ts:57-59` pins `undefined` / `null` / `[]` to `WORK_PRODUCT_MODES`. The reason is migration safety: rows written before the column existed must not silently lose their rail. **Confidence: high for the rule; the migration-safety reading is `[Inferred]` from the "after migrate" wording in the feature file.**

**Why the switcher menu is a `document.body` portal.** `[Direct]` `features/workspaces.md` Sub-features: "The menu is portaled so the rail `overflow-hidden` does not clip it." `[Direct]` the rail is in fact `overflow-hidden` (`apps/web/components/app-rail.tsx:240`). Same class of fix as the Chat model picker — see [`chat-send.md`](chat-send.md) §7. **Confidence: high.**

**Why deleting a desk needs the name typed twice.** `[Supported]` The client disables the button until the name matches (`apps/web/components/workspaces-page.tsx:423`) *and* re-checks before sending (`:188-191`), while the host independently requires `confirmName` in the body (`packages/host/src/handlers/workspaces.ts:199-203`) — three checks for one action. A desk delete cascades every thread, message and run it owns (`packages/db/src/schema.ts:432`) and hand-wipes six knowledge tables (`packages/db/src/ensure-local-owner.ts:219-232`), which is unrecoverable locally. **Confidence: high for the mechanism; "because it is unrecoverable" is `[Inferred]` — no commit or changelog states the intent.**
