## Overview

A virtual agent is a person-facing worker on the desk with its own conversations. There is one per product-mode harness spec, so the registry (`VIRTUAL_AGENTS`, `packages/core/src/agents/virtual-agents.ts:269-271`) adds no mode.

**Every agent is a full chat.** The owner's words, 2026-10-09, in the order he gave them:

1. "the default mode needs to be nultron [...] take notes and check again"
2. "the chat agents need to be able to do anything inside their chat, they dont have to create a new virtual agents to be able to generate image or videos"
3. "not just default agents, all virtual agents able to do everything, its a chat mode now, with model picker and enhance mode, can generate images, videos and all kind of docs, or even build somethings"

What the code does with them:

- **Same tools and budget for every agent** (`FULL_CHAT_TOOLS`, `FULL_CHAT_BUDGET`, `packages/core/src/agents/virtual-agents.ts:99-136`). That is Chat's 17 tools (`DEFAULT_CHAT_TOOLS`, `packages/core/src/agents/default-chat.ts:72-90`) plus the workers `research_dossier` and `finance_task` (`CHAT_WORKERS`, core `virtual-agents.ts:74-87`) and `delegate`, which asks another agent (`GENERALIST_EXTRA_TOOLS`, `:91`, section 7), under Chat's budget of 12 steps and 40 tool calls (`packages/core/src/harness/modes/chat.ts`). Per turn it also holds a ceiling of 2 dossiers (`:77`), 2 Finance runs (`:82`) and 3 hand-offs to another agent (`DELEGATE_PER_TURN`, `packages/core/src/agents/delegation.ts:35`). Paid media has no ceiling; since 2026-10-22 its brake is the permission card (`image_generate` and `video_generate` wait for the person's Run, see [`chat-send.md`](chat-send.md), "Paid media asks first"). Nobody has to hire a second agent to get a picture, a clip, a deck or a dossier.
- **An agent differs from the next by its specialty and its conversations.** A mode agent's prompt opens with who it is and what it is for (`SPECIALTIES`, `packages/core/src/agents/virtual-agents.ts:143-197`), then says "You are not limited to your specialty" (`modeAgentPrompt`, `:204-217`), then carries Chat's rules (`CHAT_BODY`, `:129-131`) and the paragraph about the worker (`GENERALIST_WORKER_PROMPT`, `:87-94`). The default agent's prompt is Chat's own plus that paragraph (`:240`).
- **`conversation` no longer says whether an agent converses.** It says where the agent's own harness runs (`VirtualAgentConversation`, `:24-30`). `harness`: the specialty is a tool of the chat, so its checked run happens in chat. Today that is `chat` and `research` (`agentFor`, `:248`, which reads `SPECIALTIES[mode].worker`). `studio`: the specialty's own checked run still lives in its studio screen. In chat that agent does the work with the general tools and its prompt tells it never to claim the studio's checks ran (`studioNote`, `:200-202`, added at `:209`). Both kinds converse.
- **The default agent's name is a brand setting.** The default agent is the brand's character: the product's name unless the brand names one (`resolvedAssistantName`, `packages/core/src/gateway.ts:29-37`). No character's name is in the code.

The chat-first shell draws a narrow rail of the desk's agents (`AgentRail`), opens each one at `/chat?agent=<mode>` (the default agent at plain `/chat`), and replaces the Workspaces page with a Virtual agents page where a person hires or lets go of agents. The word "Workspaces" on screen is now "Virtual agents" (`agents.rail.manage` and `agents.page.title`).

It is not a custom-agent builder and it has no routines or computer. One agent can ask another for an answer (section 7) but cannot hand the conversation over. See "What is not built".

### What "all kinds of docs" means today

The owner's third instruction names images, videos and "all kind of docs". What a chat can make, in the tools it binds:

| Output | Tool | Notes |
|---|---|---|
| A picture | `image_generate` | `packages/core/src/tools/platform/image-generate.ts:92`. Hidden on a turn that carries an attachment (`CHAT_UNDERSTAND_HIDDEN_TOOLS`, `packages/core/src/agents/chat-turn.ts:6`). |
| A clip | `video_generate` | `packages/core/src/tools/platform/video-generate.ts:107`. Hidden on an attachment turn, same place. |
| A PowerPoint deck (.pptx) | `build_deck` | `packages/host/src/deck/build-deck-tool.ts:18`. The only binary file a chat makes. A deck card with Open and Download draws under the answer (`chat-deck-card`, `apps/web/components/chat-deck-card.tsx:62`). |
| A text file on the desk | `write_file`, `edit_file` | `packages/core/src/tools/files/tools.ts:100-103`: "Create a text file", at most 2 MB. A Markdown, CSV or code file, not a Word file. |
| A computed result | `run_code` | Python (pandas, numpy) or JavaScript in a sandbox with no network. Output is saved to the desk as `out/<name>`, text files only, and "Binary files are not saved" (`packages/host/src/code-runner/run-code-tool.ts:49`; the packages in `scripts/sandbox-runtime.lock.json` are numpy, pandas, python-dateutil, pytz and six). |
| A sourced research dossier | `research_dossier` | The worker. The result draws as a dossier card. |
| A checked Finance review of attached figures | `finance_task` | The worker. It reads only a figures file the chat save kept. The result draws as a Finance card with Open and Download Excel and Word ([`finance-chat-worker.md`](finance-chat-worker.md)). |
| Another agent's work (a dossier, a deck, a file, a figure) | `delegate` | `packages/host/src/delegation/delegate-tool.ts:46`. The asked agent does it in its own conversation and the answer comes back as text. Section 7. |

There is **no tool that writes a Word, Excel or PDF file in chat**. A Documents agent writes Markdown and saves it with `write_file` (`SPECIALTIES.documents`, `packages/core/src/agents/virtual-agents.ts:149-152`). The mode screens still have their own export routes; I did not open those for this page. "Build something" means a deck, a file or code run in the sandbox. There is no app or site builder.

3. The route (`packages/host/src/router.ts:342`) calls `handleGetVirtualAgents` (`packages/host/src/handlers/virtual-agents.ts:7`), which calls `listVirtualAgents` (`packages/host/src/virtual-agents.ts:143`).
4. `listVirtualAgents` reads the desk's `productModes` (`deskModes`, `:94`) and keeps the default agent plus the desk's modes in catalog order (`virtualAgentsForDesk`, `packages/core/src/agents/virtual-agents.ts:287-290`). An existing desk keeps what it has.
5. **Every agent on the desk gets a row**, because every one converses: `ensureVirtualAgentRow` (`:80`) is called for each (`:146-148`). The row owns that agent's threads and nothing else (below). An agent that is not hired gets no row and `agentId: null` (`:152`). **A GET can write:** the first request after a desk gains an agent inserts its row.

With nothing cached it draws three skeleton blocks after the default agent (`agent-rail.tsx:196-200`). They do not pulse, because a loop runs only under `data-busy` (the perf contract in `apps/web/lib/motion-tokens.test.ts`) and the placeholders are on screen for one request (`agent-rail.css:187`).

### 3. What a mode agent's run is made of

For a `va-<mode>` row the run is the Chat run with these differences (`packages/host/src/runs.ts`):

1. **Model.** The host picks it, as for Chat (`:172-174`). The tier sets it.
2. **Prompt.** The registry's prompt replaces the stored one, with disabled-tool sentences removed (`:204-205`). The pieces appended after it, in this order: the earlier-chats hint (`pastHint`, `:185`), then the desk's Soul block and the retrieved Knowledge Base excerpts (`knowledge.prompt`, `:213`), then the agent's own closing (`closingPrompt`, `:213`). The closing exists because the Soul block names the desk's default assistant and tells the model to use that name and no other, and the Images agent answered with it (RECORD row 18). The closing goes last and says: you are the {label} agent, the Soul block's name is the desk's default assistant, and you can also do everything else (`modeAgentClosing`, `packages/core/src/agents/virtual-agents.ts:225-228`).
3. **Knowledge and earlier chats.** A mode agent gets both, as Chat does (`runs.ts:185-190`). The hint lists this agent's own earlier threads for this person (`formatPastSessionsHint`, `packages/host/src/session-recall.ts:12`, which asks `listPastSessionsForAgent`, `packages/host/src/threads.ts:162-183`, filtered on the agent row, the person and non-default titles). The Knowledge Base retrieval is the desk's (`knowledgeInjection`, `packages/host/src/knowledge.ts:966`). Not driven. The risk this opens is in "Known limits".
4. **Modalities.** A mode agent takes what Chat takes: text, picture and video (`:218-219`). The row is made with the same list (`packages/host/src/virtual-agents.ts:67`). An attachment turn hides `image_generate` and `video_generate` (`bindingsForChatModality`, `chat-turn.ts:11-20`, used at `runs.ts:508`).
5. **Tools and budget.** Bindings are made from `agent.tools` (`packages/host/src/virtual-agents.ts:196-203`) and the budget from `agent.budget` (`runs.ts:518-519`).
6. **Worker channel and watchdog.** `inChatRun` sets the tool-run context and the worker channel (`:489-492`), and the run hands the model runtime a longer idle budget (`:532`). Both are described in section 4.

The default agent keeps its own path (`runPolicyFor` returns null for it, `packages/host/src/virtual-agents.ts:189-191`): the stored row's prompt plus `GENERALIST_WORKER_PROMPT` (`runs.ts:207`), the stored row's bindings plus `past_sessions` and the workers (`withPastSessionsBinding`, `withGeneralistWorkers`, `runs.ts:511-513`, `packages/host/src/virtual-agents.ts:156-169`), and the registry's budget (`runs.ts:521`). The same watchdog line applies to it (`:532`).

### 4. A Research run, and any agent that calls the worker

Any agent can call `research_dossier`, because every agent binds it. The Research agent differs in being told to use it for research and not to write findings from memory (`SPECIALTIES.research`, `packages/core/src/agents/virtual-agents.ts:162-166`); the default agent's prompt tells it to use the tool when the owner asks for research, a report or a briefing (`CHAT_WORKERS.research_dossier.sentence`, `:78-79`).

1. `research_dossier` (`packages/host/src/workers/research-dossier-tool.ts:124`) takes one `question` of 8 to 2000 characters (`:12-19`). `runResearchWorker` (`:58`) calls `generateResearchNotes` (`packages/host/src/research-generate.ts:124`) in process. That is the same function the Research screen runs: plan, search, read, extract, synthesize, the citation checks and one repair round ([`research-dossier.md`](research-dossier.md)).
2. Without a live gateway key `requireLiveResearch` throws `503 runtime_stub` (`research-generate.ts:77-83`), and the tool returns `{ ok: false, reason: "failed", code: "runtime_stub" }`. The dossier's own model calls use `settings.researchGenModel` or the Research default (`:131`), not the tier the person picked. The tier sets the model of the conversation turn only.
3. **Progress.** The harness emits job events. The worker wraps the call in `runWithWorkerProgress` (`workers/worker-channel.ts:54`). The run's channel (`runs.ts:476-484`) calls `stall.touch()` for every event and sends `{ type: "tool.progress", toolKey, job }` for `job.phase`, `job.step` and `job.round` only (`:483-484`). While the harness is quiet, `runWithWorkerProgress` repeats the last such event every 20 s (`worker-channel.ts:28`, `:72-78`), and it stops repeating at `WORKER_MAX_MS`, 8 minutes (`:35`, `:73-76`). After that the run's stall guard (`run-stall.ts:30`, which uses the model's own idle budget, `:37`) sees silence and ends the run an idle budget later.
4. **Why the runtime's own watchdog is relaxed.** The model runtime arms a stream watchdog per model call (`armStreamWatchdog`, `packages/core/src/runtime/ai-sdk-runtime.ts:715`). It is fed only by parts of the model's stream: `touch()` for every part (`:753`) and `touchOutput()` for every mapped part (`:762`). A tool that is running sends the stream nothing, so a dossier of more than 60 s read as a dead stream and the run ended with "No stream events ... for 60s" (RECORD row 20, first try). The fix is in `runs.ts:532`: every run of the default agent or a mode agent passes `streamWatchdog: { idleMs: WORKER_STREAM_IDLE_MS }`, which is `WORKER_MAX_MS` plus 2 minutes, 10 minutes (`worker-channel.ts:46`). The override can only lengthen a limit and touches only the idle budget (`raisedLimit`, `stream-watchdog.ts:59-61`, `streamWatchdogLimits`, `:68-77`); the first-token budget is unchanged. It applies to **every** turn of those agents, not only a turn that calls a worker, so a model stream that goes quiet after its first output is now waited on for 10 minutes by the runtime. The run's own stall guard keeps the model's idle budget (60 s, or 180 s for a reasoning model, `stream-watchdog.ts:7-9`) and is fed by the run's events and the worker's heartbeat, so a stream that sends nothing and has no worker running still ends there (`worker-channel.ts:38-45`). Driven once: the default agent's dossier finished in about 85 s after the change. A wedged stream was not driven.
5. ### 7. Asking another agent (`delegate`)

Added 2026-10-22 at the owner's request: "communications between agents, much like delegation to subagents". An agent can hand one self-contained task to another agent on the desk and get its answer back as text, the way a sub-agent returns to its parent. Read from the code and its unit tests; not driven against a live model.

1. **Every agent binds it.** `delegate` is in `GENERALIST_EXTRA_TOOLS` (`packages/core/src/agents/virtual-agents.ts:91`), so the default agent gets it through `withGeneralistWorkers` (`packages/host/src/virtual-agents.ts:156`) and a mode agent through `FULL_CHAT_TOOLS` (`:108`). `registerTool(delegateTool)` is in `packages/host/src/register-tools.ts:46`. Its trust is `user_content` (`packages/host/src/delegation/delegate-tool.ts:46`): the answer was written by a run that may have read the owner's files or the web, so it is scanned for injection like a file's text and counts as a private read for the egress guard of the asking run.
2. **Who can be asked.** Every mode agent except `chat` (`DELEGABLE_AGENTS`, `packages/core/src/agents/delegation.ts:22`), so a chain has one root. Only an agent the desk has hired (`hiredAgentRow`, `packages/host/src/virtual-agents.ts:176`): the task is kept as a conversation of that agent, which the owner has to be able to open from the rail. Asking one that is not hired is refused with `reason: "not_hired"` and the list of those that are (`run-delegation.ts:138-148`).
3. **One run, one task.** `runDelegation` (`packages/host/src/delegation/run-delegation.ts:129`) refuses a second hand-off from a delegated run (`:130`, `currentDelegation()`), creates a thread on the asked agent's row titled from the task (`:156`), stores the task as its first message and a run row, and runs the asked agent with its own prompt followed by the rules of a delegated run (`delegatedRunPrompt`, `delegation.ts:101`), its own tools less `delegate`, `image_generate` and `video_generate` (`DELEGATE_EXCLUDED_TOOLS`, `delegation.ts:49`; bindings at `run-delegation.ts:166`), and a budget of its own (`DELEGATE_BUDGET`, `delegation.ts:63`: 8 steps, 16 tool calls, with ceilings for dossiers, decks, fetches, code and file writes). The model is the Daily tier, with the desk's default model when no model answers the tier (`delegateModel`, `:87`). The asked agent cannot see the asking chat: the task and its pasted `context` are all it gets, and the context is labelled as material, not instructions (`delegatedTaskMessage`, `delegation.ts:109`).
4. **What comes back.** `{ ok: true, agent, thread: { id }, summary, truncated, toolsUsed }`. The summary is the asked agent's last answer with secrets redacted, cut to 6000 characters (`:307`). The whole answer and every tool call are in the asked agent's conversation, with the run's usage counted as chat usage (`persist`, `:191`). A refusal says why: `nested`, `no_chat`, `not_hired`, `no_answer`, `failed`, `cancelled` or `timeout`; the last four keep the thread, so what was done can be opened.
5. **What bounds it, all in code.** Depth one. At most 3 `delegate` calls a turn (`DELEGATE_PER_TURN`, `delegation.ts:35`), each a run of the small budget above, so the turn's extra cost has a fixed ceiling; this is not the "counts against the asker's ceiling" the spec asked for, which needs the runtime's own counter. The worker ceiling of 8 minutes (`WORKER_MAX_MS`, `workers/worker-channel.ts:35`) and the asking run's stop signal both end it (`run-delegation.ts:180-182`, catch at `:287`). No picture or clip tools, so no paid media and no approval a delegated run could not get.
6. **The egress guard (SR-112).** A model-written task is not something a person typed. The delegated run starts as if it had already read private material (`tainted: true`) and its list of sites a person named is the person's own words from the asking conversation, never the task (`personText`, `:104`; `egress` at `:226`). So a task cannot launder a fetch that the asking run could not make. The runtime takes this as the optional `egress` input (`packages/core/src/runtime/types.ts:106-111`, read in `ai-sdk-runtime.ts:480-483` and `stub-runtime.ts:58-61`; `createEgressGuard`, `egress-guard.ts:178`).
7. **Files.** A delegated run has the desk's files only. `resolveFileRoot` refuses the owner's folder for it (`packages/host/src/file-roots.ts:30-36`), because nobody is there to approve a change to the real folder.
8. **What the owner sees.** While it runs, the asking turn's live row shows the asked agent's progress ("Research agent: web search"), through the same worker channel as a dossier. Under the answer a card (`apps/web/components/chat-delegate-card.tsx:117`, `DelegateCards`, drawn from `chat-turn.tsx:198`) names the agent, the first line of the task, the tools used and a Show control for the answer, and links to the asked agent's conversation (`virtualAgentHref(agent, threadId)`). It is drawn from the saved tool call (`tool-rows/delegate-result.ts:56`), so a reopened thread draws the same card. A hand-off that never started (not hired, nested) has no card; its Thinking row says why (`delegateSummary`, `apps/web/lib/tool-labels.ts:265`). `delegate` is in `NO_EMBED_TOOLS` (`apps/web/lib/message-embeds.ts:211`) so its answer is never also drawn as a link card. Copy: `agents.delegate.*` and `harness.tools.delegate` in both locales.
9. **Interplay with the safe-web-search work (PR #182).** That branch adds an outbound-text guard in `runs.ts` held in async-local state. A delegated run starts inside the asking run's async context, so it inherits that state rather than getting a fresh one. This page does not claim it behaves correctly once both are merged: it was not run together with that branch.

## Known limits

- **A mode agent reads private material and can send a question to the web.** A mode agent now gets the desk's Knowledge Base excerpts and its own earlier chats in the prompt (`runs.ts:185-190`), and binds `web_search`, `web_fetch` and `research_dossier`. The egress guard (`packages/core/src/runtime/egress-guard.ts`, created at `packages/core/src/runtime/ai-sdk-runtime.ts:461`) is the only brake, and it stops less than the name suggests. Read from its header (`egress-guard.ts:5-20`) and code (`egress-guard.ts:150-169`):
  - It refuses **`web_fetch` only** (`FETCH_TOOL`, `egress-guard.ts:39`; `beforeCall`, `egress-guard.ts:150-159`), and only after a tool with `trust: "user_content"` has run in the same turn (the file tools, `run_code`, `knowledge_search`, `past_sessions`). The guard checks no other tool, and both are `trust: "network"` (`research-dossier-tool.ts:127`; `packages/core/src/tools/platform/web-search.ts:76`). After a private read, a model can still put private text in a search query or in a dossier question.
  - It does **not** see what enters through the prompt. Knowledge excerpts and the earlier-chats hint are in the system prompt (`runs.ts:213`), not the output of a tool, so reading them does not taint the run, and a `web_fetch` to a host the person named stays open.
  - The header names its own gaps: a host the person named is trusted, a host in search results is trusted, and a new turn starts untainted.
  - Since 2026-10-13 the outbound guard covers what the bullets above say the egress guard does not: every search query, page address and source image a run sends, the prompt's private text (Knowledge excerpts, memories, attached files) from the first step, and the searches `research_dossier` makes. ## Why

- **Why every agent is a full chat.** `[Direct]` the owner, 2026-10-09, instructions 2 and 3 at the top of this page. It departs from the plan's "a bot is one harness" (`chat-first-plan.md`, "Second reference") and from the advice that a prompt-only agent is what the product is not. It is the owner's call. What keeps it honest: the tools and budget are still the host's, and the screen and the prompt say where the specialty's checked run lives.
- **Why prompt, tools and budget come from code and not from the row.** `[Direct]` `packages/host/src/virtual-agents.ts:26-28`: nothing stored on a desk can widen what an agent may do. This holds for a mode agent. The default agent still takes its prompt and bindings from its stored row, as Chat always did.
- **Why a mode agent has a closing line.** `[Direct]` the comment at `packages/core/src/agents/virtual-agents.ts:52-58`: the Soul block names the desk's default assistant and tells the model to use that name and no other, and the Images agent answered with it when driven.
- **Why the default agent is the brand's character.** `[Direct]` the owner, instruction 1 at the top of this page. On the public brand the character carries the product's name; a white-label brand's name for it is a setting that is not wired yet (section 5).
- **Why virtual agents at all.** `[Direct]` the owner, 2026-10-09: "we're going to revamp this to be more like muse and hark style, focuses on UIUX of the chat mode, removing all the workspaces and hide them, also to rebrand the name of workspaces into virtual agents, with each using their own harness and with skill and tools embed inside". "Hark" was named as a look reference; no screenshot or link for it is on file, so the layout follows the two 2026-10-06 references only.
