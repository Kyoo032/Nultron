## Overview

A virtual agent is a person-facing worker on the desk with its own conversations. There is one per product-mode harness spec, so the registry (`VIRTUAL_AGENTS`, `packages/core/src/agents/virtual-agents.ts:255-257`) adds no mode.

**Every agent is a full chat.** The owner's words, 2026-10-09, in the order he gave them:

1. "the default mode needs to be nultron or for HYP AI the default mode or the default virtual agents has to be Hypey, take notes and check again"
2. "the chat agents need to be able to do anything inside their chat, they dont have to create a new virtual agents to be able to generate image or videos"
3. "not just default agents, all virtual agents able to do everything, its a chat mode now, with model picker and enhance mode, can generate images, videos and all kind of docs, or even build somethings"

What the code does with them:

- **Same tools and budget for every agent** (`FULL_CHAT_TOOLS`, `FULL_CHAT_BUDGET`, `packages/core/src/agents/virtual-agents.ts:99-120`). That is Chat's 21 tools (`DEFAULT_CHAT_TOOLS`, `packages/core/src/agents/default-chat.ts:73`), which include the four document tools (`create_document`, `create_workbook`, `revise_document`, `import_document`; [`agent-tools-and-files.md`](agent-tools-and-files.md) § 15), plus the worker `research_dossier` (core `virtual-agents.ts:74-84`), under Chat's budget of 12 steps and 40 tool calls (`packages/core/src/harness/modes/chat.ts:32`). Each document tool gets 4 calls a turn. Per turn it also holds a ceiling of 2 dossiers (`:77`), 4 pictures and 1 clip (`PAID_MEDIA_PER_TURN`, `:107-110`). The comment there says the cost card with a Run control that the plan's decision D4 asks for before a clip is made is not built, so the ceiling is the only brake on paid media. Nobody has to hire a second agent to get a picture, a clip, a deck or a dossier.
- **An agent differs from the next by its specialty and its conversations.** A mode agent's prompt opens with who it is and what it is for (`SPECIALTIES`, `packages/core/src/agents/virtual-agents.ts:143-197`), then says "You are not limited to your specialty" (`modeAgentPrompt`, `:204-217`), then carries Chat's rules (`CHAT_BODY`, `:129-131`) and the paragraph about the worker (`GENERALIST_WORKER_PROMPT`, `:87-94`). The default agent's prompt is Chat's own plus that paragraph (`:240`).
- **`conversation` no longer says whether an agent converses.** It says where the agent's own harness runs (`VirtualAgentConversation`, `:24-30`). `harness`: the specialty is a tool of the chat, so its checked run happens in chat. Today that is `chat` and `research` (`agentFor`, `:248`, which reads `SPECIALTIES[mode].worker`). `studio`: the specialty's own checked run still lives in its studio screen. In chat that agent does the work with the general tools and its prompt tells it never to claim the studio's checks ran (`studioNote`, `:200-202`, added at `:209`). Both kinds converse.
- **Document files for every agent (2026-10-14).** The four document tools reach every agent through `FULL_CHAT_TOOLS`, so a mode agent can make a Word, Excel or PDF file from its own chat. Their row label is `docToolLabel` (`apps/web/lib/tool-labels.ts:106`). `NO_EMBED_TOOLS` (`apps/web/lib/message-embeds.ts:298`) keeps document results out of the job cards under the answer, and a file card hides the host note that starts `[Original file` (`MODEL_ONLY_NOTE_PREFIXES`, `apps/web/lib/message-embeds.ts:197`, read by `fileCardDetail`, `:205`), because that note is written for the model (`packages/host/src/chat-documents/notes.ts:79` and `:81`). The card and its Download are in [`chat-send.md`](chat-send.md) § 6.
- **The default agent's name is a brand setting.** The default agent is the brand's character: the product's name unless the brand names one (`resolvedAssistantName`, `packages/core/src/gateway.ts:29-37`). No character's name is in the code.

The chat-first shell draws a narrow rail of the desk's agents (`AgentRail`), opens each one at `/chat?agent=<mode>` (the default agent at plain `/chat`), and replaces the Workspaces page with a Virtual agents page where a person hires or lets go of agents. The word "Workspaces" on screen is now "Virtual agents" (`agents.rail.manage` and `agents.page.title`).

It is not a custom-agent builder, it has no routines or computer, and it does not let one agent hand a task to another. See "What is not built".

### What "all kinds of docs" means today

The owner's third instruction names images, videos and "all kind of docs". What a chat can make, in the tools it binds:

| Output | Tool | Notes |
|---|---|---|
| A picture | `image_generate` | `packages/core/src/tools/platform/image-generate.ts:51`. Hidden on a turn that carries an attachment (`CHAT_UNDERSTAND_HIDDEN_TOOLS`, `packages/core/src/agents/chat-turn.ts:6`). |
| A clip | `video_generate` | `packages/core/src/tools/platform/video-generate.ts:107`. Hidden on an attachment turn, same place. |
| A PowerPoint deck (.pptx) | `build_deck` | `packages/host/src/deck/build-deck-tool.ts:18`. The only binary file a chat makes. A deck card with Open and Download draws under the answer (`chat-deck-card`, `apps/web/components/chat-deck-card.tsx:62`). |
| A text file on the desk | `write_file`, `edit_file` | `packages/core/src/tools/files/tools.ts:100-103`: "Create a text file", at most 2 MB. A Markdown, CSV or code file, not a Word file. |
| A computed result | `run_code` | Python (pandas, numpy) or JavaScript in a sandbox with no network. Output is saved to the desk as `out/<name>`, text files only, and "Binary files are not saved" (`packages/host/src/code-runner/run-code-tool.ts:49`; the packages in `scripts/sandbox-runtime.lock.json` are numpy, pandas, python-dateutil, pytz and six). |
| A sourced research dossier | `research_dossier` | The worker. The result draws as a dossier card. |

There is **no tool that writes a Word, Excel or PDF file in chat**. A Documents agent writes Markdown and saves it with `write_file` (`SPECIALTIES.documents`, `packages/core/src/agents/virtual-agents.ts:144-147`). The mode screens still have their own export routes; I did not open those for this page. "Build something" means a deck, a file or code run in the sandbox. There is no app or site builder.

## How it works

### 1. The rail draws the desk's agents

1. `AppShell` picks `AgentRail` when `SHELL_LAYOUT === "chat-first"` (`apps/web/components/app-shell.tsx:35`). The published `AppRail` stays in the tree for `"modes"`.
2. `AgentRail` (`apps/web/components/agent-rail.tsx:241`) calls `useVirtualAgents` (`apps/web/lib/virtual-agents.ts:122`). That hook asks `GET /api/v1/virtual-agents`, keeps the last answer in a module variable so a second list draws at once, and asks again on `VIRTUAL_AGENTS_CHANGED_EVENT` (`:104`) and on `agentforge-shell-refresh` (`:152`).
3. The route (`packages/host/src/router.ts:342`) calls `handleGetVirtualAgents` (`packages/host/src/handlers/virtual-agents.ts:7`), which calls `listVirtualAgents` (`packages/host/src/virtual-agents.ts:138`).
4. `listVirtualAgents` reads the desk's `productModes` (`deskModes`, `:94`) and keeps the default agent plus the desk's modes in catalog order (`virtualAgentsForDesk`, `packages/core/src/agents/virtual-agents.ts:281-284`). So the first-desk rule carries over with no second list: a fresh Personal desk gets Chat, Research, Images, Videos and Presentation, and the other nine agents are `available`.
5. **Every agent on the desk gets a row**, because every one converses: `ensureVirtualAgentRow` (`:80`) is called for each (`:142-144`). The row owns that agent's threads and nothing else (below). An agent that is not hired gets no row and `agentId: null` (`:146-147`). **A GET can write:** the first request after a desk gains an agent inserts its row.
6. The payload carries the loop, tools, budget, repair rounds and skills, never the prompt (`viewOf`, `:113-125`; the test "never sends a prompt to the renderer" is in `packages/host/src/virtual-agents.test.ts`). The `tools` it reports are the registry's, the same 18 for every agent (`:120`).
7. `AgentRailView` (`agent-rail.tsx:139`) draws one link per agent. The default agent is `mode-chat`, the others `agent-<mode>`, each to `virtualAgentHref` (`apps/web/lib/virtual-agents.ts:182`). A divider follows, then the account links (`ACCOUNT_LINKS`, `agent-rail.tsx:118`): Knowledge, Channels, the Virtual agents page (`workspaces-link`), Usage, Settings. With nothing cached it draws three skeleton blocks after the default agent (`agent-rail.tsx:200-204`). They do not pulse, because a loop runs only under `data-busy` (the perf contract in `apps/web/lib/motion-tokens.test.ts`) and the placeholders are on screen for one request (`agent-rail.css:153`).
8. The footer (`rail-footer`, `agent-rail.tsx:228-230`) holds the character, the theme toggle and the updates button. The character is the small head, `DeskBuddyChip` (`:266`), the one place on screen where nothing a person or a model wrote scrolls under it. The buddy's dock is still mounted so the character has a home, but in a box with no size (`.agent-rail-buddy-dock`, `agent-rail.css:69`, mounted at `agent-rail.tsx:263-265`). With no room for a body the view is `chip` (`buddyView`, `apps/web/lib/desk-buddy-state.ts:104-111`), and `DeskBuddyChip` draws only in that view (`desk-buddy.tsx:200-204`). The view is `none`, and the head is absent, while a page stage is on screen or the buddy is suppressed. The owner's reason, 2026-10-09: "careful, to not let the IP overlap with the generated content". The composer ledge no longer draws it (section 2, step 3).

The rail has no desk switcher, collapse button or session list. Conversations are in the chat header (section 2).

### 3. What a mode agent's run is made of

For a `va-<mode>` row the run is the Chat run with these differences (`packages/host/src/runs.ts`):

1. **Model.** The host picks it, as for Chat (`:173-176`). The tier sets it.
2. **Prompt.** The registry's prompt replaces the stored one, with disabled-tool sentences removed (`:203-204`). The pieces appended after it, in this order: the earlier-chats hint (`pastHint`, `:184`), then the desk's Soul block and the retrieved Knowledge Base excerpts (`knowledge.prompt`, `:189`), then the agent's own closing (`closingPrompt`, `:212`). The closing exists because the Soul block names the desk's default assistant and tells the model to use that name and no other, and the Images agent answered with it (RECORD row 18). The closing goes last and says: you are the {label} agent, the Soul block's name is the desk's default assistant, and you can also do everything else (`modeAgentClosing`, `packages/core/src/agents/virtual-agents.ts:219-222`).
3. **Knowledge and earlier chats.** A mode agent gets both, as Chat does (`runs.ts:182-189`). The hint lists this agent's own earlier threads for this person (`formatPastSessionsHint`, `packages/host/src/session-recall.ts:12`, which asks `listPastSessionsForAgent`, `packages/host/src/threads.ts:162-183`, filtered on the agent row, the person and non-default titles). The Knowledge Base retrieval is the desk's (`knowledgeInjection`, `packages/host/src/knowledge.ts:966`). Not driven. The risk this opens is in "Known limits".
4. **Modalities.** A mode agent takes what Chat takes: text, picture and video (`:216-220`). The row is made with the same list (`packages/host/src/virtual-agents.ts:67`). An attachment turn hides `image_generate` and `video_generate` (`bindingsForChatModality`, `chat-turn.ts:11-20`, used at `runs.ts:498`).
5. **Tools and budget.** Bindings are made from `agent.tools` (`packages/host/src/virtual-agents.ts:196-203`) and the budget from `agent.budget` (`runs.ts:497-509`).
6. **Worker channel and watchdog.** `inChatRun` sets the tool-run context and the worker channel (`:480-485`), and the run hands the model runtime a longer idle budget (`:520-522`). Both are described in section 4.

The default agent keeps its own path (`runPolicyFor` returns null for it, `packages/host/src/virtual-agents.ts:189-191`): the stored row's prompt plus `GENERALIST_WORKER_PROMPT` (`runs.ts:205-206`), the stored row's bindings plus `past_sessions` and the workers (`withPastSessionsBinding`, `withGeneralistWorkers`, `runs.ts:499-503`, `packages/host/src/virtual-agents.ts:156-169`), and the registry's budget (`runs.ts:511`). The same watchdog line applies to it (`:522`).

### 4. A Research run, and any agent that calls the worker

Any agent can call `research_dossier`, because every agent binds it. The Research agent differs in being told to use it for research and not to write findings from memory (`SPECIALTIES.research`, `packages/core/src/agents/virtual-agents.ts:148-152`); the default agent's prompt tells it to use the tool when the owner asks for research, a report or a briefing (`CHAT_WORKERS.research_dossier.sentence`, `:78-79`).

1. `research_dossier` (`packages/host/src/workers/research-dossier-tool.ts:100`) takes one `question` of 8 to 2000 characters (`:12-19`). `runResearchWorker` (`:47`) calls `generateResearchNotes` (`packages/host/src/research-generate.ts:119`) in process. That is the same function the Research screen runs: plan, search, read, extract, synthesize, the citation checks and one repair round ([`research-dossier.md`](research-dossier.md)).
2. Without a live gateway key `requireLiveResearch` throws `503 runtime_stub` (`research-generate.ts:77-83`), and the tool returns `{ ok: false, reason: "failed", code: "runtime_stub" }`. The dossier's own model calls use `settings.researchGenModel` or the Research default (`:131`), not the tier the person picked. The tier sets the model of the conversation turn only.
3. **Progress.** The harness emits job events. The worker wraps the call in `runWithWorkerProgress` (`workers/worker-channel.ts:54`). The run's channel (`runs.ts:467-479`) calls `stall.touch()` for every event and sends `{ type: "tool.progress", toolKey, job }` for `job.phase`, `job.step` and `job.round` only (`:474-476`). While the harness is quiet, `runWithWorkerProgress` repeats the last such event every 20 s (`worker-channel.ts:28`, `:72-78`), and it stops repeating at `WORKER_MAX_MS`, 8 minutes (`:35`, `:73-76`). After that the run's stall guard (`run-stall.ts:30`, which uses the model's own idle budget, `:37`) sees silence and ends the run an idle budget later.
4. **Why the runtime's own watchdog is relaxed.** The model runtime arms a stream watchdog per model call (`armStreamWatchdog`, `packages/core/src/runtime/ai-sdk-runtime.ts:690`). It is fed only by parts of the model's stream: `touch()` for every part (`:728`) and `touchOutput()` for every mapped part (`:737`). A tool that is running sends the stream nothing, so a dossier of more than 60 s read as a dead stream and the run ended with "No stream events ... for 60s" (RECORD row 20, first try). The fix is in `runs.ts:520-522`: every run of the default agent or a mode agent passes `streamWatchdog: { idleMs: WORKER_STREAM_IDLE_MS }`, which is `WORKER_MAX_MS` plus 2 minutes, 10 minutes (`worker-channel.ts:46`). The override can only lengthen a limit and touches only the idle budget (`raisedLimit`, `stream-watchdog.ts:59-61`, `streamWatchdogLimits`, `:68-77`); the first-token budget is unchanged. It applies to **every** turn of those agents, not only a turn that calls a worker, so a model stream that goes quiet after its first output is now waited on for 10 minutes by the runtime. The run's own stall guard keeps the model's idle budget (60 s, or 180 s for a reasoning model, `stream-watchdog.ts:7-9`) and is fed by the run's events and the worker's heartbeat, so a stream that sends nothing and has no worker running still ends there (`worker-channel.ts:38-45`). Driven once: the default agent's dossier finished in about 85 s after the change. A wedged stream was not driven.
5. In the renderer, `readRunStream` turns an event that has a label into `onToolProgress` (`apps/web/components/chat-composer.tsx:135`, `:217`). `ChatSession` writes the label onto the newest started tool with the same key (`chat-session.tsx:531-544`), and `ChatTurn` draws it as `message-tool-progress` inside the Thinking disclosure (`apps/web/components/chat-turn.tsx:146`). Driven 2026-10-09: the tool row showed live lines ("Angkor Wat - Wikipedia", "Drafting findings") during a run of about 70 s.
6. Result: the tool returns `{ ok: true, artifact: { id, kind, title }, summary, sections, sourceCount, checks }`. The summary is cut to 1200 characters and the sections to 12 (`research-dossier-tool.ts:9-10`). The dossier text is not in it. The harness saved the dossier as an artifact and, when that worked, a Knowledge work card (`research-generate.ts:188-200`).
7. The run saves the redacted tool output into the assistant message's `tool_call` part. There is no `artifact` message part.
8. The card: `ChatTurn` reads tools from the live state or from the saved message (`toolsFromContent`, `chat-turn.tsx:231`). `DossierCards` (`apps/web/components/chat-dossier-card.tsx:179`) reads each completed `research_dossier` call with `readDossierResult` (`apps/web/components/tool-rows/dossier-result.ts:47`). `DossierCard` shows the title, source and section counts, whether the checks passed (a failed check always shows), the first four headings, and Open (`chat-dossier-open`). Open loads the artifact once with `getArtifact` (`chat-dossier-card.tsx:60`) and shows it in place. The saved file opens with a front-matter block (the question, the models), which the Research screen reads as data; shown as text it sat above the title. `dossierBodyForView` (`dossier-result.ts:31`) removes it, and only a block that starts on the first line and closes with its own `---` line (test: `apps/web/lib/dossier-body-view.test.ts`; the card calls it at `chat-dossier-card.tsx:61`). ## Agents made from a prompt, and deleting them

Rule: `docs/internal/team-board-spec.md` K-D34 items 3 and 4. The host half is the bullets below; the renderer half follows them, under "Rail (renderer)".

- **Draft.** `POST /api/v1/agents/draft` (`packages/host/src/agent-draft.ts`) makes one model call through the job seam (`collectJobAssistantText`) after the gateway gate, and stores nothing. The reply must be JSON (code fences are stripped) with a name, description, instructions and a base mode; anything else is `502 model_output_invalid`. The tools are clipped to the base mode's tools (`harnessSpecFor(mode).tools`) and to registered tools. With no key on Personal it returns a local draft with `source: "stub"`; hosted never stubs and answers the flat `403 gateway_blocked`.
- **Create.** `POST /api/v1/agents` (`agent-create.ts`) reads only name, description, instructions, base mode and tools from the body. A tool outside the mode is a 400, not a clip. The row is private, published, `productModes: ["chat"]`, `config: { baseMode, madeFromPrompt: true }` (`prompt-made-agent.ts`). Any signed-in person may make one: `AgentService.create` now asks for the builder role only when the visibility is not private (`packages/core/src/agents/service.ts`). A name whose slug is `quick-chat` or `va-<mode>` gets the `agent-` prefix (`slugify`, same file).
- **Run.** `runs.ts` (`isPromptMadeVersion`) adds no automatic `past_sessions` binding to a prompt-made agent; an older agent keeps it.
- **Privacy, server mode only.** `canView` lets an owner or admin see a colleague's private agent only off server mode (`service.ts:107-120`, flag wired in `packages/host/src/tenant.ts`). On a hosted desk the maker alone sees it, in `get`, `list`, every edit (`requireOwned`), `GET .../threads`, thread creation and runs. `share` still needs owner, admin or builder.
- **Delete.** `DELETE /api/v1/agents/:agentId` (`agent-delete.ts`): the maker, or an owner or admin without opening it. 404 for an id nobody wrote and for a colleague's private agent to a member; 403 for a workspace agent to a member who is not its maker; 409 `not_deletable` for `quick-chat` and `va-<mode>`; 409 `agent_in_use` when another person has a chat with it. The maker's chats go with their messages, runs and tool calls (foreign keys), their Knowledge cards are dropped, `project_agents` rows and pending proposals are deleted. Document versions keep the agent id.
- **Flags.** `GET /api/v1/workspaces/:id/agents` and the `specialists` of `GET /api/v1/chat` carry `madeFromPrompt` and `deletable`, computed in `packages/host/src/agent-flags.ts`. The renderer displays them and does not derive them.
- **Rail (renderer).** `AgentRail` (`apps/web/components/agent-rail.tsx`) draws the person's made agents under the default agent, one row each (`MadeAgentRailRow`, `apps/web/components/agent-made-rail.tsx`). The list comes from `GET /api/v1/chat` (`fetchMadeAgents`, `apps/web/lib/virtual-agents-made.ts`), which keeps only the specialists with `madeFromPrompt === true`; `deletable` counts only when the host sends `true`. A row links to `/chat?made=<id>` (`madeAgentHref`). The ⋯ button shows only when `deletable` is true and the rail is open; its Delete item is absent until the menu opens. Delete opens `AgentDeleteDialog` (`apps/web/components/agent-delete-dialog.tsx`), which names the agent and says its chats and messages go, then calls `DELETE /api/v1/agents/:id` (`deleteMadeAgent`). A success notifies every list and, when that agent's chat is open, returns to `/chat`. `+ New agent` (`NewAgentRailLink`) goes to `/agents/new`.
- **New agent page (renderer).** `/agents/new` (`apps/web/components/agent-new-page.tsx`, routed in `apps/web/src/App.tsx`) is one prompt box first, then `POST /api/v1/agents/draft` (`draftMadeAgent`), then the editable draft (name, description, instructions; base mode and tools under "More"), then `POST /api/v1/agents` (`createMadeAgent`). Create stays off until the name and instructions are non-empty. A draft with `source: "stub"` says no model is connected. A `403 gateway_blocked` shows the needs-key note (`NeedsKeyNote`), not an alert; the other refusal codes map to `agents.made.error.*` copy. After a create the page opens `/chat?made=<id>`.
- **A made agent's chat (renderer).** `chat-page.tsx` sends `/chat?made=<id>` to `AgentMadeChatPane` (`apps/web/components/agent-made-chat-pane.tsx`), which gives `ChatSession` a generalist-shaped shell (`madeShellAgent`, `agentId` = the made agent's row, no tools in the shell) and two shell fields: `threadHref`, so a thread opens at `/chat?made=<id>&thread=<id>`, and `emptyState`, which replaces the mode's home. `activeAgentId` (`apps/web/lib/virtual-agents.ts`) returns null on `?made=`, so the default agent is not highlighted there. The made chat has no History or Harness controls, and it does not list the agent's older threads yet.
- **Virtual agents page (renderer).** The page lists the made agents in a "Made from a prompt" section (`data-testid="agents-made"`). A deletable one gets Remove, which opens the same confirm as the rail.
- **Renderer not driven.** No browser drive of the ⋯ menu, the confirm, the draft or create against a live model, or the redirect. The rail draws whatever the host lists under `madeFromPrompt`; the host decides which agents those are.

- **Not built.** Sharing a prompt-made agent with a Workspace (`project_agents` holds mode ids only), and a per-person billing line for the draft call.

## Known limits

- **A mode agent reads private material and can send a question to the web.** A mode agent now gets the desk's Knowledge Base excerpts and its own earlier chats in the prompt (`runs.ts:182-189`), and binds `web_search`, `web_fetch` and `research_dossier`. The egress guard (`packages/core/src/runtime/egress-guard.ts`, created at `packages/core/src/runtime/ai-sdk-runtime.ts:461`) is the only brake, and it stops less than the name suggests. Read from its header (`egress-guard.ts:5-20`) and code (`egress-guard.ts:150-169`):
  - It refuses **`web_fetch` only** (`FETCH_TOOL`, `egress-guard.ts:39`; `beforeCall`, `egress-guard.ts:150-159`), and only after a tool with `trust: "user_content"` has run in the same turn (the file tools, `run_code`, `knowledge_search`, `past_sessions`). It then allows only a host the person named in a message of their own, or one a `web_search` in the same turn returned.
  - It does **not** stop `web_search` or `research_dossier`. The guard checks no other tool, and both are `trust: "network"` (`research-dossier-tool.ts:103`; `packages/core/src/tools/platform/web-search.ts:71`). After a private read, a model can still put private text in a search query or in a dossier question.
  - It does **not** see what enters through the prompt. Knowledge excerpts and the earlier-chats hint are in the system prompt (`runs.ts:212`), not the output of a tool, so reading them does not taint the run, and a `web_fetch` to a host the person named stays open.
  - The header names its own gaps: a host the person named is trusted, a host in search results is trusted, and a new turn starts untainted.
  - This is the same exposure Chat has. It is new for a mode agent, which had neither before 2026-10-09. The plan's risk 5 asked for a ruling in C0; none was made. The code treats a worker like `web_search` (`CHAT_WORKERS` comment, `packages/core/src/agents/virtual-agents.ts:70-72`). Not driven.
- **The watchdog change reaches every turn of the default agent and the mode agents.** See section 4, step 4. It is in a protected shared file (`runs.ts`), so a merge from `main` can touch it. The 8 minute ceiling is read from code. In a browser the client's cap ends a turn first (next item), so the ceiling is not reached from webdev.
- **The client cuts a long turn off at the first-token budget.** I read this and did not drive it; the longest run driven on 2026-10-09 took about 85 s, well inside the cap. `ChatComposer.send` arms `armStreamWatchdog` (`chat-composer.tsx:508`) and feeds it only `dog.touch()` from `readRunStream` (`:548`, `:610`). Nothing in `apps/web` calls `touchOutput`. In `armStreamWatchdog` (`packages/core/src/runtime/stream-watchdog.ts:138`), `streaming` becomes true only in `touchOutput` (`:168`), and until then `streamWatchdogDeadline` (`:88`) returns `startedAt + ttfbMs` whatever `touch()` did. So the deadline is a hard cap from the moment of the send: 240 s for Daily and Reasoning, 120 s for Fastest (`tierStreamLimits`, `apps/web/lib/chat-tier-pref.ts:229`, which gives the long budget to Daily and Reasoning and none to Fastest). The same arming and the same `touch`-only feed are on `main` (`apps/web/components/chat-composer.tsx:491` and `:534` in `C:\Users\rizky\agentforge`, where the model id is the label). On abort the host stops the run: `res.on("close")` aborts (`packages/host/src/http-adapter.ts:665-669`), the handler passes `request.abortSignal` (`packages/host/src/handlers/runs.ts:60`), `onClientAbort` aborts `modelAbort` (`runs.ts:270-279`), the worker channel carries that signal (`runs.ts:478`), and `generateResearchNotes` stops at `throwIfJobAborted` before it saves (`research-generate.ts:184`). - **The identity line is an instruction to the model, not an enforced rule.** A mode agent introduces itself as it does because its prompt and its closing line say so (`packages/core/src/agents/virtual-agents.ts:208-213`, `:219-222`). ## Why

- **Why every agent is a full chat.** `[Direct]` the owner, 2026-10-09, instructions 2 and 3 at the top of this page. It departs from the plan's "a bot is one harness" (`chat-first-plan.md`, "Second reference") and from the advice that a prompt-only agent is what the product is not. It is the owner's call. What keeps it honest: the tools and budget are still the host's, and the screen and the prompt say where the specialty's checked run lives.
- **Why prompt, tools and budget come from code and not from the row.** `[Direct]` `packages/host/src/virtual-agents.ts:26-28`: nothing stored on a desk can widen what an agent may do. This holds for a mode agent. The default agent still takes its prompt and bindings from its stored row, as Chat always did.
- **Why a mode agent has a closing line.** `[Direct]` the comment at `packages/core/src/agents/virtual-agents.ts:52-58`: the Soul block names the desk's default assistant and tells the model to use that name and no other, and the Images agent answered with it when driven.
- **Why the default agent is the brand's character.** `[Direct]` the owner, instruction 1 at the top of this page. On the public brand the character carries the product's name; the HYP AI brand's name for it is a setting that is not wired yet (section 5).
- **Why virtual agents at all.** `[Direct]` the owner, 2026-10-09: "we're going to revamp this to be more like muse and hark style, focuses on UIUX of the chat mode, removing all the workspaces and hide them, also to rebrand the name of workspaces into virtual agents, with each using their own harness and with skill and tools embed inside". "Hark" was named as a look reference; no screenshot or link for it is on file, so the layout follows the two 2026-10-06 references only.
