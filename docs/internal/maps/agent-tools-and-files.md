## Overview

On 2026-10-03 every product mode got one declared harness, and the modes that call a model got tools to match. A harness is a typed spec, `ModeHarnessSpec`, that holds the loop kind, the tools the mode may bind, a step and tool-call budget, and the number of check-and-repair rounds. The runtime enforces the budget. The job runner cuts a job's tools to the spec. `runChecked` makes a mode's output pass its checks before the run counts as done. Six file tools sit on top of two file roots: the desk's own versioned store on both products, and on Personal a real folder whose changes wait for the owner's approval. A seventh tool, `run_code`, runs a short Python or JavaScript program in a sandbox of its own (§ 12) and saves what it writes as files on the desk.

It is not the model-selection layer ([`model-policy.md`](model-policy.md)) and not Knowledge ingest ([`knowledge-ingest-loop.md`](knowledge-ingest-loop.md)). It adds no rail entry. Files appear inside the Knowledge Base page and the Thinking disclosure in Chat. The plan and the owner's calls of 2026-10-03 are in [`../mode-harness-tools-plan.md`](../mode-harness-tools-plan.md).

## How it works

### 1. One spec per mode

`ModeHarnessSpec` (`packages/core/src/harness/spec.ts:20`) has `mode`, `loop`, `tools`, `budget`, `repairRounds` and the descriptive `skills`. `HarnessLoop` (`packages/core/src/harness/spec.ts:9`) is `agent` (the model calls tools in a loop), `pipeline` (host code calls the model at fixed stages), `media` (a generation endpoint, no model loop) or `none`. `RunBudget` (`packages/core/src/harness/spec.ts:11`) is `maxSteps`, `maxToolCalls` and an optional `perTool` map. `MODE_HARNESS_SPECS` (`packages/core/src/harness/specs.ts:19`) is typed `Record<ProductMode, ModeHarnessSpec>`, so a new mode without a spec does not compile, and `harnessSpecFor` (`packages/core/src/harness/specs.ts:36`) reads it. One file per mode under `packages/core/src/harness/modes/` is the only place its tools and numbers live. The default is `DEFAULT_RUN_BUDGET` (`packages/core/src/harness/defaults.ts:14`): `DEFAULT_MAX_STEPS` is 6 and `DEFAULT_MAX_TOOL_CALLS` is 60, a ceiling no six-step run reaches.

A job call that carries no `jobMode` is not a studio run and keeps what it asked for. ### 3. The runtime budget

`AgentRuntime.execute` takes an optional `budget` (`packages/core/src/runtime/types.ts:80`). `createToolBudget` (`packages/core/src/runtime/tool-budget.ts:33`) makes one counter for a whole `execute`: `AiSdkRuntime.stream` builds it once (`packages/core/src/runtime/ai-sdk-runtime.ts:449`) ahead of every attempt, so a wire fallback or a contact retry cannot reset the count. Its `admit` (`packages/core/src/runtime/tool-budget.ts:40`) checks the run total first and then the tool's own `perTool` ceiling, counts only the calls it lets through, and otherwise returns a `BudgetRefusal` (`packages/core/src/harness/spec.ts:48`): `{ ok: false, reason: "budget", message }`. When the run total is spent the message says to call no more tools and answer with what it has; when one tool's ceiling is spent it says to use another tool or answer. `maxSteps` comes from `resolveMaxSteps` (`packages/core/src/runtime/tool-budget.ts:16`) at `packages/core/src/runtime/ai-sdk-runtime.ts:684`. With no budget the run keeps 6 steps and no tool-call cap. `StubRuntime` honours the same counter (`packages/core/src/runtime/stub-runtime.ts:64`).

Every tool call goes through `invokeToolGuarded` (`packages/core/src/runtime/invoke-guarded.ts:24`), in this order:

1. The budget: `budget?.admit(tool.key)` (`packages/core/src/runtime/invoke-guarded.ts:31`). A refusal is reported to the tool I/O sink like any other answer and the tool does not run.
2. The egress guard (SR-112): `egress?.beforeCall(tool.key, rawArgs)` (`packages/core/src/runtime/invoke-guarded.ts:37`). Once any `user_content` tool has answered in this run, `web_fetch` opens only a host the person named in their own messages or one a `web_search` in the same run returned; any other fetch returns `{ ok: false, reason: "egress", message }` and runs nothing (`createEgressGuard`, `packages/core/src/runtime/egress-guard.ts:140`). The refused call has already spent its budget slot. Each runtime makes one guard per `execute`, beside the budget (`packages/core/src/runtime/ai-sdk-runtime.ts:451`).
3. The disabled-tools list (`packages/core/src/runtime/invoke-guarded.ts:43`).
4. The injection scan of the arguments, `scanJson(rawArgs)` (`packages/core/src/runtime/invoke-guarded.ts:49-50`), unless the owner's `injectionGuardBypass` setting is on (`getInjectionGuardBypass`).
5. `invokeTool`, which validates the arguments against the tool's Zod schema (`:60`), then `egress?.afterCall` records what the call learned (`:67`).
6. `thinToolOutput` (`packages/core/src/runtime/invoke-guarded.ts:68`), which clones the result and trims it for the model.
7. For a tool whose `trust` is not `internal`, the injection scan of the thinned output (`packages/core/src/runtime/invoke-guarded.ts:70`). A hit replaces the output with `{ success: false, error: "Blocked by injection guard (rule: …)" }`.

That is the guard. The model reaches it through `buildAiTools` (`packages/core/src/runtime/ai-tools.ts:31`), which `AiSdkRuntime.stream` calls once per `execute` (`packages/core/src/runtime/ai-sdk-runtime.ts:448`). Three things sit around the call, and § 13 has the detail: a tool that throws comes back to the model as a `tool_error` result instead of ending the run, a tool that is disabled stays in the SDK's map (hidden from the model's list) so a call to it is refused instead of ending the run, and the stream is read for a run that ended at its step cap.

It replaces the hand-kept `NETWORK_SOURCED_TOOLS` set in `invoke-guarded.ts`, which no longer exists. `web_search` (`packages/core/src/tools/platform/web-search.ts:71`) and `web_fetch` (`packages/core/src/tools/platform/web-fetch.ts:57`) are `network`. The six file tools (`packages/core/src/tools/files/tools.ts`), `knowledge_search` (`packages/host/src/knowledge-search-tool.ts`, `knowledgeSearchTool`), `past_sessions` (`packages/host/src/session-tools.ts:9`) and `run_code` (`packages/host/src/code-runner/run-code-tool.ts:223`) are `user_content`: text the owner or a web page wrote, not text the host computed. The output scan screens a note that says "ignore your instructions" before the model reads it. It is a rule list (`scanInjection`, `packages/core/src/security/injection-guard.ts:77`), so it catches known phrasings and not every injection.

### 5. `runChecked`: done is a check that passes

`runChecked` (`packages/host/src/harness/run-checked.ts:71`) takes `produce`, `checks`, `repairRounds` and an optional `signal` and `onRound`. It calls `produce(null, 0)`, runs every `OutputCheck` (`packages/core/src/harness/spec.ts:42`) and, when one fails and rounds remain, calls `produce(note, round)` again with a note built by `formatRepairNote` (`packages/host/src/harness/run-checked.ts:35`): a fixed header and, per failed check, the three lines `ERROR:`, `WHY:` and `FIX:`. The loop stops when every check passes or `round >= repairRounds` (`packages/host/src/harness/run-checked.ts:79`); the result carries the last output, the verdicts, the rounds spent and `passed`. A check that throws counts as a failure with a fixed "could not run" verdict, and its own message is dropped because it may quote the output (`runOne`, `packages/host/src/harness/run-checked.ts:48`). A cancel rethrows the signal's reason. The note is English and fixed; the caller's prompt carries the output language.

### 6. The six file tools

`list_files`, `read_file`, `write_file`, `edit_file`, `search_files` and `delete_file` (`FILE_TOOLS`, `packages/core/src/tools/files/tools.ts:233`) are registered by `registerFileTools` (`packages/core/src/tools/files/register.ts:4`). Each takes `root`, `"desk"` by default or `"folder"` (`rootSchema`, `packages/core/src/tools/files/tools.ts:17`), and the tool bodies never branch on which it is: they ask for a root and call the `FileRoot` interface (`packages/core/src/tools/files/types.ts`: `list`, `read`, `write`, `remove`, `search`).

- **Paths.** `parseDeskPath` (`packages/core/src/tools/files/path.ts:61`) is the one place a model's string becomes a `DeskPath`. It refuses an empty path, more than 240 characters, 8 parts or 120 characters in one part (`MAX_PATH_CHARS`, `MAX_PATH_SEGMENTS`, `MAX_SEGMENT_CHARS`, `packages/core/src/tools/files/path.ts:4-6`), control and bidi-override characters, a backslash, a leading `/`, a drive letter, empty, `.` and `..` parts, a part that ends in a dot or space, the characters `< > : " | ? *`, and the Windows device names. The rules are the strictest of the two roots, so one parse serves both.
- **Reads.** `read_file` returns `formatNumberedLines` (`packages/core/src/tools/files/numbered-lines.ts:28`): a tab after a 1-based line number, at most `MAX_READ_LINES` (2000) lines, each cut at `MAX_LINE_CHARS` (2000) (`packages/core/src/tools/files/lines.ts:1-2`), with `offset` and `limit` and a `truncated` flag. `list_files` shows at most `MAX_LIST_ENTRIES` (500) entries (`packages/core/src/tools/files/tools.ts:15`), sets `truncated`, and takes a `dir` and a `glob` (`checkGlob`, `packages/core/src/tools/files/glob.ts:140`: 200 characters, `*` and `?` inside one folder, a whole `**` part across folders, `{a,b}` with at most 64 expansions, case sensitive).
- **Writes.** `write_file` and `edit_file` refuse content over `MAX_FILE_BYTES` (2 MB, `packages/core/src/tools/files/lines.ts:3`, counted in UTF-8 bytes by `checkContentSize`, `packages/core/src/tools/files/tool-support.ts:62`). `edit_file` reads the file, applies `applyExactEdit` (`packages/core/src/tools/files/edit-text.ts:19`) and writes the whole result with compare-and-set: `root.write(parsed, edited.text, author, { expectedSha256: file.sha256 })` (`packages/core/src/tools/files/tools.ts:163`; `WriteOptions`, `packages/core/src/tools/files/types.ts:52`). The write applies only if the file still has the hash the edit was computed from; otherwise the root refuses with `conflict` and the tool description tells the model to read the file again and redo the edit. `write_file` passes no hash and overwrites, which is what a rewrite means. `old_string` must occur exactly once unless `replace_all` is set: no match is `no_match`, two or more is `ambiguous_match`, an empty or unchanged `old_string` is `bad_pattern`. `matchFileLineEndings` (`packages/core/src/tools/files/edit-text.ts:55`) gives a snippet CRLF endings when the whole file uses CRLF.
- **Search.** `search_files` matches plain text, case sensitive, within one line, with at most `MAX_SEARCH_HITS` (200) hits of `MAX_HIT_TEXT_CHARS` (300) characters (`packages/core/src/tools/files/search-text.ts:7-9`), a pattern of at most 200 characters, and a `truncated` flag. With `regex: true` the tool searches itself over `list` and `read` (`searchByRegex`, `packages/core/src/tools/files/search-regex.ts:19`, at most `MAX_SCAN_FILES` 2000 files and `MAX_SCAN_BYTES` 32 MB) and runs each pattern in a `node:vm` context with a 4 s budget for the whole search and 1 s per file (`createRegexScanner`, `packages/core/src/tools/files/search-text.ts:98`), because a JavaScript regex cannot be interrupted from outside.
- **Answers.** A success is `{ ok: true, root, … }`. A write answers `{ status: "saved", path, version }` on the desk, or `{ status: "pending_approval", path, proposalId, message }` on the folder with a fixed `PENDING_APPROVAL_MESSAGE` (`packages/core/src/tools/files/tool-support.ts:24`) that tells the model to say the change is waiting (`writeResult`, `packages/core/src/tools/files/tool-support.ts:47`). A refusal is `{ ok: false, code, message }` where `code` is one of the eleven `FileRefusalCode` values (`packages/core/src/tools/files/types.ts:66`): `bad_path`, `not_found`, `too_large`, `too_many_files`, `denied`, `no_match`, `bad_pattern`, `ambiguous_match`, `root_unavailable`, `quota`, `conflict`. `withRoot` (`packages/core/src/tools/files/tool-support.ts:31`) turns anything a root throws into a refusal: a `FileRootError` keeps its code and message, and any other error becomes a fixed `root_unavailable` sentence, because an OS error can carry an absolute path (`toFileRefusal`, `packages/core/src/tools/files/refusals.ts:34`).

### 7. Choosing the root

Core cannot import the host, so the root comes through a seam. `setFileRootResolver` (`packages/core/src/tools/files/resolver.ts:16`) holds one `FileRootResolver`, and `ensureToolsRegistered` installs the host's (`packages/host/src/register-tools.ts:33-34`: `registerFileTools()`, then `setFileRootResolver(resolveHostFileRoot)`). `resolveHostFileRoot` (`packages/host/src/file-roots.ts:18`) builds the author, then returns `createDeskRoot(tenant, author)` for `desk` and `createFolderRoot(tenant, author)` for `folder`, which is either a root or a refusal. With no resolver installed, `resolveFileRoot` (`packages/core/src/tools/files/resolver.ts:24`) answers `root_unavailable`.

`currentAgentAuthor` (`packages/host/src/file-roots.ts:9`) decides who is recorded: the tool run that a job or a Chat turn set with `withToolRun` gives `{ kind: "agent", runId, mode }`; with no tool run it falls back to the thread id and `"chat"` when a thread context exists, and to `"unscoped"` and `"unknown"` when neither does. Chat sets a tool run for every turn (`inChatRun`, `packages/host/src/runs.ts:307`), so the `author_id` on a version a Chat turn wrote is that turn's run id and its `mode` is `chat`. The thread-id fallback is what a Chat write recorded before Chat set a tool run (the comment at `packages/host/src/runs.ts:304-306` says so); versions saved then keep it, and `packages/host/src/runs-tool-run.test.ts` pins the new behaviour.

### 8. The desk root: versioned files on both products

**Schema.** Migration `0022_desk_files.sql` creates three tables, and `ensureDeskFileTables` (`packages/db/src/ensure-schema.ts:636`) mirrors them for a database that was baseline-stamped past the migration. `desk_files` has one row per path with `head_version`, `bytes`, `mime`, `sha256` and `deleted_at`; a partial unique index (`desk_files_live_path_unique`) makes a live path unique per desk while a deleted one is not. `desk_file_versions` has one row per version with `object_key`, `bytes`, `sha256`, `author_kind` (`user` or `agent`), `author_id`, `mode` and `created_at`. `file_proposals` belongs to the folder root (§ 9). Drizzle declarations are `deskFiles`, `deskFileVersions` and `fileProposals` in `packages/db/src/schema.ts`.

**Bodies are not in the tables.** A version row names a sealed object, written through `putTenantObject` (`packages/host/src/tenant-storage.ts:540`) under the tenant's own prefix as `desk-files/<fileId>/<version>` (`DESK_OBJECT_DIR`, `packages/host/src/desk-files/file-store.ts:32`). `sealBody` (`packages/host/src/desk-files/body.ts:8`) wraps the text in the artifact envelope (AES-256-GCM under the wrap key); `openBody` (`packages/host/src/desk-files/body.ts:18`) refuses anything that is not that envelope instead of returning the stored bytes as the file's text.

**Saving.** `createDeskFileStore` (`packages/host/src/desk-files/file-store.ts:125`) holds the logic and takes the database and the key as arguments, so a test hands it a scratch database; `store.ts` binds it to the app database. A write runs `saveLocked` (`packages/host/src/desk-files/file-store.ts:213`) inside `withDeskLock` (`packages/host/src/desk-files/lock.ts:11`), a per-desk queue. The lock is what makes step 2 sound: the head is read and the new version committed with no other save of this desk in between.

1. `checkContent` (`packages/host/src/desk-files/file-store.ts:105`, called at `:221`) refuses over 2 MB, a NUL character, or a lone surrogate (`denied`, `too_large`).
2. **Compare-and-set.** When the caller passed `expectedSha256` and the live head does not have that hash, or the file was deleted since, the write throws `conflict` (`packages/host/src/desk-files/file-store.ts:227-229`, message `CONFLICT_MESSAGE` at `:39`). This runs before the no-op shortcut on purpose: a stale edit that happens to equal the head is still a lost update for the caller, which computed it from older text. A caller that passes no hash, which is every `write_file`, the Files section and the routes, overwrites.
3. If the sha256 equals the live head's, it answers the current version and writes nothing (`packages/host/src/desk-files/file-store.ts:230`).
4. A new path must have room: `assertRoomFor` (`packages/host/src/desk-files/file-store.ts:186`, called at `:234`) refuses file number 2001 (`MAX_DESK_FILES`) with `too_many_files`, a name that is already a file used as a folder, and a path that is a folder with files in it.
5. The sealed object is written first (`putSealed`, `:239`), then the head and version rows commit in one transaction (`:244-265`); if the rows do not commit, the object is removed (`:266-272`). The head update is guarded by `head_version`, so a second writer that got past the lock would fail rather than overwrite.

A delete sets `deleted_at` and keeps the rows and the objects (`remove`, `packages/host/src/desk-files/file-store.ts:332`). A revert (`revertTo`, `packages/host/src/desk-files/file-store.ts:409`) saves the old version's text as a new version, so history only grows, and reverting to the head changes nothing. A write to a deleted path starts a new `desk_files` row at version 1 under a new file id. `search` decrypts live files and reads at most `MAX_SEARCH_READ_BYTES` (50 MB) of plain text per call (`packages/host/src/desk-files/file-store.ts:349`). `purgeDeskFiles` (`packages/host/src/desk-files/store.ts:49`) removes a desk's objects, then its rows (`purgeDesk`, `packages/host/src/desk-files/file-store.ts:415`), and `handleDeleteWorkspace` calls it before the desk row goes (`packages/host/src/handlers/workspaces.ts:178`).

**Quota.** `putTenantObject` counts every sealed version against the tenant only in server mode; off the hosted server it puts the bytes and refuses nothing (`packages/host/src/tenant-storage.ts:551`). A refusal surfaces as the `quota` code, and as `storage_quota_exceeded` on the routes (`toApiError`, `packages/host/src/desk-files/routes.ts:46`). Deleting a file does not give the bytes back; `purgeDeskFiles` and the tenant erase do.

**Routes.** `DESK_FILE_ROUTES` (`packages/host/src/desk-files/routes.ts:172`), spread into the router at `packages/host/src/router.ts:427`. Paths ride in the query string, never in the URL, so a file name needs no escaping and the by-id surface the tenancy harness counts does not grow. They are not model routes, so the gateway gate does not apply. The desk and tenant come from `getTenant`, and every query in the store carries the desk id, so another desk's path is a 404.

| Route | Does |
|---|---|
| `GET /api/v1/files` (query `dir`, `glob`) | `{ items: FileEntry[] }`: `path`, `kind`, `bytes`, `updatedAt`, `version` |
| `GET /api/v1/files/content?path=` | the head: `path`, `text`, `sha256`, `bytes`, `version` |
| `GET /api/v1/files/download?path=` | the head as bytes with a file name, for the Download controls (below the table) |
| `GET /api/v1/files/versions?path=` | `{ items }` of `{ version, bytes, sha256, authorKind, authorId, mode, createdAt }`, oldest first |
| `GET /api/v1/files/version?path=&version=` | one version's text |
| `POST /api/v1/files` body `{ path, content }` | saves as the signed-in person (`author_kind` `user`, `author_id` the user id) |
| `POST /api/v1/files/revert` body `{ path, version }` | a new version holding an old body |
| `DELETE /api/v1/files?path=` | soft delete |

`REFUSAL_STATUS` (`packages/host/src/desk-files/routes.ts:30`) maps the refusal codes to statuses: `bad_path` 400, `not_found` 404, `too_large` 413, `too_many_files` 409, `denied` 400, `no_match`, `bad_pattern` and `ambiguous_match` 400, `root_unavailable` 503, `quota` 403, and `conflict` 409. No desk route passes `expectedSha256`, so `conflict` reaches a client only if a route starts to.

**Download.** `handleGetFileDownload` (`packages/host/src/desk-files/routes.ts:122`) reads the head through the same `deskRootFor` and `root.read` as `/content`, so the desk, the tenant, the path rules and the 404 for another tenant's path are the ones every other desk route has. It answers a bytes result: the UTF-8 text, the file's own name (the last path part, `deskFileName`, `packages/host/src/desk-files/download.ts`), and the headers from `deskFileDelivery` (`download.ts:40`). The type is `mimeForPath`'s label for plain text kinds (`text/markdown`, `text/plain`, `text/csv`, `text/tab-separated-values`, `application/json`, `application/yaml`, each with `; charset=utf-8`) and `application/octet-stream` for anything else, which includes `.html` and `.xml`, so a browser never renders a file an agent wrote (the saved copy keeps its extension). The headers are `Content-Disposition: attachment`, `X-Content-Type-Options: nosniff`, `Content-Security-Policy: sandbox` and `Cache-Control: no-store`. The last one overrides the adapter's one-hour private cache for any bytes result (`packages/host/src/http-adapter.ts:342`), which would hand back an old version after an edit. Only the newest version is served; the viewer therefore offers Download on the newest version only. Packaged, the same route runs over IPC and `apiFetch` opens the native save dialog (§ 11).

**A fourth writer (2026-10-06).** Besides the file tools, the sandbox and the Files routes, the Chat composer's save route (`POST /api/v1/chat/documents/save`, called when a message with an attached document is sent) writes the extracted text of that file as `uploads/~<user folder>/<file name>.md` (`saveDeskCopy`, `packages/host/src/chat-documents/desk-copy.ts:39`), authored as the signed-in person, through the same desk root write. It takes the same versioning, 2 MB limit, 2000-file ceiling and tenant quota; a longer text is cut to fit under 2 MB. The text is masked before it is written, because the file tools' output is not masked on its way to the model. [`chat-documents.md`](chat-documents.md) § 4.

**Private folders under `uploads/` (owner's decision, 2026-10-06).** On a hosted team desk a document a person attaches in Chat is private to that person: even inside one company, each person's own material is theirs. A folder `uploads/~<id>/` belongs to the person whose folder name it is and to nobody else, the business owner and the admins included. The rule is the host's and sits next to the store, not in the renderer: `canSeePath` (`packages/host/src/desk-files/private-uploads.ts:44`) is asked on every path through the desk file store. `assertVisible` (`file-store.ts:143`) guards write (`:220`), the version read (`:277`, which revert goes through), read and remove; the filters in `list` and `search` hide the rows, so glob is covered too. Another person's folder answers "not found", so its existence does not leak. A caller with no user id, such as a background run, sees none of them, and a person cannot create a folder with another person's name. `list_files`, `read_file`, `write_file`, `edit_file`, `search_files`, `delete_file`, the Files routes and the `run_code` input files all read through this one root, so none needs a rule of its own. Off the hosted server nothing is guarded: Personal has one person per desk and behaves as before (`private-uploads-store.test.ts`, "parity"). Still design only: an owner or admin deciding whether a leaver's files are deleted or kept (never opened), and sharing through a bot instead of a switch on a file.

### 9. The folder root: Personal only, writes wait for approval

**Availability.** `folderRootAvailable` (`packages/host/src/folder-root/availability.ts:11`) is `hostCapabilities().localPaths && !isServerMode()`, read on every call. On the hosted server every folder route except the status read answers 403 `folder_unavailable` (`requireAvailable`, `packages/host/src/folder-root/routes.ts:26`), the status read answers `{ mounted: false, name: null, available: false }` (`UNAVAILABLE_STATUS`, `packages/host/src/folder-root/mount-service.ts:19`), and `createFolderRoot` (`packages/host/src/folder-root/folder-root.ts:143`) returns a `root_unavailable` refusal. A folder path means something only when the host is the owner's own process.

**Opening a folder.** The path comes from the native picker and nowhere else:

1. The renderer's `pickDesktopFolder` (`apps/web/lib/desktop-bridge.ts:158`) calls the preload's `pickFolder` (`apps/desktop/preload.cjs:59`), which invokes the IPC handler `agentforge:pick-folder` (`apps/desktop/main.cjs:584`). The handler checks `isTrustedSender`, opens `dialog.showOpenDialog` with `openDirectory` parented to the main window, and returns `{ path }` or `{ canceled: true }`. The shell does not stat, read or list the folder.
2. The renderer posts the path to `POST /api/v1/folder/mount`. The route refuses any request whose `x-agentforge-transport` header is not `ipc` (`packages/host/src/folder-root/routes.ts:65`) with 403 `folder_mount_ipc_only`. The IPC path sets that header (`apps/desktop/main.cjs:483`), and the HTTP adapter overwrites it with `http` on every request (`packages/host/src/http-adapter.ts:689`), so a page cannot claim IPC.
3. `mountFolder` (`packages/host/src/folder-root/mount-service.ts:35`) runs `checkMountPath` (`packages/host/src/folder-root/mount-validate.ts:141`). It takes the real path and refuses, with a fixed sentence per reason (`MOUNT_REFUSAL_REASONS`, `packages/host/src/folder-root/mount-validate.ts:9`), a relative path, a missing one, a non-directory, a drive root, the home directory, the app's own data directory or any ancestor of it, a system directory, and a path with a `.git`, `.ssh`, `.aws` or `.gnupg` segment. Picking a different folder than before rejects every pending proposal for the desk first.
4. The mount is a record in `folder-mounts.json` in the local data dir (`FOLDER_MOUNT_FILE`, `packages/host/src/folder-root/constants.ts:21`), keyed by desk id and written by temp file and rename with mode 0600 (`writeMountFile`, `packages/host/src/folder-root/mount-record.ts:59`). It is machine-local on purpose.

**Every use re-checks the mount.** `openMount` (`packages/host/src/folder-root/mount.ts:19`) reads the record, runs `checkMountPath` again and insists on the same real path, so a folder that was deleted, replaced by a link elsewhere or moved under a system directory stops being a root. Closing the folder (`unmountFolder`, `packages/host/src/folder-root/mount-service.ts:53`) rejects whatever was waiting and clears the record.

**Reads touch the disk and are contained.** `parseRelPath` (`packages/host/src/folder-root/contain.ts:23`) re-parses the path (this root is the one that touches a real disk and does not trust the caller) and `resolveInside` (`packages/host/src/folder-root/contain.ts:72`) resolves it by real path inside the root. Names the agent may not read or write are refused by name, case-insensitively, wherever they appear in a path (`DENIED_EXACT`, `packages/host/src/folder-root/denied-names.ts:8`): `.env`, `.envrc`, `.npmrc`, `.netrc`, `.git-credentials`, anything starting `.env.`, `id_rsa`, `id_ed25519`, `id_ecdsa` or `id_dsa`, the extensions `.pem .key .p12 .pfx`, and the directories `.git`, `.ssh`, `.aws`, `.gnupg`. `node_modules`, `dist`, `build`, `.next` and `.turbo` are left out of listings and searches (`SKIPPED_DIRS`, `packages/host/src/folder-root/denied-names.ts:26`) but can be read by path. A file over 2 MB or with a NUL byte in its first 8 KB is not read as text (`FOLDER_TEXT_MAX_BYTES`, `FOLDER_BINARY_SNIFF_BYTES`, `packages/host/src/folder-root/constants.ts:4-7`). Listing stops at 5000 entries and `search` at 50 MB (`packages/host/src/folder-root/constants.ts:9-10`).

**Writes and deletes are proposals.** `write` and `remove` in `createFolderRoot` never touch the disk. They call `propose` (`packages/host/src/folder-root/folder-root.ts:154`), which refuses with `too_many_files` when 50 proposals are pending for the desk (`FOLDER_PENDING_MAX`, `packages/host/src/folder-root/constants.ts:14`; a path that already has a pending proposal may replace it at the ceiling), then `store.propose`. The store (`createProposalStore`, `packages/host/src/folder-root/proposal-store.ts:100`) rejects any earlier pending proposal for the same desk and path in the same transaction (`proposeTx`, `packages/host/src/folder-root/proposal-store.ts:117`), so a desk holds one per path, and seals the proposed text with the vault key (`file_proposals.after_body`). The proposal records `before_sha256`. For a delete, and for a write with no hash, that is the hash of the file when the agent proposed. For an `edit_file` it is the hash of the text the edit was computed from (`const before = options?.expectedSha256 ?? current`, `packages/host/src/folder-root/folder-root.ts:202`), even if the file changed on disk since the read, so approving then finds a different hash and answers `stale` instead of applying a diff over text the model never saw. The folder root has no `conflict` refusal: it proposes and lets the approval step compare. The tool answers `pending_approval`.

**The owner decides.** `getProposalDiff` (`packages/host/src/folder-root/decisions.ts:70`) returns the file now, the text it would become and `stale`, true when the hash of the file now is not `before_sha256`. `approveProposal` (`packages/host/src/folder-root/decisions.ts:90`) requires `pending` and a mounted folder, claims the proposal once (`store.claim`, `pending` to `approved`, so two clicks or two windows cannot apply it twice), then `applyChange` (`packages/host/src/folder-root/apply-change.ts:83`) reads the file again. If its hash differs from `before_sha256`, or the file exists when the proposal said it should not (or the reverse), nothing is written and the outcome is `stale`. Otherwise it writes a temp file in the same directory, flushes it and renames it over the target, keeping the file's mode on macOS and Linux (`writeAtomically`, `packages/host/src/folder-root/apply-change.ts:46`), or unlinks for a delete. The outcome is `applied`, `stale` or `failed` with reason `denied` or `io_error`. `rejectProposal` (`packages/host/src/folder-root/decisions.ts:109`) moves `pending` to `rejected`.

| Route (`packages/host/src/folder-root/routes.ts:99-105`) | Does |
|---|---|
| `GET /api/v1/folder` | `{ available, mounted, name }`; `name` is the last path segment, never the path. Answers on every host. |
| `POST /api/v1/folder/mount` body `{ path }` | IPC only |
| `DELETE /api/v1/folder/mount` | close and reject pending |
| `GET /api/v1/folder/proposals?status=` | summaries (id, path, kind, status, runId, times), at most 200, bodies left out |
| `GET /api/v1/folder/proposals/:proposalId` | the diff |
| `POST /api/v1/folder/proposals/:proposalId/approve` | `{ id, status: "applied" \| "stale" \| "failed", reason? }` |
| `POST /api/v1/folder/proposals/:proposalId/reject` | `{ id, status: "rejected" }` |

Deleting the desk clears the mount and the proposals. `handleDeleteWorkspace` calls `forgetFolderMount` (`packages/host/src/handlers/workspaces.ts:189`, an alias of `clearMount`, `packages/host/src/folder-root/index.ts:9`) and then `purgeFolderProposals` (`packages/host/src/handlers/workspaces.ts:191`). `purgeFolderProposals` (`packages/host/src/folder-root/purge.ts:11`) deletes every `file_proposals` row of the desk, pending or decided, through the store's `purgeDesk` (`packages/host/src/folder-root/proposal-store.ts:215`) and returns how many went. It does not look at whether a folder root is available, because the rows exist or they do not. It matters because a proposal holds a sealed copy of the text an agent wanted to write, and nothing in the app can reach a deleted desk's proposals. `packages/host/src/folder-root/purge.test.ts` covers it.

Where there is no folder, the surface renders nothing at all.

### 12. `run_code`: a program in a sandbox

`run_code` (`runCodeTool`, `packages/host/src/code-runner/run-code-tool.ts:218`) lets the model run a short Python or JavaScript program and read what it prints. `registerCodeTools` (`run-code-tool.ts:228`) registers it from `ensureToolsRegistered` (`packages/host/src/register-tools.ts:36`). It is `user_content` trust, so its output is scanned like a file read (§ 4). Chat binds it through `DEFAULT_CHAT_TOOLS` (6 calls a turn) and Data through `dataHarnessSpec` (4 calls a job). Finance and Market never get it, because their figures must come from code the host owns (plan Appendix A3, [`../mode-harness-tools-plan.md`](../mode-harness-tools-plan.md)). The isolation was chosen by a prototype recorded in the plan's Appendix A2: a worker thread was not enough, so each sandbox is a hardened child process.

**One call, start to finish.** `runCodeForTenant` (`run-code-tool.ts:165`) does four things.

1. `readInputs` (`run-code-tool.ts:96`) reads the desk files named in `files`: at most 20 (`MAX_INPUT_FILES`, the schema at `:58`), 20 MB together (`MAX_INPUT_BYTES`), each path parsed by `parseDeskPath` and read from the desk root only, never the Personal folder (`defaultFileAccess`, `:64`). A bad path, a missing file or too many bytes comes back to the model as a refusal with a reason class (`reasonForRefusal`, `:86`: `too_large` for size, count and quota, `unavailable` for a root that is down, `runtime` for the rest). No child starts.
2. `sandboxRunner().run(...)` (the shared runner from `createSandboxRunner`, `packages/host/src/code-runner/run-code.ts:188`; the accessor is at `:265`) refuses early with `too_large` when the code is over 100 KB or the inputs are over their caps (`checkRequest`, `:69`), and with `unavailable` when the ship directory is not usable or lacks that language (`checkShip`, `ship.ts:200`).
3. It takes a run slot (`createCodeLimiter`, `packages/host/src/code-runner/code-limiter.ts:47`), checks a child out of the pool (`checkout`, `pool.ts:145`), sends it the job and waits at most 30 s (`runLeased`, `run-code.ts:201`). No slot within 5 s is `busy`.
4. `interpretResult` (`run-code.ts:126`) turns the child's answer into `ok`, `stdout`, `stderr` and a reason class, and `saveOutputs` (`run-code-tool.ts:137`) writes each output file to the desk as an agent version authored by the current run (§ 7). The result is `{ ok, stdout, stderr, filesWritten: [{ path, version }], reason? }` (`CodeRunResult`, `packages/core/src/tools/code/types.ts:18`). A desk refusal while saving is reported in `stderr` and the other files still go.

**The path rule.** A desk path is the path under `/workspace`. The desk file `data/sales.csv` is `/workspace/data/sales.csv` in Python, with `/workspace` as the working directory, and `files["data/sales.csv"]` in JavaScript, as text. A result worth keeping goes under `/workspace/out/` in Python (the program creates the folder first) or into `outFiles["<name>"]` in JavaScript (`outName`, `packages/host/src/code-runner/child/qjs-child.mjs:41`, accepts `/workspace/out/x`, `out/x` and `x`). Every new or changed text file there is saved to the desk as `out/<name>`. An input the run did not change is skipped (`collectOutputs`, `child/py-child.mjs:277`). A file that is not UTF-8 text, is over 2 MB, or comes after the twentieth is left out with a one-line note, and the runner re-checks every name and size the child reports, because the child ran guest code (`collectOutputs`, `run-code.ts:92`). A run that fails saves nothing (`interpretResult`, `run-code.ts:136-150`, with the note `NOTES.discarded`).

**The child process.** `spawnSandboxChild` (`packages/host/src/code-runner/child-process.ts:102`) forks the app's own executable on the entry script in the ship directory, with these flags (`childExecArgv`, `:83`):

- `--permission` and `--allow-fs-read=<ship dir>`: the process may read the ship directory and nothing else. It has no write, child-process, worker or addon permission.
- `--disallow-code-generation-from-strings`: no `eval` or `Function` from a string.
- `--max-old-space-size=256`: a cap on the glue. The guest's own memory is the wasm instance, capped inside the child.

Its environment is empty (`childEnv`, `:97`), never the parent's, because the hosted parent holds `AGENTFORGE_SECRETS_KEY` and every tenant's keys. Under Electron the executable is the app itself, so the one variable `ELECTRON_RUN_AS_NODE=1` is set; the plan records that no Electron fuse turns that off today. The fork options are an `ipc` channel with `serialization: "advanced"` so bytes cross as bytes, no stdin, `cwd` the ship directory and `windowsHide` (`:106-115`). `trackChild` (`:116`, `packages/host/src/child-processes.ts:27`) registers the process so the desktop shell's `killTrackedChildren` stops it on quit (`apps/desktop/main.cjs:133-137`, as it does for ffmpeg). The messages are `ready`, `fatal`, `job` and `result`, and the parent checks the shape of everything the child sends (`parseChildMessage`, `packages/host/src/code-runner/protocol.ts:128`).

A cold child must boot (`boot`, `child-process.ts:168`) within 60 s or it is killed. A running job has a 30 s wall clock (`run`, `:200`): when it passes, the parent sends SIGKILL and the answer is `timeout`. The last 4 KB of the child's stderr is kept to classify a crash and is never shown (`classifyCrash`, `packages/host/src/code-runner/outcome.ts:63`: a permission denial becomes the fixed `NOTES.denied`, a heap failure `memory`, anything else `runtime`).

**The engines.** Python is Pyodide (CPython 3.14.2 compiled to wasm) with numpy and pandas and their three dependencies, started by `child/py-child.mjs`. JavaScript is QuickJS (`quickjs-emscripten-core` 0.32.0), started by `child/qjs-child.mjs`. Both run offline from the ship directory.

- *Python.* Before it boots, `py-child.mjs` hashes every Pyodide file against `vendor/pyodide/MANIFEST.json` and sends `fatal` on a mismatch (`:66-76`). It loads a lock file trimmed to the shipped wheels, so a package the guest asks for that is not shipped is not looked up on a CDN (`:106-124`). It wraps `WebAssembly.Memory.grow` to cap linear memory at 512 MB, so a memory bomb becomes a `MemoryError` (`:37-42`). It deletes `process`, `fetch`, `XMLHttpRequest`, `WebSocket`, `EventSource`, `require`, `Buffer`, `Worker`, `navigator` and `BroadcastChannel` from the realm before any guest code runs (`:170-190`). Each job gets a fresh globals dict, an emptied `/workspace` and `/tmp` (`:313-314`, `:344`), and runs through a harness that catches `SystemExit`, so `sys.exit` and `os._exit` end the run and not the child (`:146-168`).
- *JavaScript.* Each job gets a new QuickJS runtime and context (`runJob`, `qjs-child.mjs:59`) with a 128 MB heap, a 256 KB stack and an interrupt handler for the deadline (3 s before the wall clock, `JS_DEADLINE_MARGIN_MS`) and for wasm memory (`:78-88`). A run that hit any limit sets `discard: true` and the parent kills the child (`:157`, `:206`). `console.log`, `info` and `debug` go to stdout; `console.error` and `warn` go to stderr. The value of the last expression is shown after the output. There is no `require`, `import`, Node API or browser API.

**Limits.** All of them are in `packages/host/src/code-runner/limits.ts`, and the child reads the output limits from its boot config (`bootConfig`, `child-process.ts:64`), so the two sides cannot disagree.

| Limit | Value | Constant |
|---|---|---|
| Code | 100 KB | `MAX_CODE_BYTES` |
| Input files | 20 files, 20 MB together | `MAX_INPUT_FILES`, `MAX_INPUT_BYTES` |
| Boot | 60 s | `BOOT_TIMEOUT_MS` |
| One run | 30 s wall clock; JavaScript stops its own loop 3 s earlier | `RUN_TIMEOUT_MS`, `JS_DEADLINE_MARGIN_MS` |
| Memory | Python wasm 512 MB; JavaScript wasm 256 MB, heap 128 MB, stack 256 KB; child old space 256 MB | `PY_WASM_MAX_MB`, `JS_WASM_MAX_MB`, `JS_HEAP_LIMIT_BYTES`, `JS_STACK_KB`, `CHILD_OLD_SPACE_MB` |
| stdout, stderr | 64 KB each, cut with a note | `MAX_STREAM_BYTES` |
| Output files | 20 files, 2 MB each | `MAX_OUTPUT_FILES`, `MAX_OUTPUT_FILE_BYTES` |
| `/workspace` after a run | over 500 files or 64 MB is `too_large` and the child is discarded | `MAX_WORKSPACE_FILES`, `MAX_WORKSPACE_BYTES` |
| Warm child idle | 5 minutes, then killed | `IDLE_TIMEOUT_MS` |
| Wait for a slot | 5 s, then `busy` | `QUEUE_WAIT_MS` |
| Warm children | Personal 1 per language; hosted 2 in all | `PERSONAL_WARM_PER_LANGUAGE`, `HOSTED_WARM_TOTAL` |
| Concurrent runs | Personal 1; hosted 2 in all and 1 per tenant | `PERSONAL_MAX_RUNS`, `HOSTED_MAX_RUNS`, `HOSTED_MAX_RUNS_PER_TENANT` |

Hosted operators can raise the two run caps with `AGENTFORGE_MAX_CODE_RUNS` and `AGENTFORGE_MAX_CODE_RUNS_PER_TENANT` (`limits.ts:57-58`); Personal is never configurable. The limiter takes the per-tenant slot before the global one, so a tenant waiting for its own slot never holds a global one (`code-limiter.ts:75-99`). Unlike the job limiters, this one caps Personal too, because a Python child with pandas holds hundreds of megabytes.

**The pool.** `createChildPool` (`packages/host/src/code-runner/pool.ts:72`) keeps children warm because a Pyodide cold start is slow. A child is keyed by tenant, desk and language (`poolKeyString`, `:68`) and handed back only to the same key: warm never means shared. Each run still starts in a fresh namespace and a cleaned `/workspace`. When there is no room (`makeRoom`, `:95`), Personal replaces the idle child of the same language, and hosted evicts the least recently used idle child. A child that is booting or running is never evicted, and then the answer is `busy`. A child is killed instead of reused after a timeout, a memory failure, a crash, an oversize result or its own `discard` (`reuse`, `run-code.ts:152`). A child that dies while idle drops out of the table (`:173`).

**What reaches the model.** Words the host chose, or the guest's own words with the host scrubbed out. `NOTES` (`outcome.ts:26`) holds a fixed sentence for every failure the host decides: unavailable, busy, timeout, memory, denied, crashed, workspace, code too long, inputs too large. A guest exception goes through `cleanGuestError` (`packages/host/src/code-runner/sanitize.ts:74`), which drops Pyodide's wrapper frames and Node internals and replaces absolute paths, file URLs and the ship, home, temp and working directories with `[host path]` (`hostRedactions`, `:34`). The guest's printed output is passed through untouched, then capped with the runner's notes kept whole (`composeStream`, `:103`). It is the same rule as the ffmpeg failure reasons (SR-48). The reason classes are `timeout`, `memory`, `syntax`, `runtime`, `too_large`, `busy` and `unavailable` (`CodeRunFailure`, `packages/core/src/tools/code/types.ts:16`). The tool description tells the model what to do for each, including that `unavailable` means stop retrying (`RUN_CODE_DESCRIPTION`, `run-code-tool.ts:43`).

**The ship directory.** The child reads everything from one folder of real files, built outside git. `locateShipDir` (`packages/host/src/code-runner/ship.ts:83`) picks it in this order: a test override; `AGENTFORGE_SANDBOX_DIR` (a dev, test and hosted hook that the packaged app ignores, the same rule as the gateway hooks, SR-85); `<resourcesPath>/sandbox` under Electron; `<repo>/vendor/sandbox-runtime` found by walking up to `pnpm-workspace.yaml`. `checkShip` verifies it once per process and caches the verdict, a failure too (`verifyShip`, `:148`): the folder exists, its path has no comma (`--allow-fs-read` takes a comma-separated list, so a comma would grant a different directory), the optional root `MANIFEST.json` and `vendor/pyodide/MANIFEST.json` hash clean, and each language has its entry script and engine files. Python can be available while JavaScript is not. A mismatch is logged with the manifest-relative file name and reaches the model only as `unavailable`.

**Building the folder.** `scripts/build-sandbox-runtime.mjs` (`npx pnpm@9.15.9 sandbox:build`, `package.json:27`) writes `vendor/sandbox-runtime/` (gitignored, `.gitignore:86-91`):

- `MANIFEST.json`, schema 1, with the size and sha256 of every other file.
- `py-child.mjs` and `qjs-child.mjs`, byte copies of `packages/host/src/code-runner/child/`.
- `node_modules/` with a stub `ws` (`pyodide.mjs` imports it unconditionally in Node, and the stub throws), `quickjs-emscripten-core` and two `@jitl` packages.
- `vendor/pyodide/` with the four Pyodide core files, five wheels (numpy, pandas, python-dateutil, pytz, six), a lock file trimmed to them, a `.pyc` cache that cuts the cold `import pandas` from about 12 s to about 4 s, and its own `MANIFEST.json`.

Everything that is not source in the repo is pinned in `scripts/sandbox-runtime.lock.json` (Pyodide 314.0.7, Python 3.14.2, QuickJS 0.32.0: version, URL, size and sha256 per file). The build refuses any file whose hash differs, whether it came from `node_modules`, the download cache or the network. The five wheels are the only download, cached once in `vendor/.sandbox-cache`; `--offline` forbids even that, and a second run writes the same manifest. `--update-lock` rewrites the lock after a version bump, and the result is a diff to read. `npx pnpm@9.15.9 sandbox:verify` (`package.json:28`) re-hashes the folder against its manifest and, when the child sources exist, also requires the built child scripts to equal them byte for byte (`diffChildScripts`, `scripts/build-sandbox-runtime.mjs:261`). Without the source (a packed app, the image's runtime stage) it checks only the manifest. The manifest cannot see a child source edited after the build, which is why the second check exists.

**Packaging.**

- *Windows, Linux and the native macOS scripts.* The desktop build scripts run the builder before they stage and pack (`apps/desktop/package.json:9-19`), and `extraResources` copies `vendor/sandbox-runtime` to `resources/sandbox` (`:84-87`), outside the asar, because the child reads it from disk.
- *macOS.* `apps/desktop/platform/macos/docker/build-mac.sh` builds the folder in the Docker route with the wheel cache in the `/cache` volume (`:56-66`). The folder is wasm, `.mjs` and zip files with nothing per OS or per arch, so one folder serves both arches. After signing, the script re-verifies `Contents/Resources/sandbox` inside the bundle and compares the zip's manifest with the bundle's (`:156-171`).
- *Hosted image.* The build stage assembles the folder in `/opt/sandbox-runtime` with its cache in `/opt/sandbox-cache`, outside `/app` so the wholesale copy does not carry either (`webapp-deploy/Dockerfile:85-95`). The runtime stage copies it to `/app/sandbox`, root-owned and read-only (`:118-122`), and sets `AGENTFORGE_SANDBOX_DIR=/app/sandbox` (`:109`). The `node` user can read it and cannot change a byte.

### 13. When a step goes wrong: a failed tool, a tool that is off, the step limit, redaction and `self_check`

Added 2026-10-06 for Chat. Four of the five were findings of a read-only audit that this pass confirmed in the code before it changed anything. The fifth, `self_check`, gives Chat a way to learn why something is unavailable. Nothing here adds a mode.

**A tool that throws.** Before: the SDK turns a rejected `execute` into an `error` stream part with no tool result (`runToolsTransformation`, `packages/core/node_modules/ai/dist/index.js:5166-5177`), `mapStreamPart` maps it to `run.failed` (`packages/core/src/runtime/stream-parts.ts:59`), `consume` stops reading at it (`ai-sdk-runtime.ts:720`) and `stream` throws (`:601`). The model never saw the error and could not try another way. Now: `buildAiTools` wraps each offered tool (`packages/core/src/runtime/ai-tools.ts:63`). When `invokeToolGuarded` throws and no signal of the run has fired (`isRunAbort`, `packages/core/src/runtime/tool-error.ts:98`; it reads the caller's `input.signal` and the SDK's own `abortSignal` argument), the wrapper answers `toolErrorResult(error, key, { scanForInstructions })` (`tool-error.ts:67`) and records it on the tool I/O sink. An abort is rethrown, so a cancel still ends the run as a cancelled run. The result is `{ ok: false, reason: "tool_error", message }`, the shape the budget and egress refusals already use. The message is `The <key> tool failed with: "<detail>". Fix the arguments or try another way; if it still fails, tell the person plainly what could not be done.` The detail sits inside double quotes, so a provider's, a page's or a file's words read as a quotation and not as the host's advice; a double quote inside it becomes a single quote. The detail is the error's message after `redactSecrets` (keys, bearer tokens and the opaque-token rule), after host paths are replaced with `[host path]`, with whitespace collapsed and cut at 220 characters; the whole message stays under 400 (`TOOL_ERROR_MESSAGE_MAX_CHARS`). The host paths are the process's own home, temp and working directories (by value), `file://` links, drive paths, and POSIX paths under a root only a host has (`/home`, `/Users`, `/tmp`, `/app`, `/srv`, `/var`, `/etc`, `/opt`, `/usr`, `/root`, `/mnt`, `/private`). `/workspace/...` and a desk path such as `/notes/plan.md` are left alone, because the model needs them to fix its call. For every tool, unless `injectionGuardBypass` is on, a detail that matches an injection rule is replaced by a sentence saying it was withheld. The scan does not depend on the tool's trust: the media tools throw a gateway's error body under `internal` trust (`gateway-media.ts:393`, `gateway-audio.ts:245`), and on a bring-your-own-key desk that body is third-party text. The failed call keeps the budget slot it was admitted with. The renderer already reads `ok: false` as a refusal (`classifyOutcome`, `apps/web/components/tool-rows/results.ts:141`), so the row shows the message with no renderer change.

Not covered, on purpose: the SDK checks a call's arguments and its tool name before `execute` runs (`parseToolCall`, `ai/dist/index.js:4079`). A call that fails the schema (`InvalidToolArgumentsError`) or names a tool that is not bound at all (`NoSuchToolError`) still ends the run with the SDK's message. Fixing it means a loose schema for the SDK plus validation in `invokeTool`, or `experimental_repairToolCall`, and either changes the `tool.started` input the screen shows for every tool.

**A tool the run does not offer.** The old gotcha said the Chat prompt still names `run_code` when it is off "so a model may try it once and get the refusal". That was wrong. `stream` used to skip a disabled tool when it built the SDK's map (the old `ai-sdk-runtime.ts` loop), so a call to it hit `NoSuchToolError` and ended the run; the refusal in `invokeToolGuarded` was reachable only from the stub runtime. Now `buildAiTools` puts a bound, registered, disabled tool in the map with `parameters: z.any()` and an `execute` that returns `disabledToolOutput(key)` (`invoke-guarded.ts:12`: `{ success: false, error: "Tool <key> is disabled on this machine." }`) without running the tool (`ai-tools.ts:47-59`). The call is admitted against the run's budget first, like any call (`options.budget.admit`, `ai-tools.ts:54`), so refusals count toward `maxToolCalls` and the tool's own cap and then answer with the budget refusal; without that, a model, or text that steers it, could call a tool that is off without limit, each call being a row on the screen and a stored result. It is left out of `offered`, and `consume` passes `experimental_activeTools: offered` only when something is hidden (`ai-sdk-runtime.ts:677-688`), so a run with nothing disabled sends exactly the request it always sent, and a run whose every bound tool is disabled sends no tool list. The disabled list is read once per `execute` (`ai-sdk-runtime.ts:443`). The prompt side is the fragment drop in § 2: with `AGENTFORGE_CODE_RUNS` unset on the hosted server, Chat's prompt has no sentence about `run_code`. Only `run_code` and `self_check` have a droppable sentence. A tool the owner switches off in Settings whose mention shares a sentence with others (`web_search` and `web_fetch`, the six file tools) is still named, and a call to it now gets the refusal instead of ending the run. The Data job's instruction (`DATA_SYSTEM`, `packages/host/src/data-generate.ts:42`) still names `run_code` on a server where it is off, for the same reason, and gets the same refusal.

**The step limit.** The SDK stops a tool loop at `maxSteps` and says nothing when the last step asked for tools. `createStepTracker` (`packages/core/src/runtime/step-tracker.ts:13`) watches the `tool-call` and `step-finish` parts that `consume` already reads (`ai-sdk-runtime.ts:711`). `endedAtLimit(maxSteps)` is true when that many steps finished and the last one called a tool. `consume` returns `stepLimit`, and `stream` sends `{ type: "run.step_limit", steps }` once, just before `run.completed` (`ai-sdk-runtime.ts:605`), only for a run that did not fail. Chat records it (`stepLimitReached`, `packages/host/src/runs.ts:302`, set at `:561`, the event is not sent to the screen) and `persistAssistant` passes it to `settleChatTurn` (`runs.ts:330`), which appends `stepLimitNote(locale, finishedTools)` after a blank line (`withStepLimitNote`, `packages/core/src/agents/chat-turn.ts:246`) whatever else the turn said, once. The sentence names the tools that finished and says the answer did not: "list_files and web_search finished, but the answer didn't. Ask me to continue and I will pick up from where I stopped." and "list_files dan web_search sudah selesai, tetapi jawabannya belum. …". No tool finished uses the empty sentence, which still says the answer did not. It is host copy in both languages (`stepLimitNote`, `packages/core/src/agents/chat-locale.ts:154`, mirrored in `chat.harness.stepLimit`, `stepLimitEmpty` and `stepLimitAnd`). `persistAssistant` also saves a `step_limit` part with those tool keys (`runs.ts:354`). The renderer shows Continue (`chat-continue`) only when that part is on a saved assistant turn (`stepLimitToolsOf`, `apps/web/lib/chat-continue.ts`); it does not match the sentence. The click sends the word `continue` (`CONTINUE_PROMPT`) through the composer's text send (`continueSendRef`) and leaves the draft in the box. The button is off while a run is already going. An interrupted turn has its own sentence and no button. It was not done by forcing a tool-free last step because the SDK in use does not offer that for `streamText`: `experimental_prepareStep` exists only in `generateText` (`ai/dist/index.js:4247`), and a second `streamText` call by hand would sit outside the contact retry, the stall watchdog and the usage count. Jobs receive the event and ignore it; the Edit agent forwards every runtime event as SSE (`packages/host/src/edit/agent-run.ts:274`) and its renderer ignores types it does not know.

**A model call that fails after a tool completed (2026-10-07, found by a live drive).** A Word file attached in Chat, `read_file` completed, and the follow-up call failed: the turn ended with the tool row and no words and no error, three times. The cause was the keep rule, not the tool: `shouldKeepToolTurn` (`packages/core/src/runtime/retry.ts:173`) keeps a turn whose tool completed (an image made, a file written) so that a later failure neither throws the work away nor retries it, and `stream` answered that branch with a bare `run.completed`. It now sends `{ type: "run.interrupted", message: result.failed }` first (`ai-sdk-runtime.ts:597`; the type is in `runtime/types.ts`), still keeps the turn, still makes no contact retry (`shouldRetryModelContact` stops at `tooled`), and still sends no `run.failed`. Chat takes the same road as the step limit: it records the reason, masked with `redactSecrets` and cut at `INTERRUPTED_REASON_MAX` (400) characters (`interruptedReason`, `runs.ts:262`, set at `:408`, not sent to the screen), and `persistAssistant` passes it to `settleChatTurn` (`runs.ts:288`), which appends `chatTurnCopy(locale).interrupted` through the same once-only helper as the step-limit note (`withClosingNote`, `chat-turn.ts:231`). The sentence names what is true (the tool steps above ran; the answer could not be finished), the reason in its own paragraph, and the word to send, in both languages, mirrored in `chat.harness.interrupted`: "The tool steps above ran, but I could not finish the answer. Reason: … Send "continue" and I will try again." and "Langkah alat di atas sudah berjalan, tetapi saya tidak dapat menyelesaikan jawabannya. Alasan: … Kirim "lanjutkan" dan saya akan mencoba lagi." It streams as an `assistant.delta` before `run.completed` and is saved as the turn's `text` part, after the tool rows, so the live bubble and a reload agree; the renderer needed no change (`readRunStream` already draws deltas, and `chat-session.tsx` re-reads the thread on completion). The reason is the failure's own message, so it is in the app's language where the runtime wrote it (a gateway 5xx, the stream watchdog, the header limit) and English where undici did (`fetch failed`). **`continue` replays no tool result.** Only `text`, `image_url` and `video_url` parts go back to the model (`modelHistoryParts`, `packages/core/src/content/transcript.ts:39`), so the next turn sees the person's words and the sentence, and a read is read again; a write is not undone, but the model may write it again. The step-limit sentence has the same limit. Jobs and the Edit agent receive the event and ignore it (see Gotchas).

**How long a request may take to send headers.** One timer in `fetchWithHeaderTimeout` (`ai-sdk-runtime.ts:128`), around each of the three wire fetches, starts when a request starts and is cleared when its headers arrive; the body then belongs to the stream watchdog. It is per request, so a tool loop's second call has its own. It was 10 s. On 2026-10-07, with that limit stretched on a diagnostic server and Thinking Off, `gpt-6-luna` answered HTTP 200 on both calls of the Word-file turn and took 15.1 s to send headers each time (15 146 ms and 15 135 ms), where a first call minutes earlier took 3.3 s; the same turn on the real limit was cut three times in a row and ended `Could not reach gpt-6-luna after 3 tries. Gateway unreachable: no response within 10s`, 30 s after Send, from a gateway that would have answered at 15 s. It is not a Thinking effect, so the allowance is not keyed on Thinking. `HEADERS_TIMEOUT_MS` is now 45 s (`stream-watchdog.ts:243`): three times the measured 15.1 s, and three quarters of `STREAM_IDLE_MS`, because after a tool the idle watchdog is already running and this has to fire first or the person reads "no stream events" and never "no response" (`stream-watchdog.test.ts` holds that order for every family). A timeout is a stop, not a retry (`isRetryableModelFailure`, `retry.ts:82`): one more wait is the same silent call, and three would turn a 45 s wait into 135 s. A dead gateway therefore costs 45 s once, where it cost 3 × 10 s before; a refused or dropped connection fails at once and is still retried three times. The sentence is `formatHeadersTimeoutError` (`stream-watchdog.ts:251`): "No response within 45s from <model> (timeout). Try a smaller prompt, another model, or send again." and its Indonesian twin; it no longer says "unreachable", because the same gateway can answer `/v1/models` in 0.1 s. A job mode still falls to its next model on it (`GATEWAY_UNAVAILABLE` in `job-fallback.ts` matches `no response within` and now `tidak ada respons dalam`). Not known: the 45 s is evidence-backed for one model on one prompt. A model that really needs longer than that before it sends headers, which a gateway that buffers its first byte can force on a long Thinking run, is still cut, as it was at 10 s; the first-token watchdog's 120 s (240 s for the always-thinking families) would allow it, and the header limit is the tighter of the two.

**Redaction of tool input and output.** `redactSecretsDeep` (`packages/core/src/security/redact-deep.ts:70`) returns a copy with credential-shaped text masked at any depth and the value of a key named like a secret masked whole. The text shapes (`redactCredentials`, `packages/core/src/security/redact.ts`) are a bearer token, the keys `sk-`, `sk-ant-`, `tvly-` and `AIza`, a JWT (three base64url parts starting `eyJ`), a Telegram bot token (`<id>:<35 characters>` with a letter in them), an AWS access key id (`AKIA` or `ASIA`, except inside a presigned link's `Credential=` parameter), a PEM private key block (to its end line, or to the end of a cut-off text), the user and password of a URL (`postgres://u:p@h` becomes `postgres://[REDACTED]@h`), and the value of a `Cookie:` or `Set-Cookie:` header line that carries a `name=value`. The key names (`SECRET_KEY`, `redact-deep.ts:14`, exact, case-insensitive) are `authorization`, `proxy-authorization`, `x-api-key`, `api_key`, `secret`, `client_secret`, `password`, `passwd`, `token`, `access_token`, `refresh_token`, `id_token`, `auth_token`, `bearer`, `bot_token` and `telegram_bot_token`, `cookie`, `set-cookie`, `private_key`, `secret_key`, `access_key` and `credentials`. It stops at 32 levels and marks a cycle. It deliberately does not apply the opaque-token rule of `redactSecrets`, because that rule would erase content hashes, signed media links and long identifiers the renderer needs; `redact-shapes.test.ts` holds a hash, a signed link, a long id, a UUID, a URL with an `@` in its query and the numbers of a spreadsheet row unchanged (redaction may hide an identifier, never a figure). Chat applies it to three paths, all in `startModalityRun`'s `onEvent`: the frames sent to the screen (`redactToolEvent`, `packages/host/src/chat-tool-events.ts`, at `runs.ts:394`), the `tool_invocations` rows (the input, and the full output the tool I/O sink recorded, `runs.ts:414`) and the `tool_call` parts saved with the assistant message. The model-facing result is not touched, and media is collected from the unredacted full output (`collectToolMediaParts(fullOutput)`), so a signed link survives to be mirrored. No Chat path logs a tool's input or output (read, not proven by a log capture); `job_tool_outside_spec` logs the tool key only. The model's own words are not passed through the redactor, on purpose: the reply streams delta by delta, so a secret split across two deltas cannot be masked live and a masked saved copy would differ from what the screen showed; the person often asks for exactly such text (a config, a key they pasted); and free prose and code blocks are where a redactor hides identifiers it should not. The one copy that leaves the thread is masked: `chatWorkCard` (`packages/host/src/work-cards.ts:196`) passes the person's message and the reply through `redactCredentials` before the card is indexed, shown in the Sources list and retrieved into other prompts (`work-cards.test.ts` holds a key and a JWT out and figures, a code block, a hash and a signed link in). Not covered: the model reads the raw result, so a secret it repeats stays in the assistant text, in the saved `text` part and in the streamed deltas of that thread; the Edit agent streams its tool events unredacted (`edit/agent-run.ts:274`), and a job's `onEvent` hands raw events to job code. Neither of those stores them in `tool_invocations`. Security register: [SR-136](../security-register.md#sr-136).

**`self_check`.** `selfCheckTool` (`packages/host/src/self-check-tool.ts:150`, built by `createSelfCheckTool` at `:135` over `defaultSelfCheckDeps`, `:55`, so a test can inject the slow probes) is an `internal`, read-only tool with no arguments, registered in `ensureToolsRegistered` and bound by `DEFAULT_CHAT_TOOLS`. `collectSelfCheck` (`:110`) reads its facts behind one seam (`SelfCheckDeps`) and answers `{ ok: true, server_mode, gateway: { status, allowed, grace } | null, code_runs: { enabled, sandbox: "ready" | "missing" | "unusable" | "not_checked", python, javascript }, media_tools: { ffmpeg, ffprobe }, tools_not_offered, run_limits: { max_steps, max_tool_calls, per_tool } | null }`. The gate comes from `reportGatewayGate` (no network, no throw), code runs from `codeRunsEnabled`, the sandbox from `checkShip` (cached after the first call) only when code runs are on (`codeRunsFact`, `:102`; `checkShip` hashes every file of the ship directory the first time, which is wasted work for a tool nobody can call, so with code runs off the answer is `not_checked` with both languages false), ffmpeg and ffprobe from the async probes (`resolveFfmpegAsync`, `resolveFfprobeAsync`), `tools_not_offered` from the desk's disabled-tools list (which carries `run_code` while code runs are off) and the limits from the spec of the mode in `currentToolRun()`. Each read is guarded, so a probe that throws turns one fact into "not available" and the report still answers. The gate is copied field by field, because the payload also holds the endpoint, times and a technical message. The answer carries no path, key, tenant, organization, workspace or user id, probe message, OS or binary version; the tests assert each of those by value. A hosted tenant learns whether it is on the server, whether code runs are on, and whether ffmpeg exists there: booleans, recorded as [SR-137](../security-register.md#sr-137).

### 14. `build_deck`: a PowerPoint deck from Chat

`build_deck` (`buildDeckTool`, `packages/host/src/deck/build-deck-tool.ts:17`) lets Chat make a `.pptx` the person can save. `registerDeckTools` (`:27`) registers it from `ensureToolsRegistered` (`packages/host/src/register-tools.ts:41`), and it is the last of the 17 keys of `DEFAULT_CHAT_TOOLS` (§ 2), capped at 4 calls a turn by `chatHarnessSpec` (`packages/core/src/harness/modes/chat.ts:44`): a deck, then up to three repairs. It is `internal` trust: its answer is a value the host computed (an id, a file name, a count, or a refusal written in `build-deck.ts`), not text a page or a file wrote.

**The model writes the outline; no model is called inside the tool.** The arguments are `{ title, slides }` (`buildDeckInputSchema`, `packages/host/src/deck/deck-schema.ts:62`): a title and a list of slides, each with a heading and, optionally, a `kind`, a subhead, bullets, an aside and speaker notes. Shapes and layouts are not model input. **The schema sets no ceiling, on purpose.** The AI SDK checks a call's arguments against it before `execute`, and an argument that fails there ends the whole turn as `run.failed` (the person sees an error and no deck; the model is told nothing). A model cannot count characters, so the limits (up to 14 slides, `DECK_MAX_SLIDES`, which is `MAX_OUTLINE_SLIDES`; a title of 200 characters, a heading 200, a subhead 300, up to 12 bullets of 400, an aside 600, notes 2000) are stated in words in the field descriptions and enforced by the host (below). A slide kind the model invents reads as `bullets`, as in the Presentation mode. What the schema still refuses is a call that is not shaped like a deck at all (no `slides`, a heading missing): that is the usual `invalid_tool_args`. The tool description tells the model to write in the language of the conversation, to use only facts it was given or looked up, and to fix exactly what a refusal names. The Chat prompt carries the one sentence (§ 2).

**`buildDeckForTenant` (`packages/host/src/deck/build-deck.ts:63`)** does the host's half of the Presentation mode and nothing else.

0. `cleanDeckInput` (`packages/host/src/deck/deck-limits.ts:33`) makes a copy of the call with every text cleaned: characters XML 1.0 cannot hold are removed (`stripXmlIllegalChars`, `packages/host/src/xml-text.ts:42`; a form feed or vertical tab becomes a space), the ends are trimmed, and a bullet that was only blank is dropped. `deckLimitProblems` (`:70`) then lists every limit the cleaned deck breaks, and `formatDeckLimitProblems` (`:90`) answers `{ ok: false, reason: "limits", message }`: each overrun names the field by its path in the call, the limit and what was sent (`slides[1].notes is 2100 characters; the limit is 2000`), ten at most and then "and N more", then tells the model to call again with the whole outline. An empty title, an empty heading and an empty `slides` are named the same way. Nothing is saved on a refusal, and the call itself is never changed.
1. `parsePresentationOutlineBody` validates the outline as the Presentation routes do ([`presentations.md`](presentations.md) § 5 and § 6); its schema also removes the characters XML cannot hold (`slideText`, `presentation-outline.ts:10`). With step 0 in front it should not fail; a failure is `{ ok: false, reason: "invalid", message }`.
2. `runChecked` with `repairRounds: 0` runs `presentationChecks(null)` (`:79`): slide count, a heading and a body on every slide, no shared heading, and text that fits the exported slide ([`presentations.md`](presentations.md) § 3a). A failure is `{ ok: false, reason: "checks", message }` where the message is `formatRepairNote`'s ERROR, WHY and FIX text, so the model repairs the slides named and calls again. Nothing is saved on a refusal.
3. `buildPresentationPptx` builds the file, with the kicker in the owner's app language.
4. The base64 text is checked against `ARTIFACT_BODY_MAX_BYTES` (`:95`, 4 MB, so about 3 MB of file): over it is `too_large`. The per-field limits keep any real outline far below this (the largest legal deck is a few hundred kilobytes), so only a stubbed exporter reaches it in the tests.
5. `assertStorageAdmits` (`:101`) refuses on the hosted server when the tenant's use plus this deck would pass its storage ceiling (`quota`). The number it is asked about is `storedBytes`, the base64 text the row will carry (`size_bytes`), not the smaller file inside it. The tenant's use now includes its saved artifacts: `totalUse` (`packages/host/src/tenant-storage.ts:456`) adds `artifactUse` (`:447`), which reads `SUM(size_bytes)` over the tenant's desks (`TENANT_ARTIFACT_USE_SQL`, `tenant-storage-store.ts:230`) in server mode only. Off the hosted server `tenantStorageLimitBytes()` is null, it returns at once, and a desk's report never reads the table.
6. `artifactStore().create` (`:102`) saves it as `mode: "presentations"`, `kind: "draft"`, `mime: PPTX_MIME`, `meta: { source: "chat", slides }`, in the Chat run's own desk. The body is the base64 of the file, like the Legal Word and Excel artifacts (`BINARY_ARTIFACT_MIMES`, `packages/core/src/artifacts/artifact-meta.ts:34`).

The result is `{ ok: true, artifactId, filename, slideCount }`. `filename` is `artifactFilename(title, PPTX_MIME)`, the name the download route will send, and `slideCount` counts the title slide, the number PowerPoint shows. A failure of the export or the save is `unavailable` and a message that says not to retry.

**Download is the existing artifact route.** `GET /api/v1/artifacts/:artifactId/file` (`handleGetArtifactFile`, `packages/host/src/handlers/artifacts.ts`) decodes the base64 body, sends it as `PPTX_MIME` with `Content-Disposition: attachment`, `nosniff` and `Content-Security-Policy: sandbox`, and `artifactFileDelivery` names the type only because `PPTX_MIME` is now in `ARTIFACT_MIMES`. The renderer calls `downloadArtifactFile` (`apps/web/lib/artifacts-client.ts`), the call Documents, Legal and the job studios already use, so the packaged app opens its native save dialog there.

**What the person sees.** The card is under the answer, outside the Thinking disclosure, so a finished turn does not hide it. `ChatTurn` renders `DeckCards` (`apps/web/components/chat-turn.tsx:165`) for every finished `build_deck` call that made a deck. `DeckCard` (`apps/web/components/chat-deck-card.tsx:32`, `data-testid` `chat-deck-card`) shows the title, the slide count, the file name, the first four slide headings (`chat-deck-outline`), **Open** (`chat-deck-open`) and **Download** (`chat-deck-download`). Open shows the slides in place with `PresentationPreview` in its `simple` variant and no edit handlers (`chat-deck-preview` around it): the same filmstrip and stage the Presentation studio draws, read only. There is no second slide renderer. A download that fails shows `chat-deck-error`: in the packaged app, when the shell's save dialog answered `{ ok: false, reason }` for anything but `canceled`, `apiFetch` throws a `DesktopSaveError` (`apps/web/lib/desktop-save.ts:27`, thrown by `throwIfSaveFailed`, `:38`, from `api-client.ts`) and the card shows its sentence (`common.saveFailed.*`, both locales); any other failure shows `chat.deck.downloadFailed`. A closed dialog is silent. The same error reaches the Files viewer as `save_failed` (`files.errors.saveFailed`) and the studios' own error lines. In the Thinking disclosure the call keeps a one-line row (`DeckToolRow`, `apps/web/components/tool-rows/deck-row.tsx:14`, `tool-row-deck`): "Built “Title”", the slide count, and the tool's own sentence when it refused.

**A reopened thread draws the same card.** The card is rebuilt from the saved call alone: `readDeckResult` (`apps/web/components/tool-rows/deck-result.ts:41`) takes the artifact id, file name and slide count from the output and parses the call's input (`{ title, slides }`, stored with the call) with the renderer's copy of the outline schema. An input that does not parse leaves the card without Open and the preview; Download does not depend on it. If the artifact has been deleted, Download shows `chat-deck-error`.

**Two things the artifact catalog change touches.** `ArtifactPicker` (`apps/web/components/artifact-picker.tsx`) no longer offers a Word, Excel or PowerPoint artifact (`textArtifacts`, `apps/web/lib/artifacts-client.ts`), because it puts the body in a text box and a base64 deck would arrive as noise; before this the Legal Word and Excel artifacts already could. `NO_EMBED_TOOLS` (`apps/web/lib/message-embeds.ts:211`) keeps a deck result from being read as a job card.

## Gotchas

- **Stub Chat never calls a file tool or `run_code`.** `StubRuntime` (`packages/core/src/runtime/stub-runtime.ts:46`) only runs `calculator` and `datetime` (`wantsCalc`, `packages/core/src/runtime/stub-runtime.ts:66`). To see a Chat file write or a code run you need `runtime: "ai"` and a key. The Files section and the `/api/v1/files` routes work on a stub desk, and `run_code` itself needs no key: only the model that decides to call it does.
- **The folder is refused in three places, for three reasons.** On the hosted server everything but the status read is `folder_unavailable`. On webdev the status read says `available: true, mounted: false` (`localPaths` is true there), the renderer hides the control because there is no native picker, and `POST /api/v1/folder/mount` answers `folder_mount_ipc_only` because the HTTP adapter stamps every request `http`. Only the packaged shell can mount; an unpackaged `pnpm desktop:dev` window has no preload and so behaves like webdev here.
- **Regex search is refused on the hosted server** (`checkSearchPattern`, `packages/core/src/tools/files/search-text.ts:22`): it runs synchronously in `node:vm` for up to 4 s, which would block the one event loop every tenant shares. Plain-text search is not affected. Desktop and webdev keep regex, and on the folder root the tool's regex mode runs over the same `list` and `read` as the desk.
- **Desk bodies are sealed, and the quota counts every version.** A file's plain text is never in SQLite or the object store. On the hosted server a write past the ceiling is refused as `quota`; deleting a file does not free space. Off the hosted server nothing is counted.
- **`run_code` is off on the hosted server unless `AGENTFORGE_CODE_RUNS=on`.** `codeRunsEnabled` (`packages/host/src/code-runner/enabled.ts`) reads it: unset means on for Personal and webdev and off in server mode, and any value other than on/1/true or off/0/false counts as off. When off, `loadSettings` (`packages/host/src/settings-store.ts`) adds `run_code` to the run's disabled tools, so the model is not offered it, and the tool itself refuses as `unavailable`. A call to it anyway is answered by the runtime with the disabled refusal and the run goes on (§ 13). The earlier version of this note said a model "may try it once and get the refusal"; that was wrong, because the SDK found no such tool and the whole run failed. Chat's prompt no longer names the tool while it is off. The Data job's instruction still does, so a Data run may try it and get the refusal.
- **Jobs only get tools inside their spec.** A tool a job asks for that its mode's spec does not list is dropped, and the only trace is a `job_tool_outside_spec` log line. If a new Documents tool "does nothing", check `modes/documents.ts` before the generate file.
- **Chat's tools are not cut to its spec.** `runs.ts` passes the published agent's bindings. The spec's `tools` matters for the jobs, and for Chat it equals `DEFAULT_CHAT_TOOLS` by construction.
- **A run that spends all its steps on tools ends without a closing answer from the model.** The budget refusal asks the model to answer with what it has, but `maxSteps` is the hard stop, and the run completes with only tool output (`ai-sdk-runtime-budget.test.ts`, "takes the step count from the budget"). Since 2026-10-06 Chat adds one sentence saying the steps ran out and what to do (§ 13); the sentence is the host's, not the model's, and it shows only in Chat. A job that ends at its cap still ends silently.
- **A job or the Edit agent whose follow-up call fails after a tool still ends without saying so (2026-10-07; read, not fixed).** The runtime now sends `run.interrupted` to every caller, but only Chat turns it into words. `runJobAssistantOnce` (`packages/host/src/job-regen.ts:132`) reads `run.failed` alone (`:216`, `:224`), so after a kept tool turn it returns whatever text came before the tool, or an empty string, as the answer. Which jobs offer tools: Data (`data-generate.ts:361`) and the Market briefing and team editor (`market-generate.ts:460`, `:508`, `:789`; `market-team.ts:385`). Market throws `emptyMarketBriefing` on an empty reply (`market-generate.ts:470`, `:533`); Data parses the text and takes one repair round (`data-harness.ts:320-330`), so neither is silent on an empty reply, but text written before the tool is taken as the whole answer. The Edit agent forwards the event as a frame its renderer ignores (`edit/agent-run.ts:284-285`), and ends with `run.completed` (`:289`).
- **Chat's closing notes enter the Knowledge Base card.** `persistAssistant` replaces `assistantText` with the settled text (`runs.ts:293`), and `chatWorkCard` indexes it (`runs.ts:497`), so the step-limit and interrupted sentences, reason included, are part of the card a later turn can retrieve. Not changed.
- **The injection scan reads file content.** A `write_file` or `edit_file` whose text trips a rule is refused before it runs (`Blocked by injection guard (rule: …)`), and a `read_file` of such a file is replaced by the same message. The owner's `injectionGuardBypass` setting turns the scan off.
- **`thinToolOutput` trims a read.** It replaces any run of 400 or more base64-looking characters with `[omitted binary]` in every tool result (`LONG_B64_RE`, `packages/core/src/security/tool-thin.ts:3`), so the model sees that placeholder, not the run, in a text file that contains one.
- **Deleting a desk file ends its history for every route.** `listVersions` and the viewer need a live row, so the old versions stay in the database and in the quota but no route lists them. Writing the same path again starts a new file at version 1.
- **The author of a Chat write is the turn's run id, not the thread.** Since Chat sets a tool run (§ 7), `author_id` is a run id and `mode` is `chat`, and the viewer labels it "Agent in Chat" (`authorLabel`, `apps/web/components/files/file-viewer.tsx:32`, with the rail's name for the mode). Versions written before that change carry the thread id; the label is the same, so only `GET /api/v1/files/versions` tells them apart.
- **Proposals are replaced, not stacked.** A second write to the same folder path rejects the first pending proposal. The model was told the first was pending, so it should say what is still waiting.
- **A pending proposal belongs to the folder it was made against.** Picking a different folder, or closing the folder, rejects all of them. Deleting the desk deletes them: `handleDeleteWorkspace` calls `purgeFolderProposals` after it clears the mount record (§ 9). Before that call existed, `deleteLocalWorkspace` (`packages/db/src/ensure-local-owner.ts:234`) wiped knowledge and the desk row and left the desk's `file_proposals` rows, with their sealed bodies, until a tenant erase (`packages/db/src/tenant-purge.ts:111`, which still purges them). Decided proposals on a desk that lives on are never pruned.
- **The folder reads valid UTF-8 text only.** A file over 2 MB, with a NUL byte in its first 8 KB, or that is not valid UTF-8 is `too_large` or `denied` (`decodeText`, `packages/host/src/folder-root/text-file.ts:58`), so a Latin-1 source file cannot be read or edited by the agent. A byte-order mark and CRLF endings are kept, so an approved write is byte-exact.
- **`edit_file` is read, edit, write, and only the write is locked, but the write now checks.** The tool reads the file outside `withDeskLock`. The SDK starts every tool call of a step as it parses it (`runToolsTransformation`, `packages/core/node_modules/ai/dist/index.js:5037-5139`, where the `tool2.execute(...).then(...)` is not awaited), so two `edit_file` calls on one file in one step both read version N. Before the compare-and-set (§ 6, § 8) the second write replaced the first edit while both answered `saved`. Now the second finds a different hash and answers `conflict`, and the model is told to read again and redo the edit. The desk root is safe against this. The folder root is not: both calls propose from the same `before_sha256`, the second proposal rejects the first (the model was told the first was pending), and only the second edit is left to approve. Read from the code, not driven.
- **`run_code` is slow once, then quick.** The first Python run after a pause starts Pyodide with numpy and pandas: 18.7 s for the first test of the 2026-10-03 integration run (a cold start plus a pandas round trip), and 11 to 25 s on a loaded machine in the prototype. The tool description and Chat's prompt say so. A warm run takes milliseconds, a JavaScript child starts in under a second, and a cold boot that passes 60 s is killed and answers `unavailable`. A child is warm per tenant, desk and language and dies after 5 idle minutes, so a person who works in bursts pays the cold start again.
- **A warm Python child keeps its imported modules.** Each run gets fresh globals and an emptied `/workspace` and `/tmp`, but `sys.modules` and the interpreter stay. A program that patches a module changes later runs on the same desk until the child is killed. The pool never hands that child to another tenant, desk or language.
- **Network containment is removed primitives, not an OS rule.** Node's permission model does not restrict the network. The sandbox keeps a guest off the network by deleting `fetch`, `process`, `require`, `WebSocket` and the rest from the realm, stubbing `ws`, giving Pyodide `jsglobals: {}`, and running with `--disallow-code-generation-from-strings`. `sandbox.integration.test.ts` runs two escape batteries (31 ids that must be blocked) against a loopback listener and expects zero hits. A hosted deploy still owes an egress deny at the OS or network layer (plan Appendix A2 names SR-97), and the child's `--allow-fs-read` grant is the ship directory only.
- **Edit a child script, rebuild the folder.** The sandbox runs the copy in the ship directory, not `packages/host/src/code-runner/child/`. `sandbox:verify` reports `stale: py-child.mjs` when the two differ; `npx pnpm@9.15.9 sandbox:build --offline` rebuilds from the wheel cache. The manifest alone cannot see this drift, because it hashes the built copies.
- **A path with a comma in the ship directory disables the sandbox.** `--allow-fs-read` takes a comma-separated list, so `verifyShip` (`packages/host/src/code-runner/ship.ts:148`) refuses such a path (the check is at `:152`) and every call answers `unavailable`.
- **Data cannot show `run_code` work.** `run_code` in a Data job cannot see the attached table, only desk files, and its output is never evidence (`DATA_SYSTEM`, `packages/host/src/data-generate.ts:42`). `analyzeDataset` passes no `onEvent`, so a `run_code` call leaves no `job.step`: only `run_sql` queries show in the progress list.
- **Output is text only, and only when the run succeeds.** A binary file, a file over 2 MB, the twenty-first file and any file after a failed run are not saved, and the model is told which. A program that writes to a path outside `/workspace/out/` loses it when the call ends.
- **Download sends the newest version, not the one in view.** The route has no version argument, so the viewer offers Download only while the newest version is open. A file the agent edits after a Download is clicked is not in the file that was saved.
- **A deck is an artifact, so it is not in the storage counter, and the quota reads it separately.** `build_deck` stores the file as an artifact row in SQLite, and the tenant counter holds object-store bytes (desk file versions, media, uploads). On the hosted server `totalUse` adds the tenant's artifact bytes, measured on every call from `size_bytes` (the base64 text, not the file), so a tenant at the ceiling is refused (`quota`) and a deleted deck gives its room back at once. Three things hold that together. It is **server mode only**: a desk's report never reads the table. It is cheap only because of `artifacts_ws_size_idx`, created by `ensureArtifactTables` on open in server mode only (a desk's schema is unchanged): `size_bytes` follows the body in the row, so summing it from rows with megabyte bodies walks every overflow page (about 2 seconds for 100 decks, with the host stopped); `COUNT(id)` would send the read back to the row, so the query counts with `COUNT(*)`. And only `build_deck` and the object writers ask the ceiling: the other artifact writers (research, documents, finance, legal, meeting, open slide, presentation, data) do not call `assertStorageAdmits`. The counted size is the plain text and the sealed row is larger. Settings' "largest" list is media only, so a tenant full of decks sees a full meter and no deck in the list. The other limits on a deck are the 4 MB artifact body cap on the base64 text, 14 slides and the per-field ceilings.
- **An overrun is a refusal, not a failed turn.** The tool's schema sets no length, count or emptiness ceiling, so a note of 2,100 characters reaches `execute` and comes back as `{ ok: false, reason: "limits", message }`. Do not put a `.max()` back on `buildDeckInputSchema`: the SDK would reject the call before `execute` and the turn would end as `run.failed`. `build-deck-run.test.ts` drives that case through the real SDK.
- **Characters XML cannot hold are removed, not escaped.** The PowerPoint writer escapes `& < > " '` only. A form feed from a PDF, a NUL or an escape code is taken out (a form feed or vertical tab becomes a space) in `deck-limits.ts` and in the Presentation outline schema, so the Presentation export is covered too. The docx and xlsx exporters were not checked for the same flaw.
- **The deck card is outside Thinking, the deck row is inside.** A saved turn collapses Thinking, so the card and its Download are drawn under the answer and the row in Thinking is only a label and a count. A refused build (a check named a slide) shows the tool's English sentence in that row, muted, and no card.
- **The deck's slide count includes the title slide.** `slideCount` in the answer and on the card is the number PowerPoint shows. `build_deck`'s `slides` holds one fewer. The checks' `slide_count` never fires here because `deckLimitProblems` already stops at 14.
- **The deck's language has two sources.** The slides' text is the model's and follows the conversation (the prompt and the tool description say so). The kicker on the title slide and the footer are the owner's app language, from `presentationLocale()`, the same as the Presentation mode.
- **Stub Chat never calls `build_deck`.** Like the file tools, only a live model chooses it (`StubRuntime` runs calculator and datetime). The tool itself needs no key: only the model that decides to call it does.
- **The artifact picker hides Office files.** `textArtifacts` drops Word, Excel and PowerPoint artifacts from "Use a saved result" because the picker fills a text box. Legal's Word and Excel artifacts, which showed there as base64 before, are hidden too.
- **A failed save on the desktop is said, a closed dialog is not.** `saveDesktopBytes` (`apps/web/lib/desktop-bridge.ts`) returns the shell's answer to `host:save-bytes` (`{ ok: false, reason }` with `forbidden`, `bad-filename`, `too-large`, `canceled` or `write-failed`), and `apiFetch` calls `throwIfSaveFailed` on it, so every download in the app now throws a `DesktopSaveError` with a sentence when the shell could not write the file. `canceled` (the person closed the dialog) and a shell that answers nothing (older) do not throw. The shell was not changed (`apps/desktop/main.cjs:527-551`), and its real dialog and write have not been run.
- **Importing the store opens the app database.** `packages/host/src/desk-files/store.ts` does (its header says so); `createDeskFileStore` and `createProposalStore` take the database as an argument, which is how the tests hand them a scratch one.

## Why

**Why the budget is counted in the runtime, not in the tools.** `[Direct]` the plan's H1 build list ([`../mode-harness-tools-plan.md`](../mode-harness-tools-plan.md)): `AgentRuntime.execute` takes a budget, and a tool past its cap returns a refusal to the model instead of running. `[Supported]` Chat's own numbers (`chatHarnessSpec`, `packages/core/src/harness/modes/chat.ts:28`, and the comment above it): 6 steps ran out inside a single read, edit and re-read loop, which is why Chat has 12. **Confidence: high for the mechanism; the numbers 12, 40, 20, 10 and 8 are judgements sized by that comment and not measured on a live model.**

**Why a folder write is a proposal, not a blocking prompt.** `[Direct]` plan Appendix B: blocking a tool until the owner approves would let the stream watchdog and the host stall guard end the run first. `[Direct]` plan Appendix A1, owner call of 2026-10-03: on Personal, agents edit a real folder with an approval per write. **Confidence: high.**
