## Overview

The owner's question is "how does each knowledge go to the Knowledge Base?". This page answers it for fifteen surfaces at once: the eleven modes, the three manual entry points on `/knowledge`, and Soul/Memory — which look like knowledge and are not sources at all.

The machinery underneath (chunker, embedder, guard rule set, schema, backend registry, reindex) is [`knowledge-ingest-loop.md`](knowledge-ingest-loop.md); the `/knowledge` page itself is [`knowledge-base-page.md`](knowledge-base-page.md). This page does not repeat either. What it adds is the **per-surface** truth: what triggers a card, what text ends up inside it, what is silently left out, who can read it back, and what happens on delete.

Three things surprise everyone. **Every automatic card in the product goes through one function**, `upsertWorkSource` — there is no second writer. **Only Chat retrieves**: ten job modes write cards and read none, so a knowledge answer inside Finance does not exist. And **the card is text, never the bytes**: a Videos card holds the prompt, not the mp4; a Data card holds the model's evidence tables, not the dataset.

### 1. The shared funnel — `upsertWorkSource`

Every automatic card in the eleven mode rows above, without exception, is one call to `upsertWorkSource` (`packages/host/src/knowledge-ingest.ts:4-20`) with a `WorkCard`. There is no second writer. In order (`knowledge-ingest.ts:26-84`):

1. `scanInjection(card.title)` — a title that trips the guard is **replaced by the mode name** (`:28-29`), so one poisoned thread title cannot block every later card of that thread.
2. `maskPii` over **title, prompt and body field by field**, then `renderWorkCard` (`knowledge-ingest.ts:38-43`). `renderWorkCard` (`packages/host/src/work-cards.ts:58`) emits `# <title>` / `Mode: <type>` / `Model: <model>` / `Pointer: <thread|artifact|media>:<id>` / `Prompt: <≤1 200>`, then the body, capped so header + body ≤ `WORK_CARD_BODY_MAX = 8_000` (`work-cards.ts:24`, `:26`). Over-cap text gets `\n[truncated]`. **Field-by-field is new on 2026-09-17**: masking the *rendered* string ate the host-generated `Pointer:` UUID, because a UUID whose middle groups are all decimal matches the phone pattern.
3. An empty rendered card → `{status:"skipped"}`, no row at all (`:45-47`).
4. `findSourceByOrigin` (`knowledge.ts:211`) — **idempotent per `(workspace, origin.kind, origin.id)`**. An existing row is reused by id; only the first write is `created`.
5. `scanInjection(card.body) ?? scanInjection(card.prompt ?? "")` (`:62`). A hit writes a `Failed` row reading `injection_blocked (rule: …)` through `markSourceFailed` (`knowledge.ts:387`), and that source is never retrievable. The owner's `injectionGuardBypass` skips both scans (`:28`, `:94-100`).
6. `indexKnowledgeSource` (`knowledge.ts:368`).

It never throws and it never fails the work that produced it: an index error leaves a `Failed` row and the generate still returns its result.

**Idempotence is per origin id, not per run.** Only Chat rewrites in place, because a thread keeps one id across turns. Every Finance / Data / Legal / Market / Documents / Presentation generate mints a **new** artifact, so a second run of the same job adds a second card rather than replacing the first. `knowledge-ingest-loop.md`'s "re-running a thread rewrites one row instead of piling up duplicates" is true for `origin.kind = "thread"` and for nothing else.

### 2. Manual sources take the other door — `indexSource`

Paste, File and URL never build a work card. All three are gated (`requireGatewayAllowed` at `handlers/knowledge.ts:376` and `:409`) and all three reach `indexSource` (`knowledge.ts:433`) or, for a file, `indexKnowledgeSource` directly. The guard runs over the **raw name and then the text** (`injectionRule`, `knowledge.ts:424`) — the raw name, not the sanitized one, so stripping a leading `###` cannot also strip the rule that would have caught it. `origin` is `null` for all three, which is why nothing ever cascades to them and the orphan sweep cannot see them.

**What a `document` upload actually runs (new on 2026-09-17).** `documentText` (`knowledge-extract.ts:144`) hands the bytes to `extractFile` (`packages/host/src/file-extract/index.ts:172`), the one shared local file → Markdown pipeline. It loads `@firecrawl/anydoc` through `createRequire` (`file-extract/anydoc.ts:53-67`); if that native binding is missing on this platform the failure is logged once and the upload degrades to the extractors this repo already shipped (`tryLoad`, `index.ts:103-110`). `detectFormat` (`file-extract/detect.ts:67`) reads the extension **and** the first bytes and refuses `format_mismatch` when they disagree, so a workbook renamed `.csv` never reaches the CSV parser. The caps are borrowed, not invented (`file-extract/limits.ts`): `FILE_EXTRACT_MAX_BYTES = min(PDF_MAX_BYTES, FINANCE_IMPORT_MAX_BYTES)` = **25 MB** (`limits.ts:22`), `FILE_EXTRACT_TIMEOUT_MS = PDF_TIMEOUT_MS` = **20 s** (`:25`), Markdown cut on a line boundary at `KNOWLEDGE_TEXT_MAX_CHARS` = **2 000 000** chars with `meta.truncated` set (`:28`, `index.ts:89-96`), at most **200** tables (`:31`), each capped at the spreadsheet import's 5 000 rows / 100 cols / 160 cell chars (`:34-40`). The fallback path only covers `pdf`, `docx`, `xlsx`, `csv` (`file-extract/fallback.ts:77`); a `.pptx` / `.odt` / `.rtf` / `.epub` on a binding-less platform is `unsupported`, exactly as it was before the converter existed.

**Nothing in that path opens a socket.** anydoc's one network option is `ocr: 'hosted'`, which uploads the document to Firecrawl Parse; `anydoc.ts` never constructs an options object at all — `toMarkdownBytes(bytes, format)` is called with exactly two arguments (`anydoc.ts:150-164`) — and never reads a `FIRECRAWL_*` variable. A scanned PDF is refused locally as `needs_ocr`, and the sentence the owner sees says so (`file-extract/errors.ts:52`). `file-extract/privacy.test.ts` asserts the sockets stay shut for every format including that refusal, and `file-extract/no-hosted-ocr.test.ts` greps the repository so a later call site cannot add the option back. Each of the ten `FileExtractErrorCode`s (`errors.ts:12-32`) becomes an `ApiError` named `document_<code>` (`knowledge-extract.ts:139-141`), `413` for `too_large` and `400` for the rest (`:137`), so a source row records *why* it could not be read.

The fourth entry point on that route is `{artifactId}` → `sendArtifactToKnowledge` (`handlers/knowledge.ts:65`) — the "Send to Knowledge Base" button that five studios mount from one component. It is idempotent against the auto-ingest origin (200 + `alreadyIndexed: true`) and resolves the work type from the artifact's own mode first: `workTypeForArtifact` (`handlers/knowledge.ts:99`) is `artifactModeToWork(mode) ?? KB_TYPE_TO_WORK[kbType] ?? "Documents"`. Before that fix the client label won, which is how a `market/briefing` sent with `kbType="Brief"` filed itself as `Finance`.

### 3. Chunk, commit, embed

`indexKnowledgeSource` sanitizes the name, then `chunkKnowledgeText` (`packages/host/src/knowledge-text.ts:197`) splits heading-aware with `CHUNK_TARGET = 800` / `CHUNK_OVERLAP = 120` (`:109`, `:112`). `replaceSourceRows` (`knowledge.ts:271`) commits the source row and one `knowledge_chunks` FTS5 row per chunk in **one immediate transaction, before embedding** — which is why keyword search answers even when the embedding call failed and the row still reads `Indexed`. Vectors follow in batches of 16 against the pinned gateway. The rest is [`knowledge-ingest-loop.md`](knowledge-ingest-loop.md).

In practice: a media card is one chunk, a Chat turn one, a short document two or three, a three-slide deck four or five (the speaker notes dominate), and a Market briefing twelve — which is the cap, not the briefing.

### 4. Tenant scoping

Everything is parameterized by `tenant.workspaceId` in application code; `knowledge_chunks` is a bare FTS5 virtual table with `workspace_id` as a plain column, no foreign key and no row-level security (`packages/db/src/ensure-schema.ts:809-813`). The guarantee is the tests, not the schema.

Two things on this page are **organization**-scoped instead: the raw bytes a file upload leaves on disk (`uploadDir`, `knowledge.ts:448-450`), and the `media` table the sweep consults for Images / Videos / Edit cards (`ORIGIN_OWNERS`, `knowledge.ts:631` — the `media` table has no workspace column). Everything else on the path is per-desk.

On the hosted server one rule sits on top of the desk scope: the Chat card a person's thread leaves is that person's, not the desk's ([§ 7](#7-who-sees-which-source-hosted-2026-10-07)). Off server mode a desk has one person and nothing below changes.

### 5. Retrieval — Chat, and only Chat

`knowledgeInjection` (`knowledge.ts:940`) has exactly two callers: `startModalityRun` (`packages/host/src/runs.ts:155`), whose result is concatenated onto the agent's system prompt at `:162`, and the read-only popover route `GET /api/v1/knowledge/context` (`handlers/knowledge.ts:306`), which calls it only when given a `query`. **Chat never gives it one (2026-10-02).** `retrieveChunks` embeds the query through the gateway, a paid call on a keyed desk, and the pane used to send the last user message on every change of its message list, so opening a thread billed. The pane now asks with `?threadId=` alone and the host answers from the record the send left: `lastTurnRetrieval` (`packages/host/src/knowledge-last-turn.ts:67`) takes the thread's last *completed* run, reads that run's `knowledge_retrievals` rows in insertion order, and takes each chunk's text from `knowledge_vectors`, so the Sources row is the chunks the send injected and nothing is retrieved again. A last turn that was handed nothing leaves no rows and reads `0 chunks`. The line has no engine word (`3 chunks`, not `3 chunks · hybrid`): the record keeps the backend, not which half of it answered. Since `handleRun` serves `/runs/text`, `/runs/image` and `/runs/video` (`router.ts:208-210`), the retrieving surface is precisely "a run inside a Chat thread, of any input modality" — not the `chat` product mode as such.

- **Top-k is a hardcoded `4`**, in both `knowledgeInjection` and the `retrieveChunks` default (`knowledge.ts`, `retrieveChunks`). No setting, no query parameter, no per-mode override. A blank query skips retrieval entirely. A non-empty query that matches nothing still writes `## Retrieved sources`: the body is `knowledgeMissBlock` (`packages/core/src/knowledge/harness.ts`) passed through `withOutputLanguage` on the `knowledge` surface, in the desk language, telling the model not to invent a citation. The popover count stays `0 chunks`.
- **Anti-loop.** `excludedSourceIds` (`knowledge.ts:886`) resolves the asking thread's own card by origin and excludes it — which is why proving retrieval of a Chat-authored card needs a *fresh* thread.
- **Both engines always run.** `SqliteBuiltinBackend.retrieve` (`packages/host/src/knowledge/backends/builtin.ts:250`) runs a cosine scan of `knowledge_vectors` and an FTS5 `bm25(knowledge_chunks)` query and fuses them with `fuseRrf` (`:155`, `RRF_K = 60` at `:134`). "FTS fallback" is not a branch: it is one of two lists that always runs, and it carries the query alone whenever the vector side returns nothing. `fusedMode` (`:200`) labels the outcome `hybrid` / `rag` / `fts` / `none`, which `sourcesDetail` (`knowledge.ts:909`) turns into the popover's `"<k> chunks · <mode>"`, with ` (degraded)` when the desk's own engine is not the one that answered.
- **The `[n]` markers are positional.** Each hit renders as `[<index+1>] <sanitizeSourceName(name)>\n<body>` in `knowledgeInjection`. The name is sanitized *again* at render time so a row written by an older build cannot forge a citation line, and nothing name-matches — the number is order of retrieval.
- **`cites` edges.** After a run that completes (or that broke mid-stream but saved partial text), `runs.ts:366` and `:375` call `recordRetrievals` (`packages/host/src/knowledge-retrievals.ts:39` — one `knowledge_retrievals` row per injected chunk plus a `retrieved` graph edge) and `recordCites` with `citedSources` (`packages/host/src/knowledge-cites.ts:64`), which parses bare `[n]` with `/\[(\d+)\]/g`, skips fenced code blocks whole including an unterminated fence, takes `chunks[marker - 1]`, dedupes by source, and **silently drops a marker past the injected count**. `[S1]`, `[1,2]` and `[0]` are not markers. A failed or aborted run records neither.
- **Graph expansion is off.** `RetrieveOptions.expand` is built and unit-tested; there is no Settings key and Chat never passes it. The backend registry is a hardcoded `return "builtin"`.

**The sweep.** `sweepOrphanSources` (`knowledge.ts:676`; `sweepOrphanThreadSources` at `:702` is the old name and still exported) runs on every `GET /api/v1/knowledge` (`handlers/knowledge.ts:131`). It drops work cards whose subject is gone for **all three origin kinds** — `thread`, `artifact` and `media` (`ORIGIN_OWNERS`, `:631`) — takes their traces and stored uploads with them, and then calls `sweepOrphanGraph` (`packages/host/src/knowledge-graph-prune.ts:110`) to repair nodes, edges and retrieval rows left by builds that had no cascade. `orphansOfKind` returns `null` rather than an empty list when an owner table cannot be read, so an unreadable table can never be mistaken for "nothing owns these rows". **All of this landed on 2026-09-17**; at `01ea70a` the sweep was thread-only and nothing ever deleted from `knowledge_graph_*` or `knowledge_retrievals`.

### 7. Who sees which source (hosted, 2026-10-07)

On the hosted server several people share one desk, and what a person does in Chat is private to that person, **from the company's owner and admins too** (owner, 2026-10-06). The rule lives in `packages/host/src/knowledge-visibility.ts`: a source with `origin_kind = 'thread'` is visible only to the person who owns that thread (`threads.user_id`, the same user-scoped lookup `getThread` makes). Every other source (a paste, a file, a URL, a job card, a media card) is the company's, as before. There is no role override. A Chat card whose thread is gone, or that has no `origin_id`, is visible to nobody.

It applies when `isServerMode()` is true, read on every call (`chatCardsArePrivate`, `knowledge-visibility.ts:46`). Off server mode every fragment is empty, so the SQL the desktop and webdev run is the SQL they ran before. The host enforces it in SQL; the renderer filters nothing.

| Read | Where | Filter |
|---|---|---|
| The Sources list, and `knowledge_search`'s "empty desk" check | `listSources`, `knowledge.ts:213` | `andVisibleSource` |
| Full-text search | `ftsRows`, `knowledge/backends/builtin.ts:220` | `andVisibleSourceId("knowledge_chunks.source_id")`: a primary-key lookup of the chunk's source, per matching chunk |
| Vector search | `searchVectors`, `knowledge-embed.ts:326` (the source subselect, `:352`) | `andVisibleSource` inside the subselect that already limited vectors to the desk, so a hidden card's vectors are never loaded |
| The name on a hit | `sourceNames`, `builtin.ts:55` | `andVisibleSource` |
| Chat injection, the `knowledge_search` tool, Education | `retrieveChunks` → the three rows above | the one funnel |
| The popover's record of the last turn | `recordedChunksSql`, `knowledge-last-turn.ts:31` | `andVisibleSource("s")`. The route also asks `getThread` first, so another person's thread id gives an empty Sources row |
| The graph and its counts | `getGraph`, `graphCounts`, `knowledge-graph.ts:361`, `:387` | `visibleGraphNodes` (a `WITH visible(id)` prefix). A source node needs a visible source, a thread node an owned thread, a topic node every source it `covers` visible; an edge needs both ends |

**The map marker.** Hosted, `saveMap` stores the map with `privacyScope: "shared-v1"` (`knowledge-map.ts:65`; the constants are `MAP_SCOPE_KEY` and `SHARED_MAP_SCOPE`, `knowledge-visibility.ts:194-195`), and `getKnowledgeMap` returns a map only if it carries the marker, stripped before it reaches the renderer. A map saved before the marker may have been written from every person's Chat (its topic titles and its overview text), so on a hosted desk it reads as no map and the desk maps once more. That cost was accepted on 2026-10-07 because no hosted desk held real customer data. `forgetSourcesOnMap` spreads the map object, so deleting a source keeps the marker. Off server mode nothing is stamped and an old map reads as it always did.

**Cost.** Each fragment is a lookup by primary key (`knowledge_sources.id`, then `threads.id` for a Chat card), so the cost follows the rows a query returns and not the number of cards on the desk. Measured with `EXPLAIN QUERY PLAN` and a timer on a desk of 4,000 sources and 4 people, and by a probe of 20,000: the plan has no scan of `threads`; a full-text query for a word in 80 chunks went from 0.5 ms to 1.3 ms with the fragment. The first shape tried, `source_id IN (SELECT id FROM knowledge_sources ...)`, rebuilt a list of every source on each query and cost 94 ms against 4 ms at 20,000 sources, so it was replaced. No index was added: the lookups use the primary keys (`knowledge-visibility.test.ts` holds the plan).

**What is still the desk's.** The Soul and the pinned memories (`getSoul`, `knowledge.ts:139`; `listMemories`, `:178`, both by workspace alone), the retrieval count (`countRetrievals`, `knowledge-retrievals.ts:75`), and the `artifact` and `media` cards. A person's own Knowledge Base being private, sharing through a bot, and what happens when a person leaves are designed and **not built** (owner, 2026-10-06; [`security-register.md`](../security-register.md), SR-161).

### 8. A Workspace's files and chats (hosted, 2026-10-14)

A Workspace (a `projects` row, K-D20) is a shared desk inside the company, like a Claude project. It holds files, a knowledge base built from them, instructions, and the chats started inside it. Its sources carry `knowledge_sources.project_id`, and a chat started in it carries `threads.project_id`. Server mode only: off it, `project_id` is never written and every fragment below is empty.

- **Who sees a Workspace's source.** Its maker while the Workspace is private (`projects.visibility = 'private'`), everyone in the company once it is `workspace`, and nobody once it is archived. `memberOfProject` in `knowledge-visibility.ts` is the one place that rule is written. A Workspace source is never in the owner rule of § 7, so a colleague's file in a shared Workspace is not the person's own and is not found outside it.
- **Scope.** A read names the Workspace it searches from. `VisibilityOptions.projectId` (and `RetrieveOptions.projectId`, `KnowledgeInjectionOptions.projectId`) carries it. A source of another Workspace never matches, and a read with no Workspace named sees no Workspace's source at all.
- **Chat in a Workspace.** `POST /api/v1/threads` takes `projectId` and checks membership first (`requireChatWorkspace`, a 404 for a non-member). The run then reads the Workspace's instructions into the system prompt (`workspacePromptBlock`, `runs.ts`), and retrieval and `knowledge_search` (which reads `projectId` from the run context) are scoped to that Workspace plus the person's own sources.
- **Instructions** are at most 8,000 characters (`PROJECT_INSTRUCTIONS_MAX`) and pass `scanInjection` on save.
- **Uploads** (`POST /api/v1/projects/:id/uploads`) are knowledge sources, not artifacts: 25 MB, the file's magic bytes checked by `extractText`, owned by the uploader, and removable by the uploader or the maker only.
- **Not covered.** The desk-wide reads that take no scope (the knowledge-expand default, the reindex sweep, the Sources list) skip a Workspace's sources. Not driven on a hosted server.

## Gotchas

- **Several bugs described by the 2026-09-17 knowledge-flow drivers were fixed in the tree the same day. Do not read this page as saying they are permanent.** Landed while it was being written: **Market auto-ingest** (`saveBriefing` now calls `upsertWorkSource`, and `Market` is a work type); **the Brief→Market filing bug** (`workTypeForArtifact` asks the artifact's mode first; `Memo` / `Playbook` now map to `Legal`); **the Finance regenerate duplicate** (regen carries the artifact id back and re-upserts, `finance-generate.ts:357-358`); **the graph / retrieval / media / artifact orphan sweeps** (`sweepOrphanSources` + `knowledge-graph-prune.ts`); **the `.html` upload keeping its markup** (`sourceKind` routes html to `htmlToText`); **the raw upload bytes surviving a delete** (`removeStoredUpload`); **`201 Created` for a failed upload** (now a structured 4xx); and **`maskPii` eating the card's own `Pointer:` UUID** (masking is field-by-field now). **Still open at the time of writing:** the Chat card's frozen title, the duplicated prompt and wrong duration on media cards, Documents / Presentations rewrites never persisting, Legal indexing one of five deliverables, and the 8 000-char cap eating a Market briefing's provenance. Re-check before quoting any of them — this page was written against a tree that moved four times in an hour.
- **The picker now mirrors the host. Fixed since 2026-09-17.** `sourceKind` routes `.pptx .ppt .xlsx .xls .ods .odt .odp .doc .rtf .epub` to the converter (`knowledge-extract.ts:57-68`, `:101`) and `.html` / `.htm` to `htmlToText` (`:98`); `apps/web/components/knowledge-page.tsx:425` now sets `accept={KNOWLEDGE_UPLOAD_ACCEPT}`, the eighteen extensions plus nine mimes in `apps/web/lib/knowledge-upload.ts:13-47`, and `knowledge-upload.test.ts` reads `knowledge-extract.ts` so the two lists cannot drift apart again.
- **A converted document is indexed as prose; its tables are dropped.** `extractFile` returns `markdown`, `text`, `tables` and `meta`, and `documentText` keeps `extracted.text` alone (`knowledge-extract.ts:143-155`). A workbook's sheets survive only as the flattened text of the Markdown tables; nothing on the knowledge path reads `tables`, `meta.sheets` or `meta.truncated`, so a document cut at the 2 000 000-char cap is indexed silently with no marker of its own.
- **`.pdf` and `.docx` deliberately did not move to the converter.** The file's own header says why (`knowledge-extract.ts:9-13`): the knowledge index, its page markers and its `pdf_*` / `docx_*` failure codes are built on the existing parsers, and the point of the change was to add formats, not to re-cut every document already indexed. So one upload dialog now has two readers behind it with two different failure vocabularies — `pdf_*` / `docx_*` for the two old formats, `document_*` for the ten new ones.
- **The card is text; the bytes stay where they are.** A Videos card is its prompt. A Data card is the model's evidence tables, not the dataset. A Legal card is the red-flags markdown, not the `.docx`. Chat retrieves cards, never files.
- **`maskPii` used to eat the card's own `Pointer:` line.** Masking ran over the rendered string, headers included, and `PHONE_RE` matches a dash-separated run of 10–15 digits, so a UUID whose middle groups are all decimal came back as `Pointer: artifact:b73b[phone]-bde3-…` in the *indexed* copy while the database id stayed intact — silent, the card still read `Indexed`, and the corrupted copy was the one Chat was given. Fixed on 2026-09-17 by masking title / prompt / body separately (`knowledge-ingest.ts:38-43`); the header lines are host-generated and carry no user PII.
- **A Chat card's name and its body drift apart permanently.** The name follows the thread title on every upsert, but a thread title is itself derived once from the first user message and never changes, while the body is replaced on every completed turn with that turn's exchange only. The title also sits *inside* the indexed chunk as the `# <title>` header, so stale first-turn wording keeps scoring FTS hits for questions the card can no longer answer — and `[n] <name>` is what a citation shows the user. *(2026-10-07)* For a message with an attached file, the card's body and the thread title are built from `attachmentsAsMentions(message)` (`packages/host/src/runs.ts:298`, `:471`): what was typed plus `[Attached file: name]` for each file, never the file's text. Before this the card kept up to 2,000 characters of the message with the file inlined, so a private attachment could have sat in a card that is not yet owner-only on a team desk (making cards owner-only is the team-privacy lane's work, not this one's). The assistant's reply, which the card also keeps, can still restate the document (SR-145).
- **A rewrite is the one version that is never kept.** Documents section regen and Presentations slide regen return a merged draft and persist nothing — no artifact write, no `upsertWorkSource`, and the DOCX / PPTX routes are pure bytes routes. The user downloads the good file, and Chat then retrieves the first draft and cites it as this workspace's document. No error, no "unsaved" state, and closing the tab loses the rewrite.
- **Only Chat retrieves, and that is still true after today's fixes.** Ten job modes write cards and call `knowledgeInjection` zero times. `docs/product-modes.md:91`'s "other job modes will share the same retrieve later" is entirely unstarted — there is no partial implementation behind it.
- **The 8 000-char cap is sized for a Chat exchange.** A Market briefing renders ~39 KB with the watchlist, macro, chart, headline and `## Sources` tables **last**, so the auditable half is exactly what the cap eats. A Chat answer citing that card can never reach the provenance the Market guard worked to attach.
- **Legal indexes one of five deliverable kinds.** `knowledgeCard` takes `red-flags`, else `issues-memo`, and nothing else (`legal-generate.ts:186-190`). A matter whose deliverables are redline / deviation-report / executive-summary produces artifacts and **no card at all**, and the studio's button is disabled in that state, so there is no manual escape hatch. When both are produced, the memorandum — the longer document — is the one that is not indexed.
- **A media card carries its prompt in the body only.** `mediaWorkCard` writes `Prompt: …` into the body lines (`work-cards.ts:100-106`) and deliberately sets the card's own `prompt` to `undefined` (`:111`), so `renderWorkCard`'s `Prompt:` header line is skipped (`:65`) and the prompt is indexed once, uncapped by `WORK_CARD_PROMPT_MAX`. It used to appear twice, which doubled its term frequency against `bm25`.
- **A video card records the requested duration, not the generated one** — `snapVideoSeconds` goes to the tool (`studio-generate.ts:228`), the raw `body.seconds` goes to the card (`:261`) — and the common `undefined` case is falsy, so `mediaWorkCard` drops the `Duration:` line entirely for a default-length clip that had a definite one.
- **A pasted source is unreachable by any cascade.** Paste, File and URL have `origin: null`, so the sweep cannot see them and no delete anywhere else can reach them. Remove on `/knowledge` is the only path, and for a paste created from the UI every row is named "Pasted notes" / "Catatan tempelan", so telling two of them apart means opening them.
- **Two labels behave one way and four the other.** `KB_TYPE_TO_WORK` answers for `Dossier`, `Analysis`, `Brief`, `Memo` and `Playbook` and maps `Paste` to `null`; it is now only consulted when the artifact's own mode names no desk. The label is still what a text-only send (no `artifactId`) stores verbatim, so the same word means different things on the two branches of one route.
- **Hosted: a person's Chat is theirs, and the Soul and pinned memories are still the company's.** On a team desk a colleague's Chat card never reaches your list, search, prompt, graph or map (§ 7). The Soul and the pinned memories, though, are read by workspace alone (`getSoul`, `listMemories`), so a memory one person pins is in everyone's Chat prompt. That is the desk's own knowledge, as designed today; it is not the person's.
- **Hosted: the first map after this change is a re-map.** A map saved before the marker reads as no map until someone presses Map on that desk (§ 7). The rail and the Knowledge page show "no map yet", which is accurate and not an error.
- **Soul is the one un-guarded string in the system prompt.** `scanInjection` runs on every source and every work card; `putSoul` and `addMemory` do not. Defensible — it is the owner's own typing — but it should be a deliberate choice rather than an accident.
